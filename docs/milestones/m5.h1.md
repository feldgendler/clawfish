# M5.H1 — Staged movegen architecture refactor (retrospective)

Eighth M5 sub-phase, and the first half of the M5.H split. **Architecture-only refactor**: introduces the `MoveStager` type as a five-stage iterator over the negamax move sequence (TT → captures → killer 0 → killer 1 → quiets), replacing the monolithic `order_moves` + `for mv in moves_vec.iter().enumerate()` pattern at the negamax move loop. **All moves are still generated and sorted eagerly at construction**: bench parity at `1147614 nodes` (M5.G's signature, exact) is the empirical no-regression gate. M5.H2 (separate future unit) will enable lazy generation and is the SPRT-gated unit.

ADR: [`docs/decisions/0030-staged-movegen.md`](../decisions/0030-staged-movegen.md). Plan: [`docs/plans/m5.h1.md`](../plans/m5.h1.md). Research: [`docs/research/m5-staged-movegen.md`](../research/m5-staged-movegen.md).

## What landed

A new `MoveStager` type in `src/search.rs` (~300 LOC including type, methods, and helper functions). API surface:

- `MoveStager::new(pos, killer0, killer1, history, tt_move, searchmoves_filter) -> Self` — eager generation, partition, killer extraction, MVV-LVA sort of captures, history sort of quiets, total_len cache. The `searchmoves_filter: Option<&[Move]>` parameter folds the root-only UCI filter into construction (eliminating the temporal-coupling that a separate `retain_root_filter` method would have).
- `MoveStager::next() -> Option<Move>` — loop-match advancement through the five stages. Pass-through stages fall through within the same call.
- `MoveStager::peek() -> Option<Move>` — `&self`-receiver, type-enforced idempotent. Load-bearing for the M5.G SE block, which calls peek twice (once in the gate predicate, once in the verification-call's `excluded_move` argument).
- `MoveStager::len() -> usize`, `is_empty() -> bool` — pre-iteration count; does **not** decrement as `next()` advances. `MoveStager` does NOT implement `Iterator` (preserves the temporal contract on `len()` against iterator-like remaining-count intuitions). Pinned by H1-S17.
- `MoveStager::yield_sequence() -> Vec<Move>` — `#[cfg(test)]`-only; clones and drains. Used by the H1-P1 equivalence proptest.

Five pure helpers (each its own mutation-discrimination surface, per the M3.D `negate_window` / M5.C `late_move_reduction` / M5.D `ffp_pruned_bound` / M5.G `singular_beta` precedent):

1. `extract_move_by_bits(&mut Vec<Move>, target: u16) -> Option<Move>` — order-preserving `Vec::remove`; matches today's `order_moves`'s `iter().position(|m| m.bits() == tt_move)` at `src/search.rs:2906`. `target == 0` short-circuits without scanning.
2. `extract_move_by_eq(&mut Vec<Move>, target: Move) -> Option<Move>` — full-Move equality (flag bits included) for killer extraction.
3. `partition_captures_quiets(Vec<Move>) -> (Vec<Move>, Vec<Move>)` — manual loop over `Vec::into_iter`, explicit order-preservation guarantee (rather than relying on undocumented `Iterator::partition` stability).
4. `mvv_lva_sort_in_place(&mut [Move], &Position)` — `sort_by_cached_key(-mvv_lva_score(m, pos))`.
5. `history_sort_in_place(&mut [Move], &Position, &HistoryTable)` — `sort_by_cached_key(-history.score(...) as i32)`.

Negamax integration changes (production code, all in `src/search.rs:1682-2068`):

1. **Step 10-12 (move generation + filter + ordering) → `MoveStager::new` construction.** The `generate_moves` → `moves_vec.retain(searchmoves)` → `order_moves` block becomes a single `MoveStager::new(...)` call.
2. **Step 11 terminal check** — `moves_vec.is_empty()` → `stager.is_empty()`.
3. **Step 12.5 (M5.G SE block)** — `moves_vec[0].bits() == snapshot.tt_move` → `stager.peek().map_or(0, Move::bits) == snapshot.tt_move`; `Some(moves_vec[0])` → `Some(stager.peek().expect(...))`. The lazy-`in_check` short-circuit chain preserved verbatim. The `debug_assert!(!moves_vec.is_empty(), ...)` removed (subsumed by the step-11 check).
4. **Move loop** — `for (i, &mv) in moves_vec.iter().enumerate()` → `let mut i: usize = 0; while let Some(mv) = stager.next() { let cur_i = i; i += 1; if Some(mv) == excluded_move { continue; } ... }`. The position-counter pattern preserves M5.G's `i==0`-on-skip semantics byte-for-byte. `cur_i` substituted for `i` at the two body sites (`child_is_pv = is_pv && cur_i == 0` and `move_extension = if cur_i == 0 { tt_move_extension } else { 0 }`) plus a third site at the `#[cfg(test)] se_tt_move_search_depth` recorder that was not enumerated in plan §5 (caught during implementation).
5. **`order_moves` demoted to `#[cfg(test)]`** at `src/search.rs:2894`. Preserves all 14+ existing test call sites (S24/S24a-f, S26 baseline scan); production call site replaced.
6. **`#[allow(dead_code)]` annotations** added to `negamax_move_order_score`, `KILLER0_SCORE`, `KILLER1_SCORE`, `CAPTURE_OFFSET`, and `MoveStager::len` — used by tests / compile-time invariants but not on production paths post-stager-integration.

No changes to `src/movegen.rs`, `src/mov.rs`, `src/eval.rs`, `src/tt.rs`, or any other file outside `src/search.rs`. No `src/lib.rs` exports change.

Test surface: 30+ named H1-* tests in `src/search.rs::tests`:

- **H1-I1..I6** — 6 negamax integration tests through `negamax_for_test` covering terminal positions, searchmoves filter at root, SE peek matching TT bits, excluded-move skip preserving position counter, filter excluding TT (root move ∈ filter assertion), stale-TT non-firing of SE.

## v1 → v2 thin-wrapper retune

Pre-commit, the defensive 100-game SPRT confirmation match (plan §12 step 7) returned **Δ Elo −110.48 [−207.37, −28.06]** at 26 games (verdict=H0). A 300-game continuation SPRT (seed `_00F`) tracked the regression to **~−44 Elo at 222 games** (W=46 L=74 D=102, sigma 8.65) — clearly a real regression, not noise. This contradicted the bench-parity claim (`1147614 nodes` exact) and the H1-P1 proptest equivalence (2048 cases). Investigation:

- **Manual `go depth N` from startpos**: HEAD ≡ baseline at depth 8, 10, 12, 14 (same nodes, same PV, same bestmove). At depth 14 single-shot: HEAD 6426ms vs baseline 6206ms on the same 14201938-node tree — a **3.5% per-node overhead** invisible to bench.
- **Sustained-load test (20 sequential `go depth 10` in same process)**: HEAD 5–9% slower (3 runs: 1.088, 1.049, 1.036).
- **Bench-in-process (3× consecutive `bench`)**: HEAD/baseline within 1% — no allocator pattern visible at bench's scale.

**Diagnosis.** v1's per-node cost was ~3× M5.G's:
- v1 allocated 3 `Vec<Move>` per node (`all`, `captures`, `quiets`) vs M5.G's 1 (`moves_vec`).
- v1 ran 2 `sort_by_cached_key` calls (captures + quiets) vs M5.G's 1.
- Per-node overhead was ~15ns × 14M nodes = 220ms gap on byte-equivalent depth-14 tree.

Bench's snapshot at depth 7 with fresh allocator state didn't surface this. Sustained game-load did.

**Fix (v2 thin-wrapper).** Collapsed the v1 stage state machine (`Stage::{Tt, Captures, Killer0, Killer1, Quiets, Done}` + per-stage Vecs + per-stage sorts) into a single `Vec<Move>` sorted once by `negamax_move_order_score` with TT promotion to index 0 — literally M5.G's `order_moves` algorithm wrapped in the M5.H1 `MoveStager` API. The public API (`new`, `next`, `peek`, `len`, `is_empty`, `yield_sequence`) is preserved verbatim. The `Stage` enum was removed; the per-stage helpers (`extract_move_by_bits`, `extract_move_by_eq`, `partition_captures_quiets`, `mvv_lva_sort_in_place`, `history_sort_in_place`) are demoted to `#[cfg(test)]` (still mutation-discrimination surfaces for H1-H1..H10).

**v2 verification.**
- Bench: `1147614 nodes` exact, M5.G parity preserved.
- Sustained-load test (3 runs post-v2): HEAD avg ratio 0.974 vs baseline (slightly faster — within noise).
- 1481/1481 tests pass; the H1-S* yield-order tests, H1-P1 proptest, H1-I* integration tests all pass against v2 (yield sequence is unchanged from v1; v2 just gets there with one sort instead of two).
- Defensive 200-game SPRT confirmation match vs `baseline/m5g-singular` (seed `_010`) post-v2 — see SPRT log.

**API stability for M5.H2.** v2 preserves the public API verbatim. M5.H2 will swap the internal `Vec<Move> + sort` for per-stage lazy generation behind the same API. The `Stage` enum will be reintroduced as part of H2's per-stage lazy-generation work, scoped to the impl, not exposed via the API.

## Lessons learned

1. **Bench parity at depth 7 is necessary but NOT sufficient for "bench-neutral" claims.** The v1 design passed bench parity AND identical PV/nodes at single-shot depth 8/10/12/14 from startpos AND H1-P1 proptest equivalence at 2048 cases — but lost ~50 Elo in TC games due to ~3% sustained-load NPS overhead. Future bench-neutrality claims should add a sustained-load NPS measurement (multi-`go` sequential test) when the change touches the per-node hot path.

2. **The defensive SPRT confirmation match in plan §12 step 7 was load-bearing.** The plan-review pass-1 reviewer's pushback ("recommend defensive 50-pair confirmation match — cheap insurance") caught the regression. Without it, M5.H1 v1 would have committed and the regression would have surfaced (silently) only when M5.H2 ran SPRT against M5.H1 as the baseline.

3. **Stub design with placeholder return values surfaces vacuous-pass tests early.** The first test-writing pass produced 18 tests that passed against the empty-stub `MoveStager`; the test-suite reviewer caught 5 of them as vacuous. Stub-then-implement TDD is more robust than write-and-implement-together because the stub forces tests to use positive assertions — but only if the test reviewer specifically triages stub-passing tests, which our pass-1 reviewer did.

4. **The "thin-wrapper as the simplest H1" alternative considered and rejected at plan time turned out to be the correct choice.** The plan §3 considered "Simple-Vec-wrap H1 vs Stage-aware H1" and chose stage-aware ("lays out the full stage machine architecture, H2 only changes generation timing"). v1 implemented stage-aware. v2 reverted to thin-wrapper after the SPRT regression. The H2 architecture work can land at H2 itself without H1 carrying the cost.

5. **Hot-path allocation patterns matter even when total NPS looks similar at bench time.** v1's 3 `Vec<Move>` allocs per node summed to ~600K allocs/sec; bench showed NPS similar to baseline (snapshot, fresh allocator); sustained-load showed 5–9% slowdown (allocator pressure cumulative). Future hot-path designs should measure under sustained load, not just bench snapshot.

6. **Mutation testing reveals private-helper test gaps.** In v1 the `peek_from_captures` helper was invoked only when the stager's stage advanced to `Stage::Captures` then `peek()` was called. H1-S13's mid-iteration peek used the starting position which has no captures, so the helper was never exercised. The H1-S13b fix (Kiwipete fixture) closed the gap. v2 doesn't have these per-stage helpers (they're cfg(test)-only now), so the mutation surface shifted to v2's `MoveStager::next/peek` — which mutate `self.idx` in straightforward ways the existing tests cover.
