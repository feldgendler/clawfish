## Mate-cap test fixture — design choice

The plan §5.3 sketched a hand-driven three-step structure where step 1 sanity-checks via an actual chess search that returns a mate-magnitude score from the post-null position. In implementation, that approach proved unworkable because the zero-window `(-beta, -beta + 1)` causes white's MVV-LVA-ordered captures to fail-high before the mating line is reached.

Slice C replaced step 1 with a TT-seeded approach: pre-populate the post-null Zobrist with a TT entry carrying a mate-magnitude negative score (from the opponent's STM perspective post-null) at sufficient depth that the null sub-search's TT probe deterministically returns mate magnitude. The TT-seeded variant exercises the mate-cap branch deterministically and is more robust against move-ordering changes from future M5 phases (LMR, futility pruning, staged movegen) that would otherwise break a chess-search-based fixture.

The semantic interpretation: `null_score >= MATE_IN_MAX_PLY` means "we mate after passing" (post-null position has us mating the opponent in spite of giving them a free move) — that's the case the cap protects against (we didn't actually search any moves of ours, so the inflated score isn't real mate proof).

## Lessons

- **Mate-cap test fixture construction is harder than chess-fixture intuition suggests.** The plan walked through the sign analysis but didn't catch the MVV-LVA-fail-high interaction at zero-window depth-3 — surfaced at impl time and resolved via the TT-seed approach. Worth flagging in the M5.B-onwards plan template: tests that rely on specific search-tree shapes near beta cutoffs are fragile under future search-modification phases; prefer fixtures that work at the prologue level (TT seeds, direct counter checks, sister fixtures with clean discriminators).
- **Empirical-pin discipline.** The `nmp_firings` stacked-null pin K=34 is fixture-dependent; future M5 phases that add prologue-prefiltering (LMR's reduction-not-skip path, RFP at d ≤ 3) may shift this number. The test will fail loudly with a clear message ("NMP firings count must match pinned K=N; got M") on any such drift, and re-pin is a one-line update — but the brittleness is acknowledged. The plan's alternative (sister fixture with two negamax runs at different `allow_null` values) was harder to construct cleanly; the counter approach was the working compromise. Consider replacing with a pure-state assertion (e.g., on a synthetic test fixture that traces NMP entry events) if M5.C+ phases break the empirical pin too often.
- **Coverage of `Undo`/`NullUndo` patterns**: dropping `prior_fullmove` from `NullUndo` (per the existing `Undo` pattern at `mov.rs:803`) was caught only because the plan-reviewer pass 1 raised it as a nit and the orchestrator verified the existing pattern. Without that verification step, the plan's "16 bytes" claim would have shipped a 24-byte struct (with padding), and a 2-byte mutation surface would have shipped along with it. Reinforces the plan-reviewer value-add for parallel-precedent application.

## Mutation-survivor analysis

Joint M4.B+M4.C+M4.D+M5.A+M5.B campaign (748 mutants: 669 caught, 31 missed, 33 unviable, 15 timeouts — 89.4% catch rate). M5.A-specific survivors from this campaign:

### 1. `replace | with ^ in has_non_pawn_material` — bitboard union operator

**Classification: Equivalent mutant.**

`pieces_colored(side, Knight) | pieces_colored(side, Bishop) | pieces_colored(side, Rook) | pieces_colored(side, Queen)` ORs four bitboards for Knight, Bishop, Rook, Queen. A square holds at most one piece kind, so the four piece bitboards for a given color are disjoint by the `Position` invariant (`piece_bb[k] & piece_bb[k'] == 0` for k ≠ k'). For disjoint operands: `a | b == a ^ b` for every input. Same equivalence argument as the existing `replace | with ^ in Position::occupied_all` exclusion. `exclude_re` rule added to `.cargo/mutants.toml`.

### 2. `replace + with * in AlphaBetaMover::negamax` — NMP recursive `ply + 1` → `ply * 1`

**Classification: Real-bug, structurally undetectable at this milestone scope. Deferred to M5.C.**

`ply * 1` is the identity — the child receives `ply` instead of `ply + 1`, producing a 1-ply error in mate-distance calculations and MDP bounds inside the null sub-search. The observable effect is a 1-cp shift in mate scores returned from the null sub-search, insufficient to straddle the `MATE_IN_MAX_PLY` cutoff boundary for any reachable TT-stored value. All existing NMP tests pin the cutoff-vs-beta relationship or the firings count, not the exact mate magnitude, so the 1-ply shift is invisible. `exclude_re` rule added to `.cargo/mutants.toml`. Deferred to M5.C when ply-sensitive search depth tests can be added with less combinatorial complexity.

### 3. NMP mate-cap boundary at `null_score >= MATE_IN_MAX_PLY` — *not* a survivor in this campaign

The plan §10 anticipated that the M5.A NMP mate-cap `>=` could survive at the exact-`MATE_IN_MAX_PLY` boundary if cargo-mutants generated such a mutation. cargo-mutants 27.0.0 emitted the `>= → <` form (line 1102:58 in `negamax`); that mutation was **caught** by `negamax_caps_mate_score_to_beta_when_null_score_is_mate`'s TT-seeded fixture. The narrower `>= → >` form (the one that would survive at exact-`MATE_IN_MAX_PLY` per the plan's prediction) was not generated by this version of cargo-mutants. Listed here for completeness; no exclusion rule needed at M5.A scope. The structurally-analogous M5.B survivor (`< → <=` at `beta.abs() < MATE_IN_MAX_PLY`, line 1025) IS in the missed set and is excluded — see M5.B retrospective.

**Result**: clawfish ≈ **2601.45 ± 10.51 Elo** in 56 games / ~30 min wallclock. Stop reason: σ-stop. W-L-D = 19/28/9 (score 41.96%).

The σ-stop fired at 28 pairs before the SplitMix64 pre-materialised sequence asymptoted to uniform (M4.D's 200-pair run showed the sampler is unbiased at scale: χ² = 2.92, p ≈ 0.40). Practical interpretation: 2601.45 represents clawfish's rating at effective TC ≈ 25+0.25 — fast-TC-weighted.
