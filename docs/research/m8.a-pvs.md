# M8.A — Principal Variation Search (PVS): Prior-Art Research

Covers the exact fail-soft PVS algorithm, composition with LMR, `is_pv`-to-window-predicate migration, TT interaction, aspiration-window coexistence, expected Elo/node impact, and correctness verification. No engine source code was read.

## 1. Exact PVS Algorithm — Fail-Soft Form

### 1.1 Canonical fail-soft pseudocode

```
fn pvs(alpha, beta, depth) -> score:
    if depth == 0: return qsearch(alpha, beta)

    // First move: full window
    make first_move
    best = -pvs(-beta, -alpha, depth - 1)
    unmake first_move
    if best > alpha:
        if best >= beta: return best        // fail-high, return exact fail-soft score
        alpha = best

    // Subsequent moves: null window, then conditional re-search
    for each remaining move:
        make move
        score = -pvs(-alpha - 1, -alpha, depth - 1)   // null-window probe
        if score > alpha && score < beta:
            score = -pvs(-beta, -alpha, depth - 1)     // full-window re-search
            if score > alpha: alpha = score
        unmake move
        if score > best:
            best = score
            if best >= beta: return best   // fail-high, return exact fail-soft score

    return best
```

Source: CPW "Principal Variation Search" (Diepeveen fail-soft implementation).

### 1.2 Why `alpha+1` is correct for the null window

The null window `(-alpha-1, -alpha)` from the child's perspective is `(alpha, alpha+1)` at the parent. This window has width exactly 1. Under fail-soft:

- A result `score <= alpha` proves the move does not improve the current best (fail-low). No re-search needed.
- A result `score >= alpha+1` (i.e. `score > alpha`) proves the move *might* improve — but gives no exact score because the null window cannot establish one (a zero-window search can only return Lower or Upper bounds, never Exact).
- The re-search condition is `score > alpha && score < beta`: the first clause means the probe found a potential improvement; the second means we are not already at a fail-high node where the exact score is irrelevant to the parent.

### 1.3 Boundary conditions

| Condition | Meaning | Action |
|---|---|---|
| `score <= alpha` | Fail-low: move does not improve | No re-search, `best` unchanged |
| `score > alpha && score < beta` | Interior: move improves, but within window | Full-window re-search required |
| `score >= beta` | Fail-high: immediate cutoff | Return `best` (fail-soft: return `score`, not clamped `beta`) |

The fail-soft distinction from fail-hard is the return value on cutoff: fail-soft returns the actual score found (which may exceed `beta`), not clamped `beta`. This matters because callers use the returned score to set their own alpha; the actual score carries more information.

## 2. Composition with LMR

### 2.1 The canonical three-step ladder

Under PVS + LMR, a late quiet move at a non-PV node with move index `quiet_index >= LMR_MIN_QUIET_INDEX` goes through up to three increasingly-expensive tests:

```
Step 1 (pilot):   reduced depth (depth - 1 - R) + null window (-alpha-1, -alpha)
    → if score <= alpha: done (fail-low at both reduced depth and null window)

Step 2 (verify):  full depth (depth - 1) + null window (-alpha-1, -alpha)
    → if score <= alpha: done (fail-low at full depth — was a depth artifact)
    → if score >= beta:  return score (immediate cutoff — no PV re-search needed)

Step 3 (exact):   full depth (depth - 1) + full window (-beta, -alpha)
    → provides the exact score; updates alpha and best
```

Source: H.G. Muller's description in OpenChess "LMR and PVS" thread ([https://open-chess.org/viewtopic.php?t=3084](https://open-chess.org/viewtopic.php?t=3084)).

### 2.2 Is Step 2 mandatory?

Step 2 (full-depth null-window) is the standard intermediate step in modern engines, and it matters because of **search instability**: TT entries, null-move pruning, and other window-dependent techniques mean a position that fails high under a null window at reduced depth will *not always* fail high under the same null window at full depth. The intermediate null-window re-search at full depth is the cheap safety valve — it catches the depth-artifact case cheaply before paying for the full-window re-search.

Skipping to Step 3 directly (two-step ladder) is simpler and occasionally used, but the literature recommends the three-step form for this engine since it already has NMP and TT interactions that increase instability.

### 2.3 Interaction with existing LMR re-search policy

The current engine (ADR-0025 §5) already does: "if `reduced_score > alpha`, immediately re-search at full depth `depth - 1`." This is the two-step form (Step 1 → Step 3). Migrating to PVS changes the re-search window at Step 3:

| Before PVS | After PVS (at non-PV node) |
|---|---|
| Step 1: reduced depth, **full window** (-beta, -alpha) | Step 1: reduced depth, **null window** (-alpha-1, -alpha) |
| Step 3: full depth, full window | Step 2 (new): full depth, null window |
| — | Step 3: full depth, full window (only if step 2 also fails high) |

At a **PV node**, LMR does not apply (ADR-0025 §2 gate `!is_pv`). Under PVS this gate migrates to `beta - alpha == 1` (see §3). PV nodes search every move at full depth and full window.

### 2.4 TT store discipline under the three-step ladder

ADR-0025 §6 suppresses TT storage when the node's best score is backed only by reduced-only evidence. Under the three-step ladder:

- A move that clears Step 1 and Step 2 but fails low at Step 3 still did not produce a full-window-witnessed best score → store suppression still correct.
- A move that clears Step 3 is full-depth + full-window-witnessed → Lower/Exact/Upper classification applies as before.
- The existing `best_is_full_depth_after_score` provenance flag continues to apply unchanged: only full-depth full-window results update it.

## 3. `is_pv` to Window-Based Predicate Migration

### 3.1 The convention

Under PVS:
- **PV node**: `beta - alpha > 1` (real window; could produce an Exact TT bound).
- **Non-PV node** (zero-window / null-window node): `beta - alpha == 1`.

This is the universal PVS convention. CPW "Node Types": "In Principal Variation Search, PV-nodes usually satisfy `beta - alpha > 1`."

### 3.2 Which nodes are PV nodes under PVS

```
PV nodes = {root}
         ∪ {first child of every PV node}
         ∪ {every node reached by a full-window re-search at step 3}
```

The third set is small but real: a late move that survives the null-window tests and needs a full-window exact score becomes, temporarily, a PV-candidate node. After the re-search, if the score improves alpha, it replaces the current PV first child — it has earned PV status.

### 3.3 The aspiration-window corner case — a real subtlety for this engine

**The problem.** At the root, iterative deepening uses adaptive aspiration windows (M5.K / ADR-0037). The aspiration first-try window might be, e.g., `(prev_score - 50, prev_score + 50)` — a real width of 100 cp. This satisfies `beta - alpha > 1`, so the root is correctly identified as a PV node. But:

- If the aspiration window *contracts* to a re-aspiration loop and the window becomes very narrow (say `(x, x+2)`), the predicate still works — `beta - alpha > 1` is still true.
- If the window ever contracts to exactly `(x, x+1)` — a width-1 aspiration window — then `beta - alpha == 1` would wrongly classify the root as a null-window (non-PV) node.

In practice, aspiration windows in this engine start at ≥ 50 cp and widen on failure; they never contract to width 1 during normal operation. However, the *general* risk is documented:

> "If the window bounds collapse until beta == alpha+1, even at the root position, a re-search with expanded bounds should be triggered." — TalkChess "Recognizing PV nodes" thread.

**Recommendation for this engine.** Keep an explicit `is_pv` flag *at the root* (`ply == 0` forces `is_pv = true`) and use the window predicate at all other nodes. This is a two-line change from purely window-based detection and permanently inoculates against the aspiration-window false-negative:

```
is_pv = if ply == 0 { true } else { beta - alpha > 1 }
```

Child propagation: `child_is_pv = is_pv && move_is_first_move` (same rule as today's `is_pv && i == 0`).

**The existing synthetic `is_pv` flag** (ADR-0018 §11) uses `child_is_pv = parent_is_pv && i == 0`. Under PVS this is almost correct — the difference is that PVS also needs to mark full-window re-search nodes (Step 3) as PV. In practice: the re-searched child is called with the full window `(-beta, -alpha)` where `beta - alpha > 1`, so the window predicate naturally classifies it as PV. No special handling needed for the re-search case when using the `ply == 0` override.

### 3.4 Semantic equivalence after migration

After migration to `is_pv = (ply == 0) || (beta - alpha > 1)`:

- ADR-0018 §11's TT-cutoff suppression at PV nodes is semantically identical — same node set, same rule.
- LMR gate `!is_pv` (ADR-0025 §2) is semantically identical.
- History gating and killer gating are unchanged (neither references `is_pv`).

## 4. TT Interaction

### 4.1 What null-window searches store

A null-window search `(-alpha-1, -alpha)` can return only:

- **Lower bound** (fail-high, `score >= alpha+1`): the true minimax value is ≥ the returned score.
- **Upper bound** (fail-low, `score <= alpha`): the true minimax value is ≤ alpha.

A null-window search can **never** produce an Exact bound (that would require finding a score strictly inside the window, which has zero interior for a width-1 window). Source: CPW "Null Window": "a null window search can never return an exact score."

### 4.2 Implications for TT storage in PVS

| Search type | TT bound stored |
|---|---|
| First move, full window (PV node) | Lower / Exact / Upper as usual |
| Null-window probe (Step 1 or 2) — fails low | Upper |
| Null-window probe (Step 1 or 2) — fails high | Lower |
| Full-window re-search (Step 3) | Lower / Exact / Upper as usual |

The engine already stores Lower and Upper bounds correctly. The only change is that more nodes will store Lower/Upper (from the null-window probes) rather than Exact — reducing the frequency of Exact TT hits and increasing the importance of bound comparisons.

### 4.3 TT-cutoff gating (ADR-0018 §11) after PVS

The `is_pv`-gated TT-cutoff rule ("at PV nodes: extract move for ordering, never return early on stored score") is semantically unchanged by PVS. After the predicate migration:

- PV nodes (`is_pv = true`) still suppress TT cutoffs and use the stored move only for ordering.
- Non-PV nodes (`beta - alpha == 1`) still permit full TT cutoffs on bound match.

PVS makes this rule *more important*, not less: null-window searches at non-PV nodes now generate many more Lower/Upper TT entries, which will be probed and used for cutoffs by sibling null-window searches. The rule's correctness relies on PV nodes not being short-circuited by what might be a null-window-derived bound. Nothing needs to change; the migration leaves the semantics identical.

### 4.4 Depth-adequacy filter

ADR-0018 §6 / §13: the probe rule `entry.depth >= depth` already filters out shallow entries. This applies to null-window entries too — a null-window entry at depth 3 will not cut a full-width search at depth 6. No change needed.

## 5. Aspiration-Window Interaction at the Root

The root's iterative-deepening aspiration loop (M5.K) and PVS operate at different levels:

- **Aspiration**: governs the window passed to the *root* negamax call. On fail-high or fail-low, the aspiration loop widens the window and restarts the entire iteration.
- **PVS**: governs how the root negamax call searches its *children*. The first root child gets the full aspiration window; all subsequent root children get a null window `(alpha, alpha+1)` initially.

These are orthogonal. The interaction is:

1. Root receives aspiration window `(asp_alpha, asp_beta)`.
2. First root child is searched with `(-asp_beta, -asp_alpha)` — full window.
3. Second+ root children are searched with `(-alpha - 1, -alpha)` — null window, where `alpha` is the current best at the root.
4. If a root child's null-window search returns `> alpha && < beta`, Step 3 triggers a full-window re-search with `(-asp_beta, -alpha)`.
5. If the aspiration search fails high/low at the root, the aspiration loop widens and restarts — this is unchanged from today.

The two mechanisms do not interfere because aspiration acts on the iteration boundary (outer loop) while PVS acts within a single iteration's call tree.

**One gotcha**: if the root's first move fails low (the aspirated first-move search returns `< asp_alpha`), the root has no alpha improvement. PVS's `bSearchPv`-style logic would then search subsequent moves with the *full* aspiration window, not a null window — because no alpha has been established yet. This is correct behavior. Source: TalkChess PVS discussion, Gian-Carlo's correction ([https://www.talkchess.com/forum3/viewtopic.php?t=26974](https://www.talkchess.com/forum3/viewtopic.php?t=26974)):

> "if (score > alpha && score < beta)" is the re-search condition — not "if (score > original_alpha)". As long as alpha hasn't moved, subsequent moves at the root correctly receive full-window searches (no null window to probe against because no bound has been established).

## 6. Expected Elo / Node-Count Impact

### 6.1 Literature estimates

| Source | Claimed gain |
|---|---|
| CPW PVS article | "~10% search effort saved" with good ordering |
| CPW PVS article | Modern engines get "fail-highs on first move ~90% of time" |
| TalkChess "How much improvement from PVS?" (Bob Hyatt) | "~10 Elo or less" |
| TalkChess "PVS/NegaScout: Actual benefits" | No specific Elo; benefit characterized as "nominal" |
| Engine progression data (TalkChess "Rustic" reference) | +70 Elo cited (alpha-beta+TT at 1850 → PVS+killers at 1920), but killers confound the attribution |

The honest characterization from the literature: PVS is primarily a **node-count efficiency gain** (5–20% fewer nodes searched, depending on ordering quality). The Elo translation depends entirely on whether the saved nodes convert to a depth gain within the time budget. With this engine's existing strong ordering (TT move + killers + history + SEE qsearch prune), the node reduction should be in the 10–15% range. The Elo conversion from 10–15% fewer nodes is approximately:

> Additional half-depth ≈ 5–10 Elo (typical for this engine's depth profile)

### 6.2 The key risk: bad first-move ordering causes re-search overhead

PVS is *not* a free lunch. When the first move is not the best:

- The null-window probe fails high.
- A full-window re-search is required.
- Net cost: two searches instead of one, plus the original full-window cost if any.

If the first move is wrong frequently (e.g. ordering quality degrades), PVS can *lose* nodes compared to plain alpha-beta. With this engine's current ~90% first-move cutoff rate (estimated from TalkChess benchmarks), PVS should be firmly net-positive. The risk materializes if PVS is added before good ordering is in place, or if a later change degrades ordering quality.

**Diagnostic**: track the re-search rate (null-window probes that trigger a full-window re-search). If this rate consistently exceeds 15–20%, the ordering may have regressed.

## 7. Correctness-Testing Surface

### 7.1 The primary invariant

**PVS is an exact optimization — it must return the same best move and score as plain alpha-beta at the same depth on every position.**

Bob Hyatt (TalkChess): "It should produce EXACTLY the same result as a non-PVS search, just as alpha/beta should produce EXACTLY the same result as pure minimax."

This yields the primary test: at fixed depth on a test suite, PVS-on and PVS-off must agree on both best move and score. Any disagreement is a bug.

### 7.2 Invariant tests the literature suggests

| Test | What it catches |
|---|---|
| Fixed-depth score equality (PVS on vs off) | Re-search condition wrong, window boundaries off |
| Fixed-depth best-move equality | Re-search triggering too late or too early |
| Node count reduction ≥ 0 (PVS never increases nodes vs plain alpha-beta with same TT) | Re-search being triggered when not needed |
| Re-search rate within expected band (e.g. 5–20% of non-first-move nodes) | Ordering regression or null-window boundary error |
| Mate-finding equality: same mate-in-N on mate test suites | Null-window boundary edge case near MATE scores |
| Perft unchanged (for movegen-adjacent code — not applicable here since PVS is search-layer only) | Not applicable |

### 7.3 Null-window edge case near MATE

When `alpha` is near a MATE score, `alpha + 1` may overflow or wrap. Specific cases:
- `alpha = MATE_IN_MAX_PLY = 29936`: `alpha + 1 = 29937` — safe within i32.
- `alpha = INF - 1 = 30000`: `alpha + 1 = 30001 = INF` — beta equals INF, window becomes `(INF-1, INF)`, which is a valid width-1 window.

The engine uses `i32` scores (ADR-0016 §2) with `INF = 30001`. No overflow risk; verify with a targeted test.

### 7.4 Property tests

A property test: for any random position and depth ∈ [1,5], `pvs(pos, depth, -INF, INF) == alphabeta(pos, depth, -INF, INF)`. With the existing proptest infrastructure, this is straightforward. The engine already has TDD-style search invariant tests (ADR-0016).

## Open Questions

1. **Three-step vs two-step ladder**: Both are correct. The three-step ladder (intermediate full-depth null-window) is recommended by H.G. Muller as more robust against search instability from TT/NMP interactions, but the Elo difference is small. The engine's existing `reduced_score > alpha` → full-depth re-search (ADR-0025 §5) is a two-step form; extending to three steps requires one additional null-window call before the full-window re-search.

2. **LMR at PV nodes after migration**: Under ADR-0025 §2, LMR is gated by `!is_pv`. After the window-predicate migration, PV nodes (`beta - alpha > 1`) correctly skip LMR — because PVS's first-child full-window search makes every non-first move at a PV node a potential re-search candidate. This is semantically identical to the flag-based gate; no behavior change.

3. **Singular extensions at PV nodes**: M5.G singular extensions are not gated by `is_pv` (per `docs/research/m5-singular-extensions.md`). PVS does not change this interaction.
