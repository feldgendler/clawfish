# M3.F — `bench` Command + SPRT Conventions

Research synthesis for M3.F. Findings authored by chess-researcher (Sonnet) on 2026-04-29; persisted here verbatim modulo light formatting. Primary source URLs at the bottom.

## Topic 1: UCI `bench` Command Conventions

### Semantic contract

- `bench` is **not** part of the official UCI spec; it is a de-facto community standard pioneered by Stockfish and adopted by virtually every serious engine.
- Issued on the command line (`./engine bench`) or via stdin. Engine searches a fixed set of positions, sums node counts, prints a summary line, and exits.
- Required output: a final total node count and a nodes-per-second figure. Minimal acceptable format per OpenBench: `4712710 nodes 1323423 nps`.
- The node count is the canonical metric — it functions as a "fingerprint" of the exact search algorithm version.
- NPS is secondary; it scales across machines with different hardware and is used by distributed testing frameworks to normalise time controls.

### Arguments (Stockfish convention)

- `bench [ttSize] [threads] [limit] [fenFile] [limitType]`
- Defaults: ttSize=16 MB, threads=1, limit=13 (depth), fenFile=default, limitType=depth.
- For an engine without a TT (M3.F), ttSize is irrelevant; we may keep just `bench [depth]`.

### Position set

- Typically ~16–50 FEN positions vendored in the engine source.
- Stockfish's historic default was 16 positions; recent versions ~36+.
- Positions should span opening, middlegame, and endgame to exercise both search and eval broadly.
- Vendor a project-owned minimal set (16–30 hand-curated FENs). Public domain options:
  - The 6 canonical perft positions already in-repo (startpos, Kiwipete, Positions 3–6) provide structural variety; supplement with ~10 middlegame/endgame FENs.
  - WAC FENs are tactically biased; not ideal as a general bench corpus — bench positions should be diverse, not tactical.

### Default depth and determinism

- Depth 13 is the Stockfish convention.
- For an engine without a TT and without parallelism, depth 13 on a cold search is deterministic by construction — same position, same depth, same node count every run.
- At M3.F (no TT, single-threaded), there is no cache state to clear between positions; determinism is automatic.
- **Runtime estimate at M3.E:** depth-8 from startpos = 72.5M cumulative nodes (~9.2s). Depth-13 ≈ ~6 orders of magnitude bigger; far too slow for a regression baseline. **Recommend default depth 7 over 16 positions** → total wall ~5–20 s.

### "Bench: N" commit message convention

- Fishtest (Stockfish's testing infrastructure) enforces: the last line of a commit message for a functional change must match `\b[Bb]ench[ :]+[1-9][0-9]{5,7}\b` — i.e., `Bench: 1234567` (6–8 digit node count).
- Commits with no search impact use `No functional change` instead.
- Adopting now (even without OpenBench) costs nothing and establishes a clean git history where bench changes are immediately visible.

### Output to README / CONTRIBUTING

- Standard practice: document the current bench number in the README or CONTRIBUTING.md.

## Topic 2: SPRT Match Conventions vs Random / Very Weak Baselines

### SPRT bounds by engine tier

From CPW SPRT article:

| Engine tier | Gainer elo0/elo1 | Non-regression elo0/elo1 |
|---|---|---|
| Stockfish LTC | 0.5 / 2.5 | -1.75 / 0.25 |
| Top 30 engines | 0 / 3 | -3 / 1 |
| Top 200 engines | 0 / 5 | -5 / 0 |
| All other engines | 0 / 10 | -10 / 0 |

- `alpha=0.05, beta=0.05` is universal (95% confidence both directions).
- Clawfish at M3.F is "all other engines" tier: `elo0=0, elo1=10`.

### Beating a random mover: how many games does SPRT need?

- At ~100% win rate the LLR accumulates extremely fast.
- Logistic formula: Elo = -400 × log10((1-w)/w). 99% score ≈ 800 Elo; 99.9% ≈ 1200 Elo.
- With `elo0=0, elo1=10, alpha=0.05, beta=0.05`, the LLR upper bound is ln(0.95/0.05) ≈ 2.94. At a near-100% win rate, even 10–20 games suffice.
- Set a round cap of 200 rounds (400 games at 2 games/round) so the script doesn't hang.

### Time control

- `tc=10+0.1` (M2.E smoke TC) is a comfortable choice; `tc=5+0.05` also fine.
- Avoid sub-100ms base TCs — single-threaded engines with slow startup can DQ when fastchess deducts overhead.

### Opening books

- Vs-random: **no opening book needed**. The random mover doesn't punish imbalanced openings. Startpos every game is fine.

### Concurrency on Apple M4 (10-core, 4P+6E)

- Each game uses 1 thread per engine; for single-threaded engines, 2 logical cores per game.
- Sweet spot: `-concurrency 4` to `-concurrency 6`.

### Adjudication

- `-resign movecount=3 score=600` — keep on; speeds up decisive games.
- `-draw movenumber=34 movecount=8 score=20` — keep on; prevents pathological long endgames.
- `-maxmoves 200` — hard cap; safety against random-mover quirks.

### fastchess SPRT result parsing

- fastchess outputs LLR + Elo estimate per game pair; final line names accepted hypothesis.
- **Open question**: whether fastchess returns specific exit codes on H0 vs H1, or whether the wrapper script must parse stdout. Resolve empirically when implementing `scripts/sprt.sh`.
- `-report penta=true` — pentanomial stats; terminates faster than trinomial.

## Topic 3: Historical-Commit Baseline Build Flow

### Field-standard approach: confirmed

- The `git worktree` + isolated `cargo build --release` approach in `docs/workflow.md` is field-standard.
- Rust's incremental compilation caches the baseline build on re-run.

### Cache invalidation

- Built baselines are keyed by SHA/tag. Re-running SPRT against the same baseline re-uses the cached binary.
- Evict only if: Rust toolchain changes ABI, or build cache corruption suspected.
- `git worktree remove target/sprt-baselines/<tag>` evicts cleanly.

### Directory layout recommendation

- Use **annotated tag name** as directory key: `target/sprt-baselines/baseline-random-mover/`, not bare SHA.
- Tag names self-document `scripts/sprt.sh` invocations and log files.
- Sanitize `/` → `-` in tag names for filesystem-safe paths (`baseline/random-mover` → `baseline-random-mover`).

## Topic 4: First Rating Estimate Methodology

### Tools

| Tool | Approach | Notes |
|---|---|---|
| BayesElo | Bayesian; accounts for draw rate + first-mover advantage (~33 Elo) | Best-in-class accuracy; outputs CIs |
| Ordo | Pairwise; supports anchor ratings | Simpler, similar accuracy |
| Logistic formula | Elo_diff = -400 × log10((1-w)/w) | Fast point estimate; no CI |

For a first estimate: logistic formula is sufficient. Elo_self = Elo_ref + 400 × log10(w / (1-w)) where w = (wins + 0.5×draws) / total.

### Games needed for confidence

| Games | ±95% CI |
|---|---|
| 200 | ~70–100 Elo |
| 400 | ~50–70 Elo |
| 1000+ | ~30 Elo |

For M3.F first estimate: 200 games vs known-Elo reference → ±100 Elo (sufficient).

### Known-strength reference engines

| Reference | Known Elo | Notes |
|---|---|---|
| Stockfish 18, `UCI_Elo=1320` | ~1320 CCRL 40/4 | Lowest setting; calibrated at 120s+1s. Already vendored (ADR-0012). |
| Stockfish `Skill Level=0` | ~1100–1200 (estimated) | Less reliable; not separately calibrated. |

- Use Stockfish `UCI_Elo=1320` as the M3.F reference.
- Engine Elo is TC-dependent; estimate applies at the TC used.
- CCRL ratings are not comparable to FIDE human ratings.
