# M8.A.1 — Depth-Conditioned PVS: Design Research

**Builds on:** [`m8.a-pvs.md`](m8.a-pvs.md) (the PVS mechanism itself). This note covers only
the *depth-conditioning* added in M8.A.1, not PVS fundamentals.

## 1. Why depth-condition PVS at all

The M8.A SPRT vs `M7.B.2` (2-seed, mixed-TC + virtual-clock) was **net-negative but
depth-amplifying** — the mirror image of M7.B's profile:

| TC | combined W-L-D | ≈Elo | sign |
|----|----------------|------|------|
| 10+0.1 | 34-77-99 | ≈ −45 | regress |
| 20+0.2 | 40-62-102 | ≈ −25 | regress |
| 40+0.4 | 39-58-105 | ≈ −20 | regress |
| 60+0.6 | 70-32-82 | ≈ **+73** | **gain (2-seed-robust)** |

Aggregate ≈ −20 Elo ⇒ NO SHIP (record: [`bench/sprt/2026-06-25-m8a-pvs-vs-m7b2.md`](../../bench/sprt/2026-06-25-m8a-pvs-vs-m7b2.md)).
The crossover from regression to gain sits **between 40+0.4 and 60+0.6**.

### 1.1 Mechanistic cause of the profile

PVS at a non-first move does a cheap null-window **scout**; when the scout lands interior
(`alpha < s < beta`) it pays a full-window **re-search** that *also flips the child to
`is_pv = true`*, suppressing the `is_pv`-gated prunes (NMP/RFP/FFP/LMR) in that subtree
(ADR-0043 §1). Net per node: scout savings − (re-search cost + prune-suppression cost).

- **Fast TC** has no depth headroom to convert scout savings into extra plies, so the
  re-search + prune-suppression overhead dominates → regression.
- **Slow TC** converts the saved nodes into depth → gain.

The engine experiences TC **only through the ID root depth it reaches** (the M7.B.2
insight, ADR-0041): the *deciding* iteration is the deepest completed one. So the harm
lives at the **shallow** root iterations (all a fast TC ever completes) and the gain at
the **deep** ones (only a slow TC completes them). Conditioning PVS on root depth — off
shallow, on deep — is the natural fix, the depth-mirror of the M7.B.2 ramp.

## 2. Depth scale (measurement)

`go movetime {350,700,1400,2100}` (rough per-move budgets for 10+0.1 / 20+0.2 / 40+0.4 /
60+0.6) over three representative middlegames (Kiwipete, a quiet Najdorf-ish middlegame,
a closed centre), release build of the M8.A binary:

| per-move budget | measured completed depth (3 pos) | note |
|-----------------|----------------------------------|------|
| 350 ms  | 8, 9, 10 | |
| 700 ms  | 9, 10, 11 | |
| 1400 ms | 10, 11, 12 | |
| 2100 ms | 11, 12, 13 | |

The movetime proxy reads **~1.5 ply low** vs real games (M7.B.2 documented the 20+0.2
in-game median at ~11.5; the proxy gives ~10 for 700 ms). Recalibrated in-game deciding
depths: **10+0.1 ≈ 10.5, 20+0.2 ≈ 11.5, 40+0.4 ≈ 12.5, 60+0.6 ≈ 13.5**. The
regression→gain crossover therefore sits around **deciding depth ≈ d13** — a **tight ~1-ply
window** with heavy inter-TC overlap. This is the M5.K "the adaptive benefit is not cleanly
depth-localizable" risk made concrete, and the reason a **smooth ramp** (not a hard band/gate)
is mandatory here.

## 3. The two cautionary precedents

- **M7.B.2 (success, ADR-0041):** the fix for a depth-*inverse* mechanism (qsearch SEE
  prune) was a *smooth monotonic ramp on root depth* with the knee placed **above the
  protected TC's median depth** (`D0 = 12` > the 20+0.2 median ~11.5). Smoothness +
  knee-placement was the explicit, vindicated defense against M5.K.
- **M5.K (failure):** depth-*gating* the aspiration width by a **band `[8,12]`** lost
  −34.9 Elo — and the loss landed in the very bucket (20+0.2) it was meant to protect. The
  failure mode was a **non-monotonic band** + a **hard cliff**, not depth-conditioning per se.

**Takeaway for M8.A.1:** condition PVS on root depth with a **monotonic, smooth** ramp
(no band, no single-ply cliff), and keep the **off** regime byte-identical to the proven-safe
baseline (`M7.B.2`) so fast TC is *guaranteed* protected, not merely hoped-protected.

## 4. The conditioning knob: scout-start move index, ramped by root depth

PVS has no continuous per-move "aggressiveness" dial (a move is either scouted or not), so
the smooth knob is **how many of a node's moves are eligible to be scouted**, ramped by
root depth.

Move-ordering rank (the move-loop index `cur_i`: TT move, then captures by MVV-LVA, then
killers/history quiets) predicts fail-high probability: **early-ranked** non-first moves are
the ones that beat alpha → trigger the costly re-search + prune-suppression; **late-ranked**
moves almost never beat alpha → their scouts are near-pure savings. So scouting **only the
late-ranked moves** captures most of the node savings while incurring little of the harm.

Define a **scout-start rank** `pvs_scout_start(root_depth)`: a non-first move at rank
`cur_i` is scouted iff `cur_i >= pvs_scout_start(root_depth)`; otherwise it takes the
**reference full-window path** (the pre-PVS LMR loop — full-window reduced pilot →
full-window re-search, `is_pv` *not* flipped). The ramp:

- `root_depth <= D0` ⇒ `scout_start = ∞` ⇒ **no move scouted** ⇒ every non-first move takes
  the reference path ⇒ **byte-identical to `M7.B.2`**. (Fast TC, which only completes
  shallow iterations, is provably unchanged.)
- `D0 < root_depth < D1` ⇒ `scout_start` ramps **down** from a high rank to 1 — deeper
  iterations scout progressively earlier-ranked moves (a smooth, monotone, no-cliff change:
  one ply of depth unlocks `SLOPE` more ranks).
- `root_depth >= D1` ⇒ `scout_start = 1` ⇒ **all non-first moves scouted** ⇒ full PVS
  (≡ M8.A).

This makes M8.A.1 a strict generalization: M8.A = `(D0 = 0, scout_start ≡ 1)`;
M7.B.2 = `(D0 = ∞)`.

### 4.1 Why rank, not searched-count

`cur_i` is the move-ordering rank (it includes FFP-skipped quiets, which `continue`
before searching). Rank is exactly the fail-high predictor we want to threshold on; the
first *searched* move is always full-window regardless (the existing `is_first` guard), so
SE verification frames (first searched move at `cur_i == 1`) are handled correctly with no
special-casing.

## 5. Constant selection (first SPRT candidate)

Three constants (consistent with M7.B.2's own three: `D0=12, SLOPE=16, FLOOR=-64`):

| const | value | rationale |
|-------|-------|-----------|
| `PVS_RAMP_D0`    | 12 | At/below this, PVS off ≡ M7.B.2. Matches M7.B.2's `D0` and sits above the 10+0.1/20+0.2 deciding depths (~10.5/11.5) ⇒ both fast TCs fully protected; most of 40+0.4 (~12.5) too. |
| `PVS_RAMP_BASE`  | 16 | Scout-start rank just above `D0` (scout only ranks ≥16 — the deep tail) ⇒ small step off the "no scout" floor (smoothness). |
| `PVS_RAMP_SLOPE` | 4  | Ranks unlocked per ply above `D0`. ⇒ `D1 = D0 + ceil((BASE-1)/SLOPE) = 16`: scout-start reaches 1 (full PVS) at d16. |

Resulting `pvs_scout_start(d)`: d≤12 → ∞; d13 → 12; d14 → 8; d15 → 4; d≥16 → 1.

**Engagement by TC** (deciding depth): 10+0.1/20+0.2 (≤~11.5) → none (≡M7.B.2); 40+0.4
(~12.5) → ~none; 60+0.6 (~13.5) → scout ranks ≳8–12 (the tail, partial PVS); the deepest
60+0.6 iterations (d15–16) → full PVS. This is deliberately **conservative** — it
prioritizes *not re-introducing the fast-TC regression* (M8.A's actual failure, and the
M5.K-flavored risk the user flagged) over maximally harvesting the +73. A conservative
candidate that nets even slightly positive is shippable and then tunable.

### 5.1 Tuning levers if the first SPRT is marginal (in order)

1. **Lower `D0` 12→10 and/or steepen `SLOPE` 4→6** — engage PVS earlier so 60+0.6 gets
   fuller PVS (recover more of the +73). Use if fast TC is recovered but the slow-TC gain
   is muted.
2. **Raise `D0` 12→13/14** — if fast TC is *still* regressed (ramp engaged too early).
3. **Lower `BASE`** — scout more ranks at the first active depth (more aggressive onset).

All are single-constant edits; the mechanism (and its tests) are unchanged. This mirrors
the M7.B → M7.B.1 → M7.B.2 iterative-constant path.

## 6. Risks specific to depth-conditioning

- **Crossover too tight to separate (the headline risk).** Deciding depths overlap across
  TCs by ~1 ply, so any root-depth ramp has little room to help slow TC without touching
  40+0.4. Mitigated by: the **off-regime byte-identity** (40+0.4 and faster mostly land in
  the inert zone) + conservative constants + the explicit tuning levers. If even a swept
  ramp cannot net positive, the honest conclusion is that PVS's gain is not depth-separable
  on this engine — a clean shelve result, not a defect.
- **`root_depth` constancy within a tree.** `root_depth` is the ID iteration depth, fixed
  across the whole negamax tree for that iteration (published once per ID iteration, read in
  the move loop) — *not* the local node depth. This is the M7.B.2 model verbatim and is what
  makes "condition on the deciding iteration" correct. A node at `depth=2` deep inside the
  d15 iteration correctly uses the d15 ramp value.
- **No new non-determinism.** The ramp is a pure function of `root_depth`; bench (fixed
  depth ≤ d7 ≤ D0) is **inert** ⇒ byte-identical to M7.B.2/M8.A at bench. Determinism anchor
  preserved; the change can only act at d ≥ 13 in real games.
