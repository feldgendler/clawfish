# M2.D Research: Random_Seed UCI Option + SplitMix64 Random Mover

*Prepared for M2.D planning. Covers UCI `option`/`setoption` wire format, `Random_Seed`
design, SplitMix64 PRNG properties, reproducibility semantics, and option naming
conventions. Empirical Stockfish 18 probes are transcribed verbatim where load-bearing.*

Sources: UCI 2006 spec (`docs/reference/uci-protocol-2006.txt`), PRNG shootout
(prng.di.unimi.it), Chessprogramming Wiki, Rust Rand book, Stockfish 18 black-box probes.

---

## 1. UCI `option` Declaration Wire Format

### 1.1 Canonical grammar (from UCI 2006 spec §option)

```
option name <id> type <t> [default <x>] [min <x>] [max <x>] [var <x> ...]
```

- Every field after `type` is optional; a button has no `default`/`min`/`max`.
- The `spin` type is defined as "a spin wheel that can be an integer in a certain range."
- All five spec-defined types: `check`, `spin`, `combo`, `button`, `string`.

### 1.2 Spin option example from spec

```
option name Selectivity type spin default 2 min 0 max 4
```

### 1.3 Stockfish 18 spin options (black-box probe — `printf 'uci\nquit\n' | stockfish`)

| Option | Default | Min | Max |
|---|---|---|---|
| Threads | 1 | 1 | 1024 |
| Hash | 16 | 1 | 33554432 |
| MultiPV | 1 | 1 | 256 |
| Skill Level | 20 | 0 | 20 |
| Move Overhead | 10 | 0 | 5000 |
| nodestime | 0 | 0 | 10000 |
| UCI_Elo | 1320 | 1320 | 3190 |
| SyzygyProbeDepth | 1 | 1 | 100 |
| SyzygyProbeLimit | 7 | 0 | 7 |

Largest declared `max` in Stockfish 18: **33,554,432 (2^25)** — well within signed 32-bit range.

### 1.4 Critical finding: GUIs (and Stockfish itself) parse spin values as signed 32-bit int

Probe:
```
printf 'uci\nsetoption name Hash value 9999999999\nquit\n' | stockfish
```
Result: `libc++abi: terminating due to uncaught exception of type std::out_of_range: stoi: out of range`

- Stockfish 18 uses `stoi()` (C++ signed 32-bit `int`) to parse spin values.
- Any value outside `[INT_MIN, INT_MAX]` = `[−2,147,483,648, 2,147,483,647]` causes an abort.
- Boundary probe: value `2,147,483,647` (i32::MAX) accepted cleanly.
- Boundary probe: value `2,147,483,648` (i32::MAX + 1) crashes.
- **This behavior is the engine itself; GUIs likely have the same constraint or worse.**

### 1.5 Implications for `Random_Seed` range

A 64-bit seed cannot be expressed as a `spin` value without risking GUI/engine crashes.
Options:

| Approach | Max seed bits | Notes |
|---|---|---|
| `spin` with `max 2147483647` | 31 | Safe everywhere; 2^31 seeds is ample for reproducibility |
| `spin` with `max 1000000000` | ~30 | Round number, clearly safe, slightly less range |
| `type string` | 64+ | GUI renders a text box; seed must be parsed as decimal; awkward |
| Two `spin` options (lo + hi) | 62 | Ugly and unnecessary |

**Recommendation:** `option name Random_Seed type spin default 0 min 0 max 2147483647`

- Default 0 means "seed from system entropy at startup" (or alternatively "seed is 0").
- `min 0`: seeds are non-negative by convention; negative seeds have no extra meaning.
- `max 2147483647`: i32::MAX, safe for all known GUI/engine spin parsers.
- 31 bits gives 2.1 billion distinct seed values — more than enough for test reproducibility.

## 2. `setoption name X value Y` Parsing Edge Cases

### 2.1 Canonical wire format

From UCI spec §setoption:
```
setoption name <id> [value <x>]
```

- `name` and `value` are literal keywords acting as delimiters.
- The spec says: "The name and value of the option in `<id>` should not be case sensitive and can include spaces."
- The spec warns: "The substrings 'value' and 'name' should be avoided in `<id>` and `<x>` to allow unambiguous parsing."

### 2.2 Stockfish 18 probes — tabulated

| Input | Stockfish output | Interpretation |
|---|---|---|
| `setoption name Hash value 32` | (silent, accepted) | Canonical happy path |
| `setoption name Skill Level value 10` | (silent, accepted) | Multi-word name works |
| `setoption name hash value 32` | (silent, accepted) | Case-insensitive matching confirmed |
| `setoption name skill level value 5` | (silent, accepted) | Case-insensitive multi-word |
| `setoption name NonExistentOption value 42` | `No such option: NonExistentOption` | Unknown option: plain-text error to stdout |
| `setoption name Hash` (no `value` clause) | (silent, accepted) | Missing value: silently ignored |
| `setoption name Hash value 0` (below min=1) | (silent, accepted) | Out-of-range low: clamped or ignored, no error |
| `setoption name Hash value 99999999` (above max) | (silent, accepted) | Out-of-range high: clamped or ignored, no error |
| `setoption name Hash value 2147483647` | (silent, accepted) | i32::MAX: accepted |
| `setoption name Hash value 2147483648` | crash (SIGABRT) | i32::MAX+1: stoi overflow, engine crashes |
| `setoption name Hash value banana` | crash (SIGABRT) | Non-integer for spin: stoi parse failure, engine crashes |
| `setoption name draw value value 5` | `No such option: draw` | "value" in name: first `value` token acts as delimiter, name = "draw" |
| `setoption value 42` (no `name` keyword) | `No such option: 42` | Stockfish interprets "42" as the option name (different parser than ours) |
| `setoption` (no args) | `No such option: ` (empty) | Empty name emits error |

### 2.3 "No such option" output format

- Stockfish emits a **plain-text line** to **stdout** (not stderr, not `info string`-prefixed).
- Format: `No such option: <name>`
- This is **non-spec**; the UCI protocol does not define an error response for unknown options.
- A conforming GUI ignores lines it doesn't recognize.

### 2.4 Our parser (`parse_setoption` in `src/uci.rs`) — gap analysis

Our parser (per M2.B):
- Extracts `name` as tokens between the `name` keyword and the first `value` keyword.
- Extracts `value` as everything after the `value` keyword.
- Returns `Command::Unknown` if `name` keyword is missing or name is empty.

Comparison with Stockfish probes:

| Case | Our parser | Stockfish | Gap? |
|---|---|---|---|
| `setoption name Foo value 42` | `SetOption { name: "Foo", value: Some("42") }` | Accepted | No gap |
| `setoption name Foo Bar value 42` | `SetOption { name: "Foo Bar", value: Some("42") }` | Accepted | No gap |
| `setoption name Foo` (no value) | `SetOption { name: "Foo", value: None }` | Accepted | No gap |
| `setoption name Foo value` (empty value) | `SetOption { name: "Foo", value: Some("") }` | (not probed separately) | Engine must handle `Some("")` as "no change" |
| `setoption` (no args) | `Command::Unknown` | `No such option: ` | Behavioral difference; both effectively no-op |
| `setoption value 42` (no `name` keyword) | `Command::Unknown` | `No such option: 42` | Behavioral difference; both effectively no-op |
| `setoption name draw value value 5` | `SetOption { name: "draw", value: Some("value 5") }` | `No such option: draw` | Behavioral difference on name-containing-"value" |

**Key gap:** When the option name contains the literal word `value` (e.g. `name: "draw value"`),
our parser and Stockfish diverge. The spec explicitly says to avoid this — `Random_Seed` is
safe as the underscore-separated single-token name avoids the ambiguity entirely.

**Action for M2.D:** `handle_setoption` in `engine.rs` must parse `value` as a decimal integer,
reject non-parseable strings or out-of-range values (emit `info string` error when debug on,
silent otherwise), and update the PRNG seed state.

### 2.5 Engine-side error handling for `setoption` (spec + empirical)

- **Spec:** Silent. No error response is specified for unknown options or bad values.
- **Stockfish (reference):** Emits `No such option: <name>` to stdout for unknown options.
  This is non-spec behavior (a plain text line, not `info string`).
- **Our engine (M2.C baseline):** Silent when debug off; `info string setoption received: …`
  when debug on. Does not yet act on any option.

**Recommendation for M2.D:**
- Unknown option: silent (debug off); `info string setoption rejected: unknown option 'X'` (debug on).
- Bad value for `Random_Seed` (non-integer, out of range): silent (debug off); `info string setoption rejected: bad seed value 'Y'` (debug on).
- Out-of-range clamping (alternative to rejection): also defensible, but rejection with debug-mode logging is cleaner for a test engine.

## 3. SplitMix64 PRNG

### 3.1 Algorithm summary

SplitMix64 is a fixed-increment counter PRNG by Sebastiano Vigna (public domain).

Reference implementation (verbatim from prng.di.unimi.it, public domain):
```c
uint64_t next(void) {
    uint64_t z = (x += 0x9e3779b97f4a7c15ULL);
    z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9ULL;
    z = (z ^ (z >> 27)) * 0x94d049bb133111ebULL;
    return z ^ (z >> 31);
}
```

State: one `u64`. Seed by setting `x = seed` before the first call.

### 3.2 Properties

| Property | Value |
|---|---|
| Period | 2^64 (full period — visits every 64-bit value exactly once) |
| State size | 64 bits (one `u64`) |
| Output | 64 bits per call |
| Speed | ~0.63 ns per call on modern hardware; ~0.29 cycles/byte |
| Statistical quality | Passes BigCrush, DieHard, TestU01; no Hamming-weight dependency failures |
| Cryptographic security | None — not suitable for security-sensitive use |

### 3.3 Why SplitMix64 is the standard seeder

The prng.di.unimi.it reference explicitly states:
> "We suggest to use SplitMix64 to initialize the state of our generators starting from a
> 64-bit seed, as research has shown that initialization must be performed with a generator
> radically different in nature from the one initialized to avoid correlation on similar seeds."

SplitMix64 is used to seed xoshiro256**, xoshiro256+, xoroshiro128+, and similar generators
precisely because its avalanche behavior guarantees decorrelated initial states even for
seeds that differ by 1.

### 3.4 Suitability for picking uniformly from N ≤ 218 legal moves

**Modulo bias analysis:**

| Move count N | `2^64 mod N` | Bias probability |
|---|---|---|
| 20 | 16 | 8.67 × 10^−19 |
| 30 | 16 | 8.67 × 10^−19 |
| 40 | 16 | 8.67 × 10^−19 |
| 100 | 16 | 8.67 × 10^−19 |
| 218 (theoretical max) | 66 | 3.58 × 10^−18 |
| 256 (power of 2) | 0 | 0.00 |

- Bias probability for any N ≤ 218 is below 4 × 10^−18.
- One bias event per ~3 × 10^17 samples at worst (N = 218).
- **Simple modulo `rng_output % n_moves` is correct for this application.**
  Rejection sampling adds complexity with zero practical benefit.

### 3.5 Alternatives considered

| PRNG | Period | State | Suitability for M2.D |
|---|---|---|---|
| SplitMix64 | 2^64 | 64 bits | Ideal — trivial impl, 10 lines, no dep |
| xoshiro256** | 2^256 - 1 | 256 bits | Overkill for N moves selection; needs seeding via SplitMix64 anyway |
| PCG64 | 2^128 | 128 bits + stream | More complex impl; marginal quality improvement; not the established chess tool |
| `std::mt19937` / Mersenne Twister | 2^19937 - 1 | 19937 bits | Used by Arasan; overkill; large state initialization |
| `rand::thread_rng()` | OS-seeded | — | Adds `rand` dependency; per-thread state; not seedable from UCI option |

**Conclusion:** SplitMix64 is the right choice for M2.D.
- No external dependency; 10-line implementation inline in `src/search.rs` or a new `src/prng.rs`.
- Passes all standard statistical tests.
- Trivially seedable from the `Random_Seed` UCI integer option.
- The Rust `rand_xoshiro` crate provides it (as `SplitMix64`), but adding a dependency for
  10 lines of public-domain code is not warranted.

## 4. Reproducibility Semantics

### 4.1 The design question

Two models for PRNG state across a sequence of `go` calls:

**Model A — continuous state (seed → run → continue):**
- The PRNG state evolves across all `go` calls in the session.
- `seed 42 + position P1 + position P2 → deterministic game`, but only if positions arrive
  in the same order.
- Inserting or removing a `go` call changes all subsequent moves.
- Sensitive to non-go commands that might (or might not) advance the PRNG.

**Model B — per-go re-seed:**
- Each `go` call re-seeds the PRNG from a function of (seed, ply, position hash, or similar).
- `seed 42 + position P1 → always same move from P1`, regardless of history.
- Moves are individually reproducible; the game is reproducible only if positions are.

### 4.2 Prior-art discussion

No direct TalkChess or Chessprogramming Wiki discussion found on per-go vs. continuous state
for random movers specifically. The absence itself is informative: most random-mover engines
in the wild are trivially implemented with a global PRNG state seeded once at startup and never
reset. None document a per-go re-seed strategy in accessible forum posts.

The Chessprogramming Wiki notes that Zobrist keys use a PRNG seeded once at program
initialization — the opposite design: seed once, never reset. This is for *determinism of
keys*, not *randomness of play*, but establishes the conceptual baseline.

**Open question (source-code restriction applies):** Whether any widely-deployed random-mover
engine re-seeds per `go` or resets on `ucinewgame` is not determinable without reading engine
source. Flag as open.

### 4.3 Recommendation

**Use continuous state (Model A) with a `ucinewgame`-triggered reset.**

Rationale:

- **Simplicity.** One `u64` state field in the `RandomMover` struct; no interaction with
  position hash or ply count.
- **Reproducibility guarantee.** `seed 42 + ucinewgame + same sequence of go` → same game.
  This is the natural reproducibility contract for tournament play: start a game from scratch
  with a known seed.
- **`ucinewgame` as the reset hook.** The spec defines `ucinewgame` as signaling a new game;
  resetting the PRNG at that boundary is semantically correct. The PRNG resets to `seed` (the
  current `Random_Seed` value), not to 0.
- **`setoption name Random_Seed value N` mid-game.** Spec allows `setoption` only between
  `go` calls ("the engine is waiting"). Applying the new seed immediately (at setoption time)
  is correct; the engine's current game state is separate from the PRNG seed.
- **Session-wide initial seed.** At engine startup, if `Random_Seed` is never set, seed from
  system time or a fixed default (0 is a valid SplitMix64 seed; `u64::MAX` is another common
  choice). Default 0 on the `option` declaration means "seed value 0" unless the user changes
  it.

### 4.4 Interaction table

| Event | PRNG state action |
|---|---|
| Engine startup | Set `prng_state = seed_value` (seed_value = default from option decl) |
| `setoption name Random_Seed value N` | Update `seed_value = N`; do NOT reset `prng_state` yet (mid-game consistency) |
| `ucinewgame` | Reset `prng_state = seed_value` |
| Each `go` call | Pick move using `prng_state`; state advances per call |
| `stop` / cancellation | No PRNG effect (state has already advanced from the pick) |

**Open question:** Whether `setoption` should immediately reset `prng_state` or defer to
`ucinewgame`. The table above defers. If the use case is "change seed then play one game
starting now," the user should send `ucinewgame` after `setoption` anyway. Either policy is
defensible; deferred is more conservative.

## 5. Multi-Word Option Name Convention

### 5.1 The parsing problem

The spec allows option names with spaces (e.g. `Skill Level`, `Clear Hash`). This requires
the `setoption name <id> value <x>` parser to split on the `value` keyword — making names
that contain the word `value` or `name` ambiguous.

Stockfish probe confirms the ambiguity:
```
setoption name draw value value 5
→ No such option: draw
```
The first `value` token terminates the name. The spec explicitly warns against this.

### 5.2 Conventions in practice

| Option name style | Example | Parsing | GUI display |
|---|---|---|---|
| Underscore-separated single token | `Random_Seed` | Unambiguous; no `value`/`name` collision risk | Displayed verbatim |
| CamelCase single token | `RandomSeed` | Unambiguous | Displayed verbatim |
| `UCI_` prefix | `UCI_RandomSeed` | Unambiguous; GUI may suppress display (spec: "if the GUI gets an unknown Option with the prefix 'UCI_', it should just ignore it") | Hidden from dialog |
| Multi-word spaced | `Random Seed` | Safe if name contains neither "value" nor "name"; parsed correctly by our parser | Displayed with space |

### 5.3 Recommendation: `Random_Seed`

- **Single token** (no spaces) → parsing is unambiguous regardless of GUI parser quality.
- **Underscore** is the established convention for multi-component names without spaces.
  Stockfish uses it for `nodestime`; the UCI spec itself uses underscore for `UCI_Elo`,
  `UCI_LimitStrength`, etc.
- **Not `UCI_` prefixed** because the spec says GUIs should ignore (not display) unknown
  options with that prefix. `Random_Seed` is a user-visible option; it should appear in the
  GUI's options dialog.
- **Not `RandomSeed`** (pure CamelCase) — less readable in GUI option lists, and harder for
  users to remember to type when running command-line probes.
- **Avoid `Random Seed`** (two tokens with a space) — valid by spec, but requires every GUI
  to parse multi-token names correctly; spaced names are rare in practice and GUIs have been
  known to truncate at the first token.

### 5.4 Interaction with our parser

Our `parse_setoption` in `src/uci.rs` handles the multi-word name case correctly:
```
setoption name Random_Seed value 42
→ SetOption { name: "Random_Seed", value: Some("42") }
```
No parser changes needed for M2.D. The engine-side `handle_setoption` must match on
`name == "Random_Seed"` (case-insensitively per spec, though our M2.C baseline does
exact-match comparison — this needs attention).

**Case sensitivity gap:** Our current `handle_setoption` (M2.C) does nothing with the option
name. When M2.D adds real handling, it should normalize to lowercase before matching
(spec: "should not be case sensitive") or match case-insensitively.

## 6. Current Parser State vs. M2.D Requirements

### 6.1 What the existing parser already handles correctly

- `setoption name Random_Seed value 42` → `SetOption { name: "Random_Seed", value: Some("42") }` — correct.
- `setoption name Random_Seed` → `SetOption { name: "Random_Seed", value: None }` — correct
  (engine should treat missing `value` as "no change").
- `setoption name Random_Seed value` → `SetOption { name: "Random_Seed", value: Some("") }` —
  correct (engine should treat empty value as "no change" or error).

### 6.2 What M2.D must add to `engine.rs`

In `handle_setoption`:
1. Match `name` case-insensitively against `"random_seed"`.
2. Parse `value` as `u64` (or `i64` then clamp to `[0, i32::MAX]`).
3. On parse failure or out-of-range: debug-mode `info string` error; otherwise silent.
4. On success: update `seed_value`; do NOT yet reset `prng_state` (defer to `ucinewgame`).

In `handle_uci` (the `uci` response):
1. Emit `option name Random_Seed type spin default 0 min 0 max 2147483647` between `id author`
   and `uciok`.

In `handle_ucinewgame`:
1. Call `self.search.reset_seed(self.seed_value)` or equivalent — reset the PRNG to the
   stored seed value.

### 6.3 Test that needs updating (M2.C forward-compat caveat)

`handle_setoption_silent_no_output_when_debug_off` (A14 in the test suite) currently asserts
that `setoption name Hash value 16` produces zero output bytes. When `Random_Seed` lands, this
test remains valid for an *unknown* option like `Hash` (we don't implement Hash). No change
needed unless the test is broadened to cover `Random_Seed` specifically.

## 7. Summary of Load-Bearing Findings

| Finding | Impact on M2.D |
|---|---|
| UCI `spin` values are parsed as signed 32-bit by Stockfish/GUIs | `max` must be ≤ 2,147,483,647; declare `option name Random_Seed type spin default 0 min 0 max 2147483647` |
| "No such option" is Stockfish's non-spec behavior | Our engine should be silent on unknown options (debug off) or emit `info string` (debug on) — do NOT emit a bare `No such option:` line |
| Stockfish crashes on non-integer or >i32::MAX spin values | Our engine must validate before applying; reject gracefully |
| SplitMix64: 10-line public-domain impl, period 2^64, passes BigCrush | Inline implementation; no new Cargo dependency needed |
| Modulo bias for N ≤ 218 moves: < 4 × 10^−18 | Simple `rng_output % n_moves` is correct; no rejection sampling needed |
| `Random_Seed` (underscore, single token) avoids all parsing ambiguities | Use this name; no parser changes required |
| Continuous PRNG state + reset on `ucinewgame` is the natural semantic | Implement: seed_value stored in Engine; prng_state in RandomMover; reset on `ucinewgame` |
| Our `parse_setoption` already parses `setoption name Random_Seed value N` correctly | No parser changes needed for M2.D |
| Case-insensitive matching needed in `handle_setoption` | Normalize to lowercase before matching option names |

## 8. Open Questions (Source-Code Restriction Applied)

- **Whether any existing random-mover engine uses per-go re-seeding** could not be determined
  without reading engine source (e.g. `chess-random-mover` on GitHub). This is flagged as open.
  The recommendation in §4.3 is based on first-principles reasoning, not observed prior art.
- **Whether specific GUIs (Arena, Banksia, ChessBase) use 32-bit or 64-bit int parsing for
  spin values** is not definitively documented. The Stockfish 18 crash on i32::MAX+1 is the
  strongest available signal. The safe assumption is 32-bit.
