# M6.G — Per-game-file reorder protocol: prior-art research

Scope: the architectural rework of the M6.G corpus-construction pipeline
in `src/corpus/` to use a per-game-file staging area + in-order commit
consumer. This note collects prior art on the four sub-questions raised in
the planning brief: in-order commit protocols, per-file token-passing
designs, chess-specific selfplay pipelines, and determinism caveats. It
informs the architectural plan at `docs/plans/m6.g-per-game-files.md`.

ADR-0003 honored: no engine source repos browsed.

---

## 1. In-order commit protocols in parallel data-processing systems

The pattern of parallel producers emitting work in arbitrary completion
order, with a single consumer committing results in a fixed sequence, is
well-documented in several domains.

**MapReduce shuffle-sort.** Hadoop's reducer phase depends on all mapper
outputs being sorted and partitioned before the reduce step begins. The
sort is an explicit barrier: consumers never begin while producers are
still mid-flight. The analogue for the new design is the consumer's "wait
for `pending/game-{next_consume_id}.bin`" step — but unlike MapReduce, the
new design interleaves production and consumption, which removes the
barrier but introduces a reorder-buffer requirement.
[Netjstech MapReduce shuffle](https://www.netjstech.com/2018/07/shuffle-and-sort-phases-hadoop-mapreduce.html)

**Kafka parallel consumer (Confluent).** The most direct industry
analogue. Confluent's parallel-consumer library maintains in-order offset
commits against parallel message processing via a per-partition ring
buffer. The consumer tracks which game-IDs (Kafka: offsets) have completed
and scans for the largest contiguous committed prefix, committing only
that prefix. Two key documented facts:
- Ring buffer size is **bounded**. If producers fill the buffer faster
  than the consumer drains it, the system blocks new work rather than
  growing without bound.
- A slow or failed producer causes **head-of-line blocking** in the
  ordered mode: the consumer cannot advance past game N until game N
  appears, even if N+1, N+2, … are already present.

[parallel-consumer GitHub](https://github.com/confluentinc/parallel-consumer),
[Michael Diggin on HoL blocking](https://medium.com/@michael.diggin/side-stepping-head-of-line-blocking-in-kafka-consumers-6e7cbe44feb4)

**Write-ahead log replay.** WAL-based databases (LevelDB, PostgreSQL) use
sequential log replay on recovery: they scan the log from the last
checkpoint and replay records in order. The structural analogue is the
consumer's `scan_valid_blocks` on `shard.bin` plus scanning the `pending/`
directory to reconstruct `next_consume_id`. The standard pitfall is that
the checkpoint must be written **after** the data it references is durable
— the same ordering ADR-0035 §6 already specifies (game-block fsync THEN
checkpoint rename).
[Architecture Weekly WAL](https://www.architecture-weekly.com/p/the-write-ahead-log-a-foundation)

**Ordered producer-consumer (generic patterns).** The Go concurrency
literature documents three patterns for in-order output from parallel
workers: (a) a per-job reply channel (natural backpressure via blocking),
(b) a `sync.Cond` turn-taking scheme (thundering-herd at high goroutine
counts — not recommended), (c) permission-passing chains where each job
holds a "canWrite" token and passes it to the next job on completion.
Pattern (a) is structurally what the filesystem-as-queue design
implements: the pending file IS the reply channel, and the consumer
polls/blocks on the specific next-expected filename.
[Destel ordered Go](https://destel.dev/blog/preserving-order-in-concurrent-go)

## 2. Per-file token-passing / spool-directory designs

**The canonical write-tmp-fsync-rename sequence.** The crash-consistent
file-writing idiom across all spool systems is:

```
write tmp file in same directory
  → fsync(file_fd)
  → rename(tmp, final)
  → fsync(dirfd)
```

The rename is POSIX-atomic at the VFS level, but the directory entry
update is not durable without the subsequent directory fsync. A 2025
arXiv study on AI-training checkpoints on macOS/APFS confirms: without
explicit `fsync(2)` calls on both the file and its parent directory,
writes can sit in OS buffers and vanish on crash. Two durability tiers:
`atomic_nodirsync` (file fsync only) and `atomic_dirsync` (+ parent dir
fsync). For a corpus pipeline where each per-game file represents an
irreplaceable completed game, **atomic_dirsync** is the correct tier.
[arXiv 2511.18323 APFS crash-consistent checkpointing](https://arxiv.org/html/2511.18323)

**Exim's two-file journal pattern.** Exim stores each message as two
files (`-H` header/envelope, `-D` data) and uses a `-J` journal to record
delivery progress atomically. Update sequence: write new `-H` via
tmp-rename → delete `-J`. On crash before deletion, the journal survives
and `-H` is reconstructed on next processing. Lesson: the checkpoint must
be the *last* thing written, and recovery reconstructs state by reading
content files, not trusting the checkpoint alone. Exim specifically warns
that "renaming a file loses fcntl() write locks at the instant of rename"
— relevant if the new design ever needs advisory locking across workers.
[Exim spool format](https://www.exim.org/exim-html-current/doc/html/spec_html/ch-format_of_spool_files.html)

**Postfix maildrop.** Postfix uses a maildrop subdirectory as a staging
area; `postdrop` writes the message there, and a separate `pickup(8)`
daemon moves it onward. Ordering is *not* sequenced — Postfix's queue
manager explicitly says queue file access order is unspecified. This is
the correct model for a purely unordered workqueue, but it breaks down
when the consumer needs in-order commit. Not applicable to the new design.
[Postfix Architecture Overview](https://www.postfix.org/OVERVIEW.html)

**POSIX readdir ordering — critical gotcha.** `readdir()` on POSIX makes
**no ordering guarantee** — the order of entries returned is
filesystem-implementation-defined. On APFS, HFSX, and ext4 with
`dir_index`, entries are typically returned in hash order, not
name-lexicographic order. This means a consumer that does
`readdir(pending_dir)` and processes entries in returned order would
process games out of sequence. **The new design must avoid this by
polling for the specific expected filename** (`pending/game-{next_consume_id:020}.bin`)
rather than iterating directory entries.
[IBM readdir ordering note](https://www.ibm.com/support/pages/order-directory-contents-returned-calls-readdir)

**inotify / kqueue race condition.** If the consumer uses filesystem
events (inotify/kqueue) rather than polling to detect new pending files,
there is a documented near-unavoidable race: files created between
directory registration and the first `readdir()` scan are invisible to
inotify. The safe pattern is: register the watch, then do a full
directory scan, then start event processing. Missing this leads to the
consumer blocking indefinitely. For the new design, **polling** (`stat`
or `openat` in a tight sleep loop) avoids this race at the cost of some
latency.
[inotify man page](https://man7.org/linux/linux-manpages/man7/inotify.7.html)

## 3. Chess-specific: per-game-file selfplay pipelines

No prior art was found describing a chess-specific per-game-file reorder
protocol at the architectural level in blog posts, wiki articles, or
papers. The closest analogues:

**Leela Chess Zero (Lc0).** Distributed client-server model: volunteers
generate self-play games and upload them to a central server. Game data
is packed into tar.gz archives of 10,000 games each before transfer —
not individual per-game files. Ordering is not a requirement; the server
accumulates games until a threshold triggers a new training round, with
no sequencing constraint.
[Leela Chess Zero Wikipedia](https://en.wikipedia.org/wiki/Leela_Chess_Zero)

**Leorik self-play.** A TalkChess thread documents games generated from
scratch via self-play with randomization, extracted to a standard
`FEN c9 "result"` format. The thread confirms game-result labels only
(no Stockfish annotation). No architectural details about worker
coordination, per-game files, or crash recovery were published in
accessible prose.
[TalkChess labeled positions](https://talkchess.com/viewtopic.php?t=82191)

**Open finding.** Whether any existing chess training pipeline uses a
per-game-file ordered-commit model at the producer side is **not
documented in accessible public prose**. The pattern appears to be an
original design choice here. The closest structural match outside chess
is the Kafka parallel-consumer ordered-offset-commit architecture from §1.

## 4. Determinism caveats and filesystem ordering

**macOS APFS: fsync is not F_FULLFSYNC.** Critical gotcha: standard
`fsync(2)` on macOS/APFS does not guarantee data reaches persistent
storage. Apple's implementation flushes to the OS page cache but not
necessarily to the storage device. The correct syscall for durable writes
on macOS is `fcntl(fd, F_FULLFSYNC)`. **Rust's
`std::fs::File::sync_all()` wraps `F_FULLFSYNC` on macOS** — using raw
`libc::fsync()` directly would be wrong on macOS; `File::sync_all()` is
correct.
[SQLite fsync on macOS](https://avi.im/blag/2025/sqlite-fsync/),
[Phoronix macOS fsync benchmark cheating](https://www.phoronix.com/forums/forum/software/bsd-mac-os-x-hurd-others/1309928-turns-out-macos-has-been-benchmark-cheating-in-writes-by-not-doing-proper-fsync)

**APFS rename robustness.** The arXiv 2511.18323 study notes that on APFS
specifically, "rename() has been robust" in practice in their experiments
— suggesting APFS's copy-on-write metadata makes the directory entry
more durable than on ext4 without journal tuning. However, the authors
still recommend `atomic_dirsync` for critical workloads.
[Apple APFS Features](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/Features/Features.html)

**Rename atomicity vs. durability.** A documented confusion in the field:
POSIX `rename()` is atomic with respect to other processes observing the
directory (they see either old name or new name, never both), but it is
**not** atomic with respect to crash durability unless the parent
directory is also fsynced. This matters for correctness: a worker that
does `write → fsync(file) → rename(tmp, final)` but omits `fsync(dirfd)`
after the rename may lose the directory entry on power loss even though
the file content is durable. The consumer would then never see the
pending file and block forever.
[npm write-file-atomic issue #64](https://github.com/npm/write-file-atomic/issues/64),
[LWN atomic writes](https://lwn.net/Articles/789600/)

**Bounded reorder buffer.** If workers are capped at K concurrent games
and the consumer commits sequentially, the maximum number of completed-
but-not-yet-consumed pending files is K−1. Bounded by construction; no
unbounded accumulation is possible. The Kafka parallel-consumer
literature confirms this is the correct framing — the ring buffer size
is K, bounded by the concurrency level.

## Summary table

| Pattern | Domain | Key property | Primary pitfall |
|---|---|---|---|
| Write-tmp → fsync(file) → rename → fsync(dir) | All spool systems | Durable atomic placement | Omitting dir fsync loses entry on power loss |
| Sequential consumer, parallel producers | Kafka, WAL replay | In-order commit from OOO completions | Head-of-line blocking if slow worker stalls |
| Pending-dir as reorder buffer | This design, mail queues | Bounded (K files max), crash-recoverable | readdir order not POSIX-guaranteed; must probe by name |
| macOS fsync | APFS specifically | `File::sync_all()` wraps F_FULLFSYNC correctly | Raw `libc::fsync()` is not durable on macOS |
| inotify/kqueue directory watch | Event-driven consumers | Lower latency than polling | Race: files arriving before watch starts are missed |
| Checkpoint after data fsync | WAL, Exim journal | Idempotent recovery: re-emit last game on crash | Checkpoint written before data fsync loses the game |

## Recommendations to bake into the architectural plan

The per-game-file reorder model is sound and well-precedented in the
spool/WAL literature. The critical implementation requirements that the
prior art surfaces:

1. **Workers must use `File::sync_all()`** (not `libc::fsync`) for both
   the pending file and the parent directory before moving on. On macOS
   the file sync is automatically `F_FULLFSYNC`; the dir fsync is also
   needed.
2. **The consumer must probe by exact expected filename**
   (`pending/game-{N:020}.bin`), never rely on readdir order.
3. **Polling beats event-driven** for this consumer: polling is simpler
   and eliminates the inotify/kqueue creation-before-watch race entirely
   at the cost of some latency.
4. **Bounded accumulation is guaranteed by capping workers at K** — the
   pending directory holds at most K−1 files at steady state. No
   additional backpressure mechanism is needed.
5. **Head-of-line blocking from a slow or crashed worker is the primary
   liveness risk.** A worker that crashes mid-game never writes its
   pending file, so the consumer blocks at `game-{N}`. Resume logic must
   detect this: on startup, scan both `shard.bin`/`val.bin` (for
   committed games) and `pending/` (for completed-but-not-consumed
   games), then set `next_consume_id` and `next_dispatch_id` to the
   first gap. Any in-flight-at-crash game is simply re-played.
