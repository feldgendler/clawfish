# M3.D — Quiescence search

Adds qsearch as the leaf node of M3.C's negamax. Replaces M3.C's `depth == 0 → evaluate(pos)` short-circuit with `depth == 0 → qsearch(...)`. Restores tactical correctness past the search horizon by extending captures + queen-promotions until the position is "quiet." No new ADR — the qsearch design is fully covered by ADR-0016 §9 and the prior-art research's headline calls.

## 0. Goals

- `AlphaBetaMover::qsearch(pos, alpha, beta, ply, ctx) -> i32` private method in `src/search.rs` — implements stand-pat + capture/queen-promo extensions + in-check evasions.
- Stand-pat baseline: `evaluate(pos)` is the lower bound when not in check; `>= beta` produces a fail-soft cutoff; `> alpha` improves alpha. **Disallowed in check** (per CPW: stand-pat-in-check is unsound — engine could "stand pat" while king is being mated next ply).
- Move scope: captures (including EnPassant) + queen promotions (including queen-promo-captures). **No** under-promotions, **no** non-capture checks, **no** delta pruning, **no** SEE.
- In-check special case: generate **all** legal moves (evasions); no stand-pat; if move list empty → mate (return `-(MATE - ply)`).
- Terminal handling: not-in-check + no-captures-generated → return stand-pat (quiet position, no terminal claim). Critical to avoid the false-stalemate bug.
- MVV-LVA ordering on captures (reuses M3.C's `mvv_lva_score`).
- Cancellation: 4096-node cadence at top of qsearch (same shape as negamax).
- Replaces `negamax`'s depth==0 horizon: `if depth == 0 { return self.qsearch(pos, alpha, beta, ply, ctx); }`.
- M3.D is the chess-coder Sonnet+Opus parallel A/B calibration trigger (deferred from M3.C per workflow log).

## 3. `qsearch` body

**Step ordering** (the prose subtleties below mirror this order — the prose names a step's *role* in the algorithm, not necessarily its lexical position when several steps interlock):

1. Per-frame nodes increment + cancellation poll.
2. Mate-distance pruning (may short-circuit before stand-pat is computed).
3. In-check triage.
4. Stand-pat lower-bound (not-in-check only).
5. Move generation (full list in-check, captures+queen-promos otherwise).
6. Terminal handling (in-check empty → mate; not-in-check empty → explicit early-return of `best_init` for legibility, equivalent to falling through to the `return best` at the end since `best == best_init` at that point).
7. MVV-LVA ordering.
8. Recurse fail-soft (with abort propagation between iterations).

```rust
// Both `qsearch` and `qsearch_for_test` below are sibling `pub(super)` methods
// on `impl AlphaBetaMover` — the same impl block that holds `negamax` and
// `negamax_for_test` in the existing M3.C code. The separator comment between
// the two functions is a hint to the implementer; the impl-block header is
// not repeated in this illustrative block.

fn qsearch(
    &mut self,
    pos: &mut Position,
    mut alpha: i32,
    mut beta: i32,
    ply: u32,
    ctx: &SearchContext,
) -> i32 {
    use crate::eval::evaluate;
    use crate::movegen::{MoveList, generate_moves, in_check};

    // 1. Per-frame nodes increment + cancellation poll. Negamax's depth==0
    //    branch delegates to qsearch BEFORE its own increment, so this is the
    //    sole counter for the depth==0 leaf — preserves M3.C's "1 leaf = 1
    //    node" budget interpretation under `go nodes <N>`. See §5.
    self.nodes += 1;
    if self.nodes & 4095 == 0 && ctx.should_abort(self.nodes) {
        self.aborted = true;
        return 0;
    }

    // 2. Mate-distance pruning — may return mate-bound before stand-pat is
    //    computed. Safe because mate-distance pruning narrows toward provable
    //    mate scores only; if the window is already collapsed by a known mate,
    //    no static eval or capture sequence at this depth can improve on it.
    let mating_value = MATE - ply as i32;
    if mating_value < beta {
        beta = mating_value;
        if alpha >= mating_value { return mating_value; }
    }
    let mated_value = -(MATE - ply as i32);
    if mated_value > alpha {
        alpha = mated_value;
        if beta <= mated_value { return mated_value; }
    }

    // 3. In-check triage decides whether stand-pat is permitted and which
    //    moves are searched. Stand-pat-in-check is unsound (engine would
    //    "stand pat" while the king is being mated next ply — CPW).
    let in_chk = in_check(pos);

    // 4. Stand-pat lower-bound (only when NOT in check). Stand-pat =
    //    side-to-move's static eval.
    //     - >= beta: fail-soft beta cutoff, return stand-pat.
    //     - > alpha: tighten alpha (we'll see if any capture beats it).
    //    `best_init` is the seed for the move-loop's fail-soft accumulator
    //    `best`. Naming: not "stand_pat" — this binding is `-INF` on the
    //    in-check branch, where stand-pat is forbidden; the variable holds
    //    the initial value of `best`, which is stand-pat only conditionally.
    let best_init = if !in_chk {
        let sp = evaluate(pos);
        if sp >= beta { return sp; }
        if sp > alpha { alpha = sp; }
        sp
    } else {
        // In check: stand-pat forbidden; seed `best` to `-INF` so any
        // evasion's negated child score beats the seed and propagates up.
        -INF
    };

    // 5. Generate moves. In check: ALL legal moves (evasions). Otherwise:
    //    captures + queen-promos only (filter from full list).
    let mut ml = MoveList::new();
    generate_moves(pos, &mut ml);
    let mut moves_vec: Vec<Move> = if in_chk {
        ml.iter().collect()
    } else {
        ml.iter().filter(|m| qsearch_move_filter(*m)).collect()
    };

    // 6. Terminal:
    //    - In check + empty: mate (-(MATE - ply)).
    //    - Not in check + empty: fall through; the move loop is empty and we
    //      return `best`, which still equals `best_init` = stand-pat. The
    //      explicit early-return at this branch is redundant given the seed
    //      but is kept for legibility (the false-stalemate bug-trap is the
    //      most surprising case for a future reader — CPW pitfall §10.7:
    //      empty-after-capture-filter does NOT mean stalemate, the position
    //      has many quiet moves).
    if moves_vec.is_empty() {
        if in_chk {
            return -(MATE - ply as i32);
        } else {
            return best_init; // = stand_pat
        }
    }

    // 7. Order: MVV-LVA descending. Reuses negamax's helper.
    moves_vec.sort_by_cached_key(|&m| -mvv_lva_score(m, pos));

    // 8. Recurse fail-soft.
    let mut best = best_init;
    for mv in moves_vec {
        let undo = pos.make_move(mv);
        self.history.push(pos.zobrist());
        let score = -self.qsearch(pos, -beta, -alpha, ply + 1, ctx);
        self.history.pop();
        pos.unmake_move(mv, undo);

        // 9. Abort propagation: discard score; do not commit. The push/pop
        //    above is balanced even on abort because the abort check runs
        //    AFTER both `history.pop()` and `unmake_move`.
        if self.aborted { return 0; }

        if score > best {
            best = score;
            if score > alpha { alpha = score; }
            if alpha >= beta { break; } // beta cutoff, fail-soft
        }
    }

    best
}

// --- separate `pub(super)` method on the same `impl AlphaBetaMover` block ---

/// Test-only entry point that forwards verbatim to `qsearch`. Required
/// because `qsearch` is private; mirrors `negamax_for_test` (`src/search.rs`).
/// Production code never calls this.
#[cfg(test)]
pub(super) fn qsearch_for_test(
    &mut self,

    alpha: i32,
    beta: i32,
    ply: u32,
    ctx: &SearchContext,

}
```

**Subtleties to honor:**

- **No PV update in qsearch.** The triangular PV table is only updated by negamax (main search). Qsearch leaves don't contribute to the displayed PV — it ends at the negamax leaf that called qsearch. This is consistent with CPW prose (qsearch is a leaf-evaluation refinement, not a search depth). Negamax's depth==0 frame already runs `pv.clear_ply(ply)` before delegating; that leaves `lengths[ply] = 0`, so the parent's PV-update read returns an empty child PV — exactly correct.
- **History push/pop** balance: same discipline as negamax. The push/pop wrapping the recursive call is balanced on both the normal completion path and the abort path (the abort check is *after* `pop` + `unmake`). The push/pop is for invariant uniformity, not for triggering `is_repetition` — see next bullet for the design choice and its real (rather than initial) justification.
- **No repetition / 50-move check inside qsearch — design choice + correct justification.**
  - **Initial-but-incorrect intuition** (do not rely on this): "captures + promos are irreversible → halfmove_clock always 0 → repetition impossible." This is wrong on the in-check branch: when qsearch is entered while in check, evasions include non-capture king moves (and non-capture interpositions), which *increment* the halfmove clock. So a child qsearch frame's `pos.halfmove_clock()` can be non-zero.
  - **Correct justification.** The non-in-check qsearch branch only recurses on captures+promos, both of which reset `halfmove_clock` to 0 and break any repetition chain. The in-check branch can chain non-capture evasions, so a repetition is *theoretically* possible only via a continuous in-check evasion cycle (king bouncing back and forth under continuous check). This requires the opponent to also be in-check after each of its evasions — vanishingly rare and detectable only by explicit history-walking we deliberately skip for tightness. The design accepts this gap as out-of-scope at M3.D; M4+ may revisit if a real game ever triggers it.
- **`-INF` initialization for in-check `best_init`** is required because: in check, no stand-pat; the first evasion's negated child score might be very negative (we're losing). `best = -INF` ensures `score > best` always fires for the first move; the actual `best` is then propagated via fail-soft.
- **Mate-distance pruning at the top of qsearch** — same as negamax. CPW notes it's safe and cheap; including it costs 5 lines and prunes already-decided mate windows. Step ordering note: MD pruning runs *before* the in-check triage and stand-pat. When the pruning fires, qsearch returns a mate-bound score without consulting `evaluate(pos)` or generating moves. This is correct because the pruning's premise ("the score is bounded by ±(MATE − ply) regardless of what we do here") is independent of in-check status.
- **Cancellation poll cadence** — same 4096-node cadence; combined nodes counter (negamax + qsearch share `self.nodes`). At qsearch's higher node throughput, the cadence still produces sub-millisecond response. See §5 for the negamax-restructure that ensures negamax's depth==0 branch does NOT double-increment with qsearch's per-frame increment.
- **Stand-pat lower-bound semantics.** When the not-in-check branch fires *and* MD pruning did not pre-empt, stand-pat is the lower bound on `best`. Fail-soft return: `best = best_init` where `best_init = stand_pat` on the not-in-check branch and `-INF` on the in-check branch; if no move improves, return `best`.
- **Static-eval incremental discipline preserved.** `Position::static_eval_white` is updated incrementally in `make_move` / `unmake_move` per ADR-0014. The qsearch make/unmake pairs balance on every code path (normal completion, beta cutoff `break`, abort propagation), so the existing debug-build round-trip assertions in `make_move`/`unmake_move` continue to validate the discipline. No qsearch-specific eval-state plumbing is needed; the existing `make_move_no_from_scratch_in_release` perf sentinel still applies.

## 4. `qsearch_move_filter` helper

```rust
/// Returns true iff the move should be searched in qsearch (when not in check).
/// Captures, EnPassant, and queen-promo variants (with or without capture).
/// Excludes under-promotions (M3.D scope) and non-capture checks (M4+).
fn qsearch_move_filter(mv: Move) -> bool {
    use crate::mov::MoveFlag::*;
    matches!(
        mv.flag(),
        Capture | EnPassant | QueenPromo | QueenPromoCapture
    )
}
```

`RookPromo` / `BishopPromo` / `KnightPromo` (under-promotions) and `RookPromoCapture` / `BishopPromoCapture` / `KnightPromoCapture` (under-promotion-with-capture variants) are excluded — under-promotions in qsearch add noise without significant tactical benefit at M3 strength. **Note for the alert reader**: under-promo-captures are excluded *despite* being captures because under-promotion's tactical value (avoiding stalemate, knight-fork tactics) is rare enough at M3 strength that the extra qsearch breadth isn't justified. M4+ may revisit. Plain `Quiet`, `DoublePush`, `KingCastle`, `QueenCastle` excluded by definition (non-captures).

## 5. `negamax` restructure (preserves "1 leaf = 1 node" budget contract)

The naive M3.D modification — `if depth == 0 { return self.qsearch(...); }` left in M3.C's step 5 of negamax, with negamax's own `self.nodes += 1` still at step 1 — would double-count every depth==0 leaf (negamax counts the empty leaf-frame; qsearch counts its own first frame). This breaks the M3.C `go nodes <N>` budget contract (a 1000-node budget would visit ~500 leaves rather than ~1000) and skews the cancellation cadence's effective wallclock.

The fix: move negamax's per-frame nodes increment + cancellation poll *after* the depth==0 delegation, so the depth==0 path never enters negamax's "count this frame" code. Qsearch then owns the leaf count exclusively. PV clear stays *before* the delegation so a leaf's PV slot is reset (otherwise a prior subtree at the same ply could leave stale `lengths[ply] > 0`, which the leaf's qsearch wouldn't touch, and the parent would mistakenly copy stale child PV moves).

```rust
fn negamax(
    &mut self,
    pos: &mut Position,
    depth: u32,
    ply: u32,
    mut alpha: i32,
    mut beta: i32,
    ctx: &SearchContext,
) -> i32 {
    use crate::movegen::{MoveList, generate_moves, in_check};

    // 1. Clear this ply's PV slot. Stays BEFORE the depth==0 delegation so
    //    even leaves reset their slot — otherwise a prior subtree at the
    //    same ply could leave lengths[ply] > 0, which qsearch wouldn't
    //    touch, and the parent's pv.update would copy stale child PV moves.
    self.pv.clear_ply(ply as usize);

    // 2. Horizon: delegate to qsearch BEFORE incrementing self.nodes.
    //    qsearch's own per-frame increment + cancellation poll covers the leaf.
    //    Preserves M3.C's "1 leaf = 1 node" budget under `go nodes <N>`.
    if depth == 0 {
        return self.qsearch(pos, alpha, beta, ply, ctx);
    }

    // 3. Per-frame nodes increment + cancellation poll (non-leaf only).
    self.nodes += 1;
    if self.nodes & 4095 == 0 && ctx.should_abort(self.nodes) {
        self.aborted = true;
        return 0;
    }

    // 4. Repetition + 50-move draw checks at ply > 0. (Unchanged from M3.C.)
    if ply > 0 {
        if is_fifty_move_draw(pos.halfmove_clock()) { return 0; }
        if is_repetition(&self.history, pos.halfmove_clock()) { return 0; }
    }

    // 5. Mate-distance pruning. (Unchanged from M3.C.)
    let mating_value = MATE - ply as i32;
    if mating_value < beta {
        beta = mating_value;
        if alpha >= mating_value { return mating_value; }
    }
    let mated_value = -(MATE - ply as i32);
    if mated_value > alpha {
        alpha = mated_value;
        if beta <= mated_value { return mated_value; }
    }

    // 6. Move generation, ordering, and recursion — unchanged from M3.C.
    // ... (existing M3.C body from `let mut ml = MoveList::new();` onward)
}
```

**What changed vs M3.C** (per-line, since the user reads chat, not code):

- M3.C step 1 (`self.nodes += 1; cancellation poll`) **moves to M3.D step 3, conditioned on the non-leaf path** (only frames where `depth > 0` increment + poll).
- M3.C step 2 (`pv.clear_ply(ply)`) **moves to M3.D step 1** so it runs even on the leaf path — otherwise a prior subtree's stale `lengths[ply]` could cause the parent's `pv.update` to copy stale child PV moves.
- M3.C step 5 (`if depth == 0 { return evaluate(pos); }`) **becomes M3.D step 2** (`if depth == 0 { return self.qsearch(...); }`), moved before the nodes increment.
- M3.C steps 3 (repetition/50-move) and 4 (MD-pruning) become M3.D steps 4 and 5 — same internal logic, but now correctly skipped on the depth==0 path (the leaf's qsearch handles MD-pruning itself; qsearch deliberately skips repetition/50-move per §3 design).

**The implementer must preserve M3.C's negamax body from `let mut ml = MoveList::new();` (currently `src/search.rs:387`) through the end of the function (currently `src/search.rs:451`) verbatim.** This region contains three load-bearing M3.C must-fixes that M3.D does NOT modify:

1. **Empty-searchmoves-in-check pre-triage** at the terminal-handling step (`if ply == 0 && ctx.limits.searchmoves.is_some() { return 0; }` *before* the `in_check` check). Prevents a `go searchmoves <illegal>` from a check position from falsely returning `-(MATE - ply)`. M3.C v3-pass fix.
2. **Post-recursive-call abort check** (`if self.aborted { return 0; }` *after* `unmake_move`, *before* `if score > best`). Prevents committing a contaminated score / PV when the child aborted.
3. **`root_score` lockstep update** at `ply == 0` (`if ply == 0 { self.root_score = Some(score); }` *inside* the `if score > alpha` PV-update block). Allows `go` to report the last fully-explored root subtree's score under partial-abort scenarios instead of the 0 sentinel.

Do not re-derive this region. Verify by visual diff of the unchanged section in the implementation against M3.C's `src/search.rs:387–451`. The implementer's own M3.D code is *only* the new top of negamax (PV clear + depth==0 delegation + non-leaf nodes increment + repetition/50-move + MD-pruning), the new `qsearch` method, the new `qsearch_move_filter` helper, and the new `qsearch_for_test` thin forwarder.

**Cancellation-poll coverage.** Negamax leaves no longer poll for cancellation; qsearch's own per-frame poll covers them. Long qsearch subtrees from a single negamax leaf still get cancellation responsiveness via qsearch's recursive-frame polls.

## 8. Parallelization map

**Single coder slice — Sonnet+Opus parallel A/B per the workflow's calibration trigger.**

The implementation is a tightly-coupled body (qsearch internal state interacts with the existing `nodes` / `aborted` / `history` fields on AlphaBetaMover; the negamax modification is a one-line change at the depth==0 branch). Splitting `qsearch_move_filter` from `qsearch` would save ~3 minutes wall time and lose the single-coder coherence over the helper-vs-recursion interface.

**Calibration protocol** (per workflow.md calibration log entry; deferred from M3.C):

**Precondition: shared pre-reviewed test suite.** Before the A/B coder agents are spawned, the orchestrator (this main thread) writes the test suite + `qsearch_for_test` forwarder per §6.1, runs the test-suite-reviewer subagent until convergence, and *then* commits the test suite as the shared starting state for both A/B worktrees. Each A/B coder receives the identical pre-reviewed test suite + the identical implementation prompt; neither coder writes their own tests. This makes the comparison a clean coder-only A/B (not coder-AND-test-author).

1. Test-suite phase converges in main thread (orchestrator writes tests; test-suite-reviewer iterates until converged).
2. Spawn `coder-sonnet` (chess-coder agent, model override `sonnet`) on isolated worktree A via `Agent` tool's `isolation: "worktree"` parameter, with the converged test files already present.
3. Spawn `coder-opus` (chess-coder agent, model override `opus`) on isolated worktree B via the same parameter, in parallel, with the same converged test files.
4. Both receive the identical implementation prompt — this plan's §3, §4, §5 plus the verification checklist. Implementation only; do not modify test files (other than the `qsearch_for_test` forwarder if §6.1's tests reference it as part of the converged test surface).
5. When both complete, the orchestrator reads both diffs (paths returned in the agent return messages), confirms each worktree's `cargo test` (debug + release) + `cargo clippy --all-targets -- -D warnings` + `cargo fmt --check` pass, runs `final-reviewer` on each blind to the other, compares the must-fix and should-fix counts.
6. Picks the winner. Default rule: if both diffs converge structurally and produce the same correctness, the cheaper Sonnet pass is the winner. If Opus catches a substantive must-fix Sonnet missed (e.g. an off-by-one in the in-check / no-captures terminal arm, or a stand-pat-in-check oversight), the workflow's chess-coder tier flips to Opus per the stop-loss protocol.
7. Discards the loser's worktree.
8. Updates `docs/workflow.md` calibration log with the A/B comparison summary.

**Why M3.D is the right A/B trigger** (per workflow.md calibration log + plan §11 of M3.C):

- **Novel invariants**: the false-stalemate trap (CPW pitfall §10.7) requires the qsearch-not-in-check empty-list path to return stand-pat, NOT mate. A misread of CPW (or a literal pattern-match against negamax's terminal handling) would conflate the two.
- **Stand-pat-in-check correctness**: forbidden per TalkChess prose. Sonnet's pattern-matching tendency could slip the stand-pat check into a position where in_check is true.
- **Mate detection inside qsearch**: only fires when in-check + empty. Easy to forget the in_check guard.
- **Move-flag filter discipline**: under-promotions excluded; the `qsearch_move_filter` matches list determines what nodes qsearch sees.

The default Sonnet coder may handle this slice cleanly given the prescriptive §3 body, but the categorical gaps the workflow log flags are present here — the A/B is the ground-truth measurement.

## 10. Risks and gotchas

- **False-stalemate**: the not-in-check empty-after-filter case must return stand-pat, not 0. Tested by `qsearch_returns_stand_pat_for_not_in_check_no_captures`.
- **In-check stand-pat**: forbidden. Tested by `qsearch_does_not_stand_pat_in_check` using the differential-shape pattern (§6.1 row 5). The differential shape sidesteps fixture-fragility because it tests the causal claim (qsearch did not stand-pat) rather than a specific score. Lessons from M3.C's mate-in-2 fiasco apply: still validate the FEN legality + in-check status + eval-baseline in the test docstring before pinning.
- **History push/pop balance**: same as negamax. The pop runs *after* the recursion returns and *before* the abort check, so balance holds on both normal and abort paths. Add `debug_assert_eq!(self.history.len(), pre_push_len)` after the loop to guard against imbalance.
- **Static-eval incremental discipline under qsearch**: `Position::static_eval_white` is updated incrementally per ADR-0014. Qsearch's make/unmake pairs balance on every code path (normal completion, beta cutoff `break`, abort propagation). The existing `make_move`/`unmake_move` debug-build round-trip assertions catch any imbalance; the `make_move_no_from_scratch_in_release` perf sentinel still applies. No qsearch-specific eval-state plumbing.
- **Mate-score arithmetic**: qsearch's mate detection uses the same `-(MATE - ply)` shape as negamax. Verify that mate found at qsearch depth (e.g. ply=4) returns `-(MATE - 4)` consistently.
- **Node count budget**: qsearch leaves multiply node count. The M3.C `node_count_is_below_branching_bound` test's bound (8000) needs adjustment. The `go nodes <N>` budget contract ("1 leaf = 1 node") is preserved by §5's negamax restructure.
- **PV table not updated by qsearch** — the displayed PV ends at the negamax leaf. If a future feature wants to extend the PV through qsearch (e.g. for analysis modes), that's an M5+ refinement. M3.D explicitly does not.
- **Repetition / 50-move skip is by design**, not by accident: the §3 "Subtleties" bullet documents the *correct* justification (the in-check evasion king-move case can have non-zero halfmove_clock; the design accepts the theoretical-but-vanishingly-rare in-check-cycle gap). Tested by `qsearch_skips_fifty_move_at_threshold` and `qsearch_skips_repetition_when_history_contains_current_position` (§6.1 rows 12–13).
- **Under-promo-captures excluded from qsearch despite being captures.** §4 documents this explicitly. An alert reader would expect `RookPromoCapture` etc. to qualify as captures; the filter excludes them along with plain under-promos. Acceptable because under-promo tactics are rare at M3 strength; M4+ may revisit.
- **Non-trivial test fixtures**: especially `qsearch_does_not_stand_pat_in_check` (now using the safer differential shape per §6.1 row 5) and `qsearch_extends_capture_to_resolve_material` — verify FEN legality + the claimed tactical situation first-principles before pinning the assertion. Lessons from M3.C's mate-in-2 fiasco still apply.
- **E39 re-pin**: the depth-3 startpos bestmove may change with qsearch. Re-run and re-pin during impl following M3.C's protocol — verify the new bestmove is sensible (not a hanging piece) before pinning.
- **Strength match**: qsearch should strictly improve play, but the 20-0 sweep at depth 4 is already at the ceiling; expect 20-0 or close. Track adjudication-ply speed as the secondary signal.
- **Existing test-timeout audit (M3.C precedent)**: §7 step 5 calls out the audit. Without it, M3.D could hit a debug-mode test timeout regression at the eleventh hour the same way M3.C did.
