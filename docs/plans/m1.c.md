# M1.C — Sliding-piece attacks (fancy magic bitboards)

## Context

M1.B delivered `Position`, `Square`, `Bitboard`, and `Color`/`PieceKind`/`Piece`. M1.C builds the sliding-piece attack lookup that M1.E (make/unmake — needs in-check tests) and M1.F (legal-direct move generation) consume on every move.

This phase **binds ADR-0008**, which is pre-decided in the roadmap and rests on the prose research at `docs/research/m1-magic-bitboards.md`. The headline calls from that research are: **fancy magic with variable shift; magic constants hardcoded in a checked-in generated source file; attack tables built at runtime via `LazyLock`; a separate `magicgen` binary for the search/validation/codegen step; the slow ray-walker kept permanently as a `slow_attacks` differential-test oracle; PEXT skipped (ARM has no equivalent).** This plan implements that landing.

### Research skip — justified

Workflow step 1 ("deep prior-art research") is a clean skip for this phase: `docs/research/m1-magic-bitboards.md` (researched 2026-04-27) covers the technique exhaustively — mask construction (§3), the search algorithm with sparseness heuristic and carry-rippler enumeration (§4), table size budgeting against M-series caches (§5), Apple Silicon implications (§6), validation strategy (§7), and the pitfalls catalogue (§8). The architecture research's §1 also establishes the bitboard/Position layout we read from. Two open points the research did not nail down, that this plan settles from first principles plus the project's conventions:

1. **PRNG choice and seed.** No prior-art note prescribed a specific PRNG. **Resolution: SplitMix64 implemented inline in `magicgen`, seeded with the literal `0xC0FFEE_C0FFEE_u64`.** Rationale: SplitMix64 is 5 lines of Rust, has no external dependency, and is well-known as a high-quality 64-bit splittable PRNG. Sparse candidate generation is `rng.next() & rng.next() & rng.next()` per the research's §4 recommendation.

2. **How to organize the generated source file.** `docs/research/m1-magic-bitboards.md` §4 says "hardcode magics, masks, shifts, and offsets as `static` constants in a generated Rust module," but doesn't specify whether each piece-type's data is one struct array (`[Magic; 64]`) or four parallel `[u64; 64]` arrays. **Resolution: array-of-structs (`[Magic; 64]`) for readability and locality.** A square's four data items live together; the struct fits in 24 bytes plus padding; one cache line holds two struct entries. Drift between `slow_attacks::rook_mask(sq)` and the embedded `mask` is caught by a unit test.

### Why not plain / fixed-shift / black magic / PEXT — short version

Already in `docs/research/m1-magic-bitboards.md` §2 with full reasoning; the one-paragraph summary that justifies the M1.C choice:

- **Plain magic** (~2.3 MiB) — defensible but uses uniform 12-bit-rook / 9-bit-bishop slot sizes, wasting ~1.5 MiB. Marginal speed win on modern OOO cores. Switch to it later only if we want to drop variable-shift logic for some compiler reason.
- **Fixed-shift fancy** (~1.6% perft win on a 2010 Core i5; unmeasurable on modern CPUs) — saves one memory load (constant shift instead of per-square). Worth revisiting *after* we have a perft baseline; tagged future-tweak in ADR-0008.
- **Black magic** (Annuss 2017, ~692 KiB) — saves ~150 KiB by overlapping per-square slots; complicates the search and the table-build. Fancy memory footprint (~840 KiB) is uninteresting on M4. Defer.
- **PEXT** — irrelevant on ARM64. No equivalent instruction. Apple Silicon's NEON has no PEXT-shaped peer. Closed.

### What this phase delivers

A single piece of public functionality: **`magic::rook_attacks(sq, occ)`, `magic::bishop_attacks(sq, occ)`, `magic::queen_attacks(sq, occ)`** that for any square and any occupancy bitboard return the attack-set bitboard (squares the slider attacks, *including* the first blocker on each ray, *excluding* the slider's own square).

Plus the permanent `slow_attacks` oracle module exporting the same shape of API at slow-but-obviously-correct speed.

Plus the `magicgen` binary that generates the magic constants, validates them against `slow_attacks`, and emits `src/magic/constants.rs`.

## Decisions baked into this plan

1. **Fancy magic with variable shift.** Per ADR-0008. Per-square struct holds `mask`, `magic`, `shift = 64 - n` (precomputed so the lookup shifts by it directly), and `offset` into a single shared backing array per piece-type. No fixed-shift pursuit at this phase.

2. **`Magic` struct layout — `pub(crate)`.**
    ```rust
    pub(crate) struct Magic {
        pub(crate) mask: Bitboard,
        pub(crate) magic: u64,
        pub(crate) shift: u8,
        pub(crate) offset: u32,
    }
    ```
    24 bytes plus 4 bytes padding = 32 bytes. Two structs per cache line on M-series (128-byte lines). The struct lives in `magic.rs` so the generated `magic/constants.rs` can reference it via `super::Magic`. **Crate-private, not exported from `lib.rs`** — callers use the function-level API only.

3. **Public function-level API.** `magic::rook_attacks`, `magic::bishop_attacks`, `magic::queen_attacks`, all `pub fn(sq: Square, occ: Bitboard) -> Bitboard`. The `Magic` struct and the constants are an implementation detail. Same shape on the slow side: `slow_attacks::rook_attacks`, `slow_attacks::bishop_attacks`, `slow_attacks::queen_attacks`. **Symmetry between the two modules is deliberate** — it lets the differential test loop over `Square::all()` calling each module's function with the same `(sq, occ)` and assert equality without a per-piece adapter.

4. **Mask helpers live in `slow_attacks`.** `pub fn rook_mask(sq: Square) -> Bitboard` and `pub fn bishop_mask(sq: Square) -> Bitboard` — the relevant-blocker masks (excluding the slider's own square AND the last square of every ray; per `m1-magic-bitboards.md` §3). Two consumers: `magicgen` (builds masks during search) and the differential test (asserts `magic::ROOK_MAGICS[sq].mask == slow_attacks::rook_mask(sq)`). Production code (`magic::rook_attacks`) reads the *embedded* mask from the constants struct, not from `slow_attacks` — the lookup is hot, the constants array is the canonical source at runtime.

5. **No queen-specific table.** `queen_attacks(sq, occ) = rook_attacks(sq, occ) | bishop_attacks(sq, occ)` per the research's §1. One inlined OR. Implemented identically in `slow_attacks` and `magic`.

6. **Slow ray-walker direction enumeration.** Rook directions: N, S, E, W. Bishop directions: NE, NW, SE, SW. Each direction is a `(dfile: i8, drank: i8)` pair; the walker iterates `(file + k*dfile, rank + k*drank)` for `k = 1, 2, ...` until it leaves the board or hits a blocker. The blocker square *is* in the attack set. The slider's own square is *not*.

    Implementation pattern: a single helper `fn ray_attack(sq: Square, occ: Bitboard, dfile: i8, drank: i8) -> Bitboard` that walks one direction and ORs squares into the output, stopping at the first occupied square (inclusive) or the edge (exclusive). Rook attacks = OR of the four cardinal calls; bishop attacks = OR of the four diagonal calls. The mask helpers are the same walker but they exclude the *last* on-board square of each ray and exclude any blocker effect (occupancy is empty). Single source-of-truth helper avoids the pitfall in `m1-magic-bitboards.md` §8 ("forgetting to include the first blocker in the attack set").

7. **`Magic` lookup formula, exact.** Given `sq` and `occ`:
    ```rust
    let m = &ROOK_MAGICS[sq.index() as usize];
    let blockers = (occ & m.mask).0;
    let idx = blockers.wrapping_mul(m.magic) >> m.shift;
    Bitboard(ROOK_ATTACK_TABLE[m.offset as usize + idx as usize])
    ```
    Note: `wrapping_mul` (per the pitfalls — Rust panics on `*` overflow in debug mode). `m.shift` is precomputed `64 - n`, applied directly. The shared backing array is indexed by `offset + idx`, *not* a 2-D `[64][...]`.

8. **Attack tables: `LazyLock<Box<[u64]>>` per piece-type.** Built on first call to `rook_attacks` / `bishop_attacks`. Build cost is "fill the slots for every (square, blocker-subset) pair" — ~108k entries for rook, ~5k for bishop, all done by walking with `slow_attacks`. Empirically a few milliseconds on M4. We do NOT pursue `const fn` table-fill (`docs/research/m1-magic-bitboards.md` §4 cites the documented Rust-engine experience that this blows up compile time for negligible benefit). We do NOT eagerly populate at startup (UCI `isready` deadline cares; `LazyLock` lets the first attack-query absorb the cost, which in practice is `ucinewgame` setup).

    `LazyLock` was stabilized in Rust 1.80 (May 2024); this project's `edition = "2024"` requires ≥1.85 so `LazyLock` is in.

    Concretely:
    ```rust
    use std::sync::LazyLock;

    static ROOK_ATTACK_TABLE: LazyLock<Box<[u64]>> = LazyLock::new(build_rook_table);
    static BISHOP_ATTACK_TABLE: LazyLock<Box<[u64]>> = LazyLock::new(build_bishop_table);
    ```

    The build functions allocate a `vec![0; constants::ROOK_TABLE_LEN]`, walk every square × every subset of `mask` via carry-rippler, compute the slow attack, store at the magic-derived index, then `into_boxed_slice()`. **Asserts during build.** A constructive collision (two subsets index to the same slot AND produce the same attack) is fine; a destructive collision is a panic. The committed magics have already been validated by `magicgen`, so a panic here means the constants file was edited by hand — we *want* it to crash. **This is the production-engine corruption guard, distinct from magicgen's `eprintln! + exit(1)` codegen-time failure path (Decision §10 step 4):** the runtime panic protects users of the library against silently-broken constants in their built binary; magicgen's exit(1) protects the codegen author against committing broken constants in the first place.

    The "is `used[idx] == 0` a valid 'unset' sentinel?" question is settled by slider geometry: the slow walker never returns `Bitboard(0)` for a rook or bishop on any square with any blocker subset, because the minimum mask popcount is 5 (bishop edge) / 10 (rook interior) and the *first square along every ray* is always present in the attack set regardless of blockers (it's either empty-and-thus-attacked or the first blocker, which is itself in the attack set). So 0 is unambiguous in this context.

9. **Generated source file format — pinned.** `src/magic/constants.rs`. UTF-8, LF line endings (no CRLF). Top of file:
    ```
    // AUTO-GENERATED by `cargo run --release --bin magicgen`. Do not edit by hand.
    //
    // Re-run magicgen to regenerate. The generator is deterministic given its
    // PRNG seed (currently 0xC0FFEE_C0FFEE); committed constants must match a
    // fresh run with the same seed.

    use crate::bitboard::Bitboard;
    use super::Magic;

    pub(super) const ROOK_TABLE_LEN: usize = N_ROOK;
    pub(super) const BISHOP_TABLE_LEN: usize = N_BISHOP;

    pub(super) const ROOK_MAGICS: [Magic; 64] = [
        Magic { mask: Bitboard(0x...), magic: 0x..., shift: ..., offset: ... },
        ...
    ];

    pub(super) const BISHOP_MAGICS: [Magic; 64] = [
        ...
    ];
    ```
    Squares listed in LERF order (a1, b1, ..., h8). One struct per line. Hex literals with `0x` prefix, lowercase, no underscore separators inside the 16-hex-digit body (uniform format makes the file diffable; spot-grepping for a magic by value is rare). Trailing newline at EOF.

    **Visibility:** `pub(super)` because `magic.rs` (the parent) is the sole consumer. Not exported beyond `magic`.

10. **`magicgen` binary — flow.** `cargo run --release --bin magicgen [output_path]`. Default `output_path = src/magic/constants.rs` — **interpreted relative to the invocation CWD**, not the workspace root (cargo does not chdir to the manifest dir before running the binary). Run from the workspace root, or pass an absolute path. The default is correct for the canonical workflow `cd <workspace>; cargo run --release --bin magicgen`.

    **Iteration order is load-bearing for reproducibility:** rook before bishop, and within each piece-type the squares iterated in LERF order (a1, b1, ..., h8) via `Square::all()`. A single shared `SplitMix64` rng instance threads through both pieces and all 64 squares. Swapping the order changes every emitted magic — only the "diff against committed file" verification step would catch it. A comment to this effect lives at the top of `magicgen`'s `main`.

    1. For each `(piece_type, sq)` in `[Rook, Bishop] × Square::all()`:
       - Compute `mask = slow_attacks::{rook,bishop}_mask(sq)`. Compute `n = mask.count()`.
       - Enumerate every subset of `mask` via carry-rippler (`docs/research/m1-magic-bitboards.md` §4); for each, store `(blockers, slow_attacks::{rook,bishop}_attacks(sq, blockers))` in two parallel `Vec<u64>`s.
       - Search loop: draw a sparse candidate `m = rng.next() & rng.next() & rng.next()`. Allocate `used = vec![0u64; 1 << n]`; for each `(blockers, attack)`: `idx = (blockers.wrapping_mul(m)) >> (64 - n)`; if `used[idx] == 0` set `used[idx] = attack`; else if `used[idx] == attack` continue; else reject `m` and try the next candidate. **No prefilter** — `m1-magic-bitboards.md` §4 mentions an optional `popcount((mask * m) >> 56) >= 6` heuristic that filters out garbage candidates fast, but in combination with the SplitMix64+sparse-candidate setup at PRNG_SEED 0xC0FFEE_C0FFEE, the prefilter exhausted the per-square budget on f8 (rook) — investigated and dropped during step 7.D. The constructive-collision check alone converges well within budget.
       - On success: record `Magic { mask, magic: m, shift: 64 - n as u8, offset }` where `offset` is the running cumulative slot sum so far (per piece-type).
    2. After all 128 (rook+bishop) squares are searched, build the in-memory attack tables (just like the runtime `LazyLock` would) and run the differential against `slow_attacks` over every `(sq, subset)` pair for both pieces. **If any check fails, the binary `eprintln!`s the (piece, sq, reason) and calls `std::process::exit(1)` per Decision §10 step 4** — the magics never get written. **The rebuild-from-scratch is intentional**: although the search loop in step 1 already produces a per-square attack table inline (the `used` array), step 2 rebuilds via the same allocation+fill path the runtime `LazyLock` uses — that way the codegen tool exercises the production runtime build pattern end-to-end, not just the search. A future "let's optimize magicgen" pass should preserve step 2's separate build for this reason.
    3. Format the magics as the source file shape from §9. Write atomically: write to `<output>.tmp`, then rename to `<output>`. Print the table-size totals to stdout for sanity-check (e.g. `rook: 102400 entries (~800 KiB); bishop: 5248 entries (~41 KiB)`).
    4. Exit 0 on success. On any failure (including the search exhausting an iteration budget — see Decision §13 for the budget) print a one-line `eprintln!` describing the failure (`(piece, sq)` and reason) and call `std::process::exit(1)`. We use explicit non-zero exit rather than `panic!` so the exit code is predictable for any future CI automation; with `panic = "abort"` in the release profile, panicking would abort with `SIGABRT` (exit 134), and with the default unwinder it would exit 101 — neither matches "exit 1" without help. The `eprintln! + exit(1)` pattern keeps the error output as direct as a panic message would have been.

11. **Magicgen never imports the existing `src/magic/constants.rs`.** It reads only `slow_attacks` and writes from scratch. That way the generated file's own correctness is never load-bearing on the generator's run; we can blow it away and regenerate.

12. **`Cargo.toml` changes.** Cargo auto-discovers `src/bin/*.rs`; no `[[bin]]` block needed for `magicgen`. We add no third-party dependencies — `slow_attacks` is pure, the PRNG is inline, file I/O is `std::fs` / `std::io`. The package's existing `[profile.release]` (LTO thin, codegen-units 1, panic=abort) applies to `magicgen` as well; release-mode magicgen runs fast (in the seconds, not minutes).

13. **Search iteration budget.** Per square per piece, try up to `1_000_000` candidates before giving up. Plain magics for fancy-variable-shift are abundant (`m1-magic-bitboards.md` §4 cites Romstad's "all 128 in under a second"); a million candidates is comfortably above the empirical mean. Exhausting the budget on any one square = bug in the generator (almost certainly mask-construction or collision-check), not a "try a different seed" situation. The failure path is `eprintln!("magicgen: exhausted {budget} candidates for {piece:?} on {sq}"); std::process::exit(1);` per Decision §10 step 4 — exit code 1, predictable.

14. **No `unsafe` in M1.C.** Same line as M1.A and M1.B. The `LazyLock` API and `Box<[u64]>` indexing are all safe Rust. Bounds-checked indexing into the attack tables is the runtime correctness guarantee — if we replace it with `get_unchecked` later for perf, that decision is benchmark-driven and ADR-noted, not now.

15. **`pub use magic::{rook_attacks, bishop_attacks, queen_attacks};` from `lib.rs`.** Same convention as `pub use bitboard::Bitboard;`. The function-level API is the entire public surface for sliding attacks. Slow versions are reachable as `clawfish::slow_attacks::rook_attacks` etc. but **not** re-exported at the crate root — the slow path is for tests and the oracle, not for production callers; making it slightly less convenient discourages accidental misuse. (M1.E and M1.F will import from `clawfish::magic` only.)

16. **`#[derive(Copy, Clone)]` on `Magic`.** 24 bytes, four primitive fields, indexed via `&` reference in the hot path. Tests benefit from `Copy` for ergonomics. Cost is zero — never copies in the hot path, since we always borrow `&ROOK_MAGICS[i]`.

17. **Why `Bitboard(0x...)` literals in the constants file vs. `Bitboard::new(...)` or similar.** `Bitboard`'s tuple struct field is already `pub` (per `src/bitboard.rs`), so `Bitboard(0x...)` is the most direct construction. No const-fn factory needed. The generated file is clean and grep-able.

### `src/bin/magicgen.rs` — top-level shape

```rust
use clawfish::bitboard::Bitboard;
use clawfish::slow_attacks;
use clawfish::square::Square;
use std::env;
use std::fs;
use std::io::Write;
use std::path::PathBuf;

const PRNG_SEED: u64 = 0xC0FFEE_C0FFEE;
const SEARCH_BUDGET_PER_SQUARE: u32 = 1_000_000;

#[derive(Copy, Clone)]
struct PieceMagic {
    mask: u64,
    magic: u64,
    shift: u8,
    offset: u32,
}

fn main() {
    let out_path: PathBuf = env::args()
        .nth(1)
        .map(PathBuf::from)
        .unwrap_or_else(|| "src/magic/constants.rs".into());
    let mut rng = SplitMix64::new(PRNG_SEED);

    // 1. Search rook + bishop magics. Each call returns Vec<PieceMagic> of len 64
    //    plus the total slot count.
    let (rook_magics, rook_total) = search_all(Piece::Rook, &mut rng);
    let (bishop_magics, bishop_total) = search_all(Piece::Bishop, &mut rng);

    // 2. Validate in-memory: build attack tables, differential against slow_attacks.
    validate(&rook_magics, rook_total, Piece::Rook);
    validate(&bishop_magics, bishop_total, Piece::Bishop);

    // 3. Emit source file (atomic write via tmp + rename).
    emit(&out_path, &rook_magics, rook_total, &bishop_magics, bishop_total);

    println!(
        "rook: {} entries ({:.1} KiB); bishop: {} entries ({:.1} KiB)",
        rook_total,
        (rook_total * 8) as f64 / 1024.0,
        bishop_total,
        (bishop_total * 8) as f64 / 1024.0,
    );
}
```

Internals: `SplitMix64`, `enum Piece { Rook, Bishop }` (binary-local — distinct from `crate::piece::PieceKind`; we don't want to import the engine's piece taxonomy here, magicgen only deals with sliders), the `carry_rippler` iterator, `search_one(piece, sq, mask, &mut rng) -> PieceMagic` with sparse candidates and constructive-collision check (no prefilter — see Decision §10 above), the per-piece `validate`, and the `emit` formatter.

### `tests/magic_consistency.rs` — integration test

A single integration-test file that uses the public API only (`use clawfish::{magic, slow_attacks, Square, Bitboard};`). One test per piece-type. A leading file-level comment documents the `occ ⊆ mask` framing — the magic lookup begins with `(occ & m.mask)`, so any superset bits don't affect the result and any subset of the mask does. Inputs with bits outside the mask are covered by the spot tests in `magic.rs` (e.g. `rook_attacks_starting_position_a1_matches_slow`), which exercise the `& m.mask` masking step end-to-end. The differential and the spot tests together cover the full lookup contract.

```rust
#[test]
fn rook_magic_matches_slow_for_every_subset() {
    for sq in Square::all() {
        let mask = slow_attacks::rook_mask(sq);
        let mut sub: u64 = 0;
        loop {
            let occ = Bitboard(sub);
            let slow = slow_attacks::rook_attacks(sq, occ);
            let fast = magic::rook_attacks(sq, occ);
            assert_eq!(fast, slow, "rook mismatch on {sq:?} occ {occ:?}");
            sub = sub.wrapping_sub(mask.0) & mask.0;
            if sub == 0 { break; }
        }
        // The empty subset (sub == 0) is checked once at the top of the loop.
    }
}

#[test]
fn bishop_magic_matches_slow_for_every_subset() { /* symmetric */ }
```

### `tests/magic_consistency.rs` integration test

One file. Two tests (rook and bishop). For each piece, **every (sq, occ ⊆ mask) pair** via carry-rippler. Per `m1-magic-bitboards.md` §7 this is the gold-standard differential. Covers 64 squares × per-square subset count = ~108k rook + ~5k bishop assertions. Should run in well under a second on M4.

Tests use only the public API: `clawfish::magic::{rook_attacks, bishop_attacks}` and `clawfish::slow_attacks::{rook_attacks, bishop_attacks, rook_mask, bishop_mask}`. Proves that an external consumer of the crate can do the same differential without any `pub(crate)` access.

### `magicgen` — skip unit tests on the binary

The `src/bin/magicgen.rs` body is a one-shot codegen tool: search → validate → emit. The substantive correctness of its output is guaranteed by **`tests/magic_consistency.rs` running against the committed file**. Adding bin-internal unit tests for `SplitMix64`, `carry_rippler`, etc. would duplicate work that the integration test already enforces (a generator that produced wrong magics would make the consistency test fail).

What the magicgen *binary itself* gets is the runtime-validation step (Decision §10 step 2): the binary `eprintln!`s and exits with status 1 (per Decision §10 step 4) rather than emitting if its in-memory differential fails. That's the behavior-level guard; it's exercised any time we run `cargo run --bin magicgen`.

If `magicgen` ever grows past one-shot codegen (e.g. adds a `--bench` flag or an iterative refinement loop), at that point we add unit tests. For now the simplicity argument wins.

## Construction protocol — pinned for parallel implementation

Because step 7.B (magicgen) and step 7.C (magic.rs body) run in parallel, the contract between them must be unambiguous. The contract:

1. **`Magic` struct shape** is exactly Decision §2:
    ```rust
    #[derive(Copy, Clone, Debug)]
    pub(crate) struct Magic {
        pub(crate) mask: Bitboard,
        pub(crate) magic: u64,
        pub(crate) shift: u8,
        pub(crate) offset: u32,
    }
    ```
    `magicgen` emits `Magic { mask: Bitboard(0x...), magic: 0x..., shift: ..., offset: ... }` literals. `magic.rs` reads `constants::ROOK_MAGICS[i].mask.0` etc.

2. **`mask` is `slow_attacks::{rook,bishop}_mask(sq)`** for that square. `magicgen` derives it from `slow_attacks` at search time and emits it. `magic.rs` reads it from the constants struct at lookup time. The `magic_struct_mask_matches_slow_attacks_mask` test pins they don't drift.

3. **`shift = 64 - mask.count() as u8`.** `magicgen` derives from `mask.count()`; `magic.rs` reads it. Test `magic_struct_shift_matches_mask_popcount` pins it.

4. **`offset` is the cumulative slot count of all earlier squares** (in LERF order) for this piece-type. `ROOK_MAGICS[0].offset == 0`; `ROOK_MAGICS[i].offset == ROOK_MAGICS[i-1].offset + (1 << (64 - ROOK_MAGICS[i-1].shift))`. Same for bishop. Test `magic_offsets_partition_table` pins it.

5. **`ROOK_TABLE_LEN == sum_over_squares(1 << (64 - shift[i]))`.** Tests `rook_table_len_matches_offsets_sum` and `bishop_table_len_matches_offsets_sum` pin it.

6. **Attack table layout.** The runtime `LazyLock` allocates a `vec![0u64; ROOK_TABLE_LEN]` and walks every (sq, subset) pair, computing the slow attack and writing it at `OFFSET[sq] + magic_index(sq, subset)`. The build is a build-time scan, not a perf-critical path. After build the slot at every (sq, occ ⊆ mask) holds the correct slow-attack bitboard.

This protocol means `magicgen` and `magic.rs` are independently implementable; only the struct shape and the offset-arithmetic convention need agreement.

## Risks and mitigations

- **The slow ray-walker has a subtle off-by-one and the `magicgen` differential validates against itself.** This is the most plausible silent-failure mode: both modules use the same buggy walker, the in-memory differential passes, the committed constants are wrong. Mitigation: the `slow_attacks` unit tests pin specific expected attack bitboards from hand calculation (e.g. `rook_attacks_blocker_d4_d6` lists exact squares). Without those literals, a sign-error in the walker would self-confirm. **The hand-pinned tests are the load-bearing safety net — review must not let them slip.**

- **Magicgen non-determinism creeps in via thread scheduling.** SplitMix64 is single-threaded; we explicitly do not parallelize the search. Fixed seed → fixed output → reproducible commit hash on the constants file. If we ever parallelize the search, we lose this — flag in ADR-0008 if revisited.

- **Constants file becomes stale after a `slow_attacks` change** (e.g. someone changes the mask construction). The committed file's magics are tied to a specific mask shape. If a future PR changes `slow_attacks::rook_mask`, the integration test will fail loudly (mask mismatch on the first square checked), telling the contributor to re-run magicgen. Mitigation: the failure mode is *loud*, not silent. The plan-described "regenerate magic constants if mask construction changes" path (`m1-magic-bitboards.md` §4) becomes the natural fix.

- **`LazyLock` is contended on first call** in a multithreaded context (M10 territory). The std-library contract on `LazyLock` is that exactly one initializer runs and other threads block until it completes; we rely on that contract rather than trying to test it from a sibling test in the same binary (per the `concurrent_reads_consistent` test's framing — first-init contention is not pinnable from cargo's shared-static-state runner). The cost of the first call is paid once and then never re-incurred. No mitigation needed for M1.C; flag in ADR-0008.

- **Search-budget exhaustion on a square** would mean the seed is unlucky for that square — but with sparse-random 8-set-bit candidates and the `popcount-of-high-byte` filter, success rates are well above 1-in-million per the cited prose. If it fires, the `eprintln!` message (Decision §10 step 4) includes the square and piece, and the fix is "tweak the seed" — but we should investigate before doing so (could indicate a deeper mask-construction bug).
