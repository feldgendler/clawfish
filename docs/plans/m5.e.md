# M5.E — Qsearch correctness

Fifth M5 sub-phase. Two narrow corrections to quiescence search, bundled because each is < 100 LOC standalone and both touch the same `qsearch` body. The combined surface closes the M3.D horizon hole on legally-forced quiet replies and the M3.D queen-only-promo filter gap. Must land before M5.F (qsearch-in-TT) so the TT does not memoize qsearch holes.

Research synthesis: [`docs/research/m5-qsearch-correctness.md`](../research/m5-qsearch-correctness.md).

## 0. Goals

Two corrections to `AlphaBetaMover::qsearch`:

1. **Single-reply extension.** When `!in_chk && moves_vec is empty && ml.len() == 1`, recurse on the unique legal move at qsearch with `ply + 1`. Return the recursed-and-negated child score. The unique move is necessarily a non-promo quiet by movegen invariant: legal-direct movegen (`src/movegen/pawn.rs:50-54, 88-92`) emits all four promotion variants whenever a promotion is geometrically legal, so an under-promo can never appear alone (pinned by `qsearch_single_reply_under_promo_uniqueness_is_structurally_unreachable`). With the qsearch filter rejecting both quiets and under-promos, an empty filter combined with `ml.len() == 1` leaves only `Quiet | DoublePush | KingCastle | QueenCastle` — the `is_quiet` set — as reachable flags, so no defense-in-depth gate is needed at the call site. Pre-M5.E this branch returned stand-pat unconditionally — a horizon hole when the forced move is materially decisive (e.g. a forced king walk that loses a piece on the next ply but qsearch's stand-pat over-states the position because the loss is past qsearch's filter).

2. **True-stalemate detection (corollary of #1).** When `!in_chk && moves_vec is empty && ml.is_empty()`, return `0` (draw by stalemate per FIDE 9.2). Pre-M5.E this conflated with the false-stalemate guard and returned stand-pat. This change is mechanically free once we test legal-move emptiness for #1; documented separately because it is an independent correctness fix and shifts an additional rare path. Surfaced explicitly so the SPRT signal attribution is clean.

3. **Stalemate-conditional rook/bishop under-promotion.** When qsearch's move loop is about to recurse into a `QueenPromo | QueenPromoCapture` move whose post-make child position is **stalemate** (`legal_moves.is_empty() && !in_check(child)`), additionally search the `RookPromo | RookPromoCapture` and `BishopPromo | BishopPromoCapture` variants of the same `(from, to)`. The under-promo recursions update `best` / `alpha` and contribute to the per-node beta-cutoff decision **alongside the queen-promo's score** — the under-promos run *before* the cutoff check so that a queen-promo's stalemate score (= 0) does not suppress the very under-promo M5.E #3 motivates. Knight-promo deliberately not searched (fork-tactic motivation, separate; out of scope per the roadmap row).

4. **MAX_PLY ceiling guard at qsearch entry, !in_check arm only.** Defense-in-depth against pathological forced-quiet chains under #1: if `ply >= MAX_PLY as u32 - 1 && !in_check(pos)`, return `evaluate(pos)` (the side-to-move-relative stand-pat) without recursing. Pre-M5.E qsearch had no ply ceiling because captures naturally bounded recursion; #1 introduces the possibility of all-quiet recursion chains. The in-check arm is **deliberately not guarded** — at ply ceiling in check the existing evasion arm runs naturally; returning a fabricated mate-in-ply score (`-(MATE - ply)`) would propagate a false mate through `score_to_uci`, `score_to_tt`, and mate-distance pruning, and the in-check ceiling case is structurally rare (a chain of forced check evasions tall enough to hit MAX_PLY is essentially nonexistent in real positions). Stack-budget check: a qsearch frame at the deepest reach holds a `MoveList` (~1.5 KiB), the per-frame `child_ml` (~1.5 KiB), and `moves_vec: Vec<Move>` (~256 B). 63 qsearch frames atop ≤ 63 negamax frames sums to ~200 KiB peak — well under the 8 MiB macOS default thread stack.

ADR-0027 records the policy commitments. New constant inventory: none. New helpers: one (`stalemate_avoiding_under_promos`). Test-only instrumentation: `qsearch_single_reply_firings: u32` and `qsearch_under_promo_firings: u32`.

Mutation testing follows the M5.A/M5.B/M5.C/M5.D precedent: per-unit `cargo mutants --in-diff` is **run as part of pre-review mechanical checks** (not deferred — the user explicitly asked for mutation testing in the M5.E request).

## 1. Out of scope

- **Knight-promo stalemate trigger** — fork-tactic motivation is independent of stalemate avoidance. Roadmap row commits to "knight-promo's fork-tactic motivation remains uncovered."
- **Loop-over-all-four-promotions in qsearch unconditionally** — broader than M5.E and adds bench-noise on every promotion. Deferred.
- **Multi-reply extension** (any-time-quiets-are-the-only-replies). Reintroduces qsearch's termination problem (HGM: "no guarantee you ever run out of quiets"). Locked at exactly-one.
- **Quiet checking moves in qsearch** — would require `gives_check(pos, mv)` infrastructure that does not exist. Deferred to a post-M5 SPRT campaign.
- **Recursive single-reply chain handling** — if the recursive qsearch frame on the forced quiet ALSO has exactly one forced quiet, that frame fires its own M5.E #1 extension independently. No special chain handling, no chain-length ceiling beyond MAX_PLY.
- **Repetition / 50-move detection in qsearch** — pre-M5.E qsearch deliberately does not consult these (architecture.md "Qsearch does NOT consult repetition / 50-move helpers"). M5.E preserves that. The forced-quiet recursion inherits the same skip; acceptable for v1.
- **Qsearch-in-TT** — M5.F (next phase).

## 3. Type definitions and signatures

### 3.1 Helper: synthesize under-promo variants

```rust
/// Given a queen-promo move `mv`, returns the rook-promo and bishop-promo
/// variants at the same `(from, to)`. Capture-aware: if `mv` is
/// `QueenPromoCapture`, returns the `*PromoCapture` variants; otherwise the
/// non-capture `*Promo` variants. Knight-promo deliberately omitted (fork
/// motivation is separate; out of scope for M5.E per ADR-0027 §1).
///
/// Caller contract: `mv.flag()` must be `QueenPromo | QueenPromoCapture`;
/// otherwise the helper returns an empty array (defense-in-depth against a
/// future call-site refactor that loses the queen-promo gate).
pub(crate) fn stalemate_avoiding_under_promos(mv: Move) -> [Option<Move>; 2];
```

Body:

```rust
pub(crate) fn stalemate_avoiding_under_promos(mv: Move) -> [Option<Move>; 2] {
    use crate::mov::MoveFlag::*;
    let (rook_flag, bishop_flag) = match mv.flag() {
        QueenPromo => (RookPromo, BishopPromo),
        QueenPromoCapture => (RookPromoCapture, BishopPromoCapture),
        _ => return [None, None],
    };
    let from = mv.from_square();
    let to = mv.to_square();
    [
        Some(Move::new(from, to, rook_flag)),
        Some(Move::new(from, to, bishop_flag)),
    ]
}
```

The `[Option<Move>; 2]` shape (rather than `(Move, Move)`) carries the gate-fail semantics into the type: when called on a non-queen-promo move (a misuse the call site should have screened, but defense-in-depth), the helper returns `[None, None]` and the caller's `for ... if let Some` iterator naturally skips both — no panic, no UB, no crate-wide assertion noise. This mirrors the M5.D `ffp_pruned_bound -> Option<i32>` precedent: helper-level domain guard returns the empty value of the contribution type rather than crashing on an out-of-domain input. `Vec<Move>` would heap-allocate; `(Move, Move)` would force a panic on misuse and lose the iterator-friendly shape.

### 3.2 Test-only instrumentation

Add to `AlphaBetaMover` under `#[cfg(test)]`:

```rust
qsearch_single_reply_firings: u32,
qsearch_under_promo_firings: u32,
```

Naming follows the M5.A/B/C/D convention (`*_firings` suffix). No move-list trace is added — under-promos are direct synthetics constructed from `stalemate_avoiding_under_promos`, and single-reply firings always recurse on the unique legal move (no ambiguity worth tracing).

**Reset semantics.** Both counters are reset to `0` at the entry of **each** `qsearch_for_test` call AND **each** `negamax_for_test` call (so that back-to-back invocations within the same test give independent counter values). Negamax delegates to qsearch at `depth == 0`, so a negamax-driven test that touches qsearch transitively must also start with cleared counters; resetting in `negamax_for_test`'s entry is the load-bearing path. The reset in `qsearch_for_test` is symmetry / defense-in-depth for direct-qsearch tests. Both call sites reset both counters (`qsearch_single_reply_firings` AND `qsearch_under_promo_firings`) — keeping the resets symmetric prevents a future test that drives qsearch via one entry from inheriting stale counter state from a prior call via the other.

Accessors:

```rust
#[cfg(test)] pub(super) fn qsearch_single_reply_firings_for_test(&self) -> u32;
#[cfg(test)] pub(super) fn qsearch_under_promo_firings_for_test(&self) -> u32;
```

## 4. Planned production change in `qsearch`

### 4.1 MAX_PLY ceiling guard at entry (!in_check arm only)

After step 1 (nodes increment + cancellation poll) and before step 2 (mate-distance pruning), insert:

```rust
// M5.E — defense-in-depth against pathological forced-quiet chains under
// the single-reply extension (M5.E #1). Pre-M5.E qsearch terminated
// naturally as captures ran out; the single-reply extension introduces
// the possibility of all-quiet recursion. The MAX_PLY ceiling caps stack
// growth.
//
// Only the !in_check arm is guarded. At in_check + ply-ceiling, the
// existing evasion arm runs as before; returning a fabricated mate-in-ply
// score (`-(MATE - ply)`) would propagate a false mate through
// `score_to_uci`, `score_to_tt`, and mate-distance pruning. The in-check
// ceiling case is structurally near-impossible (a chain of forced check
// evasions tall enough to hit MAX_PLY does not occur in real positions),
// so the asymmetric guard is the principled choice.
if ply >= MAX_PLY as u32 - 1 && !in_check(pos) {
    return evaluate(pos);
}
```

The `MAX_PLY - 1` (not `MAX_PLY`) bound leaves one ply of headroom for the recursion's `ply + 1` argument to stay strictly under MAX_PLY at the deepest reachable frame. Compile-time safe at the assignment site because no stack array is indexed by qsearch's `ply` (qsearch does not touch the PV table or killers array).

**Stack-budget check.** A qsearch frame at the deepest reach holds a `MoveList` (~1.5 KiB) and `moves_vec: Vec<Move>` (~256 B). The `child_ml` allocation in §4.3 lives only inside the `&& { ... }` predicate-block expression, which ends before the recursion — its lifetime is the queen-promo predicate window, not the recursion frame, so it does NOT compound across stacked frames. 63 qsearch frames stacked atop ≤ 63 negamax frames sum to ~200 KiB peak — well within the 8 MiB macOS default thread stack.

### 4.2 Terminal-branch refinement (single-reply extension + true stalemate)

Replace the existing step-6 terminal handler:

```rust
// Pre-M5.E:
if moves_vec.is_empty() {
    if in_chk {
        return -(MATE - ply as i32);
    } else {
        return best_init; // = stand_pat
    }
}
```

With:

```rust
if moves_vec.is_empty() {
    if in_chk {
        // Mate at horizon — empty filtered means empty legal in the in-check
        // arm (full legal moves are evasions, no separate filter). Unchanged
        // from M3.D.
        return -(MATE - ply as i32);
    }

    // M5.E #1 + #2: distinguish the three not-in-check empty-filter cases.
    // `ml` is already populated in step 5; use the O(1) `is_empty()` /
    // `len()` accessors rather than `iter().count()`.

    if ml.is_empty() {
        // True stalemate: zero legal moves and not in check is FIDE-9.2 draw.
        // Pre-M5.E this branch returned stand-pat (M3.D approximation, since
        // the case is rare and the conflation was deliberate). M5.E corrects
        // the score; the change is structurally tied to ml.is_empty().
        return 0;
    }

    if ml.len() == 1 {
        let only_mv = ml
            .iter()
            .next()
            .expect("ml.len() == 1 → at least one move in iter");

        // The unique legal move is necessarily a non-promo quiet:
        //   - Filter rejected it (otherwise moves_vec would be non-empty).
        //   - Legal-direct movegen emits all 4 promo variants when
        //     promotion is legal (src/movegen/pawn.rs:50-54, 88-92), so
        //     an under-promo can never be unique. Pinned by
        //     qsearch_single_reply_under_promo_uniqueness_is_structurally_unreachable.
        //   - That leaves Quiet | DoublePush | KingCastle | QueenCastle
        //     (the M3.D `is_quiet` set) as the only flags reachable here.
        #[cfg(test)]
        {
            self.qsearch_single_reply_firings += 1;
        }

        let undo = pos.make_move(only_mv);
        self.history.push(pos.zobrist());
        let (child_alpha, child_beta) = negate_window(alpha, beta);
        let score = -self.qsearch(pos, child_alpha, child_beta, ply + 1, ctx, clock);
        self.history.pop();
        pos.unmake_move(only_mv, undo);

        if self.aborted {
            return 0;
        }

        return score;
    }

    // 2+ legal moves: M3.D false-stalemate guard preserved verbatim.
    return best_init; // = stand_pat
}
```

Ordering rationale within the new block: in_check arm first (fast-exit); then `legal_count == 0` (pure-correctness, no recursion); then `legal_count == 1` (extension); else stand-pat. The single-reply branch does NOT advance any history / killer / quiets_searched state — qsearch never touches those, and the extension is a correctness refinement, not a tactical scoring event.

### 4.3 Queen-promo-stalemate under-promo extension in the move loop

Inside step 8 (the existing `for mv in moves_vec` loop), capture the queen-promo-stalemate predicate **before the recursion** (i.e. between `make_move` and `qsearch(...)`), pass it through unchanged, and fire under-promo recursions **before** the per-move cutoff check (so a queen-promo stalemate score of 0 cannot suppress the under-promo expansion via cutoff):

```rust
for mv in moves_vec {
    let undo = pos.make_move(mv);
    self.history.push(pos.zobrist());

    // M5.E #3: detect queen-promo stalemate BEFORE the recursion. The
    // detection scans the post-make position (child's POV) — at this
    // point `pos` is in the post-make state. Cheap: the `matches!` gate
    // skips the movegen for non-queen-promo moves. Captured into a
    // local so the predicate's lifetime crosses the recursion / unmake
    // window cleanly without splitting `history.pop()` from `unmake_move`.
    let queen_promo_stalemates = matches!(
        mv.flag(),
        MoveFlag::QueenPromo | MoveFlag::QueenPromoCapture
    ) && {
        let mut child_ml = MoveList::new();
        generate_moves(pos, &mut child_ml);
        // True stalemate at the child: zero legal moves AND not in check.
        child_ml.is_empty() && !in_check(pos)
    };

    let (child_alpha, child_beta) = negate_window(alpha, beta);
    let score = -self.qsearch(pos, child_alpha, child_beta, ply + 1, ctx, clock);
    self.history.pop();
    pos.unmake_move(mv, undo);

    // 9. Abort propagation: discard score; do not commit. The push/pop
    //    above is balanced even on abort because the abort check runs
    //    AFTER both `history.pop()` and `unmake_move`.
    if self.aborted {
        return 0;
    }

    // 10a. Update best/alpha from the queen-promo (or other) score.
    if score > best {
        best = score;
        if score > alpha {
            alpha = score;
        }
    }

    // 10b. M5.E #3: under-promo extension — runs BEFORE the cutoff check
    //      so a queen-promo's stalemate score (0) cannot suppress the
    //      under-promo recursions via `alpha >= beta`. The cutoff check
    //      below sees the per-move max of {queen-promo, rook-promo,
    //      bishop-promo} when the trigger fires.
    if queen_promo_stalemates {
        for under_mv_opt in stalemate_avoiding_under_promos(mv) {
            let Some(under_mv) = under_mv_opt else { continue };

            #[cfg(test)]
            {
                self.qsearch_under_promo_firings += 1;
            }

            let undo2 = pos.make_move(under_mv);
            self.history.push(pos.zobrist());
            let (ca, cb) = negate_window(alpha, beta);
            let under_score = -self.qsearch(pos, ca, cb, ply + 1, ctx, clock);
            self.history.pop();
            pos.unmake_move(under_mv, undo2);

            if self.aborted {
                return 0;
            }

            if under_score > best {
                best = under_score;
                if under_score > alpha {
                    alpha = under_score;
                }
            }

            // Mid-under-promo cutoff: if a rook/bishop promo's score
            // already cut the node, skip the remaining under-promo
            // variants. The outer cutoff below is then redundant but
            // harmless (alpha >= beta from the same comparator).
            if alpha >= beta {
                break;
            }
        }
    }

    // 10c. Per-move beta cutoff (post-under-promo).
    if alpha >= beta {
        break; // beta cutoff, fail-soft
    }
}
```

**Why the queen_promo_stalemates check happens before the recursion.** The detection runs at the post-make state (we want to know whether the *opponent* is stalemated *after* the queen promo). Capturing the predicate before recursion (rather than between recursion and unmake) keeps `history.pop()` and `unmake_move` adjacent — the M3.D abort-discipline comment ("the push/pop above is balanced even on abort because the abort check runs AFTER both `history.pop()` and `unmake_move`") stays load-bearing. Re-detecting after unmake would require an extra make-detect-unmake round-trip, which is strictly worse.

**Why under-promo extension runs before the cutoff check.** When queen-promo stalemates, the score is 0. If `beta <= 0` for any reason (aspiration window, prior alpha-improving capture in the same move loop), `alpha >= beta` after assigning alpha = 0 from the queen-promo, and the outer cutoff fires before the under-promo loop. That suppresses the very M5.E #3 extension the spec motivates. Running under-promos *before* the cutoff check means each variant gets its chance to contribute its score to `best` / `alpha`, and the cutoff fires once per queen-promo move-loop iteration based on the per-move max of {queen, rook, bishop} promo scores. Fail-soft semantics preserved: every contributed score is a real fail-soft return value.

**Why under-promo searches use updated alpha (not the pre-queen-promo alpha).** Each under-promo recursion uses the running `alpha` (which may have been raised by the queen-promo's score, by a prior under-promo's score, or by an earlier move in the outer loop). This is the same fail-soft alpha-tightening pattern used by the outer loop. An under-promo that cannot beat the running alpha returns a fail-soft upper bound; the `if under_score > best` guard then prevents that fail-soft upper bound from corrupting `best` — fail-soft sequential-tightening behavior matches the outer move loop verbatim.

**Refactor note: cutoff hoisted out of the `if score > best` block.** M3.D's qsearch nests the cutoff inside `if score > best { ... if alpha >= beta { break; } }`. The §4.3 reshape moves the `alpha >= beta` test to a sibling block (10c) so the under-promo loop (10b) can run between alpha-tightening (10a) and the cutoff (10c). This is behavior-preserving on non-queen-promo moves: alpha can only be raised inside the `score > best` arm, so the outer cutoff sees the same alpha as the inner one would have. Existing M3.D capture-cutoff fixtures continue to fire identically; if any pre-existing test detects a cutoff-firing-count change on non-queen-promo paths, that's a refactor regression and must be investigated, not re-pinned.

**Synthesized move legality.** A rook-promo at the same (from, to) as a legal queen-promo is itself legal-by-construction: the only move-class differentiation between the four promotion variants is the choice of promoted piece, and the legality of the move (geometric path, check resolution, pin) is identical. Movegen would have emitted all four promo variants from the same (from, to). No re-validation needed; `make_move` will accept the synthesized variant.

### 4.4 No changes to other steps

Steps 1 (nodes increment), 2 (MDP), 3 (in_check), 4 (stand-pat), 5 (movegen + filter), 7 (MVV-LVA ordering) are unchanged. The M3.D `negate_window` helper is preserved verbatim. Existing fail-soft semantics are preserved.
