# M2.E — Tournament harness + fastchess

## Context

M2.A–M2.D landed the entire in-process UCI surface: `Move::to_uci`/`from_uci`, the line-parser, the `Engine`/`Search` orchestrator, and a SplitMix64 random-mover with a `Random_Seed` option. M2.D's E36 self-play test already drives the binary through a complete game (seed 8, 106 ply, terminates legally) via piped stdin/stdout.

M2.E is the **external validation layer** — proves the engine speaks UCI to a real tournament runner, not just to itself.

- **Plug-in points in `src/`:** one — `src/search.rs::RandomMover::go` must emit a token `info` line before `bestmove`, otherwise `fastchess --compliance` Step 12 fails. (Empirically verified against M2.D binary; see §11.) Everything else is shell scripts, a doc runbook, one new in-tree test, an ADR, and a milestone bench summary.
- **What the phase proves:** fastchess can run the engine in self-play and against Stockfish 18 with zero illegal-move adjudications, zero stalled connections, and a clean UCI-compliance check.

### Research skip — justified

`docs/research/m2-tournament-harness.md` (committed pre-M2) is exhaustive for this phase: runner choice, install, output layout, smoke contract, in-tree skeleton, GUI alternatives. No fresh research needed; this plan bakes in §1, §2, §3, §4, §5, §6 of the research note.

### Bound ADRs

- **ADR-0012** — Tournament-harness conventions. **Drafted in this phase.** Codifies: fastchess as the runner; `vendor/fastchess/fastchess` as the install path; `scripts/match.sh` as the engine-config wrapper (no `engines.json`); `target/matches/` for raw PGN/log artifacts; `bench/m2.md` for the milestone summary; M2 smoke contract (2 self-play + 2 vs Stockfish at `-rounds 1 -repeat`, adjudicated, compliance-checked); the `RandomMover::go` info-line emission required for `--compliance` Step 12.
- **ADR-0011** (UCI threading) — referenced by the in-tree smoke test (reader thread owning stdout per the pitfall §3 documented in research §5). No amendment.
- **ADR-0010** (benchmark baseline format) — `bench/m2.md` follows this shape verbatim.

### Not in M2.E

- **SPRT.** Deferred to M3 — no second engine version yet to test against. ADR-0012 sketches the `-sprt` invocation for forward reference but does not wire it up.
- **Cute Chess GUI install.** Skipped per research §6 — no working macOS binary; `chessx` cask or Lichess paste-import suffices for ad-hoc PGN review.
- **Per-engine config registry beyond the shell wrapper.** No `engines.json` (fastchess does not consume one); `scripts/match.sh` is the registry. Multi-engine matrices land in M3+ if needed.
- **Concurrency tuning.** All matches at `-concurrency 1` (each subcommand runs 2 games sequentially, ~25 s each; concurrency adds noise without throughput gain at this scale).
- **Opening book.** Self-play smoke uses the default startpos repeat; vs-Stockfish smoke uses startpos repeat too (per research §4 the practitioner default at this scale; `8moves_v3.pgn` is an SPRT concern, not M2's).
- **`go perft N` UCI extension.** Out of M2 entirely — would land at a hypothetical M2.F or be folded into M3's bench command.

### 3. fastchess install: `scripts/install-fastchess.sh`

| Step | Action |
|---|---|
| Pre-flight | Refuse to run unless `darwin` + `arm64` (script targets only the dev platform). |
| Detect | If `vendor/fastchess/fastchess --version` succeeds, exit 0 with "already installed" note. |
| Download | `curl -fsSL https://github.com/Disservin/fastchess/releases/download/v1.8.0-alpha/fastchess-mac-arm64.tar -o "$TMPDIR/fastchess.tar"`. |
| Verify | `shasum -a 256 "$TMPDIR/fastchess.tar"` compared against a pinned `EXPECTED_SHA256` constant in the script. Hard-fail with diagnostic if mismatch. |
| Extract | `tar -xf "$TMPDIR/fastchess.tar" -C vendor/fastchess/`; `chmod +x vendor/fastchess/fastchess`. |
| Verify (existence) | `vendor/fastchess/fastchess --version` returns zero exit. |
| Verify (version match) | `vendor/fastchess/fastchess --version | grep -q "$EXPECTED_VERSION_LINE"` — hard-fail otherwise. |

- **Two version constants** in the install script:
  - `EXPECTED_RELEASE_TAG="v1.8.0-alpha"` — the GitHub release tag, used in the download URL.
  - `EXPECTED_VERSION_LINE="alpha 1.8.0"` — the literal substring the binary's `--version` output starts with (`fastchess alpha 1.8.0 compiled for macos-latest 20260128-072859b (CI)`). Two constants because the URL form and the binary-reported form differ; using one literal for both would either break the URL or break the grep.
- **SHA256 pinning** is load-bearing — the binary is unsigned, downloaded over HTTPS, but pinning closes the supply-chain hole between download and execution.
  - Implementer note: capture the actual SHA at install time of the live `vendor/fastchess/fastchess` and embed in the script. (The orchestrator-installed binary bytes are the authoritative source.)
- Bumping the pinned release is a three-line script edit (`EXPECTED_RELEASE_TAG` + `EXPECTED_VERSION_LINE` + `EXPECTED_SHA256`).

### 4. `scripts/match.sh` design — subcommand per smoke

```sh
#!/usr/bin/env bash
# scripts/match.sh — M2 fastchess smoke runner
# Subcommands:
#   self-play    → 2-game self-play (-rounds 1 -repeat), RandomMover vs RandomMover, distinct seeds
#   vs-stockfish → 2-game vs Stockfish 18 at UCI_LimitStrength + UCI_Elo=1320
#   compliance   → fastchess --compliance UCI shake-out on our binary
```

- **Locator order:** `vendor/fastchess/fastchess` first; `command -v fastchess` second; hard-fail with a pointer to `scripts/install-fastchess.sh` if neither resolves.
- **Version gate on the resolved binary:** whichever path resolves, `match.sh` runs `<resolved> --version | grep -q "$EXPECTED_VERSION_LINE"` and hard-fails on mismatch (e.g. "found fastchess at /opt/homebrew/bin/fastchess but it reports `alpha 1.7.0`; expected `alpha 1.8.0`. Run `scripts/install-fastchess.sh`."). One extra line; closes the "user has stale fastchess on PATH" silent-divergence footgun.
- **Stockfish locator:** `command -v stockfish` (already at `/opt/homebrew/bin/stockfish` per M1.G fixture work). Hard-fail if absent.
- **Build step:** `cargo build --release` is invoked from inside `match.sh` (idempotent — `cargo` skips work if up to date). Keeps "I just edited code; let me run a smoke" friction low.
- **Output paths:** `target/matches/smoke/m2-${SUBCMD}-${TIMESTAMP}.{pgn,log}`. `target/` is gitignored; `target/matches/` is created on demand.
- **Set `-x` only under `MATCH_DEBUG=1`.** Default mode echoes the chosen fastchess invocation as a single comment line, then runs.

### 5. Adjudication parameters — mandatory for random-mover self-play

M2.D proved random-vs-random can cycle indefinitely (no 50-move/threefold yet). Without adjudication, the smoke would hang. Two tiers:

| Knob | Value | Rationale |
|---|---|---|
| `-maxmoves 300` | hard cap | Mirrors E36's `MAX_PLY=300`. Fastchess adjudicates as draw if 300 full moves are reached. **Primary cap** for random-mover self-play; expected to fire on the majority of self-play games. |
| `-resign movecount=3 score=600` | best-effort resign | If 3 consecutive plies stay below −600 cp from one side's POV, that side resigns. **Honest caveat:** completely no-op for random-vs-random (both sides emit no `score cp`; fastchess defaults missing scores to 0, never below −600). Vs Stockfish, fires only when SF's POV reports +600 cp for 3 plies — and SF capped at `UCI_Elo=1320` may not reach that view against a random mover until quite late. So `-resign` is best-effort acceleration, not a contractual cap. Kept as a no-cost hedge; could be dropped without affecting C1–C7. |

- **`-draw movenumber=N movecount=M score=K` deliberately omitted.** With the §11 info-line emitting no `score cp` (and fastchess defaulting absent scores to 0), any score-threshold-based draw heuristic would fire as soon as `movenumber` is reached, regardless of position. `-maxmoves 300` is the honest cap; `-draw` would be dead-code-cheating to a shorter PGN.
- **Termination tag inventory expected** (empirically verified during Phase 4, not pre-claimed): random-vs-random self-play almost always reaches `-maxmoves 300` and is adjudicated; vs-Stockfish games may end via `-resign` (when our random mover hangs material in the opening). Natural mate/stalemate is rare in random-vs-random. **NOT expected (load-bearing gates):** `[Termination "illegal move"]` and `[Termination "stalled connection"]` — the smoke contract is exactly that these never appear. Specific tag-string forms (e.g. exactly `"adjudication"` vs `"max moves"`) are validated empirically against actual fastchess output in Phase 4.

### 6. Smoke contract — exit criteria

| # | Criterion | Mechanism |
|---|---|---|
| C1 | 2 self-play games complete with a legal FIDE result (`1-0`, `0-1`, `1/2-1/2`; never `*`). One trajectory in two color assignments per `-rounds 1 -repeat`. | `grep -c '^\[Result' target/matches/smoke/*self-play*.pgn` ≥ 2 |
| C2 | 2 vs-Stockfish games complete likewise. | same shape |
| C3 | Zero `[Termination "illegal move"]` tags in either PGN. | `grep -c 'illegal move'` = 0 |
| C4 | Zero `[Termination "stalled connection"]` tags in either PGN. | `grep -c 'stalled connection'` = 0 |
| C5 | No `level=err` or `level=fatal` lines in the run log. | `grep -E '\] (err\|fatal)' target/matches/smoke/*.log` returns nothing. (Empirically validated against actual fastchess log format in Phase 4 before locking the regex.) |
| C6 | `fastchess --compliance vendor/fastchess/fastchess <our binary>` passes all steps (40 on fastchess 1.8.0-alpha; M2.D binary only reached 11 of 12 before halting on the missing-info-line check — §11 unblocks the remaining 28 steps). | match.sh subcommand `compliance` |
| C7 | `bench/m2.md` written, follows ADR-0010 schema, references PGN/log paths. | committed file present |

- **Self-play game count is 2, not 4.** With deterministic seeds (`Random_Seed=1`/`=2`) and no opening book, fastchess's `-rounds 2 -repeat` produces 4 PGNs that are 2 identical trajectories duplicated. Cutting to `-rounds 1 -repeat` yields 2 honest games (one trajectory in both color assignments).
- **C3 and C4 are the two failure modes that imply our engine misbehaved.** Per research §4 these are the load-bearing exit criteria; everything else is hygiene.
- **C6 is the load-bearing external pin on §11.** E33's amended `info`-line assertion is the in-tree pin. **Both required** — E33 verifies presence in the captured stream; C6 verifies fastchess accepts the line as a valid `info` (a stricter check than presence). A future agent dropping §11 as "redundant with E33" would not be caught by E33 alone.

### 8. Pitfalls already mitigated by the existing helpers

The `tests/uci_integration.rs::drain_stdout` helper already mitigates the research §5 pitfalls. M2.E does not introduce new pipe-handling code:

| Pitfall (research §5) | Where mitigated |
|---|---|
| Pipe-fill deadlock | `drain_stdout` spawns a reader thread that owns stdout. |
| Line buffering | Engine flushes per line (verified at M2.C; existing E33–E36 would hang if it regressed). |
| macOS signal handling — `quit` + `wait`, not EOF | E33 / E34 / E37 send `quit`; E35 deliberately tests EOF as a separate path. |
| Race between write-next / drain-prev | Existing tests pipe the entire transcript at once + drop stdin, then collect — drain happens after EOF. |
| `BufReader::lines().flatten()` swallows I/O errors | Avoided: existing helper uses `match line { Ok(l) => tx.send(l), Err(_) => break }`. |

### 11. `RandomMover::go` info-line emission — must-fix #1 from plan-review pass 1

**Empirical finding.** Running `vendor/fastchess/fastchess --compliance target/release/clawfish` against the M2.D binary, 11 of 12 steps pass; Step 12 ("Check if engine prints an info line") **fails** because `RandomMover::go` writes only `bestmove <uci>\n` with no `info` line. The engine is otherwise spec-compliant.

**Resolution.** Emit one minimal `info` line via `info_sink` from inside `Search::go`, after the wait loop and before returning. Concrete edit:

```rust
// src/search.rs::RandomMover::go — current shape (M2.D).
fn go(
    &mut self,
    position: &Position,
    ctx: &SearchContext,
    info_sink: &dyn Fn(&str),  // RENAMED: was `_info_sink` at M2.D; now used.
) -> SearchResult {
    // ... existing candidate computation (unchanged) ...
    let candidate: Option<Move> = /* ... */;

    // ... existing wait loop (unchanged) ...
    let wait = ctx.limits.infinite || ctx.limits.movetime.is_some() || ctx.limits.ponder;
    if wait {
        while !ctx.should_abort(0) {
            std::thread::sleep(std::time::Duration::from_millis(1));
        }
    }

    // NEW (M2.E): emit one info line before returning. Post-wait so `time`
    // reports the full wall-clock spent in this `go`, symmetric with how
    // M3+ iterative-deepening will report `info time` on its final iteration.
    let elapsed_ms = ctx.start.elapsed().as_millis();
    let pv_token = candidate.map(|m| m.to_uci()).unwrap_or_else(|| "0000".to_string());
    info_sink(&format!(
        "info depth 0 score cp 0 nodes 1 time {elapsed_ms} pv {pv_token}"
    ));

    SearchResult {
        bestmove: candidate,
        ..Default::default()
    }
}
```

**Placement decision: post-wait.** Two options were considered:

| Placement | `time` reports | Symmetric with M3+? |
|---|---|---|
| Pre-wait | ~0 ms (instant pick before sleeping) | No — alpha-beta will report info during/after iterations, not before any thinking. |
| **Post-wait** (chosen) | Full wall-clock used (up to `movetime`) | Yes — alpha-beta's last iteration reports cumulative `time`. |

Post-wait also gives fastchess's PGN annotation the actual time spent (visible as `{0.00/0 0.123s}` instead of `{0.00/0 0.000s}`).

**Empty-moves handling.** When `candidate.is_none()` (no legal moves — mate / stalemate / empty `searchmoves` filter), emit `pv 0000` per the UCI null-move convention. Symmetric with the worker's `bestmove 0000` emission for the same case (`engine.rs` line 214).

**Field choices:**

- **`score cp 0` is required.** Empirically verified: `vendor/fastchess/fastchess --compliance` Step 12 rejects `info depth N nodes K time M pv MV` without a `score` field; passes with `score cp 0`. Earlier draft of this plan committed on "no `score cp`" with the rationale "would be a lie"; empirical probe overturned that. Three variants tested:

  | Info line | Step 12 |
  |---|---|
  | `info depth 0 nodes 1 time 0 pv e2e4` | Failed |
  | `info depth 1 nodes 1 time 0 pv e2e4` | Failed |
  | `info string thinking` | Failed |
  | `info depth 1 score cp 0 nodes 1 time 0 pv e2e4` | **Passed** |

  The "lie" framing was wrong: fastchess defaults missing scores to 0 in its `-draw` adjudication anyway, so emitting `0` explicitly is the same value, just visible. M3+ alpha-beta will replace `0` with an honest evaluation.

- **`depth 0` / `nodes 1`.** Honest reflection of "no search; one PRNG step." Cosmetic note: `nps` reported in PGN will be `~1000` when `time=1` ms — uninteresting until M3+.
- **`time <ms>`.** From `ctx.start.elapsed().as_millis()` — the field is in `SearchContext` for exactly this purpose (M2.C plan §"`SearchContext`" already documents `start: Instant` is "used by future `info time` emission").
- **`pv <move-or-0000>`.** Bonus PGN-annotation usefulness; not strictly required for compliance.

**Touch surface.** ~6 LOC in `src/search.rs::RandomMover::go` — drop the underscore from `_info_sink`, compute `elapsed_ms`, build `pv_token`, emit via `info_sink`. No `Search` trait change (the parameter was already in M2.C's signature).

**Verification.**

- **E33 amended** (single assertion line) to check at least one `info `-prefixed line is in the captured output. **Presence-only**, no temporal binding — placement is a `RandomMover` impl detail, not a contract M3+ alpha-beta should be locked into.
- **`scripts/match.sh compliance`** (C6 in §6) is the external cross-check that fastchess accepts the line as a valid `info`.

**Mutation surface.** `cargo mutants --in-diff` will mutate format-string args, the `elapsed_ms` computation, the `unwrap_or_else` on `candidate`. E33's amended `info `-prefix assertion catches the trivial "drop the line entirely" mutant. The compliance check catches "emit a malformed line." Surviving mutants in the elapsed/pv-formatting are addressed per workflow at final review.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Random-mover self-play reaches `-maxmoves 300` every game. | Expected behavior: produces `[Termination …]` adjudication string (exact form recorded empirically in `bench/m2.md`), **not** `stalled connection`. Smoke contract C3/C4 are the load-bearing gates; long natural-termination is OK. |
| fastchess SHA256 pinning becomes stale on a version bump. | Bumping the script's `EXPECTED_RELEASE_TAG` + `EXPECTED_VERSION_LINE` + `EXPECTED_SHA256` is a documented three-line edit in ADR-0012's "How to apply." `--version` grep gate (§3) catches bump-with-stale-SHA mismatches. |
| Stockfish 18 not on PATH for `vs-stockfish`. | Hard-fail in `match.sh` with a pointer to `brew install stockfish`. Independent of C5 log inspection. |
| `scripts/match.sh` invoked from a non-repo cwd. | Script self-locates via `$(cd "$(dirname "$0")/.." && pwd)` (same idiom as `scripts/regen-perft-fixtures.sh`). |
| Hard concurrency races in E37 on slow CI. | `wait_for_exit(deadline)` set generously (2 s). `cargo test` runs locally on Apple M4 in <1 s/test; CI tightening if ever needed is a one-line edit. |
| `--compliance` Step 12 fails on M2.D binary today. | **Resolved by §11** — `RandomMover::go` emits an `info` line. E33 amendment pins it; the compliance check verifies it externally. |
| `--compliance` surfaces a *new* nit not caught by manual probe. | Reviewer-loop / final-review will surface; `src/` change reopens the loops per workflow. Phase 5's empirical run is the gate. |
| `vendor/` install path locks out users who already have fastchess installed elsewhere. | `match.sh`'s locator falls back to `command -v fastchess` (per §4). |
| Fresh-clone footgun: a new clone has no `vendor/fastchess/`. | ADR-0012 documents the bootstrap sequence (`cargo build --release` → `scripts/install-fastchess.sh` → `cargo test` → `match.sh ...`). `cargo test` works without fastchess installed; only the `match.sh` subcommands depend on it. |
| Adjudication parameters surface differently across fastchess versions. | Pin the version in `scripts/install-fastchess.sh`; `bench/m2.md` records the exact build line. |
| C5 grep pattern doesn't match real fastchess log content. | Empirically validate the regex against an actual log in Phase 5 before committing the plan's claim. Pattern is a placeholder until then; gate is "no err/fatal lines, however fastchess emits them." |
