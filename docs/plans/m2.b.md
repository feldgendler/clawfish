# M2.B — UCI command parser

## Context

M2.A landed `Move::to_uci` + `Move::from_uci` + `UciMoveError` — the leaf-level wire format for moves. M2.B sits one layer up: a pure-function parser for the GUI→engine command stream.

The deliverable:

- A `uci` module (single file `src/uci.rs` for now — rationale §"File layout" below).
- A `Command` enum covering every UCI 2006 GUI→engine command.
- `parse_uci_line(&str) -> Command` — pure function, no I/O, no engine state.

**Spec source.** `docs/reference/uci-protocol-2006.txt` is in-tree and authoritative. It is fully prescriptive for the wire grammar; the only design choices in this phase are the Rust shape of the AST and how to react to malformed input.

### Binds no ADRs

- ADR-0011 (UCI threading) binds M2.C, not here. M2.B is a pure parser; threading concerns don't surface.
- ADR-0012 (tournament harness) binds M2.E.

No new ADRs in this phase.

### Research skip — justified

- The UCI 2006 spec is in-tree.
- Pre-M2 research (`docs/research/m2-uci-threading.md`, `docs/research/m2-tournament-harness.md`) was scoped to threading and tournament infra; it touched the GUI→engine command set only in passing.
- The decisions baked into this plan (Unknown-on-malformed vs. Result return; raw-string deferred validation; numeric parse failure → field None vs. command Unknown; tokenization rule) are routine engineering choices, contested neither in the spec nor the engine community.
- Source-code-reading restriction (ADR-0003) prohibits browsing other engines' UCI parsers anyway.

### What this phase delivers

1. **`Command` enum** in `src/uci.rs` covering every UCI 2006 GUI→engine command.
2. **Helper types** — `DebugMode`, `PositionSpec`, `GoParams`, `Register` — kept inside `src/uci.rs`.
3. **`parse_uci_line(line: &str) -> Command`** — sole public entry point.
4. **Tests** — anchor unit tests + table-driven negative tests + property tests for whitespace tolerance and grammar coverage.
5. **Crate-root re-exports** in `src/lib.rs`: `Command`, `DebugMode`, `GoParams`, `PositionSpec`, `Register`, `parse_uci_line`.
6. **Documentation** — `docs/architecture.md` UCI row updated; `CLAUDE.md` + `docs/roadmap.md` status updates after commit.

### Not in M2.B

- **Engine I/O loop, dispatch, state.** That's M2.C — `Engine` struct, `run()` reading lines from stdin, handlers for each command, threading model.
- **Move-string validation in `position … moves …` and `go searchmoves …`.** Those are collected as raw `String`s and parsed via `from_uci` (M2.A) at apply-time in M2.C. Reasons:
  - The parser doesn't import `Position`/`Move`; it stays a pure string→AST function.
  - `from_uci` requires a `&Position`, which the parser doesn't have.
  - Move strings invalid for the *current* position are still syntactically meaningful; rejection is M2.C's call, not the parser's.
- **FEN-string validation in `position fen …`.** Same logic — collect raw FEN, parse in M2.C via `Fen::from_str` (or whatever the existing entry point is).
- **Engine→GUI output formatters** — `bestmove`, `info`, `id`, `option`, `uciok`, `readyok`. M2.C/D produce these; M2.B does not.
- **Benchmarks.** UCI command parsing is per command (line at a time, never inside any search loop). A microbenchmark would measure noise. Justified skip per workflow.md "Benchmark and profile" — recorded here. Same precedent as M2.A.

## Decisions baked into this plan

### 1. Return shape: `Command`, not `Result<Command, ParseError>`

The UCI 2006 spec, §"GUI to engine":

> if the engine or the GUI receives an unknown command or token it should just ignore it and try to parse the rest of the string in this line.

> if the engine receives a command which is not supposed to come, for example "stop" when the engine is not calculating, it should also just ignore it.

The spec mandates silent tolerance of malformed input. Returning `Result` would force every call site to discard the error, and there is no engine→GUI channel for parse errors anyway. So `parse_uci_line` returns `Command` directly, with `Command::Unknown` covering:

- empty / whitespace-only line,
- no recognized command keyword anywhere on the line,
- recognized command but required arguments missing or malformed (e.g. `debug` without `on`/`off`, `position` without `startpos`/`fen`).

`Command::Unknown` is opaque — it carries no original-line bytes. The diagnostic information (the line that failed to parse) is M2.C's responsibility to preserve at the read-loop layer if it wants `info string` debug logging. M2.B's contract is "did this line parse as a recognized command?" — diagnostics are a separate concern. **Forward dependency**: this design assumes M2.C wraps `parse_uci_line(&line)` with the `&line` still in scope at the call site; if M2.C ends up needing the bytes inside `Command::Unknown` itself, we revisit by adding `Unknown(String)` (one-line change).

### 2. Tokenization: `str::split_whitespace`

Spec §preamble:

> arbitrary white space between tokens is allowed
> Example: "debug on\n" and  "   debug     on  \n" and "\t  debug \t  \t\ton\t  \n"
> all set the debug mode of the engine on.

`str::split_whitespace` splits on any Unicode whitespace run, drops empty tokens, and handles tabs/CR/LF/multiple-spaces correctly. The spec only mentions ASCII whitespace, but `split_whitespace`'s broader handling is harmless (no UCI command keyword contains whitespace; if a non-ASCII whitespace token appears mid-command, the worst case is over-aggressive splitting, which is fine).

Newlines themselves are *not* part of a "line" — the M2.C read loop will hand `parse_uci_line` one line at a time (`stdin.lines()` strips trailing `\n`). The parser doesn't depend on newline handling.

### 3. Per-command leniency model

The UCI 2006 spec §preamble suggests skipping all unknown tokens uniformly (`joho debug on` → recognize `debug on`). **We deviate.** Empirical Stockfish 18 behavior is asymmetric per-command — different commands have different body-leniency rules — and the de facto reference does *not* implement leading-skip.

#### 3.1 Empirical Stockfish probes

Run locally during planning (Stockfish 18 from Homebrew). Stockfish's `d` debug command displays an ASCII board grid plus a `Fen: …` line; the `position` rows below check the `Fen:` line.

| Input | Stockfish stdout | Inferred rule |
|---|---|---|
| `xyzzybanana uci` | `Unknown command: 'xyzzybanana uci'` | strict-first-token (no leading-skip) |
| `xyzzybanana isready` | `Unknown command: 'xyzzybanana isready'` | same — strict-first-token confirmed on a second command |
| `isready xyzzybanana` | `readyok` | no-arg commands tolerate trailing junk |
| `   isready` | `readyok` | leading whitespace stripped (free from `split_whitespace`) |
| `debug` | `Unknown command: 'debug'` | required positional arg cannot be missing |
| `debug joho on` | `Unknown command: 'debug joho on'` | `debug` is strict — must be `on` / `off` immediately |
| `debug on garbage` | `Unknown command: 'debug on garbage'` | `debug` is strict-exact-2-tokens — even valid arg + trailing junk rejected |
| `position startpos garbage` (then `d`) | `Fen:` line equals `rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1` (canonical starting position) | `position` body: lenient-stop — accept what's parsed, ignore rest |
| `position startpos foo moves e2e4` (then `d`) | same `Fen:` line — confirms `e2e4` was *not* applied | `position` body: lenient-stop — junk between `startpos` and `moves` discards the `moves` clause |
| `go wtime abc btime 5000` | search runs, `bestmove …` | `go` body: lenient-skip — malformed numerics dropped, parsing continues |
| `go foo wtime 5000` | search runs | `go` body: lenient-skip — leading unknown token in `go` body silently dropped |
| `go wtime 5000 foo btime 3000` | search runs | `go` body: lenient-skip — mid-body unknown token silently dropped |

#### 3.2 Chosen rules

Per-command leniency, encoded:

| Command | First-token rule | Body rule |
|---|---|---|
| `uci` / `isready` / `ucinewgame` / `stop` / `ponderhit` / `quit` | strict — first token must be the keyword | trailing tokens silently ignored |
| `debug` | strict — first token must be `debug`, second must be exactly `on` or `off`, no third token allowed | strict-exact-2-tokens (`debug on garbage` → `Unknown`) |
| `setoption` | strict — first token must be `setoption`, immediate next must be `name` | keyword-driven (`name <id> [value <x>]`), see §8 |
| `register` | strict — first token must be `register`, immediate next must be `later` / `name` / `code` | keyword-driven, see §8 |
| `position` | strict — first token must be `position`, immediate next must be `startpos` or `fen` | strict during the position spec (`fen` requires exactly 6 tokens, else `Unknown`); lenient-stop *after* the position spec is fully parsed — peek for `moves` keyword; if found consume it, otherwise drop the rest, see §7 |
| `go` | strict — first token must be `go` | lenient-skip — unknown body tokens dropped, malformed numerics → field `None`, parsing continues, see §6 |

#### 3.3 Cross-cutting principles

- **First token (after leading-whitespace strip via `split_whitespace`) must be a recognized command keyword.** No leading-skip. `xyzzybanana uci` → `Unknown`. The user-facing rationale: the spec's leading-skip rule silently hides GUI-side typos (`xquit` would be ignored rather than treated as a clear typo of `quit`).
- **Leading whitespace is stripped** as a side effect of `split_whitespace` per §2 — the "first non-whitespace token" rule is what's actually being enforced, not "byte 0 is the keyword".
- **Lowercase command keywords only.** UCI tokens are lowercase by convention; `Debug ON` → `Unknown`. Same precedent as M2.A's strict-lowercase decision.
- **Numeric parsing** in `go` body uses `str::parse::<T>()`; out-of-range or non-numeric → field stays `None`. Documented in §6.b.

### 4. `Command` enum shape

```rust
#[derive(Clone, Debug, PartialEq, Eq)]
pub enum Command {
    /// `uci`
    Uci,
    /// `debug on` / `debug off`
    Debug(DebugMode),
    /// `isready`
    IsReady,
    /// `setoption name <id> [value <x>]`. `name` is non-empty by parser contract.
    SetOption { name: String, value: Option<String> },
    /// `register …`
    Register(Register),
    /// `ucinewgame`
    UciNewGame,
    /// `position [startpos|fen <…>] [moves <m1> <m2> …]`
    Position { spec: PositionSpec, moves: Vec<String> },
    /// `go [params …]`
    Go(GoParams),
    /// `stop`
    Stop,
    /// `ponderhit`
    PonderHit,
    /// `quit`
    Quit,
    /// Empty line, unrecognized command, or required-arg parse failure.
    Unknown,
}

#[derive(Copy, Clone, Debug, PartialEq, Eq)]
pub enum DebugMode {
    On,
    Off,
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum Register {
    /// `register later`
    Later,
    /// `register [name <name>] [code <code>]` — at least one field is `Some`
    /// by parser contract (the parser emits `Command::Unknown` if both
    /// would be `None`).
    Identify { name: Option<String>, code: Option<String> },
}

#[derive(Clone, Debug, PartialEq, Eq)]
pub enum PositionSpec {
    /// `position startpos …`
    StartPos,
    /// `position fen <field1> <field2> … <field6> …`. Exactly the 6 FEN
    /// tokens collected after `fen`, joined with single spaces. Validation
    /// (correct field count is enforced by the parser; correct field *content*
    /// is deferred) lives in M2.C's FEN parse.
    Fen(String),
}

#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct GoParams {
    /// `searchmoves <m1> …`. `None` means the keyword was not given;
    /// `Some(vec![])` means the keyword was given with no moves following.
    pub searchmoves: Option<Vec<String>>,
    /// `ponder` keyword present
    pub ponder: bool,
    /// `wtime <x>` — milliseconds remaining for white. Signed because the
    /// UCI clock can go negative under time-trouble overshoot.
    pub wtime: Option<i64>,
    /// `btime <x>` — milliseconds remaining for black.
    pub btime: Option<i64>,
    /// `winc <x>` — white increment per move (ms). Spec: "if x > 0", so
    /// non-negative; `u64` rejects negative inputs at parse time (becomes None).
    pub winc: Option<u64>,
    /// `binc <x>` — black increment per move (ms).
    pub binc: Option<u64>,
    pub movestogo: Option<u32>,
    pub depth: Option<u32>,
    pub nodes: Option<u64>,
    /// `mate <x>` — search for mate in x moves. `Some(0)` is a degenerate
    /// "is the current position checkmate?" query that consumers handle.
    pub mate: Option<u32>,
    /// `movetime <x>` — exact milliseconds; signed for symmetry with wtime/btime.
    pub movetime: Option<i64>,
    /// `infinite` keyword present
    pub infinite: bool,
}
```

Discussion of the field choices:

- **`Debug(DebugMode)`** vs. `Debug(bool)` — `bool` is fine type-wise, but `DebugMode::On` / `DebugMode::Off` reads more clearly at the M2.C dispatch site and removes the small risk of a `true` / `false` argument-order typo. One byte either way.
- **`SetOption { name: String, value: Option<String> }`** — `name` is required by spec; `value` is optional (the `button` option type takes no value per spec). The parser contract: `name` body must be ≥1 token (else `Command::Unknown`); the `value` body, if the `value` keyword appears, may be empty (yielding `Some(String::new())`) — this preserves the meaningful distinction between "no `value` keyword" (`None`) and "`value` keyword with empty body" (`Some("")`). The asymmetry is rooted in the spec: `<id>` is required, `<x>` is structurally present iff `value` was given.
- **`Register::Identify { name, code }`** — the spec example `register name Stefan MK code 4359874324` shows both can appear together. Splitting into `Name`/`Code` variants would lose the combined case. `Later` is its own variant because it's mutually exclusive with name/code per spec. The parser contract for empty bodies is asymmetric with `setoption`: `register name` (empty `name` body, no `code`) → `Unknown`; `register name foo code` (empty `code` body) → `Identify { name: Some("foo"), code: None }`. Empty `name` / `code` body for `register` becomes `None`, not `Some("")`. Rationale: `register` has no analogue to setoption's "set option to empty string" semantics; an empty registration name or code is meaningless.
- **`Identify { name: None, code: None }` is invariant-by-construction, not enforced by the type system.** External callers constructing this via `Identify { name: None, code: None }` directly would be API misuse; `parse_uci_line` never produces it (parser collapses to `Command::Unknown` first). Implementation enforcement (a `debug_assert!`) lives in §8.b near the construction algorithm, not here. Same precedent as M2.A's "no `Default` for `Move`" defense.
- **`PositionSpec::Fen(String)` carries raw bytes**, not a parsed `Position`. The parser collects exactly 6 tokens after `fen` (FEN spec mandates 6 fields per `docs/reference/pgn-spec-1994.txt` §16.1) and joins them with single spaces. Field-content validation is deferred to M2.C. See §7.
- **`Position { … moves: Vec<String> }`** vs. `Option<Vec<String>>` — for `position`, "moves keyword absent" and "moves keyword with empty list" are functionally identical (no moves to play). `Vec` is simpler.
- **`GoParams::searchmoves: Option<Vec<String>>`** vs. `Vec` — for `go searchmoves`, the distinction matters: `None` means "search all legal moves"; `Some(vec![])` means "search no moves" (degenerate, M2.D handles).
- **Numeric types in `GoParams`.** Spec-grounded: `wtime`/`btime`/`movetime` are `i64` (clock values can overshoot to negative); `winc`/`binc` are `u64` (spec literally says "if x > 0", so an increment is non-negative — negative inputs fail to parse and yield `None`); `movestogo`/`depth`/`mate` are `u32` (counter-style, never negative); `nodes` is `u64` (can be very large). All are `Option` so absence is distinguishable from zero.

### 6. `go` parameter parsing — per-keyword scan, malformed numerics drop the field

`go` is the only command with multiple optional sub-keywords.

#### 6.a. Parse loop structure

Tokens after `go` are scanned sequentially. Each iteration looks at the next token:

| Token category | Count | Keywords | Action |
|---|---|---|---|
| Move-list collector | 1 | `searchmoves` | collect raw move strings until next `go` keyword or end (see §6.c) |
| Boolean flags | 2 | `ponder`, `infinite` | set the corresponding field `true` |
| Numeric arguments | 9 | `wtime`, `btime`, `winc`, `binc`, `movestogo`, `depth`, `nodes`, `mate`, `movetime` | consume next token, parse as numeric per the keyword's type (§4), set the field (see §6.b) |
| Unknown | — | (anything else) | skip silently — does not collapse the command |

**12 recognized `go` body keywords total** (1 + 2 + 9, per the table); §6.c uses 11 of them (excluding `searchmoves` itself) as the termination set for `searchmoves`'s collection loop. Lenient-skip on unknown body tokens confirmed empirically against Stockfish (§3.1).

The `go` body's lenient-skip rule diverges from `position`'s lenient-stop and from `debug`'s strict-exact-2-tokens. Rationale: `go` is the only command whose subcommands are independent and optional. Treating an unknown `go` token as fatal would mean a single typo voids the whole search request, and the spec's "ignore unknown tokens" intent applies most naturally to a keyword-argument body.

#### 6.b. Numeric-value parsing rules

Each numeric `go` keyword (`wtime`, `btime`, `winc`, `binc`, `movestogo`, `depth`, `nodes`, `mate`, `movetime`) consumes the next token unconditionally if one exists, then attempts `str::parse::<T>()` (where `T` is the field type per §4). On parse success, the field is set; on parse failure, the field stays `None` and the consumed token is *not* re-scanned as a possible keyword.

Worked cases (cells filled only when relevant; `—` means the field is at default `None`):

| Input | Resulting non-default fields |
|---|---|
| `go` | (none — all defaults) |
| `go wtime 5000` | `wtime: Some(5000)` |
| `go wtime` (truncated) | (none — no value token to consume; field stays None) |
| `go wtime abc btime 5000` | `wtime: None` (`abc` consumed, parse fails); `btime: Some(5000)` |
| `go wtime abc wtime 5000` | `wtime: Some(5000)` (last-write wins; first attempt consumes `abc`, second consumes `5000`) |
| `go nodes 99999999999999999999999 depth 4` | `nodes: None` (u64 overflow); `depth: Some(4)` |
| `go winc -100 binc 200` | `winc: None` (u64 rejects negative); `binc: Some(200)` |

Bare `go` is valid: returns `Go(GoParams::default())` — every field `None` / `false`. Spec §`go`: "If one command is not sent its value should be interpreted as it would not influence the search." Engine layer chooses how to interpret an effectively-empty `go`.

#### 6.c. `searchmoves` termination

`searchmoves` collects tokens until either (a) the next token matches one of the **11 other recognized `go` keywords** — `ponder`, `infinite`, `wtime`, `btime`, `winc`, `binc`, `movestogo`, `depth`, `nodes`, `mate`, `movetime` (i.e., the full §6.a keyword list except `searchmoves` itself) — or (b) end of line.

Note: `searchmoves` is **not** in the termination set — a second `searchmoves` keyword inside an active `searchmoves` collection is treated as a literal move-string token (added to the list).

This is a **judgment call**, not derived from spec. Three defensible interpretations exist:

1. *Treat as literal move token* (chosen) — appended to current list; M2.C's `from_uci` rejects `"searchmoves"` as `UciMoveError::Malformed` at apply-time. Most localized; no information silently lost.
2. *Last-wins list-restart* — second keyword discards the first list, starts fresh. Consistent with §6.b's `depth 4 depth 8` rule but silent data loss.
3. *Collapse to `Unknown`* — strictest. Punitive for an unlikely real-world case.

We pick (1) and pin via test `go_repeated_searchmoves_treated_as_move_string`. If real-world fastchess data at M2.E shows GUIs ever emit repeated `searchmoves`, revisiting is a one-line change.

Worked cases:

| Input | searchmoves | other fields |
|---|---|---|
| `go searchmoves e2e4 d2d4 wtime 5000` | `Some(["e2e4", "d2d4"])` | `wtime: Some(5000)` |
| `go searchmoves` | `Some([])` (`searchmoves` keyword present, body collected zero tokens before EOL → `Some([])` per §4 distinction) | (defaults) |
| `go searchmoves wtime 5000` | `Some([])` (next token `wtime` terminates collection at zero) | `wtime: Some(5000)` |
| `go searchmoves e2e4 searchmoves d2d4` | `Some(["e2e4", "searchmoves", "d2d4"])` | (defaults) |
| `go infinite searchmoves e2e4` | `Some(["e2e4"])` | `infinite: true` |

### 7. `position fen` — strict 6-token collection, then lenient-stop trailing

The FEN field is exactly 6 space-separated subfields per the in-tree FEN spec (`docs/reference/pgn-spec-1994.txt` §16.1). The UCI command line embeds it as exactly 6 tokens after `fen`.

Algorithm after seeing `fen`:

1. Consume the next 6 tokens. If fewer than 6 tokens remain before end-of-line, the entire `position` command is `Command::Unknown`.
2. Join them with single spaces → `PositionSpec::Fen(String)` (FEN content is *not* validated at this layer; M2.C parses).

Then for both `startpos` and `fen <6-tokens>`, the trailing-clause rule (per §3 lenient-stop):

3. Peek the next token:
   - If `moves`: consume it, then collect *all* remaining tokens as raw move strings into `moves: Vec<String>`. Validation deferred to M2.C.
   - Anything else (or end-of-line): leave `moves` empty; ignore the rest.

Worked cases:

| Input | spec | moves |
|---|---|---|
| `position fen <6-fields> moves e2e4` | `Fen("<6-fields>")` | `["e2e4"]` |
| `position fen <6-fields>` | `Fen("<6-fields>")` | `[]` |
| `position fen <6-fields> garbage` | `Fen("<6-fields>")` | `[]` (matches Stockfish lenient-stop) |
| `position fen <6-fields> garbage moves e2e4` | `Fen("<6-fields>")` | `[]` (junk before `moves` discards the clause) |
| `position fen <5 tokens>` | — | — (`Command::Unknown` — incomplete FEN) |
| `position fen` | — | — (`Command::Unknown` — zero FEN tokens) |
| `position startpos moves e2e4 e7e5 garbage` | `StartPos` | `["e2e4", "e7e5", "garbage"]` (post-`moves`, all are raw move strings) |
| `position startpos` | `StartPos` | `[]` |
| `position startpos garbage` | `StartPos` | `[]` (lenient-stop) |

Why strict-6-FEN-tokens (rather than "collect until `moves` or end"):

- Matches the FEN spec — there's no ambiguity.
- Allows trailing junk after a valid FEN to be silently dropped (matches Stockfish lenient-stop on `position` body — confirmed empirically against `position startpos garbage`).
- The simpler "collect until `moves`/end" rule would always collect trailing junk *into* the FEN string, forcing M2.C's FEN parser to reject otherwise-acceptable inputs.

`moves` cannot legally appear as content of any FEN field per the FEN spec (board layout, side `w`/`b`, castling letters, EP square, halfmove digits, fullmove digits) — so a malicious `position fen moves moves moves moves moves moves moves e2e4` (note: 7 `moves` tokens) would collect `["moves"; 6]` as the FEN string and then peek the 7th `moves` as the post-FEN keyword, consuming `["e2e4"]` as moves. The 6-token-only variant `position fen moves moves moves moves moves moves e2e4` instead collects 6 `moves` as the FEN, peeks `e2e4` (not `moves`), drops it — `moves` ends up empty. Either way the malformed FEN string is rejected at M2.C's FEN parse layer. Acceptable.

### 8. Multi-word `name` / `value` / `code` parsing

#### 8.a. `setoption name <id> [value <x>]`

- After `setoption`, the next token must be `name` (else `Unknown`).
- Collect `name` body tokens until next `value` keyword or end.
- If the `value` keyword is found, collect all remaining tokens (no further keywords — `name` and other reserved words inside `value` body are taken at face value).
- **Empty-body rules (asymmetric between `name` and `value`):**
  - **`name` body must contain ≥1 token, else the whole command is `Unknown`.** Two failure cases both reduce to "name body is empty":
    - No tokens follow `name` at all (`"setoption name"`).
    - The next token is the `value` keyword (`"setoption name value foo"`) — the `name` body collects zero tokens before terminating on `value`.
    - The spec requires `<id>` — there is no "set option named empty-string" semantics worth preserving.
  - **`value` body, if the `value` keyword is present, may be empty** — yielding `Some(String::new())`, *not* `None` and *not* `Unknown`. `setoption name X value` produces `SetOption { name: "X", value: Some(String::new()) }`. The empty `Some("")` is intentional: it preserves the meaningful distinction between "no `value` keyword" (e.g. button-type option, `value: None`) and "`value` keyword with empty body" (string-type option set to its `<empty>` sentinel per spec §`option type string`).
- Join collected body tokens with single spaces.

#### 8.b. `register [later | name <x> | code <y>]`

- After `register`, the next token decides the variant:
  - `later` → `Register::Later`. Trailing tokens after `later` ignored (lenient, mirroring no-arg trailing-junk per §3).
  - `name` or `code` → enter `Identify` collection mode:
    - `name` body collects until next `code` keyword or end.
    - `code` body collects until next `name` keyword or end.
    - Either keyword may appear first; both can coexist; repeating either keyword overwrites (last-wins).
  - Anything else → `Unknown`.
- **Empty-body rule (uniform):** an empty `name` or `code` body produces `None` for that field — *not* `Some("")`. Asymmetric with §8.a's `setoption value` empty-body rule because `register` has no analogue to setoption's "set option to empty string"; an empty registration name or code is meaningless. After collection:
  - If both `name` and `code` end up `None` (e.g. `register name`, `register code`, `register name code`), the whole command is `Unknown`.
  - Otherwise → `Register::Identify { name, code }` with at least one field `Some(non-empty-string)`.
- **Last-wins meets empty-body — rule.** When a keyword repeats, the second occurrence's collected body wins, even if empty. Pure last-wins, consistent with §6.b's `go depth 4 depth 8` rule; the empty-body-→-`None` rule applies uniformly to whichever body wins.
- **Last-wins meets empty-body — worked examples:**
  - `register name Stefan code 123 name` → `Identify { name: None, code: Some("123") }` (second `name` body is empty → overwrites prior `Some("Stefan")` with `None`; `code` is unaffected).
  - `register name Stefan code 123 name code` → `Unknown` (last-wins overwrites *both* fields with `None`; final state has both `None`, the "both None → Unknown" check at the construction site converts to `Command::Unknown`). This is the case the §4 `debug_assert!(name.is_some() || code.is_some())` defends against — exercised by group B test `rejects_register_last_wins_to_both_none`.
- **Implementation note.** The construction site for `Identify` includes a `debug_assert!(name.is_some() || code.is_some())` so any future regression that allows the both-`None` case (e.g. someone forgets the both-None → Unknown check) fires loudly in debug builds.

Spec example: `register name Stefan MK code 4359874324` → `Register::Identify { name: Some("Stefan MK"), code: Some("4359874324") }`.

### 9. Command keyword lowercase — exception for `setoption` `<id>`

Cross-references §3.3 (lowercase keyword rule). The one nuance worth pulling out: `setoption`'s `<id>` *is* case-insensitive per spec §`setoption`, but that case-folding is option-name semantics handled at M2.C — the parser preserves whatever case the GUI sent in the `String` it returns. So `setoption name Hash` and `setoption name hash` both round-trip as their original case.

### 10. File layout

Single file `src/uci.rs` (impl + tests). The M2.A plan note speculated a `src/uci/` directory at this point; reconsidered:

- **M2.B has no substantive sub-module** that would justify the promotion. Other modules in this project moved to a directory only when a sub-module (`magic/constants.rs` for generated tables, `zobrist/keys.rs` for the vendored Polyglot key set, `movegen/` for per-piece emit fns) appeared.
- M2.C will likely add `src/uci/engine.rs` (engine state + dispatch) and possibly `src/uci/io.rs` (read/write thread); the promotion is natural at *that* point.

So `src/uci.rs` it is. The crate-root re-exports list grows by `Command`, `DebugMode`, `GoParams`, `PositionSpec`, `Register`, `parse_uci_line`.

### 11. No errors, no `Result` — and no panics

`parse_uci_line` is total — every input string maps to a `Command`. No panics:

- `str::split_whitespace` is panic-free.
- All numeric parsing uses `str::parse::<T>()` which returns `Result` (consumed via `.ok()`).
- `Iterator::take(6)` (used in §7's strict-6 FEN-token collection) consumes at most 6 elements; `Vec` allocation for ≤6 `&str` references is bounded and well under any plausible OOM threshold.
- `String::from(&str)` and `Vec::push` are panic-free given finite input.

### 11.5 Helper-function visibility

The internal sub-parsers (`parse_debug`, `parse_setoption`, `parse_register`, `parse_position`, `parse_go`) are **private** (`fn`, not `pub` or `pub(crate)`). The public surface is the single `parse_uci_line` entry point; helpers are tested through it, not directly. This keeps the boundary minimal and avoids any "should these be `pub(crate)` for testing?" debate at code-review time.

**Exception — the `searchmoves` termination keyword set as data, not code.** §6.c relies on a fixed list of 11 keywords. To make a regression "I forgot one keyword" easily catchable, this set is extracted as a private constant:

```rust
const SEARCHMOVES_TERMINATORS: &[&str] = &[
    "ponder", "infinite",
    "wtime", "btime", "winc", "binc",
    "movestogo", "depth", "nodes", "mate", "movetime",
];
```

Name communicates the call-site purpose: `if SEARCHMOVES_TERMINATORS.contains(&token) { break; }`. A unit test `searchmoves_terminators_constant_matches_6a_table` asserts the constant has exactly 11 entries matching the §6.a table — a single check that fails if either source drifts. Doesn't violate the "test through the public surface" principle (it's data, not a function).

### 12. Tokens that look like reserved keywords inside `name`/`value`/`code` payloads

Spec §`setoption`:

> The substrings "value" and "name" should be avoided in <id> and <x> to allow unambiguous parsing,
> for example do not use <name> = "draw value".

The parser respects the spec's terminator rule literally: a `value` token after `name` always splits, even if the GUI ignored the spec's "should be avoided" guidance. For `setoption name foo value bar value baz`:

- `name` body collects until first `value`: `name = "foo"`.
- `value` body collects rest: `value = "bar value baz"` (subsequent `value` tokens are taken at face value as part of the body — there's no further keyword after `value`).

For `register name Stefan code 123 name Bob`:

- `name` body until next `code`: `name = "Stefan"`.
- `code` body until next `name`: `code = "123"`.
- `name` body until next `code` or end: `name = "Bob"` (overwrites).

Last-write-wins for repeated keywords. Reasonable; the spec is silent and a real GUI would never emit this.

### F. Property tests (proptest)

Three properties:

#### F.1. Whitespace insensitivity within a fixed token list

```rust
proptest! {
    #[test]
    fn prop_whitespace_does_not_change_command(
        tokens in prop::collection::vec(arbitrary_uci_token(), 1..8),
        whitespace_runs in prop::collection::vec(arbitrary_whitespace_run(), 8),
    ) {
        let baseline = tokens.join(" ");
        let with_varied_ws = interleave(&tokens, &whitespace_runs);
        prop_assert_eq!(parse_uci_line(&baseline), parse_uci_line(&with_varied_ws));
    }
}
```

`arbitrary_uci_token()` strategy: select from the union of:
- known keywords (`uci`, `debug`, …),
- typical option names (`Hash`, `Clear Hash` split into pieces),
- numeric strings (`5000`, `-300`, `0`, `abc`),
- typical UCI moves (`e2e4`, `e7e8q`, `0000`),
- arbitrary short ASCII identifiers.

`arbitrary_whitespace_run()` strategy: 1–4 chars from `' '`, `'\t'`, `'\n'`, `'\r'`.

`interleave` joins tokens with a randomly-chosen whitespace run from the strategy.

This pins the §2 tokenization invariant against any future split-rule regression.

#### F.2. Trailing junk after a no-arg command is ignored

```rust
proptest! {
    #[test]
    fn prop_trailing_junk_after_no_arg_command_ignored(
        cmd in prop::sample::select(&["uci", "isready", "ucinewgame", "stop", "ponderhit", "quit"]),
        junk in prop::collection::vec(arbitrary_unknown_token(), 0..4),
    ) {
        let baseline = parse_uci_line(cmd);
        let with_trailing = format!("{} {}", cmd, junk.join(" "));
        prop_assert_eq!(baseline, parse_uci_line(&with_trailing));
    }
}
```

`arbitrary_unknown_token()`: ASCII identifiers explicitly excluded from the keyword set (curated literal list to avoid generating `"uci"`, `"go"`, etc. by accident).

This pins §3 trailing-junk rule.

(There is no symmetric "leading unknown tokens" property because §3 specifies strict-first-token — that case is covered by groups B's anchor tests asserting `Unknown` for `"joho uci"` etc.)

#### F.3. Total function, no panics

```rust
proptest! {
    #[test]
    fn prop_parse_never_panics(line in "(?s).*") {
        let _ = parse_uci_line(&line);
    }
}
```

Cheap fuzz. The `(?s)` regex flag makes `.` match `\n` and `\r` too, so generated strings include line-endings and other control characters that might accidentally reach `parse_uci_line` (M2.C strips trailing `\n` via `stdin.lines()`, but a defensive line of bytes containing embedded newlines could still arrive). With proptest's default 256 cases and arbitrary Unicode generation, this catches any panic-shaped regression in tokenization or numeric parsing.

2. Add `pub mod uci;` and `pub use uci::{…};` to `src/lib.rs`.
3. Write the test suite in full per groups A–F above. Tests panic from `parse_uci_line`'s `todo!()` body — expected; tests are the contract.
4. Test-suite review loop. Convergence gates implementation.
5. Implement `parse_uci_line` and its private helpers (`parse_debug`, `parse_setoption`, `parse_register`, `parse_position`, `parse_go`, `parse_go_searchmoves`). All helpers `fn` (private) — see §11.5.
6. `cargo build --release`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. All must pass.
7. Final review loop.
8. `cargo llvm-cov --summary-only --lib` on `uci.rs`. Inspect for uncovered lines.
9. `cargo mutants --in-diff /tmp/m2.b.diff` (with `git add -N src/uci.rs` first — new file, would otherwise be invisible to `git diff HEAD`). Address survivors.
10. Update `CLAUDE.md` (status), `docs/roadmap.md` (M2.B ✓ + verification table), `docs/architecture.md` (UCI parser row).
11. Commit.

## Parallelization map

**Two sequential phases, modest in-phase parallelism.**

- **Phase α — type skeleton + tests + test review** (steps 1–4). Sequential — types and tests are tightly interdependent (tests reference enum variant names; reviewer reads both together).
- **Phase β — implementation** (steps 5–6). Can be parallelized across coding agents per command group:
  - Agent 1: `parse_uci_line` orchestrator + simple no-arg commands (`uci`, `isready`, `ucinewgame`, `stop`, `ponderhit`, `quit`).
  - Agent 2: `parse_debug`, `parse_setoption`, `parse_register`.
  - Agent 3: `parse_position`.
  - Agent 4: `parse_go` + `parse_go_searchmoves`.

  Each agent writes its function in isolation; the orchestrator dispatches by keyword. Shared state: none beyond the `Command` enum + helper types frozen at end of Phase α. Merge: trivial (each agent edits a non-overlapping function within `src/uci.rs`).

  *However*, the implementation is small enough (~250–350 lines for the parser body) that the parallelism overhead (4 agent spawns + merge synchronization) likely costs more than the sequential time. **Default to sequential implementation by a single agent** unless the size of any one sub-parser blows up beyond expectations during writing. The parallelization map is documented as available but not the default.

- **Phase γ — final review + mutants + coverage + docs + commit** (steps 7–11). Sequential per workflow.

The genuine parallelism opportunity at the end is `cargo llvm-cov` and `cargo mutants` running concurrently (independent reads of the build artifacts) — cheap to do, executed inline.

## Dependencies

This phase depends on:

- Nothing. M2.B is freestanding — it doesn't import `Position`, `Move`, `Fen`, etc. Pure string→AST.

This phase blocks:

- M2.C engine I/O loop, dispatch, state, threading. M2.C consumes `Command` and uses M2.A's `from_uci` to turn `position … moves` and `go searchmoves` raw strings into `Move` values against the current `Position`.

## Risks

- **Misreading the UCI spec on a subtle case.** Mitigated by testing against the spec's exact examples (`"setoption name Clear Hash"`, `"setoption name UCI_Opponent value GM 2800 human Gary Kasparov"`, `"register name Stefan MK code 4359874324"`). Any divergence shows up as test failure.
- **`Go` body parsing too lenient or too strict.** §6 documents the chosen rule. Real-world fastchess and other GUIs only emit well-formed `go` commands; the lenient handling is a courtesy. The risk is "fastchess emits something we map to None when we should have errored" — fastchess discoverable at M2.E. Cost to revisit is small (per-keyword tweak).
- **`position fen <…> moves <…>` collision.** Mitigated by §7 — `moves` cannot appear in any FEN field per the FEN spec.
- **Strict-lowercase on `debug`/`go` keywords.** UCI 2006 spec is ambiguous on case for command keywords. Every observed implementation emits lowercase. Same one-line relax (`make_ascii_lowercase` before keyword match) if discovered necessary at M2.E.
- **`Command::Unknown` is opaque — no diagnostic carried.** Mitigated by M2.C logging the original line via `info string` if `debug on`. M2.B's contract is "did this line parse as a recognized command, and if so what?" — diagnostic is a separate concern.
