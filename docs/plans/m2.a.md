# M2.A — UCI move encoding

## Context

M1 delivered the engine's full state model, legal move generator, perft validation, and benchmark harness. M2 builds the UCI surface around that core; M2.A is the first sub-phase — translation between our internal `Move` type and the UCI long-algebraic wire format.

Two functions:

- `Move::to_uci(self) -> String` — pure conversion. Produces the byte sequence that goes on the wire (e.g. into a `bestmove e2e4` line).
- `Move::from_uci(s: &str, pos: &Position) -> Result<Move, UciMoveError>` — parses a UCI move string in the context of the position the move applies to. Needed for `position … moves m1 m2 …` and `go searchmoves m1 m2 …`.

### Binds no ADRs

The UCI spec at `docs/reference/uci-protocol-2006.txt` §"Move format" is fully prescriptive for the wire format. No new architectural choices; no ADR drafted in this plan.

### Research skip — justified

No external research was needed:
- UCI move format is one short paragraph in the in-tree spec.
- The decisions baked into this plan (null-move handling, case sensitivity, generate-and-match parsing, error type granularity) are all routine engineering choices, not contested in the wider engine community.
- M2 prior-art (`docs/research/m2-uci-threading.md`, `docs/research/m2-tournament-harness.md`) covers the protocol-level questions that bind later sub-phases (M2.C, M2.E); none of those touch wire-format encoding.

### What this phase delivers

1. **`UciMoveError`** — error enum in `src/mov.rs` with four variants.
2. **`Move::to_uci(self) -> String`** — method in `src/mov.rs`.
3. **`Move::from_uci(s: &str, pos: &Position) -> Result<Move, UciMoveError>`** — method in `src/mov.rs`.
4. **Tests** — anchor unit tests, negative-parse tests, round-trip on the existing `CASES` corpus, round-trip on every legal move from the canonical-6 starting positions, plus a property test.
5. **Crate-root re-export** — `pub use mov::UciMoveError;` in `src/lib.rs`.
6. **Documentation** — `docs/architecture.md` Move-API row gets a new line; `CLAUDE.md` + `docs/roadmap.md` status updates after commit.

### Not in M2.A

- A `Move::NULL` sentinel or any internal representation of the null move. Deferred until null-move pruning (M5).
- Any changes to the existing `Display`/`Debug` impls on `Move`. `to_uci` is added alongside, not replacing.
- Changes to `divide`'s use of `mv.to_string()` for UCI sorting (unaffected — `to_uci` and `to_string` produce the same bytes).
- Benchmarks. UCI move parsing is per `position` command, not in any hot path; a microbenchmark would measure noise. Justified skip — recorded here.

## Decisions baked into this plan

### 1. `to_uci` is a thin wrapper around `Display`

```rust
impl Move {
    pub fn to_uci(self) -> String {
        self.to_string()
    }
}
```

Two reasons not to restructure:

- `Display::fmt` is already correct (M1.E lands it; tested by existing `move_display_*` tests in `src/mov.rs`'s test module).
- `format!("{mv}")` and `write!(out, "{mv}")` stay zero-alloc when piped to a writer; only the `String`-returning `to_uci` allocates.

The public surface gains `to_uci(self) -> String` as the canonical name (matches the roadmap signature and reads better at call sites like `writeln!(out, "bestmove {}", mv.to_uci())`). `Display` remains available unchanged.

**Anchor test discipline.** Both `Display` and `to_uci` would be silently wrong in symmetric ways if we relied only on round-trip tests. The test plan below pins specific literal outputs (`e2e4`, `e1g1`, `e7e8q`, etc.) precisely to catch a symmetric bug.

### 2. `from_uci` strategy: generate-and-match

The implementation generates all legal moves for `pos` and searches for one whose `(from, to, promotion_kind)` matches the parsed string. Any match found is returned; otherwise `IllegalForPosition`.

Why not construct the `Move` directly from the string:

- Direct construction needs ~150 lines of disambiguation logic — king-step vs. castle (depends on `from`/`to` distance plus castling rights and check-status), pawn diagonal vs. EP (depends on `ep_target` plus piece occupancy on `to`), single- vs. double-push (depends on rank of `from`), `Capture` vs. `Quiet` (depends on `pos.piece_at(to)`), promo-capture vs. plain promo (same).
- Direct construction can produce a syntactically valid `Move` that is illegal in the position (moves into check, ignores pins) — to validate, you have to compare against generated moves anyway.
- Generate-and-match composes both steps into one. It is naturally pin-aware, EP-discovery-aware, and castling-rights-aware because `generate_moves` already is.
- Cost: `generate_moves` is on the order of microseconds. UCI move parsing happens per `position … moves` line and per `searchmoves` token — never inside the search inner loop. The cost is irrelevant.

Algorithm:

```rust
pub fn from_uci(s: &str, pos: &Position) -> Result<Move, UciMoveError> {
    // 1. Reject the null move explicitly. Done before any byte slicing —
    //    `0000` is fixed-length ASCII so equality-check is safe.
    if s == "0000" {
        return Err(UciMoveError::NullMove);
    }

    // 2. ASCII-only guard. Without this, the `&s[0..2]` / `&s[2..4]`
    //    slices below can panic on non-char-boundary indices for a
    //    5-byte string like `"e2e°"` (4 ASCII bytes + one 2-byte UTF-8
    //    char that splits at byte 4). Length-only checks on `bytes.len()`
    //    are not sufficient. Reject any non-ASCII as `Malformed`.
    if !s.is_ascii() {
        return Err(UciMoveError::Malformed);
    }

    // 3. Length: only 4 or 5 are accepted.
    let bytes = s.as_bytes();
    if bytes.len() != 4 && bytes.len() != 5 {
        return Err(UciMoveError::Malformed);
    }

    // 4. Parse the squares first, then the promo letter. Order matters
    //    for error-categorization: a malformed square dominates a
    //    malformed promo letter. E.g. `"e2 e4"` has length 5 but
    //    byte-2 is space, so `Square::parse_uci("&s[2..4]") = " e"`
    //    rejects with `Malformed` BEFORE byte 4 (the promo) is examined.
    let from = Square::parse_uci(&s[0..2]).ok_or(UciMoveError::Malformed)?;
    let to   = Square::parse_uci(&s[2..4]).ok_or(UciMoveError::Malformed)?;
    let promo: Option<PieceKind> = if bytes.len() == 5 {
        match bytes[4] {
            b'n' => Some(PieceKind::Knight),
            b'b' => Some(PieceKind::Bishop),
            b'r' => Some(PieceKind::Rook),
            b'q' => Some(PieceKind::Queen),
            // Anything else (including uppercase NBRQ, p/k, digits,
            // punctuation) is an illegal promo piece. See §4.
            _ => return Err(UciMoveError::IllegalPromotionPiece),
        }
    } else {
        None
    };

    // 5. Generate-and-match. `MoveList` may be empty (checkmate /
    //    stalemate) — the iterator's `find` correctly returns None then.
    let mut moves = MoveList::new();
    generate_moves(pos, &mut moves);
    moves
        .as_slice()
        .iter()
        .copied()
        .find(|mv| {
            mv.from_square() == from
                && mv.to_square() == to
                && mv.promotion_kind() == promo
        })
        .ok_or(UciMoveError::IllegalForPosition)
}
```

#### Why `(from, to, promotion_kind)` uniquely identifies a legal move

The generate-and-match strategy is sound only if `generate_moves` never emits two legal moves with identical `(from, to, promotion_kind)`. The argument from chess-rules first principles:

**Non-promotion moves.** The six non-promotion `MoveFlag` variants (Quiet, DoublePush, Capture, EnPassant, KingCastle, QueenCastle) are pairwise mutually exclusive for a given (from, to) pair:

- *Quiet vs. Capture* differ on the occupancy of `to` by an enemy piece. A square is either occupied by an enemy or it isn't — not both.
- *DoublePush vs. Quiet (single push)* differ on the rank-distance between from and to (2 vs. 1). One pair of squares has one rank-distance.
- *KingCastle vs. quiet king step* differ on the file-distance (2 vs. 1). Standard chess kings only step one square non-castling, so a (from, to) with file-distance 2 from the king's home square exists only as castling.
- *EnPassant vs. Capture* differ on whether the captured pawn sits on `to` or one rank back. For pawn diagonal moves to a square, EP is legal only when the EP target is set to that square; in that case, `to` itself is empty (otherwise the prior double-push to the rank that set the EP target would have been blocked), so a regular Capture to that exact square cannot coexist.
- *KingCastle vs. QueenCastle* differ on the destination file (g vs. c) — different `to`.

**Promotion moves.** The eight promotion variants split into four `*Promo` (no capture) and four `*PromoCapture` (with capture), differentiated by promo kind (knight/bishop/rook/queen). The match key is `promotion_kind` only — so `*Promo` and `*PromoCapture` of the same kind would collapse onto the same key. They can't coexist for the same (from, to) for the same reason as Quiet vs. Capture: `to` is either occupied by an enemy or it isn't.

So for any chess-legal position, every (from, to, promo) triple maps to at most one legal move. The plan codifies this with `prop_at_most_one_legal_move_per_from_to_promo` (see §Tests) — if a future movegen change ever violates the invariant, the property test catches it before `from_uci` silently picks the wrong move.

### 3. Null move `0000` → reject as `UciMoveError::NullMove`

Per UCI spec, `0000` is described only as engine→GUI (post-search "I have nothing to play" signal). We have no internal `Move::NULL` to round-trip into, and our random mover (M2.D) will never need to emit one — when no legal moves exist, M2.D either signals stalemate or the position would be illegal anyway.

A separate variant (rather than rolling into `Malformed`) lets M2.B/C distinguish "the GUI did something the spec doesn't authorize on this channel" from "the GUI sent garbage." Cheap to do; no cost to revisit if/when null-move pruning lands and we add `Move::NULL`.

### 4. Strict case-sensitivity on input — committed

Files must be lowercase a–h (already enforced by `Square::parse_uci`). Promo letter must be lowercase n/b/r/q. Uppercase rejects with `IllegalPromotionPiece` (for the promo letter) or `Malformed` (for the squares — `Square::parse_uci` already rejects).

Spec note: UCI 2006 §"Move format" gives `e7e8q` as an example but does not normatively commit to lowercase. We choose strict-by-default. Stockfish, fastchess, every modern UCI GUI emits lowercase. If we encounter a real-world tool emitting uppercase, the relax is mechanically trivial: change `match bytes[4]` to `match bytes[4] | 0x20` (one line, no branch — bit 0x20 is the ASCII case bit). The `IllegalPromotionPiece` variant explicitly named in §5 makes the relax site discoverable.

This is committed for M2.A, not deferred to "M2.E discovers we need to relax."

### 5. Error type: four variants

```rust
#[derive(Copy, Clone, PartialEq, Eq, Hash, Debug)]
pub enum UciMoveError {
    /// Length not 4 or 5; or one of the square substrings is not a valid
    /// algebraic square (`Square::parse_uci` rejected). Catches the bulk
    /// of garbage input.
    Malformed,
    /// Length is 5 but the promo letter is not one of `n`, `b`, `r`, `q`.
    /// (Pawn `p` and king `k` are syntactically possible SAN piece letters
    /// but illegal as promotion targets per FIDE rules.)
    IllegalPromotionPiece,
    /// The literal string `"0000"`.
    NullMove,
    /// The string parsed cleanly but no legal move in `pos` matches the
    /// requested `(from, to, promotion_kind)` triple. Subsumes:
    ///   - empty `from` square,
    ///   - opposite-color piece on `from`,
    ///   - target unreachable from `from` (any reason — blocked, off-board
    ///     for this piece type, would-leave-king-in-check, missing castling
    ///     rights, missing EP target, etc.),
    ///   - promo letter present where no promotion is legal,
    ///   - promo letter absent where one is required.
    IllegalForPosition,
}

impl std::fmt::Display for UciMoveError { /* short human-readable */ }
impl std::error::Error for UciMoveError {}
```

The four buckets are enough to give M2.B/C readable diagnostics. Splitting `IllegalForPosition` into finer sub-causes would require duplicating chunks of `generate_moves`'s logic for diagnostic purposes only — premature.

### 6. No `Move::NULL` sentinel

See §3. A `Move` value with `from == to` and `MoveFlag::Quiet` is currently representable but produced by no public constructor and emitted by no movegen path. Leaving it that way; null-move pruning will introduce `Move::NULL` cleanly when M5 needs it.

### 7. File layout

All code (impl + tests) lives in `src/mov.rs`. The file is currently 1923 lines; M2.A adds ~150 lines of impl + ~250 lines of tests. Total ~2300 lines. Same precedent as `position.rs` (1216) and `fen.rs` (1270) — single-file modules in this project run up to ~2k lines before considering a split.

A dedicated `src/uci/` directory will appear in M2.B for the command parser; M2.C onward layers in there. Move encoding stays with `Move` for cohesion.

## Public API

```rust
// src/mov.rs

#[derive(Copy, Clone, PartialEq, Eq, Hash, Debug)]
pub enum UciMoveError {
    Malformed,
    IllegalPromotionPiece,
    NullMove,
    IllegalForPosition,
}

impl std::fmt::Display for UciMoveError { /* ... */ }
impl std::error::Error for UciMoveError {}

impl Move {
    /// UCI long-algebraic encoding of this move. Examples: `"e2e4"`,
    /// `"e1g1"` (king-side castle), `"e7e8q"` (queen promotion).
    /// Produces identical bytes to the `Display` impl on `Move`;
    /// `Display::fmt` is the canonical writer (zero-alloc when piped to
    /// a `Write`), and this method exists for self-documenting call
    /// sites in M2 protocol code.
    pub fn to_uci(self) -> String;

    /// Parse a UCI move string in the context of `pos`. Returns
    /// `IllegalForPosition` if no legal move in `pos` matches the
    /// requested `(from, to, promotion_kind)` triple.
    ///
    /// Rejects the null move (`"0000"`) with `NullMove`.
    /// Rejects strings with length other than 4 or 5, or with malformed
    /// square substrings, with `Malformed`. Rejects 5-char strings whose
    /// promo letter is not one of `n`/`b`/`r`/`q` with
    /// `IllegalPromotionPiece`.
    pub fn from_uci(s: &str, pos: &Position) -> Result<Move, UciMoveError>;
}
```

### Round-trip tests

`from_uci(to_uci(mv), pos) == Ok(mv)` for every move that arises during play. Two scopes:

- **`round_trip_curated_cases`** — for each entry in `CASES`, parse `entry.before`, round-trip `entry.mv`. 30 cases.
- **`round_trip_canonical_six_d1`** — for each canonical-6 FEN, generate all legal moves at depth 1 and round-trip each. ~20–48 moves per position; ~150 moves total.
- **`round_trip_canonical_six_d2_proptest`** — property test: pick a canonical-6 starting position, apply a random sequence of 0–4 random legal moves, then round-trip every legal move from the resulting position. Default 256 cases, deterministic seed via `proptest`'s default RNG (matches the M1.F precedent in `prop_no_legal_move_leaves_us_in_check`).

The proptest is the only test that goes deeper than D1 — the D1 enumeration plus the curated `CASES` cover every flag, but the proptest exercises positions that arise in actual play (including positions with EP targets set, mid-game castling rights, mid-game promotion candidates).

### Property test on uniqueness

`prop_at_most_one_legal_move_per_from_to_promo` — uses the same random-walk strategy as `round_trip_canonical_six_d2_proptest` (pick a canonical-6 seed FEN, apply 0–4 random legal moves, then test the invariant on the reached position). For the reached position, group `generate_moves`'s output by `(from, to, promotion_kind)` and assert every group has size 1.

Why the same strategy and not just the six fixed seed FENs: bugs that violate the invariant are most likely to live in mid-game positions with EP targets set, mid-castling rights, and pawn-promotion candidates — not in the six well-trodden seed FENs whose move lists every engine has stared at. Reusing the random-walk strategy explores ~256 mid-game positions per run, materially raising the bar for bugs to slip through.

This pins the invariant that `from_uci`'s generate-and-match strategy depends on. If a future movegen change ever emits two legal moves with the same `(from, to, promo)` — say, a misclassified EP and capture coexisting — `from_uci` would silently pick whichever comes first, and this test catches the regression.

Does this property cover what the unit tests cover? It pins the *uniqueness invariant*, not the *correctness* of any specific match — the unit anchor tests (e.g. `from_uci_castle_kingside_white`) still document that a specific `(from, to, promotion_kind)` resolves to a specific flag.

## Risks

- **Generate-and-match is wrong if `generate_moves` ever emits two legal moves with identical `(from, to, promotion_kind)`.** Mitigated by `prop_at_most_one_legal_move_per_from_to_promo`. If a future variant or NNUE pre-pass changes this, the property test catches it before `from_uci` silently picks the wrong move.
- **Strict case-sensitivity may bite if a real GUI emits uppercase.** Mitigated by being a one-line relax. Caught at M2.E (fastchess integration) if it happens. The risk is "M2.E discovers we need to relax"; the cost is tiny.
- **Null-move rejection may bite if a future UCI-derived protocol uses `0000` for input.** None known today (UCI 2006, UCI 1.0, MultiPV extensions). Mitigated by the explicit `NullMove` variant making the relax a one-line change.
