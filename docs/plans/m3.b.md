# M3.B — Game-history + draw-detection plumbing

Pure plumbing phase. Wires the data structures and helper functions that M3.C's negamax will consume for repetition + 50-move draw detection. Keeps the production search at depth-1 GreedyMover (no behavioral change in self-play). No new ADR.

## 0. Goals

- `Engine::game_history: Vec<u64>` populated by `handle_position` and `handle_ucinewgame`; one entry per position observed since the last "fresh game" boundary, including the current position.
- `SearchContext::history: Vec<u64>` cloned at `go`-start, available for M3.C's negamax to push/pop while recursing.
- Helper functions in `src/search.rs`: `is_repetition` (single occurrence in search stack counts as draw, per CPW) and `is_fifty_move_draw` (`halfmove_clock >= 100`).
- No production-search consumer yet — M3.C alpha-beta is the first consumer. Helpers stay `pub(crate)` and are exercised by unit tests only.

## 1. Out of scope

- Negamax / alpha-beta / iterative deepening — all M3.C+.
- Any change to `GreedyMover`. Depth-1 doesn't recurse, so neither helper is called from production search at M3.B.
- Threefold-repetition detection from game history (FIDE 9.2 — *two* prior occurrences). Engine-side draw reasoning: a single occurrence in the search stack is the practical rule per CPW; the FIDE three-fold-claim rule is what the GUI/tournament adjudicator enforces. We don't need to draw the line ourselves.
- 75-move auto-draw (FIDE 9.6.2) — once the 50-move-claim threshold is crossed at 100 plies, the engine treats the position as drawn for search reasoning. Beyond that, the game isn't reachable in well-played chess and the deterministic auto-draw at 150 plies adds nothing to engine strength.
- Stalemate / insufficient material — already handled (movegen returns no moves; `evaluate` returns 0 for KvK/KvN/KvB).

## 3. `Engine::game_history` invariant

**Invariant.** `engine.game_history.last() == Some(&engine.position.zobrist())` holds after every command handler returns.

**Concretely:**

- `Engine::new(stdout, search)` — `position = starting_position()`; `game_history = vec![position.zobrist()]`. Single entry: the start.
- `handle_ucinewgame` — `position = starting_position()`; `game_history = vec![position.zobrist()]`. Same single-entry shape as `new()`.
- `handle_position(spec, moves)`:
  1. Build `base` per existing logic. On FEN parse error, emit info string, **leave both `self.position` and `self.game_history` untouched**, return.
  2. Initialize a working `pos = base` and a working `hist = vec![base.zobrist()]`.
  3. For each `mv_str` in `moves`:
     - On `Move::from_uci` error, emit info string, set `self.position = base`, set `self.game_history = vec![base.zobrist()]`, return.
     - On success, `pos.make_move(mv)` then `hist.push(pos.zobrist())`.
  4. Commit: `self.position = pos`; `self.game_history = hist`.
- `handle_go`:
  - `SearchContext::history` = `self.game_history.clone()`. The clone is intentional — M3.C will mutate it (push/pop on make/unmake inside negamax). Keeping the engine's copy pristine means a subsequent `go` (e.g. after `stop`) still sees the unchanged history.

**Why include the current position.** Two reasons:

1. The repetition test compares the current position against priors. Putting the current entry at `history.last()` and comparing against earlier entries is the standard idiom — eliminates an off-by-one ambiguity at the call site.
2. M3.C's negamax push-on-make / pop-on-unmake protocol falls out naturally: the per-ply entry on the stack is "the position *at* this ply", and the leaf check compares `history.last()` against priors.

## 4. `SearchContext::history`

**Type.** `pub history: Vec<u64>`. Owned, not borrowed: M3.C needs `&mut Vec<u64>` for push/pop, and threading a borrow through the per-`go` worker conflicts with the existing `Send` bound on the search worker (the context already moves into the worker thread per ADR-0011).

**Construction.** `handle_go` builds the `SearchContext` with `history: self.game_history.clone()`.

**Test seams.** All existing `SearchContext { ... }` literals in `src/search.rs::tests` and `src/engine.rs::tests` need a `history: Vec::new()` (or a representative value where the test matters) to keep compiling. M3.C will replace `Vec::new()` with the real history at point of use; for M3.B the helpers operate on `&[u64]` so empty is fine for tests that don't exercise them.

## 5. Helper functions (free functions in `src/search.rs`)

### 5.1 `is_repetition`

```rust
/// Single-occurrence-in-search repetition test.
///
/// `history` is the full Zobrist trajectory ending with the current
/// position (i.e. `history.last()` is the position to test). Returns
/// `true` if any earlier entry equals `history.last()`, walking back at
/// most `min(halfmove_clock, history.len() - 1)` plies in 2-ply steps.
///
/// Per CPW "Repetitions": a single match inside the search counts as a
/// draw. The FIDE 9.2 three-fold-claim rule is enforced by the GUI /
/// tournament adjudicator, not the engine. The 2-ply step exploits the
/// fact that only same-side-to-move positions can repeat (the Zobrist
/// turn key flips on every ply). The `halfmove_clock` cap is the
/// irreversible-move stop: any pawn move or capture zeros the clock and
/// severs the repetition chain. The `history.len() - 1` cap is the
/// safety bound — `halfmove_clock` is loaded from FEN and may exceed
/// the history depth the engine has actually observed.
pub(crate) fn is_repetition(history: &[u64], halfmove_clock: u8) -> bool {
    let Some((&current, prior)) = history.split_last() else {
        return false;
    };
    let max_back = (halfmove_clock as usize).min(prior.len());
    for i in (2..=max_back).step_by(2) {
        if prior[prior.len() - i] == current {
            return true;
        }
    }
    false
}
```

**Why `split_last`.** Empty history returns `false` (no current → nothing to compare); avoids underflow on `prior.len() - i`.

**Why iterate `i = 2, 4, 6, ...` rather than 1, 2, 3, ...**. Only same-side-to-move positions can match: the side-to-move flips on every ply. A 1-ply walk would compare opposite-color positions and could never return true on a real repetition (the Zobrist turn key differs).

**Why cap at `halfmove_clock`.** Any pawn move or capture is irreversible. The position before such a move can never repeat after it (a piece is gone or a pawn is on a different square). `halfmove_clock` resets to 0 on those moves, so its current value is exactly the number of plies since the last irreversible move — the maximum reachable repetition window.

**Bounding by `prior.len()`.** `halfmove_clock` is loaded from FEN and may exceed the actual history depth (the engine doesn't have history before its first `position` command). Capping at `prior.len()` keeps the index within bounds.

### 5.2 `is_fifty_move_draw`

```rust
/// 50-move rule: returns true at `halfmove_clock >= 100`.
///
/// 100 plies = 50 full moves without a pawn move or capture; this is the
/// FIDE 9.3 "claimable" threshold. The engine treats a claimable draw as
/// drawn for search reasoning — strictly speaking, a tournament arbiter
/// only adjudicates after a claim, but a side that wants the draw can
/// always claim it, so the position is effectively a draw at the search
/// horizon. The 75-move auto-draw (FIDE 9.6.2, 150 plies) is not
/// separately handled; we cross the claim threshold first.
pub(crate) fn is_fifty_move_draw(halfmove_clock: u8) -> bool {
    halfmove_clock >= 100
}
```

**Why exactly 100.** FIDE 9.3.2: "the last 50 moves by each player have been completed without the movement of any pawn and without any capture." 50 moves by each player = 100 plies. The clock counts plies (M1.B convention) and is incremented on every non-pawn non-capture move; resets to 0 on a pawn move or capture. The trigger is `>= 100`, not `> 100` — at exactly 100, the threshold is reached and a side can claim the draw.

**Why a function and not just inline.** One-liner today, but: (a) symmetric with `is_repetition` (call sites consistent), (b) named contract, (c) M3.C/M3.D will call from multiple sites in negamax/qsearch; keeping the threshold as a single named constant prevents a future "let's use 99" off-by-one drift.

### 6.1 `src/search.rs::tests` — helper unit tests

| Test name | Asserts |
|---|---|
| `is_fifty_move_draw_threshold_at_100` | `false` for 0, 1, 50, 99; `true` for 100, 101, 200, 255. Pins exact `>= 100` boundary (catches `> 100` mutant). |
| `is_repetition_empty_history_returns_false` | `is_repetition(&[], 0)` → `false`; `is_repetition(&[], 50)` → `false`. |
| `is_repetition_single_entry_returns_false` | `is_repetition(&[0xABC], 50)` → `false`. No prior to compare. |
| `is_repetition_no_match_within_window_returns_false` | History `[0x1, 0x2, 0x3, 0x4]` (last differs from all priors); halfmove=4 → `false`. |
| `is_repetition_match_at_2_ply_returns_true` | History `[X, Y, X]`, halfmove=2 → `true`. Most basic case. Catches `i = 0` start mutant (would match current against itself). |
| `is_repetition_match_at_4_ply_returns_true` | History `[X, Y, Z, W, X]`, halfmove=4 → `true`. Pins the loop's second iteration. |
| `is_repetition_even_distance_match_returns_true` | History `[X, A, B, C, X]`, halfmove=4 → `true`. The match is at distance 4 (even). Companion to the next test. |
| `is_repetition_odd_distance_match_returns_false` | History `[Y, X, A, B, X]` — current X at index 4, only prior X at index 1 (distance = 4 − 1 = 3, odd). halfmove=3 → `false`. The 2-ply step must skip odd distances; a `step_by(1)` mutant or a `(2..=max_back) → (1..=max_back)` start-mutant would falsely return `true` here. |
| `is_repetition_capped_by_halfmove_clock` | History `[X, Y, Z, W, X]` (5 entries), halfmove=2 → `false`. The X at distance 4 must be invisible because halfmove=2 caps the search at 2. Catches removal of the halfmove-side cap (`max_back = prior.len()` mutant): under that mutation max_back becomes 4, the loop reaches i=4, and `prior[0] == X` returns true — test expects false. |
| `is_repetition_no_panic_when_halfmove_exceeds_history_match` | History `[X, Y, X]` (prior.len()=2), halfmove=200 → `true`. Pins the `min(halfmove, prior.len())` safety bound: an unsafe `prior[prior.len() - i]` at `i=4` would be index `-2usize` and panic. |
| `is_repetition_no_panic_when_halfmove_exceeds_history_no_match` | History `[X, Y, Z]` (prior.len()=2), halfmove=200 → `false`. Companion to the previous: a buggy `max_back = halfmove as usize` (no cap-by-length) would panic on the second iteration (`i=4`, `prior.len() - 4` underflows). Together these two tests pin both directions of the length cap. |
| `is_repetition_halfmove_zero_returns_false` | History `[X, Y, X]`, halfmove=0 → `false`. Just-made-irreversible-move case (no repetition possible after a pawn move or capture). |

**Mutants this set is intended to catch.**

- **`>= 100` boundary in `is_fifty_move_draw`** — row 1 pins both 99 and 100, catching `> 100` and `>= 99` mutants.
- **`step_by(2)` step size** — rows 7 + 8 (even-distance match returns true, odd-distance match returns false). A `step_by(1)` mutant or a `(2..=max_back) → (1..=max_back)` start-mutant fires `true` on row 8's odd-distance fixture; test expects `false`.
- **Loop start `i = 2`** — row 5 catches `(2..=) → (0..=)`: at i=0 the index `prior[prior.len() - 0] = prior[prior.len()]` is out of bounds and panics, failing the test (the catch is via panic, not via wrong return). Row 8 catches `(2..=) → (1..=)` (the more likely cargo-mutants candidate, smaller numeric perturbation): at i=3 the mutant matches the prior X at index 1 returning true, test expects false.
- **Cap-by-`halfmove`** — row 9 catches `max_back = prior.len()` (i.e. drop the `.min(halfmove…)` factor): under the mutation max_back becomes 4, finds the X at distance 4, returns true; test expects false.
- **Cap-by-`prior.len()`** — row 11 catches `max_back = halfmove as usize` (drop the `.min(prior.len())` factor): with halfmove=200 and prior.len()=2, the loop reaches i=4 where `prior[2-4]` underflows to an enormous usize and panics. Row 10 is the no-false-negative companion: it returns true under both real and mutated impls (the match at i=2 fires before any out-of-bounds index), so it's a sanity check on the cap, not a mutant-catching test on its own.
- **Empty / single-entry early returns** — row 2 (empty) and row 3 (single entry) catch mutants on the `split_last` arm and the empty-loop guards.
- **`>=` vs `==` in `halfmove_zero` early return** — row 12 (halfmove=0) catches an off-by-one in the `max_back` clamp where 0 might be treated as "go forever" (e.g. via integer underflow in a buggy refactor).

## 7. Test fakes

`HistoryCapturingFake` lives in `src/engine.rs::tests` alongside the existing `InfoEmittingFake` (same shape, same module placement convention as M2.C/M2.D test fakes):

```rust
struct HistoryCapturingFake {
    captured: Arc<Mutex<Vec<u64>>>,
}
impl Search for HistoryCapturingFake {
    fn go(&mut self, _pos: &Position, ctx: &SearchContext, _sink: &dyn Fn(&str)) -> SearchResult {
        *self.captured.lock().unwrap() = ctx.history.clone();
        SearchResult::default()
    }
}
```

The two `handle_go` tests use this fake as follows:

- `handle_go_clones_history_into_search_context`: drive position+go, then read the captured buffer; assert it equals the engine's `game_history` at the moment `go` was issued. Pins "ctx.history is built from engine.game_history." This is the only test that's location-coupled to `SearchContext::history` — it reads `ctx.history` from inside the fake.
- `handle_go_does_not_consume_engine_history`: drive position+go, then assert `engine.game_history == expected` where `expected` is the trajectory's known correct value (computed from the test's known move list, e.g. `vec![startpos.zobrist(), post_e2e4.zobrist(), post_e7e5.zobrist()]`). Pins "handle_go does not drain engine.game_history into the context." A regression where `handle_go` does `std::mem::take(&mut self.game_history)` would leave `engine.game_history` empty after `run` returns, failing the assertion. This test is **location-agnostic**: no `ctx.history` read inside the fake — it could use `GreedyMover` directly. The existing channel-based `drive` helper queues all commands then runs `engine.run`; `engine.run` returns only after `Quit` is dispatched and `handle_quit` joins the worker, so the post-run assertion sees a quiesced engine. We extend `drive` to a `drive_with_history` variant that returns `engine.game_history` after `run` returns.

Note: `Search::go` currently takes `ctx: &SearchContext` (immutable borrow). M3.C will need to either change this to `&mut`, wrap `history` in a `Cell`/`RefCell`, or thread `history` as a separate `&mut Vec<u64>` parameter — see §11. For M3.B, the immutable-borrow shape is fine because nothing mutates `ctx.history` yet.

## 8. Order of operations (single coder slice)

1. Add `history: Vec<u64>` field to `SearchContext` (default-empty in tests via `Vec::new()`); update the 8 existing test-site literals listed in §6.3.
2. Add `is_repetition` and `is_fifty_move_draw` free functions in `src/search.rs` plus their unit tests (§6.1).
3. Add `game_history: Vec<u64>` field to `Engine`; initialize in `new()` as `vec![Position::starting_position().zobrist()]`.
4. Update `handle_ucinewgame` to set `self.game_history = vec![Position::starting_position().zobrist()]` after the position reset.
5. Update `handle_position` per §3, with the paired-state invariant explicit:
   - **FEN parse error path**: return early *before* touching `self.game_history` (preserves prior history alongside prior position).
   - **Move-clause path** (success or error): build a fresh local `let mut hist = vec![base.zobrist()];` from the *new* base; do **not** start from `self.game_history`. On move-error, set `self.game_history = vec![base.zobrist()]` (single entry, the new base — not `vec![]`, not the prior `self.game_history`, not the partially-built `hist`). On success, commit `self.game_history = hist` alongside `self.position = pos`.
6. Update `handle_go` to clone `self.game_history` into the new `SearchContext::history` field — `history: self.game_history.clone()`. Do **not** `take`, do **not** drain.
7. Add the engine invariant + lifecycle tests (§6.2), in particular the new `handle_position_second_command_move_error_resets_to_new_base_history` and `handle_go_does_not_consume_engine_history` tests.
8. Add `HistoryCapturingFake` fake; tests for the `handle_go` clone semantics.
9. `cargo test`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt`. All must pass.

## 9. Parallelization map

**One coder slice — sequential.**

The split between `src/search.rs` (helpers + SearchContext field) and `src/engine.rs` (game_history + handlers) is technically independent at the source-code level, but:

- The `SearchContext::history` field addition forces every test-site literal to update across both files in lockstep — splitting the slice would create a transient broken-build window between coder agents.
- Total code: ~80 lines of impl + ~150 lines of tests = ~230 LOC unit. Well under the 500-LOC parallelization break-even.
- The §3 paired-state invariant (Engine.game_history.last() == position.zobrist() under all error paths) is the one piece of subtlety here. It's not "novel" in the M3.A sense (no new helper to invent), but it's a *paired-state* invariant applied for the first time, and the workflow's calibration log notes Sonnet has occasionally drifted on "discipline application across modules." Mitigation: §8 step 5 spells out the exact code shape for each error path (FEN-error returns early, move-error writes `vec![base.zobrist()]` from the new base) so the coder doesn't have to derive it.

A two-coder split would save ~5 minutes of wall time at best, costs orchestration overhead, and risks the broken-build window. Single coder slice is the right call. **No `model: opus` flag** per the workflow's "When to flag a coder slice for Opus" criteria — this slice involves no tricky lifetimes (`Vec<u64>` is a vanilla owned collection), no novel invariants requiring invention (the invariant is stated explicitly with code shape in §8), and no parallel-precedent application risk (no existing helper to mirror — `Engine::position` is the closest analogue and it's just a single field). The default Sonnet tier should handle this cleanly given the prescriptive §8.

## 11. Risks and gotchas

- **`Position::zobrist()` is `const fn`** (verified via `grep`); the field is private but the accessor is public. No API change.
- **`SearchContext` is `Clone`** (already required by M2.C for ownership transfer to the worker). Adding `Vec<u64>` keeps it Clone — `Vec` impls Clone. The clone is performed once per `go` (in `handle_go` before spawn); the worker holds its own copy. No `Arc`-vs-clone tradeoff to debate at this scale.
- **Test seams.** Adding a field to `SearchContext` breaks every literal construction. Mitigation: add `history: Vec::new()` to each literal listed in §6.3. Mechanical search-and-replace; chess-coder verification step (`cargo test`) catches any miss.
- **No info-line emission.** Helpers are pure functions, not search; nothing emits `info` output. No UCI-protocol surface change.
- **GreedyMover unchanged.** D38 (E38) self-play test still pins `seed=0` / `ply=116` / `f2f3` — with no behavioral change to the search, that test must still pass.
- **`SearchContext::history` location is a deferred M3.C decision.** M3.C's negamax will need `push`/`pop` on `history` per make/unmake during recursion (per `docs/research/m3-search-basics.md` §8). `Search::go` currently takes `ctx: &SearchContext` (immutable borrow), which precludes `&mut history` mutation in place. M3.C will face one of three choices: (a) change the trait signature to `&mut SearchContext`, (b) wrap `history` in a `Cell`/`RefCell`, or (c) move `history` out of `SearchContext` and thread it as a separate `&mut Vec<u64>` parameter to negamax (with the spawn-time copy still owned by the worker thread's stack). M3.B does **not** decide between these. Among the §6.2 tests, only `handle_go_clones_history_into_search_context` (1 test) is location-coupled to `SearchContext::history`; the other (`handle_go_does_not_consume_engine_history`) is location-agnostic. So M3.C's relocation work touches one test, not two. The `is_repetition` / `is_fifty_move_draw` helpers take `&[u64]` / `u8` and don't care where the data lives.
