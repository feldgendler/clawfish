# M6.F — Tier-1 HCE features (plan)

Sixth M6 sub-phase. Adds **three Tier-1 HCE features** — (1) knight/bishop
**outposts**, (2) **rook on open/semi-open file**, (3) **endgame
draw-scaling** — *before* the M6.I joint Texel pass so they co-calibrate in
the one tune (the "extend then tune" law — Texel cannot discover absent
features). **Shipped score-neutral from the start**: all new additive weights
zeroed + the endgame scale ≡ identity ⇒ `evaluate` byte-identical to `M6.E`.
The M6.C/M6.D/M6.E inert-landing disposition: no SPRT, no screen ladder.

- Research: [`docs/research/m6-remaining-hce-features.md`](../research/m6-remaining-hce-features.md)
  (roadmap-designated binding note; Priority-1 list).
- ADR: [`docs/decisions/0034-tier1-hce-features.md`](../decisions/0034-tier1-hce-features.md)
  (binds on M6.F per roadmap §M6).
- Precedent: M6.C/M6.D/M6.E (score-neutral inert landing, ADR-0032 §7/§8 +
  ADR-0033 §8), ADR-0032 §4 (eval-boundary rule), the M6.E `pub(crate)`
  testable-seam precedent.
- Production HEAD / inert-landing baseline tag: **`M6.E`**.

## 1. Goal & non-goals

- **Goal.** Three white-perspective constructs entering `evaluate_core`:
  two additive `(mg, eg)` terms (outpost, rook-file) in the blend numerator
  and one multiplicative draw-scale on the blended value. **All additive
  weights zeroed; the scale ≡ identity** (`EG_SCALE_DEN/EG_SCALE_DEN`) ⇒
  `evaluate` byte-identical to `M6.E`; full term math live + tested,
  M6.I-ready. Same pattern as M6.C/M6.D/M6.E.
- **Non-goal (deferred by design — ADR-0034).**
  - **Weight calibration is M6.I's joint Texel pass.** M6.F ships literature
    defaults *zeroed*; the additive weights and the scale coefficients all
    enter the one M6.I joint pass.
  - **Endgame-scaling lands inert, not live** (ADR-0034 §4 — the open
    roadmap question is resolved *inert-per-precedent*; the live alternative
    is recorded + rejected with rationale).
  - **No KBvKB-same-color duplication.** That draw is already in M6.A
    `is_insufficient_material`; the endgame-scale pawnless-pattern set is
    disjoint from it (ADR-0034 §3).
  - **No rook-on-7th, no doubled-rooks, no Kaufman material adjustments,
    no threats** (research Priority-2/3 — out of M6.F scope).
  - **Not pawn-hash-cached.** Computed live in `evaluate_core`, never cached
    (the ADR-0033 §6 live-term class). No `PawnHashEntry`/`PawnEval` change.
  - **Pseudolegal, no x-ray** (the M6.D mobility precedent — outpost
    pawn-support uses immediate pawn attacks; no pin awareness).

**Outpost** (prescriptive — the coder transcribes; mirror `mobility.rs`'s
`for (side, sign) in [...]` style, **no** match-on-kind beyond the two loops):

**Outpost-hole correctness invariant (load-bearing — the coder MUST NOT
"simplify" the `(3..=5)` gate away).** `!bitboard::black_attack_front_spans(bp)`
flags a square as "no black pawn can ever capture onto it." `black_front_spans`
starts **one rank ahead** of each black pawn (toward rank 1) and is widened
E/W, so it captures exactly "some black pawn on an adjacent file, currently on
or north of (rank+1), can march down and capture here." This complement is a
**valid hole test only for squares in the enemy half** (White's outpost band):
on a square on White's *own* side the relevant challenging black pawns may sit
*south* of it, which the front-span (which only looks ahead/south of each
black pawn) does not model. The `(3..=5)` relative-rank gate (chess ranks 4–6)
is what guarantees every scored square is in the enemy half, making the
span-complement sound. The gate is therefore **correctness-load-bearing, not
just a value-table index** — removing it would make the hole test wrong, not
merely wider. Worked: White Nd5, Black pawn e7 ⇒ `black_attack_front_spans
({e7})` ⊇ d5 (e7 span = {e6,e5,…} widened ⊇ d6,d5,…) ⇒ d5 **excluded**
(e7 can play e6/e5 then capture) — correct. White Nd5, no black c/e pawns,
white c4+e4 ⇒ d5 pawn-supported ∧ unchallengeable ⇒ scored.

The hole+support set is computed by the **`outpost_squares` seam** (so the
structural test pins the real selector — must-fix from test-suite review):

```rust
// THE SEAM — outpost_term_white MUST call this, not inline the formula.
pub(crate) fn outpost_squares(pos: &Position, side: Color) -> Bitboard {
    let wp = pos.pieces_colored(Color::White, PieceKind::Pawn);
    let bp = pos.pieces_colored(Color::Black, PieceKind::Pawn);
    match side {
        // White hole = no BLACK pawn can ever capture onto it; supported by a
        // WHITE pawn (immediate pawn-attack set). Black is the mirror.
        Color::White => {
            let unchallengeable = !bitboard::black_attack_front_spans(bp);
            let pawn_def = wp.shift_north_east() | wp.shift_north_west();
            unchallengeable & pawn_def
        }
        Color::Black => {
            let unchallengeable = !bitboard::white_attack_front_spans(wp);
            let pawn_def = bp.shift_south_east() | bp.shift_south_west();
            unchallengeable & pawn_def
        }
    }
}
```


`relative_rank(side, sq)` = `sq.rank()` for White, `7 - sq.rank()` for Black
(a private `fn relative_rank(side: Color, sq: Square) -> u8` in `tier1.rs` —
the `pawns.rs` `CONN_*` relative-rank-mirror precedent; `sq.rank()` is 3-bit
so the result is always `0..=7`). The `(3..=5)` gate makes the predicate
"enemy half, classic outpost ranks 4-6" structural (out-of-band table entries
are dead-and-zeroed — pinned by `outpost_rank_gate_structural`); it is
**correctness-load-bearing per the invariant above**, not a removable filter.

**Rook-file:**

**No file-mask helper exists or is needed.** There is no `file_mask`/
`Bitboard::file()` fn, no `FILE_MASKS` array, and no `Shl<u8> for Bitboard`
(verified against `src/bitboard.rs` — only the `Bitboard::FILE_A..FILE_H`
constants). None is introduced: `file_fill(own_pawns)` already sets **every
square of any file that holds an own pawn**, so the rook's own square is in
that projection **iff** an own pawn is on the rook's file. The test is simply
`(own_files & Bitboard::from_square(sq)).any()` — no per-file mask.

```rust
let wp_files = bitboard::file_fill(wp);
let bp_files = bitboard::file_fill(bp);
let (mut mg, mut eg) = (0i32, 0i32);
for (side, sign) in [(Color::White, 1i32), (Color::Black, -1i32)] {
    let (own_files, enemy_files) = match side {
        Color::White => (wp_files, bp_files),
        Color::Black => (bp_files, wp_files),
    };
    for sq in pos.pieces_colored(side, PieceKind::Rook).iter() {
        let rook_bit = Bitboard::from_square(sq);
        let on_own = (own_files & rook_bit).any();    // own pawn on rook's file
        let on_enemy = (enemy_files & rook_bit).any(); // enemy pawn on rook's file
        if !on_own && !on_enemy {        // fully open
            mg += sign * ROOK_OPEN_FILE_MG; eg += sign * ROOK_OPEN_FILE_EG;
        } else if !on_own {               // semi-open (own absent, enemy present)
            mg += sign * ROOK_SEMI_OPEN_FILE_MG; eg += sign * ROOK_SEMI_OPEN_FILE_EG;
        }
    }
}
(mg, eg)
```

`on_own`/`on_enemy` test the rook's own file via the `file_fill` projection
(a pawn anywhere on a file ⇒ that whole file set ⇒ the rook's square, which is
on that file, is set). Pinned by `rook_file_own_pawn_blocks_bonus_structural`.

**Endgame scale** (returns numerator; identity = `EG_SCALE_DEN`):

```rust
let mut scale = EG_SCALE_DEN;
if is_ocb_with_pawns(pos)   { scale = scale.min(OCB_WITH_PAWNS_SCALE); }
if is_pawnless_drawish(pos) { scale = scale.min(PAWNLESS_DRAW_SCALE); }
// 50-move taper: linear ramp DEN → FIFTY_MOVE_FLOOR over halfmove
// FIFTY_MOVE_TAPER_FROM..=100. At ship FLOOR == DEN ⇒ ramp flat at DEN.
let hmc = pos.halfmove_clock() as i32;
if hmc > FIFTY_MOVE_TAPER_FROM {
    let span = (100 - FIFTY_MOVE_TAPER_FROM).max(1);
    let prog = (hmc - FIFTY_MOVE_TAPER_FROM).clamp(0, span);
    let tapered = EG_SCALE_DEN - (EG_SCALE_DEN - FIFTY_MOVE_FLOOR) * prog / span;
    scale = scale.min(tapered);
}
scale.clamp(0, EG_SCALE_DEN)
```

`is_ocb_with_pawns`: each side has **exactly one** bishop, on **opposite**
color complexes, and at least one pawn exists for either side; **no queens
or rooks** (the literature OCB-drawishness condition is bishops + pawns only —
heavy major pieces break the draw; CPW Bishops-of-Opposite-Colors). Reuses the
M6.A `LIGHT_SQUARES`/`DARK_SQUARES` popcount idiom (`bishop_pair_term_white`
precedent). **Disjoint from `is_kbkb_same_color`** by construction (same vs
opposite complex; that draw stays solely in `is_insufficient_material`).

`is_pawnless_drawish` — **exact accepted material signatures (enumerated, not
prose; conservative-correct so the M6.I-active form never scales down a win).**
Requires: zero pawns both sides **and** zero queens both sides **and** zero
rooks both sides (any major ⇒ generally mating ⇒ not drawish). Then accept
**iff** the non-king material is one of:
- **KNNvK** — one side `knights == 2 ∧ bishops == 0`, the other side **bare
  king** (KNN cannot force mate; the canonical pawnless draw, *new* coverage
  beyond M6.A insufficient-material which only covers ≤1 total minor).
- **balanced ≤1-minor-each** — each side has `bishops + knights ≤ 1` (e.g.
  KBvKB any complex, KNvKN, KBvKN, and the bare-minor-vs-bare-minor cases):
  all draws/insufficient, none mating.

**Explicitly EXCLUDED (these are wins, must NOT be flagged drawish):** any side
with `bishops + knights ≥ 2` other than the exact KNNvK pattern above — in
particular **KBNvK** (forced win), **KBBvK** (two bishops vs bare K, win),
**KBBvKN / KNNvKN-imbalanced** etc. The predicate is the *narrow* accept-list,
not a "no major ⇒ drawish" sweep. Conservative at M6.F (zeroed; M6.I widens
only the *coefficient*, **not** the pattern set — ADR-0034 §3 fixes the set at
M6.F). **Overlap with `is_insufficient_material`, stated precisely (the
predicate is a directly-tested `pub(crate)` seam — the rationale must be on
record).** The accept-set as written *does* return `true` for some
insufficient-material positions: KBvK / KNvK satisfy "balanced ≤1-minor-each"
(heavy side `bishops+knights ≤ 1`, other side bare K). This is **not** a bug
and **not** double-handling: `evaluate_core` early-returns `0` at
`src/eval.rs:228` for `is_insufficient_material` *before* `endgame_scale` is
ever called, so the overlap is **unobservable in eval** — `endgame_scale` is
never reached for KvK/KvN/KvB/KBvKB-same-color. The *observable* new coverage
(positions that actually reach `endgame_scale`) is **KNNvK + KBvKB-opposite +
KNvKN + KBvKN** (4-piece, not `is_kbkb_same_color`). `pawnless_drawish_
predicate` asserts the predicate **in isolation** (the seam, not via
`endgame_scale`), so its KBvK/KNvK→true region is *expected* and documented
here — a future reader must not read that as a defect. Documented out-of-scope
gap: KRvKN / KQvKR-style "hard but not dead" tablebase draws need EGTB (M9) —
ADR-0034 §3 records this; they are *not* swept in (rooks/queens excluded
above). Pinned by `pawnless_drawish_predicate` **and**
`pawnless_drawish_excludes_KBNvK` (§4).

**Index/clamp invariants.** `relative_rank ∈ 0..=7` (always — `sq.rank()` is
3-bit); the `(3..=5)` gate is real behavior (the classic outpost-rank
discriminator), not defensive masking. `scale.clamp(0, EG_SCALE_DEN)` is real
(a tuned `FLOOR > DEN` or negative would be a data bug — clamp keeps the
multiplier a valid `[0,1]` fraction; at ship every input is `DEN` so it is a
no-op). Verify imports: `crate::bitboard::{self, Bitboard}`,
`crate::piece::{Color, PieceKind}`, `crate::position::Position`,
`crate::square::Square`, the `core::ops::Not` (`!Bitboard`) impl, the
`eval::data` constants.

```rust
    + (eg + bp_eg + pe_eg + pp_eg + mob_eg + ks_eg + op_eg + rf_eg) * (24 - phase))
    / 24;
let scaled = blended * scale / data::EG_SCALE_DEN;
let result_white = scaled + mop_up;
```

**Inert-identity proof.** At ship: `op_*≡0`, `rf_*≡0` (all weights 0) ⇒ blend
numerator identical to M6.E; `scale ≡ EG_SCALE_DEN` (every scale tunable =
`EG_SCALE_DEN`, the `min`/taper math returns `EG_SCALE_DEN` for all inputs) ⇒
`scaled = blended * D / D == blended` **exactly** in i32 (`blended·D` is
exactly divisible by `D` for any i32 `blended`, `D≠0`). No overflow:
`blended` is the phase-blend of PST + the additive addends, each in the
material+positional centipawn range; the existing in-tree
`debug_assert!(result_white.abs() < MATE_IN_MAX_PLY - 1)`
(`src/eval.rs:325-328`) confirms the whole pipeline stays in-band across the
bench corpus, and `MATE_IN_MAX_PLY·64` ≈ 1.9M ≪ `i32::MAX` ≈ 2.1e9 gives
ample headroom — the bound is tied to the existing invariant, not a magic
literal (phrased non-circularly: it does not infer the pre-scaling `blended`
bound *from* the post-scaling assert; it observes the pipeline is empirically
in-band and that `·64` has ~1000× headroom). ⇒ `result_white` byte-identical
to `M6.E` ⇒ `evaluate` byte-identical ⇒ bench `1213649` / depth-4 `90591`
byte-for-byte (§9/§10).

symbolic value tests *and* `endgame_scale_never_exceeds_den` are dormant at

## 5. Order of operations

1. **Test-scaffolding + tests slice.** Append the `data.rs` constants (pure
   vendored data — safe to land early) + `tier1.rs` with the five `fn`s as
   **stubs** (`outpost_term_white`/`rook_file_term_white` → `(0,0)`;
   `endgame_scale` → `EG_SCALE_DEN`; `is_ocb_with_pawns`/`is_pawnless_drawish`
   → `false`) with final signatures + `pub(crate) mod tier1;` in `eval.rs`
   (NOT yet wired into `evaluate_core`). Then write all tests. TDD state vs
   the stubs: symbolic/definitional/predicate tests **fail** (they demand
   real computation — the anti-confirmation-bias property);
   structural-only (`tier1_startpos_is_neutral`,
   `tier1_tables_have_expected_lengths`, the pure-arithmetic
   `endgame_scale_fifty_move_ramp_structural`) and the three boundary tests
   (weight-free, GREEN by construction — accessor/mop-up are PST-only)
   **pass**. Crate compiles.
2. Test-suite blind-review loop → convergence.
3. Implement: replace the stub bodies with the verbatim §3 algorithms → wire
   `evaluate_core` (the `TIER1_IN_EVAL` block + blend extension + scale step).
   All tests go green; the terms are `(0,0)` and the scale `EG_SCALE_DEN` at
   the shipped zeroed config.
4. `cargo test` green (plain **debug** + `--release`). No extended perft (not
   triggered — §2).
5. Pre-review mechanical checks (§7) → final-review loop.
6. Benchmark — assert `bench` byte-identical to `M6.E` (§9/§10).
7. Commit + push + tag `M6.F`; docs (§11).

## 6. Parallelization map

**None — sequential.** ~150–200 LOC across 3 tightly-coupled files; data

precedes implementation (TDD ordering). One coder slice for tests, one for
implementation, in sequence. Splitting `data.rs` (pure transcription) or the

(the M6.D/M6.E §6 finding verbatim). The three features share the `tier1.rs`
module and one `TIER1_IN_EVAL` wiring block — co-located by design.
