# M6.G — Per-Game-File Reorder Protocol (architectural plan, rev 3)

**Status:** Plan, rev 3 (addressing plan-reviewer pass 2 — 4 blockers, 6 substantive, 5 nits).
**Scope:** Rewrite of `src/corpus/{selfplay.rs,store.rs}` + add `pending.rs`, `dispatcher.rs`, `consumer.rs`; thin `cmd_build` in `src/bin/corpus.rs`.
**Binding inputs:** ADR-0035 (§6 ordering invariant survives; §3.5/§3.6/§3.7/§3.8 rewritten per §5); research `docs/research/m6.g-per-game-file-reorder.md`.

The pinned M6.G↔M6.H interface contract is unchanged (`QUIET_MARGIN_CP`, `OPENING_SKIP_PLIES`, `HIGH_SCORE_CP`, `PER_GAME_CAP=10`, the three sources, the on-disk frame layout). What changes is *where* cross-game cap/dedup/split happen (inline in the consumer) and *how* the shard is produced (in-order commit from a per-game reorder buffer).

---

## 1. The win

Each worker writes its completed game to `pending/game-{game_id:020}.bin`. A single consumer thread polls for the next-expected game_id, applies dedup → per-game cap → per-game split *inline* in strict game_id order, and appends to `shard.bin` / `val.bin`. The dispatcher hands workers the lowest game_id not yet in `shard ∪ val ∪ pending ∪ claimed`.

The property delivered: `sha256(shard.bin)` and `sha256(val.bin)` are byte-identical across any choice of K ∈ {1..N_cores}. Holds because every step is a deterministic function of `(seed, split_seed, game_id)`; K affects only completion timing, not commit order. Auxiliary win: `cmd_build` becomes a thin finalization step (verify + digest + manifest).

**Byte-equivalence scope:** self-play-only corpora. Multi-source diverges (the old pipeline's `min-(source,game_id,ply)` dedup ordering ≠ new first-seen-by-dispatch); multi-source ingest is deferred per §6.

Preserved: the CRC-framed game-block on-disk format; the ADR-0035 §6 ordering invariant (strengthened, not weakened); R2 (interrupted in-flight game = zero records); R7 per-game seed (`substream_seed(base_seed, game_id)`).

## 2. Architecture

### 2.1 Directory layout

```
out_dir/
  shard.bin              # append-only train CRC-framed blocks, in game_id order
  val.bin                # append-only val   CRC-framed blocks, in game_id order
  checkpoint.bin         # resume cursor (CRC-protected; whole-file atomic replace)
  pending/               # per-game reorder buffer (≤ K-1 files at steady state)
    game-00000000000000000000.bin
    ...
    .game-<N>.bin.tmp                 # in-flight worker writes
```

`pending/` is on the same FS as `out_dir` so `rename(2)` is atomic. Created via `create_dir_all` on first run; never removed.

### 2.2 Pending-file format

Contents of `pending/game-{N:020}.bin` are exactly the bytes `store::encode_block(N, &records)` produces — the same CRC-framed game block today's writer appends to `shard.bin`. The consumer decodes via `store::decode_block` (promoted to `pub(crate)`), and re-encodes the dedup-survivor subset before appending.

**Max size bound (Nit #12):**
```
MAX_PENDING_BYTES = max_plies * 100 + BLOCK_HEADER_BYTES + CRC_BYTES + slack
```
At `max_plies = 400` (committed knob), ~90 B per record × 400 ≈ 40 KB. We pick 64 KB as the runtime ceiling (headroom). Oversize handling is **fatal at both write and read sides** per Blocker #4 below.

### 2.3 Atomic per-game write

`pending::write_pending(pending_dir, game_id, block_bytes) -> Result<(), CorpusError>` writes via the standard tmp-then-rename idiom:

- Pre: `block_bytes` is the CRC-framed output of `store::encode_block(game_id, &records)`.
- Tmp filename is **deterministic per game_id** (`.game-{game_id:020}.bin.tmp`), so any worker re-attempt overwrites a prior orphan — no duplicate-orphan accumulation.
- Sequence: `File::create(tmp)` → `write_all` → `sync_all` (Rust wrapper invokes `F_FULLFSYNC` on macOS; never raw `libc::fsync`) → `rename(tmp, final)` → parent-dir fsync (error **propagated**, not best-effort — APFS honors it).
- **Blocker #4(a):** the previous `debug_assert!(block_bytes.len() <= MAX_PENDING_BYTES)` is promoted to a hard runtime check. On violation, return `CorpusError::Checkpoint("oversized pending block at game_id {gid}: {len} bytes > {MAX_PENDING_BYTES}")`. The worker exits with `fatal_io_error`; the orchestrator surfaces. **Not retryable** (the worker would just regenerate the same oversize block).
- Post on `Ok`: the file at the final path is durably visible and decodes via `store::decode_block`.

Signal-handler interaction: between games → clean exit; mid-game → R2 zero-record drop; mid-write SIGKILL → orphaned `.tmp` cleaned at next resume; post-rename SIGKILL → may or may not survive (gap-fill replay if not).

### 2.4 Worker model

Long-running thread loop with no central channel: `dispatcher.claim_next` → `play_one_game` → `pending::write_pending` → `guard.notify_completed()` → loop. A shared `alive_workers: Arc<AtomicUsize>` is initialized to `cfg.workers.max(1)` before spawn; each worker holds an `AliveGuard` whose `Drop` decrements (panics and clean exits both account). The consumer uses this for wedge detection (§2.6).

Worker control flow per iteration (prose summary; line-by-line deferred to implementation):

1. Check `stop`; break if set.
2. `let claim = dispatcher.claim_next()?;` — a `ClaimGuard<'_>` (see §2.5 / Blocker #3). On `None`, break.
3. Reseed: `Prng::new(substream_seed(cfg.seed, claim.game_id()))`; sample depth rung; fresh `AlphaBetaMover` and `QSearcher` (R3 per-game state hygiene).
4. `play_one_game(...)`:
   - **None (stop-aborted in-flight):** drop `claim` without calling `notify_completed` — its `Drop` calls `release_unclaimed`. Increment `games_dropped_inflight`. R2 satisfied.
   - **Some(gr):** `let block = store::encode_block(game_id, &gr.records);` → `pending::write_pending(...)`:
     - **Ok:** `claim.notify_completed()` (consumes the guard, suppresses `Drop` via `std::mem::forget`). Increment `games_emitted`.
     - **Err(_):** return `WorkerStats { fatal_io_error: Some(e.to_string()), .. }`. The `claim`'s `Drop` releases. Includes the oversize check from Blocker #4(a).

Contract: `release_unclaimed` is reserved for the R2 graceful-shutdown path AND the RAII-via-`Drop` panic / error path. I/O failure on `write_pending` terminates the worker with `fatal_io_error` (it does not re-enqueue the same game — that would loop forever on a persistent disk problem). The orchestrator joins all workers and surfaces any `fatal_io_error` as `CorpusError::Checkpoint`; `thread::scope` additionally catches panics (defense in depth).

### 2.5 Dispatcher

```rust
pub struct Dispatcher {
    games_target: u64,
    inner: Mutex<DispatcherInner>,
}
struct DispatcherInner {
    next_dispatch_id: u64,       // Substantive #5: plain u64 under the lock; AtomicU64 dropped.
    gap_queue: VecDeque<u64>,
    claimed: HashSet<u64>,
}
```

**Claim ordering invariant (prose):** under a single `Mutex` acquisition,
1. if `gap_queue` is non-empty, pop the front, insert into `claimed`, return it;
2. else if `next_dispatch_id < games_target`, return `next_dispatch_id` and increment (insert into `claimed`);
3. else return `None`.

Because the gap-vs-steady decision and the cursor advance are *inside the same critical section*, a `release_unclaimed` racing against a `claim_next` cannot leak a gap past a fresh steady-state dispatch. The lock is contended only at game boundaries (every ~100 ms+ per worker); overhead is negligible. (Substantive #5: this is also why the prior `AtomicU64` was redundant.)

**Blocker #3 — `ClaimGuard` RAII.** `claim_next` returns `Option<ClaimGuard<'_>>` (not a bare `u64`). The guard exposes `game_id() -> u64` and `notify_completed(self)`, the latter consuming the guard, calling `Dispatcher::notify_completed`, and suppressing the drop via `std::mem::forget`. The guard's `Drop` calls `Dispatcher::release_unclaimed(game_id)` *unless* `notify_completed` was called. Effect: any non-happy path — panic in `play_one_game`, early `return Err`, `None` from `play_one_game` — releases the claim back onto `gap_queue` without explicit cleanup. The wedge detector now functions correctly under worker panic.

```rust
pub struct ClaimGuard<'d> { dispatcher: &'d Dispatcher, game_id: u64, notified: bool }
impl<'d> ClaimGuard<'d> {
    pub fn game_id(&self) -> u64 { self.game_id }
    pub fn notify_completed(mut self) {
        self.dispatcher.notify_completed(self.game_id);
        self.notified = true;
        std::mem::forget(self);
    }
}
impl<'d> Drop for ClaimGuard<'d> {
    fn drop(&mut self) {
        if !self.notified { self.dispatcher.release_unclaimed(self.game_id); }
    }
}
```

Other public methods: `notify_completed(g)` removes `g` from `claimed`; `release_unclaimed(g)` removes from `claimed` and `push_back`s onto `gap_queue`; `is_fully_drained_at(g)` returns `true` iff `gap_queue` is empty AND no `claimed` entry is `<= g`.

Invariant: every game_id `< next_dispatch_id` is in exactly one of {committed, pending, claimed, gap_queue}. `gap_queue.len() + claimed.len() ≤ |initial_gap_list| + K`.

### 2.6 Consumer loop

Single thread. Owns `next_consume_id`, `fen_set`, `committed_ids_at_resume`, the shard/val file handles (reopened per append), and the `alive_workers` reference for wedge detection.

```rust
const POLL_INTERVAL_MS: u64 = 10;     // Substantive #7: overridable per cfg.

pub struct ConsumerState {
    pub next_consume_id: u64,
    pub fen_set: HashSet<String>,
    pub committed_ids_at_resume: HashSet<u64>,    // Blocker #1; immutable after resume.
}
```

Loop body (prose; defer line-by-line to implementation):

1. **Exit checks:** if `state.next_consume_id >= cfg.games`, break. If `stop` is set AND `dispatcher.is_fully_drained_at(state.next_consume_id)` is true, break.
2. **Blocker #1 — skip-committed bypass.** If `state.committed_ids_at_resume.contains(&state.next_consume_id)`: increment `next_consume_id`, atomically replace `checkpoint.bin`, `continue`. This closes the deadlock where a checkpoint-absent bootstrap + gappy shard would otherwise wait forever for a pending file that no worker would ever produce (the game was already empty-post-dedup and committed without a block). Reads only; `committed_ids_at_resume` is never modified during steady state.
3. **Probe** `pending/game-{next_consume_id:020}.bin` by exact name (never `readdir` for ordering).
   - **Ok(bytes), Blocker #4(b) oversize fatal:** if `bytes.len() > MAX_PENDING_BYTES`, return `Err(CorpusError::Checkpoint("oversized pending block at game_id {gid}: {len} > {MAX_PENDING_BYTES}"))`. Do **not** `release_unclaimed` — the same worker would just regenerate the same oversize block; we want the operator to see this.
   - **Ok(bytes), torn write:** if `store::decode_block(&bytes)` returns `None` OR consumed length ≠ `bytes.len()`: unlink, `dispatcher.release_unclaimed(next_consume_id)`, `continue`. (Distinct from oversize: a not-oversized file with CRC / decode failure is the torn-write path and DOES use release-and-retry.)
   - **Ok(bytes), filename mismatch (Substantive #10):** if `block.game_id != next_consume_id`, return `Err(CorpusError::Checkpoint("pending filename / block game_id mismatch at game_id {expected}: block reports {actual}"))` and unlink the file (treat as torn — the replay produces a correctly-named file). Promoted from `debug_assert!`.
   - **Ok(bytes), happy path:** apply inline pipeline — dedup against `fen_set`, then per-game cap on the dedup survivors, then split decision. If post-cap is non-empty, `store::append_raw_bytes(dest, &store::encode_block(game_id, &capped))`. Increment `next_consume_id`. Atomically replace `checkpoint.bin`. Unlink the pending file. If post-cap is empty, increment `games_empty_post_dedup` (`games_committed` and `next_consume_id` both still advance; no shard write).
   - **NotFound:** if `dispatcher.is_fully_drained_at(next_consume_id)` AND `alive_workers.load(Acquire) == 0`, return `Err(CorpusError::Checkpoint("consumer wedged: no live workers, no pending file for game_id {gid}"))`. Otherwise sleep `cfg.poll_interval_ms.unwrap_or(POLL_INTERVAL_MS)` ms and loop.
   - **other Err:** propagate as `CorpusError::Io`.

Polling cadence is **test-overridable** via `cfg.poll_interval_ms: Option<u64>` (Substantive #7); has **no effect on byte-identity** — only on commit latency.

Wedge detection: the canonical wedge is "all workers dead AND no pending file for `next_consume_id`." `alive_workers.load() == 0` is the primary signal (decremented via `Drop` guard, so it catches panics too). `thread::scope` join in the orchestrator additionally detects panic — defense in depth.

### 2.7 Resume protocol (checkpoint authoritative)

The checkpoint is authoritative for `next_consume_id`. The shard scan is a fallback for `fen_set` reconstruction and ghost-pending detection only — **not** for the consume cursor.

```
resume(out_dir):
  1. Truncate torn tails (ADR-0035 §6 discipline):
     (shard_blocks, shard_valid_len) = scan_valid_blocks(out_dir/shard.bin)
     truncate_to_valid(out_dir/shard.bin, shard_valid_len)
     (val_blocks, val_valid_len)     = scan_valid_blocks(out_dir/val.bin)
     truncate_to_valid(out_dir/val.bin, val_valid_len)

  2. Rebuild fen_set + committed_ids from durable shards only:
     fen_set       = ∅
     committed_ids = ∅
     for block in shard_blocks ∪ val_blocks:
         for r in block.records: fen_set.insert(r.fen)
         committed_ids.insert(block.game_id)

  3. Read checkpoint. Decoder rejects MAGIC mismatch / CRC failure as "absent":
     ckpt = read_checkpoint(out_dir/checkpoint.bin)
     if ckpt is valid:
         next_consume_id := ckpt.next_consume_id              # authoritative
     else:
         next_consume_id := (smallest u64 not in committed_ids, starting from 0)

  4. Scan pending/ for cleanup ONLY (orphan .tmp + gap enumeration):
     pending_ids = ∅
     for entry in readdir(out_dir/pending/):
         if entry matches ".game-*.bin.tmp":  unlink; continue
         if entry matches "game-{N:020}.bin":
             bytes = read(entry)
             if len(bytes) > MAX_PENDING_BYTES or decode_block(bytes) is None:
                 unlink; continue
             pending_ids.insert(N)
         else: log_warning   # unknown file; leave alone

  5. Ghost-pending self-heal (Blocker #2):
     ghost_ids = (pending_ids ∩ committed_ids)
               ∪ (if ckpt valid: pending_ids ∩ {0..ckpt.next_consume_id})
     for N in ghost_ids:
         unlink(out_dir/pending/game-{N:020}.bin); pending_ids.remove(N)
     # Covers BOTH: pending file for a committed-with-records game (existing case)
     # AND pending file for an empty-post-dedup game with N < ckpt.next_consume_id
     # (new case). When ckpt absent, union degenerates to the original
     # `pending_ids ∩ committed_ids` intersection only.

  6. Gap list = [0..upper) \ (committed_ids ∪ pending_ids), where
     upper = max(committed_ids ∪ pending_ids ∪ {next_consume_id}) + 1
     # Shard's last block's game_id MAY be < next_consume_id - 1 (gaps from
     # empty-post-dedup games). Expected, not corruption.
     next_dispatch_id := upper

  7. committed_ids_at_resume := committed_ids   # frozen for the run.
```

**Memory note for `committed_ids_at_resume`:** ~8 bytes per committed game_id × millions ≈ tens of MB at M6.H scale (the worst case is ~5–10 M committed games ⇒ ~40–80 MB). Held in `ConsumerState` for the lifetime of the run; read-only after resume. Acceptable.

Empty-records games: a game whose every record was a dedup-duplicate (or whose post-dedup-cap record count was zero) leaves NO block in `shard.bin` / `val.bin` but DOES advance `next_consume_id`. The checkpoint records this advancement. No marker block (less disk waste, simpler invariant). Documented contract: shard's last block's game_id can be strictly less than `ckpt.next_consume_id - 1`.

**Checkpoint version bump:** `CKPT_MAGIC` changes from `0x4357_4B31` ("CWK1") to `0x4357_4B32` ("CWK2"). The new format adds `next_consume_id: u64` and drops `ladder_cursor`, `per_worker_next_game_id`. Decoders reject old MAGIC as corrupt → resume treats it as missing → falls back to shard scan.

## 3. Inline pipeline (consumer-side)

### 3.1 Order: dedup → cap → split

Matches `cmd_build`'s old semantics (`dedup_fen → per_game_cap → split_by_game`). The byte-content equivalence for self-play-only corpora is the load-bearing motivation: dedup-first means novel positions are never discarded by a per-game cap that picked already-seen duplicates.

### 3.2 Dedup

`state.fen_set: HashSet<String>`. For each record in game_id order, `fen_set.insert(r.fen.clone())` returns `true` (keep) or `false` (drop). Consumer processes in strict game_id order ⇒ "first-seen wins" is K-independent. Memory bound: ~120–250 MB at M6.H scale (1.5–3 M unique FENs × ~90 bytes). Reconstructed on resume from durable shards only (O(committed records); a few seconds).

### 3.3 Per-game cap (dedup-survivors input)

```rust
fn inline_cap_dedup_survivors(records: Vec<CorpusRecord>, split_seed: u64,
                              game_id: u64, cap: usize) -> Vec<CorpusRecord>
```

Per-game seed = `substream_seed(split_seed, game_id)` (no `CAP_TAG` xor). Seeded reservoir sampling, K-independent because it depends only on `(split_seed, game_id)`.

### 3.4 Per-game split

```rust
fn split_decision(split_seed: u64, game_id: u64, val_fraction: f64) -> bool {
    let threshold = (val_fraction.clamp(0.0, 1.0) * (u64::MAX as f64)) as u64;
    substream_seed(split_seed, game_id) < threshold
}
```
Identical-in-semantics to today's `split_by_game`. Whole-game routing.

### 3.5 `cmd_build` becomes thin

Scan shard/val for validity → compute `corpus_sha256` → write manifest + filter_spec + corpus_stats + re-run.sh. No more `dedup_fen` / `per_game_cap` / `split_by_game` calls. `cmd_build` errors if `pgn-shard.bin` exists and is non-empty (per §6); the error message includes (Nit #13): `"Delete pgn-shard.bin to use the per-game-file architecture (multi-source ingest deferred — see ADR-0035 §6)."`

### 4.7 Orchestrator (`selfplay::run`) — prose summary

Pre-conditions: `cfg.out_dir` may or may not exist; `cfg.workers >= 0` (clamped to 1).

Sequence:

1. `create_dir_all(out_dir)` then `create_dir_all(pending_dir)`.
2. `let resumed = resume(out_dir, pending_dir)?;` (§2.7).
3. Build `Dispatcher::new(resumed.gap_list, resumed.next_dispatch_id, cfg.games)`, wrap in `Arc`.
4. `let alive_workers = Arc::new(AtomicUsize::new(cfg.workers.max(1)));`.
5. Build `ConsumerState { next_consume_id, fen_set, committed_ids_at_resume } = resumed`.
6. `std::thread::scope`:
   - Spawn the consumer first (so it's ready when workers start producing).
   - Spawn `cfg.workers.max(1)` workers; each receives an `AliveGuard` whose `Drop` decrements `alive_workers`.
   - Join all workers. If any returned `fatal_io_error`, the consumer may still complete in-flight; we then surface the first fatal as `CorpusError::Checkpoint`. Otherwise join the consumer.
7. Aggregate `SelfPlayStats` from worker stats (emitted/dropped) + consumer stats (committed/empty/positions). Return.

Post-conditions on `Ok`: `shard.bin` + `val.bin` + `checkpoint.bin` are durable and internally consistent; `pending/` contains only `.tmp` orphans if any worker crashed mid-write.

## 7. Determinism caveats

1. `File::sync_all` only — never raw `libc::fsync` (not durable on macOS).
2. Parent-dir fsync after rename — error propagated (not best-effort).
3. `readdir` never used for ordering — only for cleanup (orphans, ghosts, gap enumeration).
4. Polling, not inotify/kqueue — sidesteps the creation-before-watch race. Cadence is operator- and test-overridable; doesn't affect byte-identity.

## 11a. Implementation notes (pass-3 reviewer substantives)

These three items came out of the pass-3 review as not-blocking but worth pinning before implementation begins:

1. **`ClaimGuard<'d>` lifetime under `thread::scope`.** The dispatcher should be captured by the `std::thread::scope` closure as `&'scope Dispatcher` (no `Arc` needed for the dispatcher itself; only `alive_workers` needs `Arc<AtomicUsize>`). `ClaimGuard<'scope>` borrows from that scope reference. Avoid the `Arc<Dispatcher>` + `&'d ClaimGuard` reconciliation problem.
2. **Skip-committed checkpoint-rewrite batching.** Pathological case: corrupted checkpoint + dense `committed_ids_at_resume` ⇒ §2.6 step 2 fires N atomic checkpoint rewrites before reaching the first pending file. Batch the rewrite: when entering a run of committed_ids, only rewrite the checkpoint when *leaving* the run (i.e., when the loop body next probes a pending file). The intermediate `next_consume_id` values are recoverable from `committed_ids` on next resume anyway.
3. **Drop order: `ClaimGuard` before `AliveGuard`.** On worker panic, the desired ordering is "claim released to `gap_queue` *before* `alive_workers` decrements." Otherwise a consumer racing the panicking worker can observe `alive_workers == 0` while `is_fully_drained_at` is momentarily false (the released id hasn't been popped to `gap_queue` yet). Achieve by declaring `_claim_guard` *after* `_alive_guard` in the worker scope (Rust drops in reverse declaration order — last-declared drops first).

A small bonus test (Nit from pass 3): `reproducibility_check_skipped_with_warn_on_sentinel_value` in `tests/corpus_quality_gate.rs` (or unit test inside `src/corpus/quality_gate.rs`) — asserts the sentinel-path WARN behavior.
