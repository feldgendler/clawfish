# M1.B — Position struct + FEN parsing

## Context

M1.A delivered the `Square` and `Bitboard` primitives. M1.B builds the position representation that everything from M1.C onward consumes: the data shape that magic-bitboard attack lookups (M1.C), Zobrist hashing (M1.D), make/unmake (M1.E), and legal move generation (M1.F) all read from and (later) mutate.

Per `docs/research/m1-engine-architecture.md` §1 and `docs/architecture.md`, the layout is settled: **6 piece-kind bitboards + 2 color-occupancy bitboards + a 64-entry mailbox + cached king squares + auxiliary state (side to move, castling rights, EP target, halfmove clock, fullmove number).** Zobrist is added in M1.D; it is *not* part of M1.B.

FEN is the canonical text encoding, defined in `docs/reference/pgn-spec-1994.txt` §16.1. We parse and format the six-field form per the spec — no de-facto truncated forms (Stockfish accepts FEN missing the last two fields; we don't, until a real consumer demands it).

### Research skip — justified

Workflow step 1 is "deep prior-art research." For M1.B this is a clean skip: `docs/research/m1-engine-architecture.md` (researched 2026-04-27) covers the Position layout exhaustively (§1 "Bitboard layout & square indexing"), and §16.1 of the vendored Edwards 1994 spec covers FEN syntax exhaustively. Two things the existing research does **not** discuss explicitly that this plan settles from first principles plus the spec text:

1. **Storage rule for EP target on parse.** Per spec §16.1.3.4, FEN encodes EP after *any* double pawn push, irrespective of whether an opponent pawn can immediately capture. The Polyglot Zobrist convention (per the architecture research §5) hashes EP only when the capture is pseudo-legally possible. **Resolution: store the spec-FEN form (set whenever the prior move was a double push). The pseudo-legal-only filter is applied at Zobrist-XOR time in M1.D — never to the stored EP target.** Ensures FEN round-trip stays clean.

2. **How strict to be at parse time.** No prior-art note prescribed this. Stance for M1.B: **strict syntactic validation; a small set of structural sanity checks** — see Decision §8 below for the precise enumeration. No deeper semantic validation (the side-not-to-move-in-check rule, castling-rights-consistent-with-rooks rule, etc. are deferred to a later layer or accepted as the caller's responsibility).

### Canonical perft positions referenced by this phase

The architecture research's §6 lists exactly **six** canonical perft positions (no Position 4 mirror — that and the wider perfect-perft mini-positions are deferred to M1.G's regression suite). M1.B uses these six FEN strings as the test fixture for parse round-trip:

## Decisions baked into this plan

1. **`Color` is a `#[repr(u8)] enum { White = 0, Black = 1 }`.** Indexing `[T; 2]` arrays by `color as usize` is the most idiomatic and the `Color` enum gives us exhaustive `match` for branching code in later phases. Two variants means there is no UB risk from raw `u8` casts (every value in `0..=1` is valid). `flip()` returns the other color.

2. **`PieceKind` is a `#[repr(u8)] enum { Pawn = 0, Knight, Bishop, Rook, Queen, King }`.** Same reasoning. Six variants; `as usize` indexes the piece-bitboard array. `PieceKind::COUNT = 6` constant pinned for array sizing. Order matters — this enumeration matches the **kind sub-axis** of the Polyglot Zobrist piece enumeration (P-N-B-R-Q-K), so the M1.D Zobrist key table doesn't need a kind-axis remap. Color is independently handled by the Polyglot layout and isn't affected by `Color::White = 0, Black = 1`.

3. **`Piece` is a small struct, not a packed `u8`.** `pub struct Piece { pub color: Color, pub kind: PieceKind }` is 2 bytes (1 byte each, both `repr(u8)`). `Option<Piece>` is 2 or 3 bytes depending on whether the compiler exploits niches in `PieceKind`'s 0..=5 discriminant range — we do **not** bank on the niche. Mailbox `[Option<Piece>; 64]` is therefore **at most 192 bytes** (3 bytes × 64). 192 bytes is fine for now. Packing into a `NonZero<u8>` for guaranteed-niched `Option<Piece>` is premature; revisit only if the mailbox shows up in profiles. `Piece` deliberately has no `index()` method — the mailbox is sparse and indexed by Square; piece queries decompose `(Color, PieceKind)` into the two bitboard arrays, never into a flat `[T; 12]`.

4. **`CastlingRights(u8)` newtype, 4 bits used.** Layout: bit 0 = white kingside, bit 1 = white queenside, bit 2 = black kingside, bit 3 = black queenside. The `K, Q, k, q` ordering matches the Polyglot Zobrist castling-key convention (Polyglot's bits 0–3 are also white-kingside, white-queenside, black-kingside, black-queenside) — M1.D's hash code reads the same field directly. Constants `WHITE_KING`, `WHITE_QUEEN`, `BLACK_KING`, `BLACK_QUEEN`, plus `NONE = empty` and `ALL = 0b1111`. Operations: `has(flag)`, `with(flag)`, `without(flag)`, `Display` produces the FEN substring (`"KQkq"`, `"-"`, etc.). Make/unmake at M1.E will use these to clear bits; M1.F's castling-legality check will read them. Inline in `position.rs` because `Position` is the only consumer. Not exported as a top-level item from `lib.rs` — accessible as `crate::position::CastlingRights` if a later layer needs it.

5. **EP target is `Option<Square>`, stored *as FEN encodes it*.** Per spec §16.1.3.4 — set whenever the immediately preceding move was a double pawn push, regardless of whether an opposing pawn can capture. The "EP-only-when-pseudo-legal" rule is **separately** applied by Zobrist hashing at M1.D; it does not affect storage. Documented in module docstring so this distinction is preserved.

6. **No Zobrist hash in `Position` at M1.B.** ADR-0009 binds at M1.D — that's where the field lands. Adding a `zobrist: u64` field now would require choosing whether to update it at FEN parse time, which means we'd have to write the from-scratch hasher in this phase. Cleaner to land it whole in M1.D. The architecture research's "sketch" struct (which lists `zobrist: u64`) is a forward-looking sketch; the M1.B realization is one field shy by design.

7. **Field order pinned for cache-line residency.** Position struct fields ordered with hot fields toward the front: bitboards first (8 × 8B = 64B, half a 128B M-series cache line), then mailbox (≤192B), then small auxiliary state. Documented in `position.rs`. Not load-bearing at M1.B (no hot path) but cheap to pin now.

8. **Sanity checks at FEN parse time — three structural rules:**
   - **One king per color** is invariant for `king_sq[color]: Square`. If we accept zero or two kings, the cache field is meaningless — making it `Option<Square>` would propagate ugliness everywhere downstream. Validating at parse time and storing a guaranteed-valid `Square` is much cleaner than relaxing the invariant.
   - **Pawns can never be on rank 1 or 8** — pawns promote on reaching the back rank. Catches the most common malformed-FEN class (typo'd promotion). Cheap.
   - **EP target square is on rank 3 (Black to move) or rank 6 (White to move).** Per spec §16.1.3.4: a White double-push leaves EP on rank 3 (Black is the active color); a Black double-push leaves EP on rank 6 (White is the active color). Any other rank is impossible from a legal preceding move. This check is structural enough to apply at parse time even though it relates to "what could have happened" — like the pawn-on-back-rank check, it cannot be reached from any legal game and its rejection is unambiguous. **Note:** the rank-vs-side-to-move *consistency* (e.g., side-to-move = White ↔ EP rank = 6) is not separately checked here; the spec wording makes it implicit in the "rank 3 or rank 6" rule but a White-to-move position with an EP target on rank 3 would slip through. Justified: this is the same class of "doesn't affect movegen correctness" subtlety as the side-not-to-move-in-check rule, deferred consistently with the rest of the §"Skipped" list.
   - **Skipped: side-not-to-move-not-in-check** — requires attack-square computation that lives in M1.C. We accept that an FEN with the wrong side-to-move-in-check parses successfully; the make-move layer will reject any move into self-check anyway, and search will not produce one.
   - **Skipped: castling-rights-consistent-with-rook-positions** — the FEN spec doesn't require this and many test fixtures (esp. shrunken endgame positions) violate it harmlessly. We accept the FEN as written; if a castling right is set without a viable rook, M1.F's castling generator simply emits no castling move.
   - **Skipped: total-piece-count limits** — beyond the king check, no validation. Promotion can produce nine queens; we accept any board state the bitboards can hold.

9. **`Position::Display` = FEN, `Position::Debug` = grid.** Mirrors `Bitboard`'s convention (Display = compact, Debug = visual). FEN is the natural single-line text form; the grid is the human-debugging form. Documented in module docstrings so the inversion-of-stdlib-convention is intentional. **Source-of-truth for both formats: bitboards (for piece placement) + auxiliary fields (`side_to_move`, `castling`, `ep_target`, `halfmove_clock`, `fullmove_number`). The mailbox and `king_sq` cache are derived state — neither `Display` nor `Debug` reads them.** The grid `Debug` printer iterates squares and reads `piece_at` for each (which the implementation may back via the mailbox), but the canonical print path goes through bitboards-by-color and bitboards-by-kind. The `set_piece` mutator (Decision §17) is responsible for keeping bitboards, mailbox, and king cache mutually consistent on every call; the `debug_assert_consistent` test validates this contract.

10. **`from_fen` returns `Result<Position, FenError>`; `FenError` is a non-exhaustive enum.** Variants: `WrongFieldCount { found: usize }`, `BadPiecePlacement(String)`, `BadActiveColor(String)`, `BadCastlingRights(String)`, `BadEnPassant(String)`, `BadHalfmoveClock(String)`, `BadFullmoveNumber(String)`, `MissingKing(Color)`, `TooManyKings(Color)`, `PawnOnBackRank(Square)`. The `String` payload is a brief reason (the original token, plus optional context) — keeps the error type small while still being debuggable. Marked `#[non_exhaustive]` so we can add variants later without breaking semver. **Layout: `derive(Debug)` (auto), implement `Display` separately as the human-readable form, implement `std::error::Error` as a leaf error (default `source()` returns `None` — no underlying cause for FEN parse errors).**

11. **No `FromStr` for `Position` yet.** `Position::from_fen(&str) -> Result<Position, FenError>` is the named entry point. Adding `impl FromStr for Position { type Err = FenError }` is a one-liner delegating to `from_fen`, which is fine to add when we have a real `parse::<Position>()` caller; deferring keeps the surface tighter. Same pattern as we used for M1.A's `Square::parse_uci`.

12. **`Position::starting_position()` is a `const fn` constructor — not just `from_fen("rnbqkbnr/...")`.** Reason: starting-position construction will be called by every `ucinewgame` UCI handler and every benchmark setup. Building it from constants is `const fn`-able (every Position field is const-constructible: `Bitboard` is const, `Option<Piece>` is const, `[Square; 2]` is const, `Color`/`CastlingRights`/`Option<Square>`/`u8`/`u16` all const). `Position::empty()` is also marked `const fn`. The constructor's correctness is anchored by a test that asserts `starting_position() == from_fen(STARTING_POSITION_FEN).unwrap()`.

13. **Exposed bitboard accessors return `Bitboard`, not `&Bitboard`.** `Bitboard` is `Copy`; reference accessors would just add ceremony. Pattern follows M1.A.

14. **No `unsafe` blocks anywhere in M1.B.** Same reasoning as M1.A — the user can't audit `unsafe`. `Square::new_unchecked` (already exists) is fine because it's debug-asserted and produces no UB on release-mode misuse.

15. **`#[derive(Copy, Clone)]` on `Position`.** At ~270 bytes (8 × 8B bitboards + ≤192B mailbox + ~9B aux state + alignment padding), copying is ~3 cache lines. Worth it for ergonomics — `make_move` (M1.E) will work on `&mut Position` so the typical hot path doesn't copy. Tests benefit from `Copy` (write `let p = starting_position(); let p2 = p.with_some_change();` style). If profiling later shows the copy hurts, we drop `Copy` and force `&mut`. The cost of removing `Copy` later: search/replace on test code, no production-call-site disruption. Cost of *keeping* `Copy` and not regretting it: zero. Defer the decision: keep `Copy` for now.

16. **`PartialEq` on `Position` is the structural derive. `Hash` is *not* derived in M1.B.** Two Positions are equal iff every field matches — including auxiliary state. Notably this means two FEN-parsed positions are equal iff their FEN strings are equal field-by-field (not just position-equal in the chess sense — which is FEN-equality without halfmove/fullmove). Documented; if a "chess-equivalent" comparison is later needed (e.g. for repetition detection), it's a separate function/Zobrist comparison, not `PartialEq`. **`Hash` deliberately omitted on `Position` for M1.B** — the only sensible hash for `Position` is Zobrist (lands at M1.D), and the structural-`Hash` derive would hash 270 bytes pointlessly. `Hash` *is* derived on the small types — `Color`, `PieceKind`, `Piece`, `CastlingRights` — because the cost is one trait impl per type, they're plausible map keys, and removing later for a real caller is friction we can avoid.

17. **`set_piece` debug-asserts against king-overwrite.** The `pub(crate)` `set_piece(&mut self, sq: Square, piece: Piece)` mutator places a piece, updating bitboards + mailbox + king cache. If invoked on a square that already holds a king of either color, **it `debug_assert!`s** — overwriting a king would silently invalidate the `king_sq` cache for that color. The FEN parser walks the placement string left-to-right and never overwrites; tests that use `set_piece` are expected to start from `Position::empty()`. A king must be explicitly cleared first if it ever needs to move via `set_piece` (the M1.E `make_move` will use a different mutator path). In release builds the assert is compiled out; in debug builds (i.e., `cargo test`) it panics with a clear message.

    #[must_use] pub const fn without(self, flag: CastlingRights) -> CastlingRights;
    pub const fn bits(self) -> u8;

impl fmt::Display for CastlingRights {
    /// "-" if NONE, else uppercase-before-lowercase, kingside-before-queenside (FEN convention).

#[derive(Copy, Clone, PartialEq, Eq)]   // Debug is custom, prints grid; Hash deliberately omitted
pub struct Position {
    // 8 × 8 bytes = 64 bytes (one M-series half cache line)
    piece_bb: [Bitboard; PieceKind::COUNT],   // 6
    color_bb: [Bitboard; Color::COUNT],       // 2

    // 64 × ~2 bytes ≈ 128 bytes
    mailbox: [Option<Piece>; 64],

    // Small aux state
    king_sq: [Square; Color::COUNT],
    side_to_move: Color,
    castling: CastlingRights,
    ep_target: Option<Square>,
    halfmove_clock: u8,
    fullmove_number: u16,
}

    /// Has zero kings — produced positions WILL FAIL the parse-time invariants;
    /// this function is only suitable as a starting point that the FEN parser
    /// (or a test) immediately fills in. It is `pub(crate)`.
    pub(crate) const fn empty() -> Position;

    pub const fn starting_position() -> Position;
    pub fn from_fen(s: &str) -> Result<Position, crate::fen::FenError>;
    pub fn to_fen(&self) -> String;       // backed by Display

    // set_piece debug-asserts against overwriting an existing king.
    pub(crate) fn set_piece(&mut self, sq: Square, piece: Piece);
    pub(crate) fn set_aux_state(
        &mut self,
        side: Color,
        castling: CastlingRights,
        ep: Option<Square>,
        halfmove: u8,
        fullmove: u16,

    pub(crate) fn validate_post_parse(&self) -> Result<(), crate::fen::FenError>;

    pub const fn fullmove_number(&self) -> u16;

    pub const fn piece_at(&self, sq: Square) -> Option<Piece>;
    pub const fn pieces(&self, kind: PieceKind) -> Bitboard;            // both colors
    pub const fn pieces_colored(&self, color: Color, kind: PieceKind) -> Bitboard;

### `src/fen.rs` — public surface

```rust
use crate::position::Position;
use crate::square::Square;
use crate::piece::Color;

#[derive(Clone, Debug, PartialEq, Eq)]
#[non_exhaustive]
pub enum FenError {
    WrongFieldCount { found: usize },
    BadPiecePlacement(String),     // "rank 5 has 9 squares", "unknown piece 'X'", etc.
    BadActiveColor(String),        // value seen, e.g. "W"
    BadCastlingRights(String),
    BadEnPassant(String),
    BadHalfmoveClock(String),
    BadFullmoveNumber(String),
    MissingKing(Color),
    TooManyKings(Color),
    PawnOnBackRank(Square),
}

// Auto-derived Debug shows the variant tag and payload — handy for assertion-failure messages.
// Display is the human-readable form; std::error::Error has the default `source() = None`
// since FEN parse errors are leaf errors (no underlying cause to chain).
impl fmt::Display for FenError { /* friendly form per variant */ }
impl std::error::Error for FenError {}

// Parse driver — Position::from_fen delegates here.
pub(crate) fn parse(s: &str) -> Result<Position, FenError>;

// Format driver — Position's Display delegates here. Always emits all 6 fields.
pub(crate) fn format(p: &Position, f: &mut fmt::Formatter<'_>) -> fmt::Result;
```

The parser is `pub(crate)` because the public path is `Position::from_fen`; same for format/Display. Splitting `fen.rs` lets the FEN logic be reviewed and tested as a unit, and isolates the largest single chunk of M1.B code.

### Position grid `Debug` format — pinned for snapshot test

8 rank rows (rank 8 top, rank 1 bottom), each prefixed by its rank number and a space; cells are space-separated, FEN piece letters for occupants (uppercase white, lowercase black), `.` for empty. A trailing file-label row prefixed by two spaces, then a one-line summary (`<color> to move, halfmove=N, fullmove=M, castling=KQkq, ep=e3` or `ep=-`) for context. Each line ends with `\n`. The summary line is included so the auxiliary state is visible at a glance — without it, the grid alone hides side-to-move, castling, EP, etc.

Concrete encoding rules (mirroring `Bitboard`'s grid format, with the summary line added):

- Every line — including the file-label and summary rows — ends with `\n`. The full string therefore ends with `\n`.
- No leading newline; no blank line anywhere.
- Cells inside a row are separated by exactly one space; one space follows the rank-number prefix and precedes the first cell.
- No trailing whitespace on any line.
- The file-label row begins with two spaces.
- The summary line format: `<color> to move, halfmove=<n>, fullmove=<m>, castling=<rights>, ep=<sq-or-dash>` where `<color>` is `White` or `Black`, `<rights>` is the FEN castling form (`KQkq`, `-`, …), `<sq-or-dash>` is the EP square in lowercase or `-`.
- Source-file representation of the snapshot literal uses `\n` line endings (Rust formatters never emit `\r\n`). If a future contributor edits the snapshot in a Windows-line-ending editor, the test will fail loudly — that's intended.

Example for the starting position:

```
8 r n b q k b n r
7 p p p p p p p p
6 . . . . . . . .
5 . . . . . . . .
4 . . . . . . . .
3 . . . . . . . .
2 P P P P P P P P
1 R N B Q K B N R
  a b c d e f g h
White to move, halfmove=0, fullmove=1, castling=KQkq, ep=-
```

This is the literal byte sequence pinned by the snapshot test below.

## Test coverage

### `piece.rs` tests

### `tests/fen_round_trip.rs` integration test

A single integration-test file that uses only the public API (`use clawfish::Position;`). Its job: prove the public API is sufficient (we don't quietly depend on `pub(crate)` internals to compose a Position) and that a downstream consumer can do FEN round-trip end-to-end. Tests:

- `starting_position_round_trip` — `STARTING_FEN.parse_via_from_fen.to_fen == STARTING_FEN`.
- `canonical_perft_positions_to_fen_matches_input` — for each canonical FEN: `Position::from_fen(s).unwrap().to_fen() == s`. Direct round-trip check on the public API.
- `canonical_perft_positions_idempotent_round_trip` — `from_fen(s).unwrap() == from_fen(&from_fen(s).unwrap().to_fen()).unwrap()` for the canonical six. Stronger: catches a class of formatter bugs where `to_fen` produces a *different* but still-parseable string.

### Test naming conventions

All test names are `snake_case`, beginning with the verb of the assertion (`parse_rejects_…`, `format_emits_…`, `castling_…_displays`). No `it_should_…` prefixes. Numbered variants only when nominal differentiation isn't possible.

## Construction protocol — pinned for parallel implementation

Because step 7.2 and 7.3 run in parallel, the contract between `Position` and `fen.rs` must be unambiguous. The contract:

1. **`Position::empty()`** is a `pub(crate)` constructor that returns a `Position` with all bitboards `Bitboard::EMPTY`, mailbox all `None`, `king_sq` set to `Square::A1` for both colors (placeholders — the empty board violates the king-cache invariant, hence not public), `side_to_move = White`, `castling = CastlingRights::NONE`, `ep_target = None`, `halfmove_clock = 0`, `fullmove_number = 1`.

2. **`Position::set_piece(&mut self, sq: Square, piece: Piece)`** is a `pub(crate)` mutator that:
   - clears any previous occupant at `sq` (mailbox → `None`, removes from all relevant bitboards);
   - sets the new occupant (mailbox → `Some(piece)`, sets the piece bitboard, sets the color bitboard);
   - if `piece.kind == King`, updates `king_sq[piece.color]`.

3. **`Position::set_aux_state(&mut self, side: Color, castling: CastlingRights, ep: Option<Square>, halfmove: u8, fullmove: u16)`** is a `pub(crate)` mutator that sets all five auxiliary fields in one call.

4. **`fen::parse` workflow:** start with `Position::empty()`, then walk the placement string left-to-right calling `set_piece` for every occupant. **The pawn-on-back-rank check (Decision §8) and the EP-rank check fire synchronously during placement-walk and field-parse** — i.e., in `fen::parse`'s body, before `set_piece` is called for a back-rank pawn (so the invalid pawn never enters the position) and before `set_aux_state` is called for a bad EP square. Then `set_aux_state` once with the validated auxiliary state, then `validate_post_parse` runs the cross-field invariants (king count). If everything passes, return the position; otherwise return the matching `FenError`.

5. **Invariant validation** is split between two layers: (a) **per-token validation** during parse-walk (pawn-on-back-rank, EP-on-rank-3-or-6, all syntactic checks), embedded in `fen::parse`; (b) **cross-field validation** after construction via `pub(crate) fn validate_post_parse(&self) -> Result<(), FenError>` in `position.rs`, which currently only counts kings — exactly one of each color via `pieces_colored(color, King).count() == 1` plus `king_sq[color]` consistency. Splitting like this means `validate_post_parse` doesn't need to re-walk the board to re-check pawn ranks.

This protocol means `position.rs` exposes the construction primitives and `fen.rs` orchestrates them — neither file needs to import the other's parsing logic.

## Reviewer-revision notes

Revisions applied during the plan-review loop are recorded here for traceability.

### §A — Strict castling order in FEN parsing

The FEN spec §16.1.3.3 says: "Those letters which appear will be ordered first uppercase before lowercase and second kingside before queenside." This is a positive statement about the export form, not a permissive statement about what to accept on import. We are conservatively strict: parse rejects re-orderings (`QKkq`, `qkQK`, etc.). Justification: (a) the spec is unambiguous; (b) a reordered FEN we accept silently is most likely malformed; (c) we can relax later if a real input forces it. Test `parse_rejects_bad_castling_order` pins this stance.

### §B — Strict whitespace in FEN parsing

The FEN spec §16.1.3 says: "Adjacent fields are separated by a single ASCII space character." The parser uses **`s.split(' ')`** (strict — exactly one space, no leading/trailing/internal-double-space tolerance), not `s.split_whitespace()` (lenient). Same reasoning as §A: spec wording is positive, we follow it literally and relax only when a real input forces us. Tests `parse_rejects_leading_whitespace`, `parse_rejects_trailing_whitespace`, `parse_rejects_double_space` pin the stance.

### §C — Strict-decimal integer parsing for halfmove and fullmove

Halfmove and fullmove fields are parsed via `u8::from_str_radix(s, 10)` and `u16::from_str_radix(s, 10)` respectively. Both reject leading `+`, leading `-`, leading whitespace, trailing whitespace, and any non-digit character. Tests `parse_rejects_negative_*`, `parse_rejects_plus_prefixed_*`, `parse_rejects_non_numeric_halfmove` pin this. Boundary tests `parse_accepts_max_halfmove` (255), `parse_accepts_max_fullmove` (65535) anchor that the maximum representable value is accepted.
