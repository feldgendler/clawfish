**Status:** Plan (drafted 2026-06-14). Workflow: research → plan → tests → implement → review → bench → SPRT.

Land a correct, allocation-free SEE evaluator and wire it into move ordering as the ADR-0030 deferred "good/bad capture split", gated by:

## 2. SEE semantics — the spec (pin down the ambiguities *before* coding)

Different sources define SEE edge cases differently (research note `m7-see-test-positions.md`). We commit to one explicit definition so the fast resolver, the slow oracle, and the curated tests all agree:

- **Pins are IGNORED.** A pinned defender still participates in the exchange (it "recaptures"). This is the mainstream bitboard-SEE definition and is what an attacker-bitboard resolver computes for free. Consequence: the slow oracle must also ignore pins (so it is built from attacker bitboards, **not** from legal movegen — see §5.2).
- **Least-valuable-attacker (LVA) recapture order**, iterating piece kinds Pawn → Knight → Bishop → Rook → Queen → King (the `PieceKind as usize` order, matching `MATERIAL` indexing).
- **X-ray / batteries:** when an attacker leaves a square, a slider behind it on the same line (rook/queen on rank+file, bishop/queen on diagonal) is revealed and joins the exchange. Pawns/knights/kings are never revealed.
- **King recapture rule:** the king may recapture only when it is the side's chosen LVA *and the opposing side has no remaining attacker on the square* (otherwise the king would be moving into capture — illegal). Implemented by giving the king a large sentinel value (§3) and breaking the swap loop if the LVA is the king while the other side still has an attacker.
- **Promotion-on-capture:** the standard "best promotion is a queen" assumption. A pawn capturing onto the last rank: the gain includes `(SEE_VALUE[Queen] − SEE_VALUE[Pawn])`, and the piece now occupying the square (for the opponent's next recapture) has the **queen** value, not pawn. Non-capture promotions are **out of scope** (we only call `see()` on captures).
- **En passant:** the captured pawn is **not** on the destination square. Initial victim value = `SEE_VALUE[Pawn]`; the starting occupancy removes **both** the moving pawn (from-square) and the EP-captured pawn (the square behind the destination), so x-ray rescans see through the vacated EP-victim square.
- **Return value:** `see(pos, mv) -> i32` = net material outcome, in centipawns on our value scale, from the perspective of the side making `mv` (positive = the capturing side comes out ahead; the move at least breaks even iff `see >= 0`).

These commitments are recorded in the M7 ADR at landing.

## 3. Value scale

New `const SEE_VALUE: [i32; 6]` in `src/see.rs`:

```
SEE_VALUE = [82, 337, 365, 477, 1025, 30000]   // P, N, B, R, Q, K
```

- The first five **mirror PeSTO MG `MATERIAL`** (`src/eval/data.rs`) for consistency with the existing `mvv_lva_score` tier, but are defined **independently in `see.rs`** so SEE is decoupled from any future eval re-tuning (SEE is a search primitive; NNUE does not obsolete it — roadmap §M7).
- King = `30000`: a sentinel larger than the maximum material one side can have on the board, so a king recapture is only ever "spent" as the last resort and never makes a losing capture look winning. Pinned by `const _SEE_KING_SENTINEL_DOMINATES: () = { assert!(SEE_VALUE[King] > 9*SEE_VALUE[Queen] + 2*SEE_VALUE[Rook] + 2*SEE_VALUE[Bishop] + 2*SEE_VALUE[Knight]); };` (9 queens + the rest of a maxed promoted army; `9*1025+2*477+2*365+2*337 = 11583 < 30000`) to prevent accidental edit.

Scale note for tests: community test positions usually publish answers on a P=100 scale. Our curated expected values are **re-derived on the `SEE_VALUE` scale** (the exchange *sequence* is identical; only the numeric total differs). The proptest is scale-independent (both resolvers share `SEE_VALUE`).

## 4. The SEE evaluator (`src/see.rs`) — fast path

### 4.1 `attackers_to`

```rust
pub(crate) fn attackers_to(pos: &Position, sq: Square, occ: Bitboard) -> Bitboard
```

Union over both colors of: `pawn_attacks_from(sq, side.flip()) & pawns_of(side)` (note the colour flip — squares a *side*'s pawn attacks `sq` from are where the *opposite* pawn-attack pattern of `sq` lands), `knight_attacks(sq) & knights`, `bishop_attacks(sq, occ) & (bishops|queens)`, `rook_attacks(sq, occ) & (rooks|queens)`, `king_attacks(sq) & kings`. All primitives exist (`src/movegen/masks.rs`, `src/magic.rs`). Returns all attackers of both colors; the swap loop masks by side.

**Incremental-attacker discipline (fast path).** The swap loop maintains a running `attackers: Bitboard`, initialized once from `attackers_to(pos, to, occ)`. Pawn/knight/king attackers are occupancy-independent and are **never rescanned** — they are computed once into `attackers` and only ever *removed* (cleared as spent). After clearing the spent LVA bit from both `occ` and `attackers`, the loop ORs in **only newly-revealed sliders**: `attackers |= ((bishop_attacks(to, occ) & bishop_like) | (rook_attacks(to, occ) & rook_like)) & occ & !already_counted`. The full `attackers_to` is called exactly once (initialization); the per-step rescan touches sliders only. (Contrast: the slow oracle in §5.2 deliberately calls full `attackers_to` *every* step — that recompute is its independence axis, and it is fine for an O(captures) test path but must not be the fast path, or the "fast" path is no faster than the oracle and the §7 NPS gate is at risk.) Recomputing both slider sets (diagonal + orthogonal) against the shrinking `occ` each step is simple and correct; the incremental-direction-only optimization is a deferred micro-opt.

### 4.2 `see(pos, mv) -> i32` — swap-list

Allocation-free: `gain: [i32; MAX_SEE_DEPTH]` on the stack, `const MAX_SEE_DEPTH: usize = 32` — comfortably above the maximum number of attackers any one square can have (≤ 16 per side in legal material, far fewer in practice; 32 is a safe over-bound, **not** the 32-pieces-on-board bound). Algorithm (standard swap-list):

1. Decode `from`, `to`, flag. Determine **initial victim value** and **occupancy setup**:
   - normal `Capture`: `victim = SEE_VALUE[piece_at(to).kind]`; `occ = occupied_all`.
   - `EnPassant`: `victim = SEE_VALUE[Pawn]`; `occ = occupied_all` with the **EP-victim square** cleared. **EP-victim square derivation (pinned, used identically by fast path, slow oracle, and curated tests):** for an EP move `to == ep_target` (the empty landing square); the captured pawn sits one rank *toward the moving side* on `to`'s file — equivalently the square sharing `from`'s rank and `to`'s file (`square(file_of(to), rank_of(from))`). Compute it from `from`/`to` directly, **not** from a shared helper (independence requirement, §5.2).
   - `*PromoCapture`: `victim = SEE_VALUE[piece_at(to).kind]`; the mover's on-square value becomes `SEE_VALUE[Queen]` and `gain[0]` adds `(SEE_VALUE[Queen] − SEE_VALUE[Pawn])` (queen-promo assumption — see §6 nit on under-promo-captures).
   - non-capture move: **never called** (caller restricts to `mv.is_capture()`).
2. Set `next_on_square` = the value of the moving piece *as it sits on `to` after the move* (`SEE_VALUE[Queen]` for a promo-capture, else `SEE_VALUE[mover.kind]`). Remove the mover from `occ` (clear `from`). Initialize the running `attackers` set (§4.1) against this post-mover `occ`. Side to move flips to the opponent.
3. `gain[0] = victim`. Iterate at depth `d = 1, 2, …`: select the side-to-move's **LVA** = lowest-`SEE_VALUE` piece in `attackers & occ & pieces_of(side_to_move)`; if the set is empty, stop. **King-recapture legality (exact predicate):** if the selected LVA is a king *and* `attackers & occ & pieces_of(side_to_move.flip()) != 0` — i.e. after this king would capture, the opponent still has an attacker on `to` and would capture the king — **break before scoring `gain[d]`** (the king cannot legally recapture into a still-attacked square; the sequence ends at `d-1`). The opponent-still-attacks test is evaluated on the current (post-prior-removal, post-rescan) `attackers & occ`, not the pre-iteration set. Because the king's sentinel value makes it the *last* LVA chosen, this fires only when no cheaper same-side attacker remains. Otherwise: `gain[d] = next_on_square − gain[d-1]`; set `next_on_square = SEE_VALUE[lva.kind]` (→ `SEE_VALUE[Queen]` if the LVA is a pawn moving to the last rank); clear the LVA bit from `occ` and `attackers`; rescan x-ray sliders into `attackers` (§4.1); flip side; `d += 1`.
4. **Minimax back-up (CORRECTED — see note).** Use the **raw-gain-array** form: `gain[d]` stores the *raw* value captured at depth `d` (the value of the piece sitting on `to` that the depth-`d` capturer takes; for a promoting pawn, `piece_on_sq + (SEE_VALUE[Queen] − SEE_VALUE[Pawn])`). Fold from the deepest scored entry down: for `i` from `d-1` to `1`, `gain[i-1] -= max(0, gain[i])`; return `gain[0]`. This is the iterative form of the recursive definition `f(i) = captured(i) − max(0, f(i+1))` with the **initial** capture forced (no `max(0,·)` on `gain[0]`). Each side recaptures only if it improves on standing pat.

   > **Implementation note (formula fix during Slice A).** An earlier draft of this step wrote the back-up as `gain[i-1] = max(-gain[i], gain[i-1])` with `gain[d] = next_on_square − gain[d-1]` — this is **algebraically wrong** (it drops the outer negation of CPW's `gain[d-1] = −max(−gain[d-1], gain[d])`, yielding an always-non-negative result, e.g. RxP/P → +82 instead of −395). The raw-gain form above is what shipped. The differential proptest cannot catch a formula error (both resolvers share it); the **hand-computed curated values** are what caught it — and separately caught a **mid-sequence-promotion** bug (a promoting *recapture*'s gain must include the captured piece's value, not just the queen value), exposed only by a hand-authored pawn-recaptures-and-promotes-onto-a-rook position (research §5 gap #6) because the Arasan suite has promotion only as the initial move. Lesson reinforced: a differential test between two implementations that share a value table / formula proves *agreement*, not *correctness* — externally-grounded hand-computed values are the real gate.

The intricate promotion/EP arithmetic is the bug surface; it is covered by the curated hand-computed tests (§5.1) and the differential proptest (§5.2).

### 4.3 Optional fast-out (perf, behavior-preserving)

Captures where `SEE_VALUE[victim] >= SEE_VALUE[attacker]` are **always** `see >= 0` (you cannot lose material capturing an equal-or-greater piece — worst case it is traded off and you are ≥ 0). The ordering hook (§6) short-circuits these to "good" without running the full swap loop, keeping SEE off the hot path for the common PxN/RxQ/etc. cases. Precise predicate: `see_nonneg_fastout(mv) = SEE_VALUE[piece_at(to).kind] >= SEE_VALUE[piece_at(from).kind]` for a plain `Capture`; for `EnPassant` the victim is `Pawn` and the attacker is `Pawn` so it is always true (PxP, SEE≥0 trivially); for `*PromoCapture` the promotion gain only *increases* the outcome, so `victim >= attacker` is still sufficient (and the case it misses — e.g. a pawn promo-capturing a pawn — falls through to the full `see()`, which correctly credits the promo). **Evaluated on `SEE_VALUE`** (consistent with `see()`), and lives in the *ordering hook*, not inside `see()` (so `see()` stays a pure full resolver for testing). **Correctness-neutral** (a strict subset shortcut; the curated/proptest exercise the full resolver directly). Caveat for §7: the fast-out fires exactly on cheap-takes-expensive captures, so it does **not** bound worst-case per-node cost — every `attacker > victim` capture (most defended QxP-class bad captures) still runs the full `see()`. The §7 NPS gate must therefore measure a capture-dense tactical position, not only startpos. Confirm the fast-out actually helps via §7; drop it if it doesn't.

## 5. Test surface (authored before implementation — §workflow TDD)

### 5.1 Curated correctness suite — `see.rs` `#[cfg(test)]`

Hand-computed `(FEN, move-uci, expected_see)` cases, **expected values derived by hand from the `SEE_VALUE` numbers** (not lifted from either resolver — so a wrong `SEE_VALUE` constant, invisible to the proptest since both resolvers share it, is still caught here), grouped by corner case. Seeded from `docs/research/m7-see-test-positions.md` (community/prose-sourced, ADR-0003-clean) plus hand-authored fills where the research flags coverage gaps:
- **X-ray / battery:** rook-behind-rook, queen-behind-bishop reveals.
- **Promotion-on-capture:** pawn x-takes onto rank 8 with/without recapture.
- **En passant:** EP capture where an x-ray opens through the vacated victim square.
- **Multi-defender / multi-attacker:** squares with 2–3 attackers each side, exercising LVA order.
- **Pinned-edge & equal-value stop:** documents the pin-ignoring choice (§2) explicitly — a position where a pinned defender *does* participate in our SEE.
- Trivial sanity: PxQ (always +), hanging-piece capture, defended-equal trade.

### 5.2 Property test — `see()` ≡ slow reference

- **Slow reference** (`see::slow_see`, `#[cfg(test)]`): a structurally-independent bitboard SEE that **recomputes the full attacker set from scratch after every removal** (calls full `attackers_to` each step, no incremental x-ray bookkeeping) and uses the same LVA order, same `SEE_VALUE`, same pin-ignoring semantics. Independence is in the x-ray mechanism (the primary bug surface) and loop structure — the M1.C slow-ray-walker-vs-magic precedent. **Independence requirement (must-hold):** the slow oracle derives the EP-victim square and the promotion-rank trigger by its **own** inline computation from `mv`'s from/to ranks (§4.2 step 1), **not** by importing a shared helper from the fast path — otherwise a shared EP/promo *square-arithmetic* bug is baked into both and the differential test cannot see it. The shared `SEE_VALUE` array and pin-ignoring semantics are *spec* (intended shared), and are independently guarded by the hand-derived curated suite (§5.1).
- **Proptest:** generate random legal positions (reuse the existing position generators / random-playout helper used elsewhere in the suite); for each, enumerate all capture moves (`generate_moves` filtered by `is_capture()`); assert `see(pos, mv) == slow_see(pos, mv)` for every one. Target ≥ 2048 cases (the H1-P1 magnitude).

### 5.3 Move-ordering split tests — `search.rs` `#[cfg(test)]`

- A good capture (SEE ≥ 0) ranks **above** killer0 and any history quiet.
- A bad capture (SEE < 0, e.g. QxP defended by a pawn) ranks **below** every quiet (after killers and history-quiets).
- TT move still promotes to index 0 even when it is a bad capture.
- The new compile-time tier invariant (§6) holds.
- Audit + update the specific H1-S*/HS* fixtures ADR-0030 §8 lists as pinning the all-captures-outrank-quiets discipline — **S20–S26, HS9, HS12** (plus the H1-P1 equivalence proptest, which stays valid by construction since both `MoveStager` and `order_moves` share the modified comparator). Slice B enumerates which of these contain a SEE-negative capture and bounds the churn up front, rather than discovering it mid-implementation.

### 5.4 Bench / determinism pins

Move ordering changes → node counts change. Update the deterministic-bench fixtures (the `bench: <N>` signature + the depth-4 pin) to the new post-SEE counts once measured. This is expected, not a regression (§7).

## 6. Wiring the split into move ordering (`src/search.rs`)

Single hook: `negamax_move_order_score` (the comparator shared by `MoveStager::new` production and the `#[cfg(test)] order_moves` reference — modifying it keeps H1-P1 equivalence intact by construction).

New tier constant + invariant. The bottom tier must sort strictly below the worst history-quiet (`-MAX_HISTORY`), so the bound is the **real** maximum `mvv_lva_score` (a promo-capture: `victim*16 − attacker + promo` ≤ `1025*16 − 82 + 1025 = 17343`), not a magic fudge. Define it from the value tables and **fold the bad-capture clause into the existing `_SCORE_TIER_INVARIANTS` block** (search.rs:3013) rather than a parallel const that can drift:

```rust
const BAD_CAPTURE_BASE: i32 = -2_000_000;
/// Real upper bound on mvv_lva_score: max victim (Q) ×16 − min attacker (P) + max promo (Q).
const MVV_LVA_MAX: i32 = MATERIAL[Queen] * 16 - MATERIAL[Pawn] + MATERIAL[Queen]; // 17343
// extend the existing _SCORE_TIER_INVARIANTS const block:
assert!(BAD_CAPTURE_BASE + MVV_LVA_MAX < -(MAX_HISTORY as i32)); // -1_982_657 < -16384 ✓
```

New ordering, full tier ladder (top → bottom):

```
TT move  >  good captures (SEE>=0, MVV-LVA order)  >  killer0  >  killer1
         >  history quiets  >  bad captures (SEE<0)
```

`negamax_move_order_score` change (captures branch only; quiets/killers untouched):

```rust
if !is_quiet(mv) {
    let mvvlva = mvv_lva_score(mv, pos);
    if mv.is_capture() {
        // fast-out: victim>=attacker ⇒ SEE>=0 (good) without the resolver
        if !see_nonneg_fastout(mv, pos) && see(pos, mv) < 0 {
            return BAD_CAPTURE_BASE + mvvlva;   // demote below quiets
        }
    }
    return mvvlva + CAPTURE_OFFSET;             // good capture / promotion (unchanged)
}
```

- Good captures keep their **existing MVV-LVA sub-order** (byte-compatible with today among good captures) — we do **not** reorder good captures by SEE value, minimizing behavioral surface.
- Bad captures keep MVV-LVA sub-order, just offset into the bottom tier.
- Non-capture promotions (`QueenPromo` etc.) are **not** split (not `is_capture()` per `mov.rs:238`; also not `is_quiet()` per search.rs:3026, so they hit the `!is_quiet` branch and keep `CAPTURE_OFFSET`) — unchanged from today.
- **Under-promotion captures** (`KnightPromoCapture` etc.) *do* run through `see()`, which assumes a queen promotion (§2). This over-values an under-promo-capture's outcome — an accepted, standard SEE simplification (the engine rarely searches under-promo-captures as the principal line); noted, not fixed.
- **TT-move / split interaction (made explicit):** TT promotion happens *after* the sort, by `bits()`-keyed `Vec::remove`+`insert(0,…)` in `MoveStager::new` (search.rs:3637) and `order_moves` (3144) — it does **not** consult the ordering score. So a bad-capture TT move still promotes to index 0; the score demotion only affects sort position *among non-TT moves*. The §5.3 "TT bad capture promotes to index 0" test pins this is intentional, not accidental.
- **qsearch ordering untouched** (qsearch has its own MVV-LVA path; ADR-0030 §9 keeps qsearch out of the stager). M7.B owns qsearch.

## 7. Performance gate — the ADR-0030 §10 scar (hard, not optional)

`bench`'s 16-position fresh-allocator snapshot **did not** surface the H1 v1 per-node regression; sustained game-load did (−110 then −44 Elo). SEE-in-ordering adds per-node cost, so we apply the same defensive checks **before** committing:

1. **`see()` is allocation-free** (stack `[i32; 32]`; no `Vec`). Enforced by reading the code + a `#[should_panic]`-free design; noted in review.
2. **Sustained-go check:** 20-sequential-`go depth 10`, HEAD-with-SEE vs HEAD-without, wall-clock ratio reported, **on a capture-dense tactical position** (a WAC / Bratko-Kopec position with heavy piece contact, where `attacker > victim` captures — the ones that bypass the §4.3 fast-out and run the full resolver — are frequent) **in addition to** startpos. SEE's cost is concentrated in sharp middlegames, so startpos alone is a weak probe (ADR-0030 §10's scar was an allocation regression visible under *any* load; SEE's is paid per resolved capture). Also a single-shot `go depth 14`. Target: **NPS parity** within run-to-run noise after accounting for the (legitimate) node-count change — not node parity.
3. **Defensive short SPRT** (50–100 pairs, mixed-TC) folded into the main SPRT campaign launch — the first checkpoint must not be a sharp negative the way H1 v1 was.

If NPS regresses materially, tune the fast-out (§4.3) / x-ray rescan before proceeding.

## 11. Risks & open items

- **Per-node cost (primary).** Mitigated by the fast-out + allocation-free resolver + the §7 gate. Highest-probability failure mode given §10.
- **Promotion/EP arithmetic.** Highest-probability *correctness* bug; covered by curated + differential tests.
- **Test-fixture churn** in H1-S*/HS*: expected; audit during Slice B.
- **Research dependency:** the curated-position research note (`m7-see-test-positions.md`) is in flight; if it under-delivers a category, hand-author fills (§5.1) — the differential proptest is the real correctness backstop, so a thin curated set is acceptable.
- **ADR:** allocated at landing (records the §2 semantics + the §3 value scale + the §6 tier).
