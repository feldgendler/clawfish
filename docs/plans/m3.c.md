# M3.C — Negamax + alpha-beta core

First playing engine that *searches*. Replaces M3.A's depth-1 GreedyMover with full alpha-beta recursion at fixed depth (set via `go depth N`). Single iteration; no iterative deepening, no time management, no qsearch (all deferred to M3.D / M3.E). Calls `evaluate(pos)` at `depth == 0` (horizon effect accepted; M3.D adds qsearch).

ADR-0013 codifies the design. Research consensus across Sonnet + Opus parallel passes converged on every headline call.

## 0. Goals

- `AlphaBetaMover` Search impl in `src/search.rs` — replaces `GreedyMover` as production search. Plays significantly stronger.
- Fail-soft negamax with `i32` scores, `MATE = 30000`, ply-adjusted mate-in-N; mate-distance pruning.
- Triangular PV recovery; `info ... pv <line>` shows full PV at depth.
- MVV-LVA capture ordering (quiets in movegen order).
- Repetition + 50-move draw detection via M3.B helpers (called at `ply > 0` only; root always picks a move).
- UCI `score mate N` translation (full moves, signed).
- Cancellation: 4096-node cadence + sentinel-return + post-call abort check.
- ADR-0013 codifies search structure.
- Strength sanity via fixed-depth hand-driven match against `baseline/material-greedy` worktree (SPRT-runner-driven validation lands at M3.F per roadmap).

## 1. Out of scope

- Quiescence search — M3.D. Leaf evaluation at `depth == 0` is `evaluate(pos)` directly.
- Iterative deepening — M3.E. Single negamax invocation at the requested depth.
- Time management — M3.E. `go movetime` / `go wtime btime ...` honored only for cancellation deadline; no soft/hard cap discipline yet.
- PVS / aspiration windows — M4. Plain alpha-beta only.
- Transposition table — M4. No persistent state across nodes.
- Killer / history / SEE — M4 / M5.
- Bench command + SPRT runner (`scripts/sprt.sh`) + SPRT acceptance gating — M3.F. M3.C runs a fixed-depth hand-driven match against the M3.A `baseline/material-greedy` worktree as a strength sanity check.
- `Random_Seed` UCI option deletion — deferred to a separate cleanup commit. The option remains as a no-op for alpha-beta (alpha-beta is deterministic; `set_seed` and the option's value have no observable effect). Dropping it would touch `scripts/match.sh`'s self-play target (which currently differentiates the two engines via `option.Random_Seed=1` vs `=2`), the M2.D test surface, and the engine's `handle_uci` / `handle_setoption` — all out of M3.C's search-implementation scope.

### 3.2 `PvTable`

```rust
struct PvTable {
    moves: [[Move; MAX_PLY]; MAX_PLY],  // moves[ply][slot]
    lengths: [usize; MAX_PLY],          // lengths[ply] = how many slots populated at this ply
}

impl PvTable {
    fn new() -> Self {
        Self {
            moves: [[Move::default(); MAX_PLY]; MAX_PLY],  // requires Move: Default (added per §2)
            lengths: [0; MAX_PLY],
        }
    }
    fn clear_ply(&mut self, ply: usize) { self.lengths[ply] = 0; }
    fn update(&mut self, ply: usize, mv: Move) {
        let child_len = self.lengths[ply + 1];
        self.moves[ply][0] = mv;
        for i in 0..child_len {
            self.moves[ply][i + 1] = self.moves[ply + 1][i];
        }
        self.lengths[ply] = 1 + child_len;
    }
}
```

The zero-bits sentinel comes from `Move::default() == Move(0)` added in `src/mov.rs` (§2); decodes as `from=A1, to=A1, flag=Quiet` — never produced by movegen (a1→a1 is illegal). Updates fire only at PV nodes (the move improved alpha) AND only when the recursive subtree completed (the post-call `aborted` check skipped). `clear_ply(ply)` runs at the start of each negamax frame so a no-improving-move return leaves `lengths[ply] = 0`.

Memory: `[[Move; 64]; 64]` = `2 × 64 × 64 = 8192 B` = 8 KiB. The roadmap entry's "~4 KB" referred to the flat-triangular-array layout (`[Move; MAX_PLY * (MAX_PLY+1) / 2] = [Move; 2080] ≈ 4 KiB`); we use the 2D-square layout instead because the indexing is simpler (no `(ply * (ply + 1)) / 2`-style arithmetic at every access) at the cost of 4 KiB extra zero-init bytes. Trivial in the hot path.

`PvTable` is a direct field on `AlphaBetaMover` (no `Box`). `AlphaBetaMover` itself lives inside `Arc<Mutex<Box<dyn Search>>>` (engine.rs storage shape), so the table is already heap-allocated transitively; an extra `Box` would only add a second indirection on every access.

## 4. `Search::go` body

```
go(&mut self, position: &Position, ctx: &SearchContext, info_sink: &dyn Fn(&str)) -> SearchResult:
    // Per-go reset.
    self.history = ctx.history.clone();   // owned; M3.B invariant: last() == position.zobrist()
    self.nodes = 0;
    self.aborted = false;
    for i in 0..MAX_PLY: self.pv.lengths[i] = 0;

    // Determine target depth. Default 4 when `go` did not specify depth.
    let depth = ctx.limits.depth.unwrap_or(4).min(MAX_PLY as u32 - 1);

    // Single-iteration negamax. negamax handles move generation at every ply, including
    // the root, so movegen runs exactly once per node. searchmoves filtering is applied
    // at ply == 0 inside negamax. We pass &mut Position to negamax via a clone (mirrors
    // GreedyMover's M3.A pattern); make_move/unmake_move are balanced by the recursion.
    let mut pos_clone = *position;
    let score = self.negamax(&mut pos_clone, depth, 0, -INF, INF, ctx);

    // Position must be restored by balanced make/unmake.
    debug_assert_eq!(pos_clone, *position, "negamax must restore position via balanced make/unmake");

    // bestmove comes from pv[0][0] if any move improved alpha; otherwise None
    // (terminal at root: stalemate, mate, or empty searchmoves filter).
    let bestmove = if self.pv.lengths[0] > 0 { Some(self.pv.moves[0][0]) } else { None };

    // Emit info line BEFORE the wait loop. Real depth + real score (cp or mate, per
    // score_to_uci). PV from the triangular table.
    let elapsed_ms = ctx.start.elapsed().as_millis();
    let pv_str = if self.pv.lengths[0] == 0 {
        "0000".to_string()
    } else {
        self.pv.moves[0][..self.pv.lengths[0]]
            .iter()
            .map(|m| m.to_uci())
            .collect::<Vec<_>>()
            .join(" ")
    };
    info_sink(&format!(
        "info depth {} score {} nodes {} time {} pv {}",
        depth, score_to_uci(score), self.nodes, elapsed_ms, pv_str
    ));

    // Honor infinite/movetime/ponder wait loop. Same shape as GreedyMover.
    // KNOWN BUG inherited from M3.A: when bestmove is None (true mate/stalemate or
    // empty searchmoves filter), the search has nothing to return — but the UCI spec
    // says `go infinite` should still block until `stop`. The current shape returns
    // immediately in that case. Pre-existing M3.A bug; M3.E or a follow-up cleanup
    // will fix. Documented here so it doesn't get rediscovered as an M3.C regression.
    let wait = ctx.limits.infinite || ctx.limits.movetime.is_some() || ctx.limits.ponder;
    if wait {
        while !ctx.should_abort(self.nodes) {
            std::thread::sleep(Duration::from_millis(1));
        }
    }

    SearchResult {
        bestmove,
        depth,
        score_cp: Some(score),  // see "score_cp semantics" note below
        nodes: self.nodes,
        ponder: None,
    }
```

**`score_cp` semantics — known contract gap, deferred fix.** `SearchResult::score_cp: Option<i32>` is doc-commented as "Score in centipawns from the side-to-move's perspective." M3.C may store a mate-relative score (e.g. `Some(MATE - 1) = Some(29999)`) rather than a true centipawn value. Today the only consumer is `info`-line emission, which routes the value through `score_to_uci` for the cp-vs-mate split — so the mismatch is invisible. Future consumers (M3.F's `bench` command, M3.E's strength sentinel, NNUE training-data exporters) will need a clean cp-vs-mate split. The deferred fix splits `score_cp` into `score_cp: Option<i32>` (true centipawns; `None` when score is a mate score) plus a new `score_mate_plies: Option<i32>` (signed plies-to-mate; `None` when score is cp). M3.C explicitly does NOT make this change to keep the diff focused on the search; the doc-comment in `src/search.rs` is updated in this phase to flag the temporary mate-score-stuffed semantics. Ticket-style tracking: M3.E's bench/strength-sentinel work or a separate M3.C+1 cleanup commit picks up the field split.

## 5. `negamax` body

Pseudocode-with-Rust types:

```
fn negamax(
    &mut self,
    pos: &mut Position,
    depth: u32,
    ply: u32,
    mut alpha: i32,
    mut beta: i32,
    ctx: &SearchContext,
) -> i32 {
    // 1. Cancellation poll (4096-node cadence).
    self.nodes += 1;
    if self.nodes & 4095 == 0 && ctx.should_abort(self.nodes) {
        self.aborted = true;
        return 0;
    }

    // 2. Clear PV slot at this ply (so a no-improving-move return leaves length 0).
    self.pv.lengths[ply as usize] = 0;

    // 3. Repetition + 50-move draw checks (only at ply > 0 — root must always pick a move).
    if ply > 0 {
        if is_fifty_move_draw(pos.halfmove_clock()) { return 0; }
        if is_repetition(&self.history, pos.halfmove_clock()) { return 0; }
    }

    // 4. Mate-distance pruning.
    let mating_value = MATE - ply as i32;
    if mating_value < beta {
        beta = mating_value;
        if alpha >= mating_value { return mating_value; }
    }
    let mated_value = -(MATE - ply as i32);
    if mated_value > alpha {
        alpha = mated_value;
        if beta <= mated_value { return mated_value; }
    }

    // 5. Horizon: M3.C calls evaluate directly (qsearch is M3.D).
    if depth == 0 {
        return evaluate(pos);
    }

    // 6. Generate + order moves.
    let mut moves = MoveList::new();
    generate_moves(pos, &mut moves);
    let mut moves_vec = moves.iter().collect::<Vec<_>>();

    // Searchmoves filter at root (ply == 0).
    if ply == 0 {
        if let Some(filter) = &ctx.limits.searchmoves {
            moves_vec.retain(|m| filter.contains(m));
        }
    }

    // 7. Terminal: no legal moves.
    //    - At ply == 0 with searchmoves filter applied, an empty list means the filter
    //      eliminated every legal move (degenerate user input — e.g. all-illegal moves
    //      or empty filter list). Return 0; orchestrator emits `bestmove 0000`. This
    //      MUST short-circuit BEFORE the in_check / stalemate triage, otherwise a check
    //      position with a degenerate filter would falsely return -MATE.
    //    - At any other empty case (filter not active, or ply > 0): real terminal —
    //      mate if in_check, stalemate if not.
    if moves_vec.is_empty() {
        if ply == 0 && ctx.limits.searchmoves.is_some() {
            return 0;
        }
        if in_check(pos) {
            return -(MATE - ply as i32);
        } else {
            return 0;
        }
    }

    // 8. Order: MVV-LVA on captures + queen-promo bonus. Sort descending by score.
    moves_vec.sort_by_cached_key(|&m| -mvv_lva_score(m, pos));

    // 9. Recurse fail-soft.
    let mut best = -INF;
    for mv in moves_vec {
        let undo = pos.make_move(mv);
        self.history.push(pos.zobrist());
        let score = -self.negamax(pos, depth - 1, ply + 1, -beta, -alpha, ctx);
        self.history.pop();
        pos.unmake_move(mv, undo);

        // 10. Cancellation check: aborted score is invalid; do not commit.
        if self.aborted { return 0; }

        if score > best {
            best = score;
            if score > alpha {
                alpha = score;
                // 11. PV update: at ply, this move is best so far. Copy child's PV.
                let child_len = self.pv.lengths[(ply + 1) as usize];
                self.pv.moves[ply as usize][0] = mv;
                for i in 0..child_len {
                    self.pv.moves[ply as usize][i + 1] = self.pv.moves[(ply + 1) as usize][i];
                }
                self.pv.lengths[ply as usize] = 1 + child_len;
            }
            if alpha >= beta {
                break;  // beta cutoff (fail-soft: return `best` not `beta`)
            }
        }
    }

    best
}
```

**Subtleties to honor in the implementation:**

- **Allocation discipline**: `Vec::collect` for `moves_vec` is a per-node allocation (~30 moves × 2 bytes = 60 bytes typical). Acceptable for M3.C (matches GreedyMover's existing pattern). M4 will introduce a stack-allocated `MoveList`-with-scores variant if profiling shows allocation overhead.
- **`sort_by_cached_key`** computes the key once per element — important since `mvv_lva_score` reads `pos.piece_at(...)` per call.
- **Searchmoves filter scope**: only at `ply == 0`. Inner plies have no concept of "user-restricted moves."
- **Mate-distance pruning order**: the two checks must come *before* the depth==0 horizon check. CPW ordering — pruning a known-mate window before paying for an eval call is the win.
- **Position restore on cancellation**: even on `self.aborted = true; return 0`, the recursive call's `unmake_move` has already run by the time we propagate up. The post-call sequence `unmake → history.pop → aborted-check` ensures position state is restored before propagation.
- **History push/pop balance**: every `push(pos.zobrist())` must be paired with a `pop()` — including on abort. The sequence above pops *before* the aborted check; correct.
- **Per-ply PV length clear at step 2**: prevents stale PV from a sibling subtree leaking into the current frame's PV computation. CPW pitfall #3.

## 6. `mvv_lva_score`

```rust
fn mvv_lva_score(mv: Move, pos: &Position) -> i32 {
    use crate::eval::data::MATERIAL;
    use crate::mov::MoveFlag::*;

    let flag = mv.flag();
    let attacker_kind = pos.piece_at(mv.from_square()).unwrap().kind;
    let attacker_value = MATERIAL[attacker_kind as usize];

    match flag {
        Quiet | DoublePush | KingCastle | QueenCastle => 0,  // quiets / castling sort below all captures/promos
        Capture => {
            let victim_kind = pos.piece_at(mv.to_square()).unwrap().kind;
            let victim_value = MATERIAL[victim_kind as usize];
            victim_value * 16 - attacker_value
        }
        EnPassant => {
            // Victim is always a pawn for EP (regardless of capture-square arithmetic).
            MATERIAL[PieceKind::Pawn as usize] * 16 - attacker_value
        }
        QueenPromo | RookPromo | BishopPromo | KnightPromo => {
            let promo_value = MATERIAL[mv.promotion_kind().unwrap() as usize];
            promo_value  // no victim; no attacker subtraction
        }
        QueenPromoCapture | RookPromoCapture | BishopPromoCapture | KnightPromoCapture => {
            let victim_kind = pos.piece_at(mv.to_square()).unwrap().kind;
            let victim_value = MATERIAL[victim_kind as usize];
            let promo_value = MATERIAL[mv.promotion_kind().unwrap() as usize];
            victim_value * 16 - attacker_value + promo_value
        }
    }
}
```

`MATERIAL` is `pub(crate)` from `src/eval/data.rs` (PeSTO MG: P=82, N=337, B=365, R=477, Q=1025, K=0). The `× 16` factor ensures victim *kind* dominates attacker *kind* across the standard MVV-LVA matrix. **Worked-out ordering with these specific values:**

| Move | Score | Notes |
|---|---|---|
| QxQ (queen takes queen) | 1025·16 − 1025 = 15375 | high tier |
| RxQ | 1025·16 − 477 = 15923 | RxQ > QxQ ✓ |
| PxQ | 1025·16 − 82 = 16318 | smaller attacker, larger margin ✓ |
| Q-promo (non-capture) | 1025 | between captures and quiets |
| QxR | 477·16 − 1025 = 6607 | victim still dominates |
| QxP | 82·16 − 1025 = 287 | small victim, large attacker — *below* a non-capture queen-promo (1025) |
| Quiet / DoublePush / Castle | 0 | bottom tier |

The "quiet queen-promo (1025) > QxP (287)" ordering is intentional given PeSTO values: a non-capture queen-promotion gains ~+1000 cp of material (a pawn becoming a queen ≈ 1025 − 82 = 943 cp), while QxP gains only ~+82 cp. Searching the promotion first surfaces the larger material swing earlier in the alpha-beta tree. This is consistent with the "promotions are big material events" intuition that motivates qsearch's queen-promo inclusion (M3.D) and is why we use `promo_value` as the bonus rather than a fixed constant.

The function takes `pos: &Position` by ref; it doesn't mutate. Called at sort time; once per move per ply.

`Move::from_square()` / `to_square()` / `flag()` / `promotion_kind()` are the existing `pub` accessors on `Move` (see `src/mov.rs`); `promotion_kind()` returns `Option<PieceKind>` — `.unwrap()` is safe inside the promo-flag arms because the flag-arm enumeration guarantees the optional. `pos.piece_at(square)` is the existing `pub` accessor on `Position` (returns `Option<Piece>`; `.unwrap()` is safe at the from-square because every legal move has a piece on its from-square, and at the to-square inside the `Capture`/`*PromoCapture` arms because by definition those flags imply a victim).

## 7. `score_to_uci`

```rust
fn score_to_uci(score: i32) -> String {
    if score.abs() >= MATE_IN_MAX_PLY {
        // Mate score; convert to UCI "mate N".
        let plies_to_mate = MATE - score.abs();
        let moves = (plies_to_mate + 1) / 2;
        let signed_moves = if score > 0 { moves } else { -moves };
        format!("mate {signed_moves}")
    } else {
        format!("cp {score}")
    }
}
```

Worked examples:
- `score = MATE - 1 = 29999` → mate-in-1-ply → moves = 1 → `"mate 1"`.
- `score = MATE - 5 = 29995` → mate-in-5-plies → moves = 3 (rounded up, white+black+white) → `"mate 3"`.
- `score = -(MATE - 4) = -29996` → mated-in-4-plies → moves = 2, signed negative → `"mate -2"`.
- `score = 36` → `"cp 36"`.
- `score = 0` → `"cp 0"`.

## 10. Order of operations

The unit's slices are tightly coupled — see §11 parallelization map for why this is single-coder (with Sonnet+Opus parallel A/B per the calibration trigger). Sequence:

1. **Add `Default` to `Move`'s derive list** in `src/mov.rs`: change `#[derive(Copy, Clone, PartialEq, Eq, Hash)]` (line 147) to `#[derive(Copy, Clone, PartialEq, Eq, Hash, Default)]`. The derive produces `Move::default() == Move(0)` (since `u16`'s default is 0). Doc note above the derive (or in the type-level docstring): "Default produces `Move(0)` which decodes as `from=A1, to=A1, flag=Quiet` — never emitted by movegen (a1→a1 is illegal); safe as a zero-value sentinel for array initialization (e.g. `PvTable`). Distinct from M5's null-move pseudo-move concept; the existing `from_uci` doc-comment at `src/mov.rs:266-268` about 'no `Move::NULL` sentinel today' remains accurate — we are not adding `NULL` as a name."
2. **Constants and `PvTable`** in `src/search.rs` — add `MAX_PLY`, `MATE`, `INF`, `MATE_IN_MAX_PLY` constants. Define `PvTable` with `new` / `clear_ply` / `update` methods. Unit-test `PvTable` operations (rows 9, 10 of §8.1).

## 11. Parallelization map

**One coder slice — sequential. Sonnet+Opus parallel A/B per the workflow's chess-coder calibration trigger.**

The implementation is a tightly-coupled body (negamax internal state interacts with PV table, history, node counter, abort flag — all fields on the same struct). Splitting `mvv_lva_score` + `score_to_uci` + `PvTable` into a separate slice from `negamax` would save ~5 minutes wall time but lose the single-coder coherence over the helper-vs-recursion interface.

Per `docs/workflow.md` calibration log (2026-04-28 chess-coder watchlist entry): **M3.C is the trigger for chess-coder Sonnet vs Opus parallel A/B calibration**. Spawn both Sonnet and Opus on the same slice; compare diffs and final-review feedback. The slice meets all three "When to flag a coder slice for Opus" criteria in workflow.md:

- **Novel invariants requiring invention**: PV-update-only-on-improving-move-and-completed-subtree; history-push/pop balance under abort propagation; mate-score-vs-cp-score discrimination at root.
- **Parallel-precedent application**: AlphaBetaMover follows GreedyMover's struct shape and `Search` trait satisfaction, but the recursion structure has no parallel in the existing codebase — Sonnet's literal-pattern-matching tendency could surface here.
- **Anticipating qualitative behavior shifts that break existing tests**: production-switch breaks E38, the M3.A `handle_setoption_random_seed_changes_future_bestmoves_but_not_past_ones` KvK-tie-break test, and any test that pinned GreedyMover's tie-breaking — Sonnet may not pre-emptively flag the test surface.

**Calibration protocol** (sequence):

1. Spawn `coder-sonnet` (chess-coder agent, model override `sonnet`) on isolated worktree A via the Agent tool's `isolation: "worktree"` parameter.
2. Spawn `coder-opus` (chess-coder agent, model override `opus`) on isolated worktree B via the same parameter, in parallel.
3. Both receive the identical implementation prompt — the M3.C plan slice (this document, §3–§7).
4. When both complete, the orchestrator reads both diffs, captures the worktree paths from the agent return messages, and:
   - Runs `cargo test` + `cargo clippy --all-targets -- -D warnings` + `cargo fmt --check` in each worktree to confirm both pass the verification gates.
   - Runs `final-reviewer` on each worktree separately (two passes, each blind to the other).
   - Compares: number of must-fix and should-fix items in each final-review pass; coverage / mutation numbers; subjective code-quality observations.
5. Picks the winner. If the diffs converge (same headline approach, same correctness, same coverage), the cheaper Sonnet pass is the default winner. If Opus catches a substantive concern Sonnet missed (mirrors the M2.C plan-reviewer calibration's stop-loss trigger), the workflow's chess-coder tier flips to Opus.
6. Discards the loser's worktree.
7. Updates the workflow calibration log with the A/B comparison summary.

The `Agent` tool's `isolation: "worktree"` parameter is documented in the system prompt's tool description and creates a temporary git worktree that's automatically cleaned up if the agent makes no changes; otherwise the path and branch are returned in the result. Confirmed available.

## 13. Risks and gotchas

- **Position-restore invariant**: every `make_move` must be paired with `unmake_move` even on abort propagation. The §5 step-9 sequence (unmake → history.pop → aborted-check → break) is critical. A debug_assert at the end of `Search::go` body verifying `pos_clone == *position` catches imbalanced make/unmake.
- **History push/pop balance under abort**: every `push` must be paired with `pop`, including on aborted return. The §5 step-9 sequence is explicit on this.
- **Mate-score arithmetic at the root**: `negamax(root, ...)` returns the mate score from white's perspective if white is to move, else from black's. The `score_to_uci(score)` conversion treats `score > 0` as "side-to-move-at-root delivers mate" — UCI spec says positive `mate N` means *the engine is mating*, so this matches.
- **PV stability**: a PV write only fires when a move improves alpha. If alpha is never improved at a ply (every move is ≤ alpha — an all-node), `lengths[ply] = 0` and the parent's PV at that branch is empty. The triangular table's discipline (clear at frame entry, write only on improvement) is what keeps the PV consistent.
- **`Random_Seed` deferred-cleanup discipline**: option preserved as no-op for M3.C. M2.D's D2–D10/D12 + engine.rs setoption-Random_Seed tests stay green unmodified (the option's parse / accept / boundary-validate behavior is unchanged). The one M3.A test that asserted seed-driven divergence in bestmoves (the KvK-tie-break test) does need to rewrite — see §8.2.
- **E38 deletion vs replacement**: E38 was the M2.D self-play smoke test, then re-pinned at M3.A for GreedyMover. The replacement E39 needs to capture the alpha-beta-from-startpos depth-3 bestmove at impl time (placeholder runs, captured value committed).
- **Default depth when `go` lacks `depth`**: `unwrap_or(4)`. Choice rationale: depth 4 completes in <100 ms at M3.C strength; matches "reasonable default" for a fastchess `--compliance`-driven test that doesn't pass `depth` and just wants a `bestmove`. Depth 1 would echo GreedyMover's blunders; depth 8 would risk timeout on a cancellation-bound test. 4 is the middle ground.
- **`go infinite` / `go ponder` / `go movetime`**: M3.C honors them via the wait loop after the single search invocation completes — same shape as GreedyMover. Not a regression.
- **Time-control fields (`wtime`, `btime`, etc.) are *received but ignored* in M3.C**. The M3.E phase adds the soft/hard-cap discipline. For now, `go wtime 10000 btime 10000 ...` still runs at the default depth-4 search and returns immediately. Document this in the milestone retrospective so M3.E doesn't silently change strength.
- **PvTable lives inline on AlphaBetaMover (no Box)**: `AlphaBetaMover` itself sits behind `Arc<Mutex<Box<dyn Search>>>` in `Engine::search` (M2.C storage shape), so the PvTable's 8 KiB is already heap-allocated transitively via that outer Box. Adding a second Box would just add an extra indirection on every PV access. One subtlety: `AlphaBetaMover::new()` constructs `[[Move::default(); MAX_PLY]; MAX_PLY]` on the stack before the value is moved into the outer Box. Rust's RVO usually elides this, but worst-case is an 8 KiB transient stack frame inside `new()` — well below any thread-stack ceiling (worker thread default 2 MiB).
