# M4.C — History heuristic

Third M4 phase. Adds a butterfly-indexed history table (`[side][from][to]` i16, 16 KiB) updated with `+= depth*depth` bonus on quiet-move beta cutoff and matching malus on quiets searched-but-failed at the same node, layered into move ordering as the tiebreaker among quiets.

**Parallelism with M4.B.** Developed in parallel with M4.B (killer moves) on a separate branch off M4.A. The M4.C branch's move ordering is `TT → captures (MVV-LVA) → history-scored quiets`. At merge with M4.B, the killer-bubble step inserts between captures and history-scored quiets. **Killers are quiet moves and participate in `quiets_searched` like any other quiet** — they receive malus when tried-and-failed (per research §10's "Penalizing killers" row). The merge produces a manual three-way conflict in the move-ordering comparator that we handle at merge time, NOT by anticipating killer slots in this branch's code. Detail in §7.

**Per the user's standing instructions for this branch:** mutation testing is **prepared but not run** in this loop (overnight campaign deferred to user-go-ahead); SPRT is **deferred to merge time**. The plan still spells the exact `cargo mutants` invocation and the SPRT bound the merged engine targets.

Research synthesis: `docs/research/m4-history-heuristic.md`. Lands ADR-0019 (history table indexing + bonus/malus formula + saturation policy + reset boundary).

## 0. Goals

- New `src/history.rs` module: `HistoryTable` (`[i16; 2 * 64 * 64]`), `score(side, from, to) -> i16`, `update(side, from, to, bonus: i32)` (clamps to `[-MAX_HISTORY, MAX_HISTORY]` after add), `clear()`. `MAX_HISTORY = 16384`.
- `is_quiet(mv) -> bool` predicate (Quiet/DoublePush/KingCastle/QueenCastle) shared between move ordering and history updates. Lives in `src/mov.rs` as a `Move` method or a free function in `src/search.rs`; exact home decided in §3.
- `AlphaBetaMover` gains `history_table: HistoryTable` field. **Add (do NOT replace)** `self.history_table.clear()` to the existing `Search::reset()` body, alongside the existing `self.history.clear()` (M3.B game-history Vec) call. The reset is called from `Engine::reset_for_new_game()` per the M4.A boundary.
- `negamax` body change at the move-loop epilogue: on quiet-move beta cutoff, apply `+depth*depth` to the cutter and `-depth*depth` to every prior quiet at this node. Quiets that complete recursion without cutting are pushed onto a stack-local `MoveList` (`quiets_searched`, capacity 256, no heap alloc).
- `negamax` body change at move ordering: after MVV-LVA + TT-move-first (existing M4.A logic), score quiets by `history_table.score(side, from, to)` descending. Approach: replace the single comparator. New `move_ordering_score(mv, pos, &history) -> i32` returns `mvv_lva_score(mv, pos) + CAPTURE_OFFSET` for captures/promos and `history_score as i32` for quiets, with `CAPTURE_OFFSET > MAX_HISTORY` so all captures sort above all quiets.
- `qsearch` is **not** modified. History does not interact with qsearch — qsearch uses MVV-LVA only and never sees the history table.
- No new UCI option: `Hash` already covers TT memory; the 16 KiB history table is below the threshold cited in the M4.A research note (TalkChess t=67878).
- Mutation testing **prepared** (diff file written, `cargo mutants` command documented in the milestone retrospective and `bench/m4.md`) but **not run** in this loop. Overnight campaign on user go-ahead.
- SPRT **deferred to merge time** (gated against `baseline/alpha-beta-tt-killer` after M4.B lands; see §7). No SPRT log lands with this branch's commit.

## 3. Type definitions and signatures

### 3.1 `MAX_HISTORY` and `HistoryTable`

```rust
// src/history.rs

/// Saturation cap for history scores. Per ADR-0019; per research §6
/// (`16384 < i16::MAX = 32767` leaves headroom for transient overflow during
/// arithmetic before the clamp lands).
pub(crate) const MAX_HISTORY: i16 = 16384;

/// Butterfly-indexed history table: `[side][from][to]` → i16 score.
/// `Color::White as usize == 0`, `Color::Black as usize == 1`. 2 × 64 × 64 ×
/// 2 bytes = 16 KiB; fits in Apple Silicon M4's 192 KiB L1d.
pub(crate) struct HistoryTable {
    entries: [[[i16; 64]; 64]; 2],
}

impl HistoryTable {
    pub fn new() -> Self;
    pub fn clear(&mut self);
    pub fn score(&self, side: Color, from: Square, to: Square) -> i16;
    pub fn update(&mut self, side: Color, from: Square, to: Square, bonus: i32);
}

impl Default for HistoryTable { fn default() -> Self { Self::new() } }
```

**`update` formula:**
```rust
pub fn update(&mut self, side: Color, from: Square, to: Square, bonus: i32) {
    let entry = &mut self.entries[side as usize][from.index() as usize][to.index() as usize];
    let new_value = (*entry as i32 + bonus).clamp(-MAX_HISTORY as i32, MAX_HISTORY as i32);
    *entry = new_value as i16;
}
```

`bonus` is `i32` (not `i16`) so the call site can pass `depth * depth` (up to `63 * 63 = 3969` per call; well within i32 range) and `-depth * depth` without intermediate clamping. The clamp lands inside `update` after the add.

**Why a 3-D const-generic-shaped `[[[i16; 64]; 64]; 2]` over `Vec<i16>`:** the table size is fixed at compile time (16 KiB); a `Vec` adds a pointer indirection and heap-alloc on `HistoryTable::new()`. The 16 KiB lives in the `AlphaBetaMover` struct, which itself lives behind an `Arc<Mutex<...>>` field of `Engine`. M4.A's `AlphaBetaMover` is already on the heap via `Box<dyn Search>`, so the 16 KiB sits in a heap-allocated frame. No stack-overflow risk.

**Fallback if NPS regression > 5%:** wrap as `Box<HistoryTable>` (single pointer indirection inside `AlphaBetaMover`); not predicted by `MoveList` precedent but listed as the immediate optimization-lever if the post-impl bench shows regression.

**`clear()` body spelling:** `*self = Self::new()` (compiler lowers to `memset(0, 16384)`); equivalent to `self.entries = [[[0; 64]; 64]; 2]`. Do NOT write a manual `for` loop — it inhibits the memset lowering. Pinned by H8.

### 3.2 `Move::is_quiet`

```rust
// src/mov.rs

impl Move {
    /// Returns true iff this move is a "quiet" — non-capture, non-promotion,
    /// non-EP. Used by history heuristic and (eventually) killer move logic.
    /// Castling (king-side / queen-side) is treated as quiet (it's a
    /// non-capture irreversible move; standard CPW classification). Double-push
    /// is quiet. Castling-as-cutter is rare in practice; the history table
    /// will accumulate `[from=e1][to=g1]` bonuses on cutoffs that involve
    /// castling but the volume is low.
    pub fn is_quiet(self) -> bool {
        use MoveFlag::*;
        matches!(self.flag(), Quiet | DoublePush | KingCastle | QueenCastle)
    }
}
```

Pinned by `mov.rs::tests::move_is_quiet_classifies_all_flags` (one assertion per `MoveFlag` variant — 14 cases).

### 3.4 `move_ordering_score`

Replaces inline `mvv_lva_score` calls in negamax's sort step. `mvv_lva_score` itself stays in place (qsearch still uses it; new function delegates).

```rust
fn move_ordering_score(mv: Move, pos: &Position, history_table: &HistoryTable) -> i32 {
    if mv.is_quiet() {
        // Quiet score: history value, signed in [-MAX_HISTORY, MAX_HISTORY].
        // Range: [-16384, 16384].
        history_table.score(pos.side_to_move(), mv.from_square(), mv.to_square()) as i32
    } else {
        // Capture/promo/EP: MVV-LVA score offset by CAPTURE_OFFSET to ensure
        // every capture sorts above every quiet.
        // mvv_lva_score range for captures+promos: [287, 17425] (research note);
        // CAPTURE_OFFSET = MAX_HISTORY + 1 = 16385 places the smallest capture
        // (287) at 16672 — well above the highest quiet (16384). Spelled as
        // `MAX_HISTORY as i32 + 1` so the constant tracks if MAX_HISTORY changes.
        mvv_lva_score(mv, pos) + (MAX_HISTORY as i32 + 1)
    }
}
```

Sort then uses `sort_by_cached_key(|&m| -move_ordering_score(m, pos, &self.history_table))`. TT-move-first bubble runs after the sort, identical to M4.A.

**Test-only ordering accessor** (for HS9's verification mechanism). Add to `AlphaBetaMover`:
```rust
/// HS9-only test accessor: returns the comparator-sorted move list for `pos`
/// against `self.history_table`, **without** the post-sort TT-move-first
/// bubble that production negamax step-10 applies. To test the full step-10
/// pipeline (including TT-bubble), use `negamax_for_test` and read PV[0]
/// post-search. Production code never calls this.
#[cfg(test)]
pub(super) fn ordered_moves_for_test(&self, pos: &Position) -> Vec<Move> {
    use crate::movegen::{MoveList, generate_moves};
    let mut ml = MoveList::new();
    generate_moves(pos, &mut ml);
    let mut moves_vec: Vec<Move> = ml.iter().collect();
    moves_vec.sort_by_cached_key(|&m| -move_ordering_score(m, pos, &self.history_table));
    moves_vec
}
```

This accessor returns the sorted `Vec<Move>` post-comparator without the TT-move-first bubble, so HS9 can directly assert the ordering across N quiets without inferring it from recursion side-effects.

### 3.5 `quiets_searched` accumulator

In the negamax move loop, we maintain a stack-local `MoveList` recording quiets that have completed recursion without producing a beta cutoff:

```rust
let mut quiets_searched: MoveList = MoveList::new();   // capacity 256

for (i, &mv) in moves_vec.iter().enumerate() {
    let undo = pos.make_move(mv);
    self.history.push(pos.zobrist());
    let (child_alpha, child_beta) = negate_window(alpha, beta);
    let child_is_pv = is_pv && i == 0;
    let score = -self.negamax(pos, depth - 1, ply + 1, child_alpha, child_beta, child_is_pv, ctx);
    self.history.pop();
    pos.unmake_move(mv, undo);

    if self.aborted {
        return 0;   // unchanged: no history update on abort path
    }

    if score > best {
        best = score;
        if score > alpha {
            alpha = score;
            self.pv.update(ply as usize, mv);
            if ply == 0 { self.root_score = Some(score); }
        }
        if alpha >= beta {
            cutoff_move = Some(mv);
            // M4.C: history bonus + malus on quiet-move beta cutoff.
            if mv.is_quiet() {
                let bonus = (depth as i32) * (depth as i32);
                // SIDE-TO-MOVE INVARIANT: pos has been restored to the
                // pre-move-loop state by `pos.unmake_move(mv, undo)` above,
                // so `pos.side_to_move()` here is the **mover's color** (the
                // side whose move list this node enumerated). Read here,
                // BEFORE any future make/unmake; do NOT recompute inside the
                // malus loop. Refactoring this into a helper that re-reads
                // `pos.side_to_move()` at a different point would silently
                // invert the side. Pinned by HS8 (root White) + HS8b
                // (non-root Black).
                let side = pos.side_to_move();
                self.history_table.update(side, mv.from_square(), mv.to_square(), bonus);
                for prior in quiets_searched.iter() {
                    self.history_table.update(side, prior.from_square(), prior.to_square(), -bonus);
                }
            }
            break;
        }
    }

    // Did not cut. If quiet, record for potential malus by a later cutter.
    if mv.is_quiet() {
        // SENTINEL DEFENSE: `Move::default()` (a1→a1 Quiet) must never enter
        // `quiets_searched`. Movegen never produces it, and `mv` here came
        // from the legal `moves_vec`, so this is a structural invariant —
        // assert it as a defense against future code that might inject a
        // sentinel via a refactor.
        debug_assert!(
            mv.from_square() != mv.to_square(),
            "Move::default() sentinel must never enter quiets_searched"
        );
        quiets_searched.push(mv);
    }
}
```

**`MoveList` capacity vs. legal-move ceiling.** `MoveList` panics on `push` past capacity 256. The 256-slot capacity covers Petrović 1964's 218-move legal-position ceiling with margin. `quiets_searched` only pushes quiet (non-capture, non-promo, non-EP) moves, so its size is bounded above by `218 − captures` ≤ 218 < 256. No legal position can overflow. The panic is unreachable from any chess fixture; not pinned by a test (would require synthesizing an over-capacity position that does not exist in chess).

**Stack-budget calculus for the per-frame `MoveList`.** `MoveList` is `[Move; 256]` + `len: usize` ≈ 520 bytes. At MAX_PLY=64 simultaneous frames the per-call-stack cost is 64 × 520 ≈ 32 KiB. The worker thread is spawned via `std::thread::spawn` (per ADR-0011) with the default 2 MiB stack — 32 KiB is 1.5% of that, well within budget. Acknowledged: a smaller per-frame buffer (`[Move; 64]` ≈ 130 bytes/frame, 8 KiB total) would suffice for typical positions (≤35 quiets), but reusing `MoveList` is the simpler choice given the stack-budget headroom.

**Critical invariants (load-bearing for tests):**

- **Side-to-move at history update**: `pos.side_to_move()` at the time of update is the side that **just moved** (i.e., the negamax frame's mover). The make/unmake is **balanced** by the time we reach the cutoff; `pos` is restored to pre-move-loop state by `pos.unmake_move(mv, undo)`. So `pos.side_to_move()` here is the **mover's color** (the side whose move list this node was scoring). Pinned by `negamax_history_bonus_uses_movers_side_at_root_for_white` and the symmetric Black test.

- **Abort path skips history update**: the `if self.aborted { return 0; }` returns BEFORE any history update — the cutoff didn't really happen, the partial bound is invalid. Pinned by `negamax_does_not_update_history_on_abort`.

- **Capture / promo / EP cutoffs do not update history**: only quiet cutoffs produce a history bonus. Captures are ordered by MVV-LVA, which is path-independent. Pinned by `negamax_does_not_update_history_on_capture_cutoff`.

- **Malus excludes the cutter**: only the moves in `quiets_searched` (i.e., quiets that completed recursion before the cutter) receive malus. The cutter itself receives bonus, not malus. Pinned by `negamax_history_malus_excludes_cutter`.

- **Non-quiet moves don't enter `quiets_searched`**: only quiets, so capture-move-then-quiet-cutoff doesn't malus the capture. Pinned by `negamax_quiets_searched_excludes_captures`.

- **No update on no-cutoff**: if the move loop completes without `alpha >= beta`, no history update fires. Pinned by `negamax_does_not_update_history_when_no_cutoff`.

- **No update on TT cutoff**: the TT-cutoff early-return at step 7 of the M4.A negamax prologue exits before the move loop runs. No history update. Pinned by `negamax_does_not_update_history_on_tt_cutoff`.

## 4. Order of operations inside `negamax` (post-M4.C)

The M4.A-defined prologue (steps 1–9) is unchanged. Step 10 (move ordering) and step 11 (move loop) gain the history integration.

```text
1.  clear PV slot at this ply                              [unchanged from M4.A]
2.  depth==0 → qsearch                                     [unchanged]
3.  nodes increment + cancellation poll                    [unchanged]
4.  capture original_alpha                                 [unchanged]
5.  ply > 0 rep / 50-move check                            [unchanged]
6.  mate-distance pruning                                  [unchanged]
7.  TT probe + non-PV cutoff                               [unchanged]
8.  generate moves                                         [unchanged]
9.  terminal: empty list → mate / stalemate / 0            [unchanged]
10. M4.C-MODIFIED: order via move_ordering_score (history-aware quiet score),
    then TT-move-first bubble. Quiets sort below all captures (CAPTURE_OFFSET
    in move_ordering_score guarantees this).
11. M4.C-MODIFIED: recurse fail-soft. Maintain stack-local `quiets_searched:
    MoveList`. On beta cutoff with a quiet cutter: bonus + malus. On no
    cutoff with a quiet move: push to `quiets_searched`. Captures never enter
    `quiets_searched`. The abort-skip rule (no history update on abort) is
    enforced by the existing `if self.aborted { return 0; }` at the top of
    the loop body's continuation.
12. store on completion                                    [unchanged from M4.A]
```

**No changes** to the qsearch frame (depth==0). qsearch never observes or updates the history table.

| HS8 | `negamax_history_bonus_uses_movers_side_at_root_for_white` | At a White-to-move root, force a quiet cutoff. Verify the bonus lands on `entries[White][..][..]`, not on `entries[Black][..][..]`. |

| HS9 | `move_ordering_score_sorts_quiets_descending_with_four_distinct_history_values` | Pre-populate `history_table.update(side, e2, e4, +500)`, `update(side, d2, d4, +300)`, `update(side, b1, c3, +100)`, plus a 4th legal quiet at history value 0 (e.g. `g1f3`). | HS10 | `history_table_update_clamps_at_positive_saturation_boundary_via_negamax` | Pre-populate one entry at `MAX_HISTORY - 1` (i.e., 16383). Post-search, verify `history_table.score(side, from, to) == MAX_HISTORY` (16384, NOT 16383+16=16399 — the clamp fires). **Deterministic: exactly one cutoff fires the clamp; no dependence on cutoff-count statistics over a multi-iteration search.** Negative-side clamp is covered by H6 at the `history` module level — not re-pinned at the negamax integration level (the clamp logic lives entirely in `HistoryTable::update`; the integration just passes `+bonus` or `-bonus` through). |

| HS12 | `move_ordering_score_places_all_captures_above_all_quiets_and_promos_above_captures` | Construct three moves at the same position: (a) a small QxP-like capture, (b) a quiet at MAX_HISTORY in `history_table`, (c) a non-capture QueenPromo. Verify `move_ordering_score(c) > move_ordering_score(a) > move_ordering_score(b)`. Pins CAPTURE_OFFSET correctness AND the M4.A "promo > capture" intuition (per ADR-0016 §6 — non-capture QueenPromo at score 1025 sorts above QxP at 287). |

**Anti-stub defenses:**
- HS1 / HS4 / HS5 use **specific arithmetic values** (`+4`, `-4` at depth 2; etc.) that depend on the exact `depth*depth` formula. HS1 tests at depth 2 (`+4` expected, distinguishing `depth*depth=4` from `depth=2` from `+1`); HS10 tests the clamp boundary directly (16383 + 16 = 16399 → clamps to 16384), distinguishing both formulas from `+= constant`. A stub that does `+= depth` (linear) produces `+2` instead of `+4` at HS1; a stub that does `+= 1` produces `+1`.
- HS3 deliberately uses a TT-cutoff hit; a stub that updates history after every cutoff (TT or real) would fail.
- HS9 specifies that the *higher* history value is tried first, not just that ordering changed; a stub sorting ascending would fail.
- HS12 uses values designed to invert the expected ordering if CAPTURE_OFFSET is omitted: small-value capture (e.g., QxP scoring 287) vs. quiet at MAX_HISTORY (16384). Without offset, the quiet sorts first; with offset, the capture sorts first (287 + 16385 = 16672 > 16384).

### 5.7 Confirmation-bias defense (cross-cutting)

- **Tests pre-clear the history table** (`mover.history_table.clear()` at test setup) so an inadvertent value from a prior test in the same module doesn't leak. The clear is the load-bearing setup; if a test passes only because of stale state, deleting the clear surfaces the dependency. (Each HS test should explicitly clear at setup.)
- **HS3's TT-cutoff test** anchors a property (no history update on TT-hit) that would otherwise be silently violated by a misplaced update inside the TT-probe block of negamax. The test is the only check on this discipline.
- **HS5's quiet-after-capture test** anchors the `quiets_searched` capture-exclusion. A bug that pushes ALL non-cutter moves (including captures) onto `quiets_searched` would cause the capture C1 to receive `-bonus` malus — observable as `score(C1) != 0`.

**Slice C Opus flag.** Per `docs/workflow.md` "When to flag a coder slice for Opus":
- **"Parallel-precedent application across modules" (the load-bearing criterion).** Three call sites must agree on the `is_quiet(mv)` predicate (cutter bonus, malus loop, push-on-no-cutoff). And the abort-skip + end-of-loop-only discipline composes with M4.A's TT-store rules from `tt::store` — a Sonnet pattern-match on M4.A without thinking through which discipline applies could introduce a partial-iteration history pollution bug analogous to the M4.A's mid-loop-store bug that pass-1 review caught.
- **Cross-call-site invariant** — the side-to-move read at the cutoff site is load-bearing; reading at the wrong point (e.g., inside a refactored helper that touches `pos` after make/unmake) silently inverts the side. - **Bench-signature regression risk** — introducing a per-frame `MoveList` allocation in the hot path can shift NPS observably; if the implementation accidentally heap-allocates the accumulator (e.g., using a `Vec` that grows beyond inline capacity), benchmarks will show a regression. ## 7. Dependencies on other units

- **Hard:** M4.A `AlphaBetaMover` field-add discipline + `Search::reset` lifecycle + `Engine::reset_for_new_game` boundary (`ucinewgame` + bench-position). M4.C extends `Search::reset` to clear the history table; the bench determinism contract carries over for free.
- **Hard:** M4.A `mvv_lva_score` and the `MoveList` 256-slot buffer (M1.E). `move_ordering_score` delegates to `mvv_lva_score` for non-quiets; `quiets_searched` reuses `MoveList`.
- **Soft (parallel branch):** M4.B (killers). At merge:
  - The merge produces a manual conflict in negamax's move-loop body (M4.B inserts killer-bubble between captures and quiets; M4.C inserts history-scored quiet sort in the same vicinity). Resolution: keep both — bubble killers immediately after the captures (per research §7), then sort the remaining non-killer non-capture quiets by history.
  - **Killers ARE quiet moves.** Per research §10 ("Penalizing killers" row): when a killer is tried and fails to cut at this node and a later quiet does, the killer **should** receive malus — it was tried-and-failed. The merge integration therefore treats killers as ordinary quiets in `quiets_searched`: the killer enters the accumulator on no-cutoff (it's a quiet by `is_quiet()`), and receives malus from the malus loop if a later quiet cuts. **Do NOT** add a "skip killers in malus" filter at merge — that inverts the research recommendation. The earlier draft of this plan called for the filter; corrected per plan-review pass 1.
  - The merged engine's `Search::reset` body becomes "clear history Vec; clear killer table; clear history_table" — both branches add a line; merge takes both.
  - SPRT against `baseline/alpha-beta-tt-killer` (M4.B's tag) lands at merge time.
- **Soft:** M4.D (aspiration). Aspiration's iteration-aborting re-search would normally produce mid-iteration aborts; M4.C's history table persists across aborts (the table is not iteration-reset), and the abort-skip rule prevents partial cutoffs from polluting it. M4.D's plan should reference this.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| History malus underflow on signed `i16` | `update()` clamps to `[-MAX_HISTORY, MAX_HISTORY]`. H6/H7 pin the negative-direction clamp. |
| `quiets_searched` heap-allocates and tanks NPS | Plan §3.5 specifies `MoveList` (stack 256). HS-bench check (smoke) post-impl confirms NPS within ~5% of M4.A. |
| TT move ordering breaks because move_ordering_score is asymmetric across quiet/non-quiet | HS9 + HS12 + the M4.A S6/S12 tests (TT-move-first preservation under reorder) jointly cover. |
| History persists too long across games and biases ordering | `Engine::reset_for_new_game()` already calls `Search::reset()` which now also clears history. E_h pins `ucinewgame` clear; E46 pins `bench`-position clear (via the existing `reset_for_new_game()` per-position call). |
| Merge with M4.B inverts research §10's "killers receive malus" rule | Merge plan §7 explicitly treats killers as ordinary quiets in the malus loop (per research §10's "Penalizing killers" row): a killer that is tried-and-failed at this node and a later quiet cuts → killer receives malus. **The risk is the inverse**: a future maintainer wrongly excludes killers from `quiets_searched`. Merge-time test addition (HS-merge series, post-merge with M4.B) should pin "killer that fails to cut receives malus when later quiet cuts" as the explicit invariant. NOT M4.C-branch's responsibility. |
| Mutation survivors land hidden because mutation run is deferred | The `git diff HEAD > /tmp/m4.c.diff` step runs at the pre-review checkpoint; the diff file is preserved in `target/` (gitignored, regenerable). Survivor triage at the user-scheduled overnight campaign uses this diff. |
| Bench signature changes confuse "is this an M4.C regression?" | Expected. Recorded explicitly in `bench/m4.md` with the M4.A → M4.C delta. The signature is deterministic across runs (E46 pins it); regression-debug compares the new signature to itself across re-runs, not to M4.A. |
| Per-frame `sort_by_cached_key` heap-allocates `4 × n` bytes (i32 cache) per node — known-hot path, M4.A inheritance | M4.A-inherited shape; not introduced by M4.C. Typical internal node has ~30 quiet moves → ~120 bytes; max legal-move position 218 moves → ~872 bytes (i.e., upper bound). Post-impl benchmark check: bench NPS within ~5% of M4.A end. If regression > 5%, the optimization-lever is to replace `sort_by_cached_key` with an in-place sort-by-key that doesn't allocate. Documented for future reference; not blocking M4.C landing. |
