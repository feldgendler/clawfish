M1.G is the **validation + measurement layer**: a recursive perft driver, Stockfish-confirmed fixtures on the canonical 6 plus the Whittington EPD corpus, and a `criterion` benchmark harness. ## Decisions baked into this plan

### 1. Module layout: single file `src/perft.rs`

Total estimated surface ≈400–600 lines impl + ≈250–400 lines tests. Below the "split into a directory" threshold (`mov.rs` is similar in size and stayed flat). One file is the right shape.

The module declares `pub fn perft`, `pub fn perft_bulk`, `pub fn divide`, `pub fn perft_categorized`, `pub struct PerftCounts`. No submodules. Tests live inline in `#[cfg(test)] mod tests` for the unit-level invariants (`perft(starting, 0) == 1`; `perft(starting, 1) == 20`; bulk-vs-plain agreement at small depths; categorized-count invariants); cross-position regression tests live in `tests/perft.rs` per the integration-vs-unit boundary established in `docs/research/m1-perft-and-rust.md`.

### 2. Public API

```rust
/// Plain recursive perft. Counts leaf nodes at `depth` plies from `pos`.
/// Allocates a single `MoveList` per recursion depth on the stack.
pub fn perft(pos: &Position, depth: u32) -> u64;

/// Bulk-counting perft (CPW "bulk counting"): at depth 1, returns the
/// legal-move count without making + unmaking each leaf. Equivalent to
/// `perft` but ~20–30% faster (community + research consensus). Used as
/// the headline benchmark.
pub fn perft_bulk(pos: &Position, depth: u32) -> u64;

/// Divide: for each legal move at depth `depth`, report the move and
/// `perft(make(pos, mv), depth - 1)`. Output is **sorted by UCI move
/// notation ascending** — a deterministic, stable ordering that does not
/// depend on `generate_moves`'s internal emit order.
///
/// Stockfish 18's `go perft N` emits divide output in its engine-internal
/// generation order, NOT in lex-sorted order (verified at plan-write
/// time: `position startpos / go perft 2` produces `a2a3, b2b3, ...,
/// h2h3, a2a4, b2b4, ..., h2h4, b1a3, b1c3, g1f3, g1h3` — pawn moves
/// first ordered by source file, then knights, etc.). For the documented
/// debugging workflow (`docs/research/m1-perft-and-rust.md` §"Divide as
/// a debugging tool"), pipe both outputs through `sort` before `diff`:
///
/// ```sh
/// # `our_divide` is the debug harness that prints `divide(pos, N)` —
/// # one "from-to[promo]: count" line per move, e.g. an `eprintln!` loop
/// # over the returned Vec. `sort_stockfish` is the Stockfish equivalent:
/// #   printf 'position fen $FEN\ngo perft $N\nquit\n' | stockfish \
/// #     | grep -E '^[a-h][1-8][a-h][1-8][nbrq]?:'
/// our_divide       | sort > ours.txt
/// sort_stockfish   | sort > theirs.txt
/// diff ours.txt theirs.txt
/// ```
///
/// Our output being already-sorted means `our_divide | sort` is a no-op,
/// keeping our side trivial; theirs needs the `sort` step. UCI-sort cost
/// on our side is ≤218 string formats + a sort; trivial vs the recursion
/// the function spends most of its time in.
///
/// Panics if `depth == 0`.
pub fn divide(pos: &Position, depth: u32) -> Vec<(Move, u64)>;

/// Categorized perft counts. Per ADR-0006 these are **internal sanity
/// only** — not cross-validated against Stockfish, but useful for
/// catching specific bug classes (zero EP count at depth 5 from start
/// → broken EP generator).
#[derive(Default, Clone, Debug, PartialEq, Eq)]
pub struct PerftCounts {
    pub nodes: u64,
    pub captures: u64,
    pub en_passant: u64,
    pub castles: u64,
    pub promotions: u64,
    pub checks: u64,
    pub discovery_checks: u64,
    pub double_checks: u64,
    pub checkmates: u64,
}

/// Categorized recursive perft. Slower than `perft_bulk` (no leaf-skip;
/// must classify each leaf event), so intended for shallow-depth runs.
/// `nodes` field equals what `perft(pos, depth)` would return.
pub fn perft_categorized(pos: &Position, depth: u32) -> PerftCounts;
```

**Move-list allocation strategy.** Each recursion frame owns a fresh `MoveList::new()` — 512 bytes of stack (with `MaybeUninit`, no zero-init cost). Depth 7 → 7 × 512 = 3.5 KiB stack. Well within macOS's 8 MiB default thread stack. No heap allocation in the perft hot path. (`divide`'s return vector is the sole heap allocation and lives outside the recursion.)

**No `&mut MoveList` reuse across recursion depths.** A reused buffer would require careful save-restore at recursion boundaries. The move-list is small enough that per-frame allocation is the simpler, safer pattern; `MaybeUninit::new()` is essentially a no-op (no zero-fill), so allocation cost is just the 512-byte stack slot reservation. Profile may revisit this if `samply` flags it; M1.G ships per-frame.

**Why `u64` for counts.** Starting position D7 is 3,195,901,860 nodes (>2³¹). Whittington's deeper rows reach trillions. `u64` is mandatory.

**`PerftCounts: Clone, not Copy`.** Nine `u64`s = 72 bytes. Copy is technically fine but unusual at that size, and a future field (e.g. stalemates, nullmoves) silently inflates the per-call cost. The recursion uses `&mut PerftCounts` accumulation, never copies; public callers get `Clone`.

**Bulk counting at exactly depth 1.** When called with `depth == 1`, `perft_bulk` returns `move_list.len() as u64`. When called with `depth == 0`, it returns 1 (matching `perft`). For `depth >= 2`, it recurses with `depth - 1` and bottoms out at depth 1 via the leaf-skip path. This means `perft_bulk(pos, 0) == 1` and `perft_bulk(pos, 1) == perft(pos, 1)` exactly — same contract.

### 3. Categorized counts — implementation detail

Categorized counts run a **non-bulk** perft and classify each move as it's made-and-recursed. The classification logic at each move:

| Category | Detection |
|---|---|
| `nodes` | Equals what `perft` would return; counted at the leaf (see "Recursion-base contract" below). |
| `captures` | `mv.flag().is_capture()` — the predicate covers regular `Capture`, `EnPassant`, and the four `*PromoCapture` flag codes. |
| `en_passant` | `mv.flag() == MoveFlag::EnPassant`. (Subset of captures.) |
| `castles` | `mv.flag() == MoveFlag::KingCastle || mv.flag() == MoveFlag::QueenCastle`. |
| `promotions` | `mv.flag().is_promotion()` — covers all eight promotion-flagged codes (four `*Promo` + four `*PromoCapture`, i.e. four promoted-to piece kinds × two capture-or-not). |
| `checks` | After make_move, `!checkers_of(&post_pos, post_us, king_sq, occ).is_empty()`. (Computed using the post-move side-to-move and its king square.) |
| `discovery_checks` | Subset of checks. After make_move, `checkers_of(...)` returns a bitboard with at least one checker NOT on `mv.to_square()`. |
| `double_checks` | Subset of checks. `checkers_of(...).count() == 2`. |
| `checkmates` | At leaf depth (`depth == 1`, since checkmate is determined at the next ply): after the move, generate the post-move legal-move list; if empty AND `checkers_of(...).count() >= 1`, count one. |

**Recursion-base contract.** Two distinct paths reach `depth == 0`, and they behave differently:

- **Top-level call `perft_categorized(pos, 0)`** — no move has been made; `nodes = 1` (matching `perft(pos, 0) == 1` and the unit-test contract `categorized_starting_position_depth_0_returns_one_node`); all other counters stay 0.
- **Recursion-leaf at `depth == 0`** — reached only via the parent-at-depth-1 dispatch. Classification of the just-made move (the parent's per-move iteration) happens at the parent ply *before* this recursion, where `mv` is still in scope; the depth-0 leaf only contributes `nodes += 1`.

Equivalently: classification is anchored to the ply that *makes* the move, not the ply that *consumes* it. The implementation pattern:

```rust
// (pseudocode)
fn perft_categorized_inner(pos, depth, &mut counts) {
    if depth == 0 { counts.nodes += 1; return; }
    let mut ml = MoveList::new();
    generate_moves(pos, &mut ml);
    if depth == 1 {
        // Leaf-classification ply. Classify each move's flag category +
        // (after make) check / mate state, but recurse only to add nodes.
    }
    for mv in ml.iter() {
        // capture / en_passant / castle / promotion classification on `mv`.
        let undo = make_move(pos, mv);
        // check / discovery / double-check / checkmate classification using
        // `checkers_of(&pos, ..)` and (when depth == 1 and check) the
        // post-move legal-move set's emptiness.
        perft_categorized_inner(pos, depth - 1, counts);
        unmake_move(pos, mv, undo);
    }
}

pub fn perft_categorized(pos, depth) -> PerftCounts {
    let mut c = PerftCounts::default();
    if depth == 0 { c.nodes = 1; return c; }
    perft_categorized_inner(&mut pos.clone(), depth, &mut c);
    c
}
```

The inner function takes `&mut Position` to thread the make/unmake recursion. Public API takes `&Position` and clones (Position is small, ~136 bytes).

**Detection caveats.**

- Discovery and double check categorizations are **subsets**, not exclusives. CPW reports total `checks` independently. We mirror: a move that gives double-check is counted in `checks`, in `discovery_checks` if either checker is non-mover, AND in `double_checks`. This makes `discovery_checks ≤ checks` and `double_checks ≤ discovery_checks` invariants the categorized test asserts.
- "Discovery check" excludes castling-by-convention noise: when the rook delivers check after castling, the moving piece is the king (the "primary" mover from the move record's perspective), and the rook's check-from-its-new-square IS classified as discovery here. CPW makes the same call. Documented in the test header.
- `checkmates` requires generating moves at the leaf, which negates the bulk-skip — categorized perft is therefore strictly slower than `perft_bulk` at the same depth. This is acceptable: categorized counts run only on the canonical 6 at D3 (and inside-a-test, never on the bench hot path). The shallow depth keeps the runtime trivial.

**API contract.** `PerftCounts::default()` is the zero value. `perft_categorized` uses internal `&mut PerftCounts` accumulation through the recursion to keep the per-frame surface small. No public mutators on `PerftCounts` are exposed outside the module.

### 4. Test fixture format

#### Canonical-6 fixture: `tests/fixtures/perft_canonical6.txt`

EPD-style, one position per line:

```
<FEN>; D1 N; D2 N; D3 N; D4 N; D5 N; D6 N
```

Header comment lines (start with `#`) record provenance:

```
# Perft fixtures for the canonical six positions.
# Generator: Stockfish 18 (Homebrew install), invoked as:
#   stockfish << EOF
#   position fen <FEN>
#   go perft <DEPTH>
#   quit
#   EOF
# Generated at: <yyyy-mm-dd> on Apple Silicon Mac.
# Format: <FEN>; D1 N; D2 N; ...; D6 N
# Counts are leaf-node totals; D0 is implicit (1).
```

**Why a vendored file rather than const-baked.** Six positions × six depths = 36 numbers; the const-baked form would be readable in-source and avoid a parse step. But: (a) regenerating against a future Stockfish release is trivial with the file (`./scripts/regen-perft-fixtures.sh` overwrites it); (b) the same parser handles the Whittington corpus; (c) ADR-0006 explicitly anticipates "fixture files" with a Stockfish-version header. File-with-header is the right shape.

#### Whittington corpus: `tests/fixtures/perft_whittington.epd`

Vendored from `https://github.com/ChrisWhittington/Chess-EPDs/blob/master/perft.epd` (FEN list only). **Counts are stripped from the upstream file and regenerated by us via Stockfish** per ADR-0006. The committed file format matches the canonical-6 fixture: `<FEN>; D1 N; D2 N; D3 N; D4 N`. Header comment lines record:

```
# Whittington perft regression suite.
# Position list source: ChrisWhittington/Chess-EPDs/perft.epd (commit <HASH-OR-DATE>).
# Counts: regenerated by Stockfish 18 (Homebrew install) on <yyyy-mm-dd>.
# Per ADR-0006 we use the position list as a diversity corpus and regenerate
# our own counts; we do not consume Whittington's published numbers.
```

**Depth choice — D1–D4 only in committed file.** D5 takes orders of magnitude longer to generate over 175 positions; the regression suite runs at D4 by default. Higher depths can be added on demand via the regen script; not committed.

**Regeneration script: `scripts/regen-perft-fixtures.sh`** — drives `stockfish` over the FEN list, parses `Nodes searched: N` from divide output, writes the `<FEN>; D1 N; ...` lines back. Committed alongside the fixtures so future regenerations are reproducible. Bash + `awk`. ~110 lines.

#### Fixture parsing

A small private helper in `tests/perft.rs` reads each fixture file and yields `(Position, [u64; 6])` (or `[u64; 4]` for Whittington). Parser is permissive within the EPD-style grammar: skip empty lines and `#`-comments; split on `;`; each `Dn N` token contributes to the depth-indexed array. Any malformed line is a hard test failure with a descriptive message — fixtures are committed data, not user input, so silent skips are wrong.

### 5. Test layout

#### Unit tests (`#[cfg(test)] mod tests` in `src/perft.rs`)

Inline tests verify the function-internals invariants — anchor cases that documents every component of the API:

- `perft_depth_zero_returns_one` — both `perft(starting, 0) == 1` and `perft_bulk(starting, 0) == 1` and `perft_categorized(starting, 0).nodes == 1`.
- `perft_depth_one_starting_position` — `perft(starting, 1) == 20`. (Anchor for the trivial case; canonical-6 covers all six in the integration suite.)
- `perft_bulk_agrees_with_perft_at_depth_2` — for `starting`, `kiwipete`, `position_3`, assert `perft(pos, 2) == perft_bulk(pos, 2)`. Pins the bulk-counting logic against the reference.
- `perft_bulk_agrees_with_perft_at_depth_3_kiwipete` — Kiwipete D3 specifically, because Kiwipete exercises captures, EP, castling, promotions in one position; if the bulk path mishandles any leaf class, this catches it.
- `divide_at_depth_one_equals_legal_move_set` — `divide(pos, 1)` returns a `Vec<(Move, u64)>` where every entry has count 1, and the move set equals `generate_moves(pos)` modulo order.
- `divide_total_equals_perft` — for `(starting, 3)`, `divide(starting, 3).iter().map(|(_, n)| n).sum::<u64>() == perft(starting, 3)`. Same for Kiwipete D2.
- `divide_panics_on_depth_zero` — `divide(starting, 0)` panics. Documented as the API contract.
- `categorized_starting_position_depth_4_invariants` — assert the standard invariants:
  - `nodes == perft(starting, 4)`.
  - `discovery_checks <= checks`.
  - `double_checks <= discovery_checks`.
  - `en_passant <= captures`.
  - `castles + promotions + en_passant <= nodes`.
- `categorized_starting_position_depth_3_no_promotions_no_castles_no_ep` — at D3 from starting, no promotion / castle / EP is reachable. Asserts each of those counters is 0. Plus `checkmates == 0` (no mates within 3 plies from starting).
- `perft_kiwipete_depth_4_total` — anchor against the Stockfish-known D4 value (4,085,603 — verified at fixture regen). Pins one non-trivial value in unit tests so a PR that breaks Kiwipete fails before the integration suite runs.

#### Integration tests (`tests/perft.rs`)

The cross-position regression suite. Test functions:

- **`canonical_six_fast_d1_d3`** — for each canonical-6 position, for each of D1–D3, assert `perft(pos, d) == fixture[d - 1]` AND `perft_bulk(pos, d) == fixture[d - 1]`. Plain + bulk parity built into the test loop. Run by default (`cargo test`).
- **`canonical_six_fast_d4_light_only`** — Pos-3, Pos-4 only at D4: assert `perft_bulk(pos, 4) == fixture[3]`. The two lightest D4 cases (43k + 422k ≈ 465k leaves total). Pos-5 D4 (2.1M) was demoted to ignored heavy-D4 during final-review iteration 1 to fit the ≤10 s `cargo test` budget. Run by default.
- **`canonical_six_d4_heavy_slow`** (`#[ignore]`): starting D4, Kiwipete D4, Pos-6 D4 — the three heavy D4 cases. Run via `cargo test --release -- --ignored`. Plain + bulk parity assertion.
- **`canonical_six_d5_slow`** (`#[ignore]`): all six at D5, `perft_bulk` only. Run via `cargo test --release -- --ignored`.
- **`canonical_six_d6_slow`** (`#[ignore]`): all six at D6, `perft_bulk` only. Document expected runtime (Kiwipete D6 = 8.0B nodes — at 1.4 Mnps bulk that's ~95 minutes; the test scales with throughput improvement). Most-aggressive validation gate.
- **`whittington_epd_d4_slow`** (`#[ignore]`): iterate the Whittington fixture file, asserting `perft_bulk(pos, 4) == fixture[3]` for each. Run via `cargo test --release -- --ignored`. Per the §"Risks" table, expected ~2 minutes at 1.4 Mnps; investigate if >5 minutes.
- **`divide_starting_position_depth_4_matches_canonical`** — `divide(starting, 4)` returns 20 entries (one per legal move at depth 1 from start), the sum equals the fixture's D4 value, AND the entries are UCI-sorted (validates the §"Public API" sort contract). Run by default.

**No `#[ignore]` smoke benchmark in M1.G output** — the M1.F-era `bench_generate_moves_throughput` in `tests/movegen.rs` is **deleted** as part of M1.G. See §"Smoke benchmark resolution" for the rationale. After M1.G, the criterion `benches/movegen.rs` is the sole `generate_moves` throughput surface.

### 6. Benchmark layout

#### `benches/perft.rs` — perft throughput

Three scenarios chosen for **per-iteration wall-clock under ~250 ms at the §10 estimated throughput (~1.4 Mnps bulk, ~1 Mnps plain)**, which keeps criterion's 100-sample statistical regime stable. A 1 s/iter target is the upper edge of "stable" per criterion guidance; we plan ~250 ms so a 4× regression still leaves us in the stable regime.

| Bench | Position | Path | Depth | Estimated leaf count | Estimated wall at 1 Mnps plain / 1.4 Mnps bulk |
|---|---|---|---|---|---|
| `perft_starting_d4_plain` | starting | `perft` | 4 | 197,281 | ~200 ms (plain) |
| `perft_starting_d4_bulk` | starting | `perft_bulk` | 4 | 197,281 | ~140 ms (bulk) |
| `perft_kiwipete_d3` | Kiwipete | `perft_bulk` | 3 | 97,862 | ~70 ms (bulk) |

Each is a `criterion::Bencher::iter` closure invoking the perft function. Throughput in Mnps is computable from the criterion timing + the known leaf count (the ratio's the headline number).

**Depth choice rationale.** §10 estimates plain ~1 Mnps, bulk ~1.4 Mnps. At those rates, `perft_bulk_starting_d5` (4.86M nodes) would take ~3 s/iter — outside criterion's stable-sample regime and contradicting the per-iter budget. Same for `perft_kiwipete_d4` (4.09M nodes ≈ 2.9 s/iter). The depths above keep iteration time at ~70–200 ms, comfortably stable and reactive to a 5–10× landed-throughput improvement (which would let M1.H or later milestones bump depths up). The starting-position plain+bulk pair lets us measure the bulk-counting speedup directly.

**If actual throughput far exceeds the estimate** (≥10 Mnps), depths can be bumped at benchmark-capture time without changing the bench surface — the benches' point estimates are the headline; depth is a parameter set in source. The plan does not pin specific depths beyond M1.G's first capture.

#### `benches/movegen.rs` — `generate_moves` throughput

### 7. ADR-0010 — benchmark baseline format

Lands as a small (~60-line) ADR in `docs/decisions/0010-benchmark-baseline-format.md`. Contents:

- **Status.** Accepted, 2026-04-27.
- **Context.** Both `workflow.md` and `roadmap.md` (entries) marked "TBD format" for `bench/`. `docs/tooling-backlog.md` #1 surfaces the decision and binds it to M1.G's plan-mode pass.
- **Decision.**
  1. `criterion` 0.7 (current stable) for microbenchmarks.
  2. Per-machine raw artifacts under `target/criterion/` — gitignored, not portable across machines or runs.
  3. Per-milestone human-readable summary at `bench/<milestone>.md` — committed to git, the cross-commit regression-tracking source of truth.
  4. Saved baselines via `cargo bench -- --save-baseline <milestone>`; comparisons via `--baseline <milestone>`.
  5. The committed `bench/<milestone>.md` records, for each benchmark, the median ns/call (criterion's robust statistic), the iteration count, and the derived throughput (Mnps for perft, ns/call for movegen).
- **Consequences.**
  - Across-machine comparisons happen via the committed table, not via raw criterion artifacts.
  - Statistical-significance comparisons (within a single machine across two commits) use criterion's `--baseline` workflow on local raw artifacts.
  - Future milestones extend the table cumulatively (one column per milestone) OR add a new `bench/<milestone>.md` per milestone, depending on how stable the benchmark set turns out to be.
- **How to apply.** First commit at M1.G writes `bench/m1.g.md`. The format is fixed; future milestones append new rows / columns.

### 9. Stockfish fixture regeneration script

`scripts/regen-perft-fixtures.sh` (~110 lines, bash). Implementation pattern (committed in this same change):

```bash
#!/usr/bin/env bash
set -euo pipefail

# Preconditions: stockfish on PATH; record version + date for header.
SF_VERSION="$(echo 'uci' | stockfish 2>/dev/null \
    | awk '/^id name/ { sub(/^id name /, ""); print; exit }')"

# Per-FEN, per-depth: spawn one stockfish, run multiple commands via stdin
# heredoc, parse stdout for the `Nodes searched: N` line.
perft_for_fen() {
    local fen="$1"; local max_depth="$2"; local out="$fen"
    for ((d = 1; d <= max_depth; d++)); do
        local n; n=$(
            { echo "position fen $fen"; echo "go perft $d"; echo "quit"; } \
                | stockfish 2>/dev/null \
                | awk '/^Nodes searched:/ { print $3; exit }'
        )
        [[ -z "$n" ]] && { echo "ERROR: no Nodes-searched line for $fen D$d" >&2; exit 1; }
        out+="; D$d $n"
    done
    echo "$out"
}
```

**Why this UCI invocation pattern works.** Stockfish 18's `go perft N` is a Stockfish-extension command (not in base UCI) that does *not* require prior `uci` / `isready` handshake — Stockfish starts in a state ready to accept `position fen` directly. The banner output (`info string NNUE evaluation using ...` plus the `Stockfish 18 by ...` line and the `id name` / `id author` lines that an `uci` query emits) is filtered by the `awk '/^Nodes searched:/ { print $3; exit }'` line; only the perft total reaches our output. Verified at plan-implementation time: a one-line probe matches the prose-cited starting-position D4 = 197,281.

**One stockfish process per (fen, depth) pair.** Spawning one process per pair (rather than one per fen with multiple depths) is ~50ms × 36 = ~1.8s of overhead for the canonical-6 — negligible vs the actual perft compute, which dominates at D5+. Simplifies the parsing (each invocation produces exactly one `Nodes searched:` line). Keep it simple.

**Whittington downloading.** `curl -sSfL` from the public raw-URL. The upstream commit hash is recorded in the fixture file header for full provenance. Per ADR-0006 we strip the upstream's published counts and regenerate via Stockfish; the FEN list is consumed verbatim.

**Idempotent** — re-running on a clean Stockfish install reproduces the committed file byte-for-byte (modulo the `Generated:` date header line and the upstream-commit-hash header line if Whittington's master moves). Stockfish 18 is deterministic for perft.

**Sandbox-friendly tempdir.** `mktemp "${TMPDIR:-/tmp}/perft_whittington.XXXXXX"` so the script works inside Claude Code's sandbox where `/var/folders/...` paths may be denied. Plain `mktemp` (no template arg) on macOS picks `/var/folders/...` by default, which the sandbox blocks; the explicit template forces the sandbox-friendly path. Verified at fixture-regen time.

Committed alongside the fixtures so future regenerations are reproducible.

### 10. Performance posture

**Target.** ≥100 Mnps single-threaded perft on Apple Silicon (`docs/roadmap.md` §M1 exit criteria). ≥200 Mnps would be excellent.

**Reference points.**
- M1.F smoke benchmark recorded ns/call ranging 37–129 ns across the canonical 6 — that's `generate_moves` cost only, not full perft including make/unmake + recursion.
- Each perft node's cost ≈ generate_moves + (legal_moves × make_unmake) + recursion overhead. Rough: 100 ns generate + 30 (avg legal moves at start) × 30 ns make_unmake = 1000 ns per parent → ≈ 1 Mnps in plain perft. Bulk counting cuts ~30% off: ≈ 1.4 Mnps. **That's two orders of magnitude below the 100 Mnps target.**
- The 100 Mnps target assumes either (a) the engine's per-call costs drop substantially with PGO / hot-path tuning, or (b) the target is aspirational and M1.G ships a reasonable number with a follow-up optimization pass.

**Plan posture: M1.G ships honest numbers; we don't fake hitting 100 Mnps.** If the M1.G baseline lands at, say, 5 Mnps, that's the recorded `bench/m1.g.md` number. The `roadmap.md` "M1 exit criteria" is the milestone-completion gate — not the per-phase gate. M1.G's exit criteria are: perft suite passes (correctness) + benchmark harness records nodes/sec (measurement). The Mnps target is M1's exit gate, achievable through optimization passes that may follow M1.G if needed. See §"What if numbers miss the target" below.

### 11. What if numbers miss the target

If the benchmarked Mnps falls substantially short (say <20 Mnps), the M1.G commit lands the honest number and we surface the gap. Two follow-up paths:

1. **M1.H (optional optimization pass).** Profile with `samply` and `criterion`'s comparison workflow; chase the obvious wins first (move-list reuse across recursion frames; pin-rays-on-demand if the array zero-fill profiles hot; magic-table prefetch; PGO build). Each optimization SPRT-style: bench-baseline before, change, bench-after, decide.
2. **Push optimization to a later milestone.** Search-layer profiling is what really sets the production Mnps; the perft number is a signal but not the user-visible one. Document the gap and move on.

The M1.G plan does not prescribe optimization work — that's a separate ADR + plan if pursued. M1.G ships the validation infrastructure; the optimization decision is informed by M1.G's measurement.

### 12. Per-machine stability of the bench/m1.g.md table

ADR-0010 notes the committed baseline is human-readable, not machine-comparable across runs. To keep the table stable across re-runs on the same hardware, the committed numbers are taken from a **single capture run** invoked at commit time, not regenerated per-PR. Future milestones either:

- Run on the same Apple Silicon dev machine and append a column.
- Re-baseline if the dev machine changes; document the hardware change in the ADR.

The committed numbers are **reference points**, not assertions — a 2× regression on a future run is investigated; a 5% wobble is cache-line noise.

### 13. Edge cases & gotchas

| Risk | Mitigation |
|---|---|
| **Perft + categorized counts agreeing on `nodes` but disagreeing on totals** | Categorized's `nodes` field equals the plain perft total by construction (counted at the leaf). Asserted by `categorized_starting_position_depth_4_invariants` and `nodes == perft(...)`. |
| **`divide` order stability** | Pinned by §"Public API" contract: output is sorted by UCI move notation ascending — deterministic and independent of `generate_moves`'s internal emit order. The integration test `divide_starting_position_depth_4_matches_canonical` asserts both the count sum and the UCI-sortedness. For diffing against Stockfish, see the workflow snippet in §"Public API"'s `divide` doc comment. |
| **Stockfish version drift** | Fixtures' header records the SF version string. If a future `stockfish` install reports a different version and regen produces different counts, the user investigates *before* committing the new fixtures (a count change suggests Stockfish hit a bug or the upstream FEN list updated). |
| **Whittington EPD line variance** | The upstream file has trailing whitespace, mixed line-endings, possibly EPD-extension fields beyond `D1..D6`. The fixture-parsing helper accepts only `Dn N` tokens and ignores everything else (other tokens in EPD aren't perft-relevant). Hard parse failure on FEN issues. |
| **Bulk counting + categorized counts incompatibility** | Documented: `perft_categorized` always uses the non-bulk path. Tests cover the equivalence with `perft` (plain) only, never with `perft_bulk`. |
| **Categorized checkmate detection vs. depth taxonomy** | Per §3 "Recursion-base contract", checkmate is detected at depth==1 (post-make, leaf-classification ply) — *not* at depth==0. The depth-0 leaf only contributes `nodes += 1`; `is_empty` of the post-move legal-move set is checked one ply earlier, where the move that produced the leaf is still in scope. Pinned by the Kiwipete-D1-mate-style anchor unit test. |
| **Recursion stack overflow on deep perft** | D8 from Kiwipete recurses 8 deep; per-frame ≈ 1 KiB local + 0.5 KiB MoveList = 1.5 KiB → 12 KiB total. Well under macOS's 8 MiB default. Fine. |
| **`#[ignore]` tests not run before commit** | Workflow's "all tests pass" gate runs `cargo test` (fast suite). Plan adds `cargo test --release -- --ignored` as an additional pre-commit gate (mentioned explicitly in §"Verification plan"). |
| **Whittington FEN list licensing** | Public domain (the Chris Whittington repo is licensed CC0). No restriction on vendoring the FEN list. The committed file's header notes the source for attribution; ADR-0006 governs the count provenance separately. |
| **`criterion` removed in future stable releases** | Pinned at "0.7" — semver-major-pinned in `Cargo.toml`. cargo-deny `licenses` allowlist already covers criterion's transitive deps (MIT/Apache-2.0). |

## Test coverage strategy

Per `docs/workflow.md` §"Property tests vs. unit tests": ordinary unit tests anchor specific cases; property tests where the invariant is more compact than enumeration.

**Unit tests** (in `src/perft.rs`'s `#[cfg(test)] mod tests`):

Listed above in §"Test layout — Unit tests". Each test pins a specific invariant; together they exercise the four public functions and the `PerftCounts` invariants.

**Integration tests** (in `tests/perft.rs`):

Listed above in §"Test layout — Integration tests". The canonical-6 fast suite is the primary regression gate.

**Property tests** — none added in M1.G beyond M1.F's existing movegen properties. Justification: perft is an aggregation function over `generate_moves`/`make_move`/`unmake_move`, all of which are property-tested at M1.F. A perft property like "perft(pos, d) is deterministic" is implied by the function's pure dependency on those tested primitives. A property like "bulk == plain at every depth" is the purpose of the unit-test parity assertions and doesn't need proptest sampling — the unit tests at three positions × two depths cover the bulk-counting logic exhaustively. **If the test-suite reviewer flags a useful property, add it; the plan does not preempt their judgment.**

**Test-suite review will be asked to confirm:**

- Unit-test coverage adequately exercises each function's documented contract.
- Integration tests cover the cross-position regression surface.
- Categorized-count invariants cover the documented relationships.
- No silent dropped categories (e.g. a test that doesn't assert ep count zero from starting D3 would let an ep-zero bug slide).

## Parallelization map

The unit splits into independent shards once Step 1 (fixtures) and Step 2 (skeleton) land.

### Strict prerequisites (sequential, must be first)

- **Stockfish fixture regeneration** — produces the canonical-6 + Whittington files. ~5–10 minutes wall clock for D6 generation across the canonical 6; Whittington D4 across 175 positions is ~30 seconds. Already run at plan-write time; fixtures committed.
- **`src/perft.rs` skeleton** — public API + `todo!()` bodies. Unblocks the test-writing shards.

ADR-0010 is **not** a strict prerequisite — its content is finalized alongside the bench harness in Step 6 (per §"Order of operations"), since the ADR ratifies decisions that the bench files implement. A stub ADR can be drafted earlier; the final text lands at Step 6.

### Parallel after prerequisites land

| Shard | Scope | Estimate | External deps |
|---|---|---|---|
| **Shard P** | `perft` + `perft_bulk` + `divide` implementations + their unit tests | ~250 + ~150 lines | `generate_moves`, `make_move`, `unmake_move` (M1.E/F) |
| **Shard C** | `perft_categorized` + `PerftCounts` + categorized unit tests | ~150 + ~100 lines | All of P's deps + `masks::checkers_of` (in-crate) |
| **Shard FX** | Fixture parser + canonical-6 integration tests + Whittington integration test | ~150 lines | Fixture files (from Step 1) |
| **Shard B** | Both bench files + `Cargo.toml` `[[bench]]` entries + criterion dev-dep | ~120 lines | Compiling perft API (Shard P done) |

Shard P and Shard C share the recursion-driver logic; the natural way to factor:

- `perft_inner_plain<const BULK: bool>(pos, depth, &mut MoveList) -> u64` — generic over bulk/plain, dead-code-eliminated at monomorphization.
- `perft_categorized_inner(pos, depth, &mut PerftCounts)` — separate path, no bulk option.

If two coding agents work P and C in parallel, the boundary is: Shard P writes `perft`, `perft_bulk`, `divide`; Shard C writes `perft_categorized` + `PerftCounts`. Shared inner-recursion factoring is left to the reviewer / final pass — initial split allows the two implementations to land without coupling.

**Unit-test ordering caveat.** The `categorized_starting_position_depth_4_invariants` unit test compares `perft_categorized(starting, 4).nodes` against `perft(starting, 4)`, so Shard C's tests assume Shard P's `perft` is callable. In practice both shards' tests compile against the skeleton `todo!()` bodies; if Shard C's tests run before Shard P's body lands, the `perft` call inside Shard C's test panics with `not yet implemented`. Resolution: the test-suite review loop (workflow step 6) and the implementation phase (step 7) sequence Shard P's body landing before Shard C's tests are *run* (compile is fine against the skeleton). Documented here so the implementation agents don't churn on this dependency.

### Sequential after parallel shards converge

- **Shard E** — Final wiring: ensure `lib.rs` re-exports settle, ensure all four public functions interoperate (e.g., test categorized's `nodes` agrees with plain `perft`). Documentation updates land here.

### Honesty about dependencies

- Shards P, C, FX, B are genuinely independent at the file level: P touches `src/perft.rs` recursion logic; C touches the categorized path in the same file but a separate function; FX touches `tests/perft.rs` and adds the fixture parser; B touches `benches/`, `Cargo.toml`, and nothing else.
- The shared file `src/perft.rs` between P and C is the only touch-point. Resolved by structuring the file with a clear separation: `// ---- plain / bulk ----`, `// ---- categorized ----`. Merge conflicts are mechanical at worst.
- A single agent could do all four sequentially. Spawning four is throughput.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| **Bulk counting silently miscounts** at depth 1 | Unit tests assert bulk == plain at D2 and D3 across multiple positions; integration tests assert bulk == plain at D1–D3 (fast suite) and D4-heavy (`canonical_six_d4_heavy_slow`, ignored). The strongest single regression check is Kiwipete D3 (unit test) — Kiwipete exercises captures, EP, castling, promotions in one position, so a bulk-vs-plain divergence on any leaf class fires there. The `#[ignore]` D4-heavy adds the same parity check at higher depth. |
| **Categorized counts undercounting checkmates** | Specific anchor: a known-mating position's perft at depth 1 reports `checkmates == 1`. Add a constructed mate fixture (`white queens deliver mate at depth 1`) in unit tests. |
| **Discovery / double-check classification bugs** | The unit-test invariants `discovery_checks ≤ checks` and `double_checks ≤ discovery_checks` catch over-counting. Anchor: from the EP-double-check fixture, `perft_categorized(parent, 1).double_checks >= 1`. |
| **Stockfish output parsing brittleness** | Regen script is bash + awk; output format `Nodes searched: N` is stable since at least Stockfish 11. Asserted by an explicit grep regex. |
| **Whittington FEN list contains malformed FENs** | The fixture parser fails hard on parse error with line number + FEN, surfacing the issue. We accept dropping any line that fails our FEN parser; ADR-0006 covers this — Stockfish accepts FENs we reject only if our FEN parser is over-strict. Plan adds a `tests/fixtures/perft_whittington_known_skips.txt` file, empty at commit, listing any FEN we skipped + reason. |
| **D6 ignored test runtime regression on slow hardware** | The test header documents expected runtime on Apple Silicon. CI / future-mobile-port docs note that ignored tests are dev-only. |
| **Whittington `#[ignore]` D4 wall-clock** | At §10's 1.4 Mnps bulk estimate, ~125 s. Test header documents "expected ~2 minutes; investigate if >5 minutes." Treats a 2× regression as a real signal. |
| **Mnps target miss** | Documented in §"Performance posture" and §"What if numbers miss the target." Honest reporting; optimization is its own follow-up unit if needed. |
| **`criterion` 0.7 license check** | `cargo deny check` passes (criterion is MIT/Apache-2.0). Verify at Cargo.toml change time. |
| **Cargo.lock churn from criterion's transitives** | Expected (criterion has ~30 transitives via `plotters`, `rayon`, `serde`). Run `cargo audit` + `cargo deny check` after the dep add. |
| **`#[ignore]` test pyramid scaling** | `cargo test --release -- --ignored` runs all ignored tests including the M1.E sentinel + M1.G's D4-heavy + D5 + D6 + Whittington D4. Total runtime grows with each milestone. Acceptable up through M1; if M1's ignored suite breaks the 5-minute mark we reorganize at M2. (Note: M1.F's `bench_generate_moves_throughput` smoke is deleted in M1.G — replaced by the criterion harness.) |
