# M1.A — Skeleton + primitives

## Context

M0 is complete and M1 prior-art research has converged. M1 (move generator + perft) is decomposed into seven sub-phases A–G in `docs/roadmap.md`; this plan covers **M1.A: skeleton + primitives**, the foundation everything else builds on.

The current repo is just a `cargo new` hello-world. We need to:
- introduce the library/binary split so later phases can have integration tests,
- lock in the release-profile settings the engine will compile under for the rest of the project,
- create the `Square` and `Bitboard` types, with primitives sharp enough that M1.B–G consume them without modification.

Why now: the `Position` struct (M1.B) holds bitboards keyed by squares; magic-bitboard generation (M1.C) iterates squares and ANDs/ORs bitboards by the thousand; perft reads them at every node. Getting the primitives wrong is structural — we'd be re-touching every file later. Getting them right is cheap.

The user does not read code. The plan must be reviewable from the artifact alone, and the eventual implementation must be free of `unsafe` blocks the user cannot audit.

The plan was pressure-tested by a Plan subagent; substantive recommendations from that pass are folded in (notably: omit `types.rs` entirely, lean harder into newtype `Square`, defer `mov.rs` / `between` / `line_through` / `tests/` directory until they have real callers).

## Decisions baked into this plan

1. **`Square` is a newtype, not an enum.** A `#[repr(u8)] enum` would require `unsafe { transmute(byte) }` or 64-arm matches at every byte-to-square boundary downstream (FEN parsing, Zobrist indexing, magic occupancy iteration, move decoding). Newtype with `const fn new(u8) -> Option<Self>` keeps construction safe and explicit. The user cannot audit `unsafe` blocks by reading code, so we avoid them.

2. **`Bitboard`'s inner field is `pub`, `Square`'s is private.** Asymmetry is intentional: `Square` has the invariant `inner < 64`; `Bitboard` is a 64-bit set with no invariant. Direct access to the `u64` is ergonomic in tests and at construction.

3. **Aggressive `const fn`.** Pure operations on `Square` and `Bitboard` are `const fn`. Magic-bitboard generation in M1.C and the named square / mask constants here both want compile-time evaluation. Cost: near zero. **Caveat:** `std::ops` traits (`BitAnd`, `BitOr`, etc.) cannot be `const fn` on stable Rust 2024, so we provide both — `impl BitAnd for Bitboard` for ergonomics, and inherent `const fn` versions where const contexts need them. This duplication will be visible in code review and is called out here so the user isn't surprised.

4. **`Square::A1`…`Square::H8` named constants exist.** ~64 lines of declarations. Worth it: every bitboard test below reads dramatically better with `Bitboard::from_square(E4)` than `Bitboard::from_square(Square::new(28).unwrap())`.

5. **Pretty-print convention: `Debug` prints the 8×8 grid** (rank 8 at top, file a at left, `X`/`.` cells), `Display` prints `Bitboard(0x...)` hex. This is the inverse of the usual std-lib convention but matches what we actually want during debugging — the grid is the human-readable form, and `dbg!(bb)` is the most common ad-hoc inspection. Documented in the module docstring. Research flagged the LSB-first naive print as a footgun ("a naive LSB-first bitboard print reads top-down ranks 1..8, which is unintuitive — provide a debug pretty-printer day one"), so we treat the grid printer as load-bearing, not decorative. **Exact format pinned below in §"Pretty-print formats."**

6. **No license field in `Cargo.toml` yet.** Pre-distribution; avoids committing to a license without thought. Add when we publish or share.

7. **No `unsafe` anywhere in M1.A.** `Square::new_unchecked` uses `debug_assert!` plus plain field assignment — same release-build performance, no UB potential. **Purpose:** `new_unchecked` exists *only* so internal hot paths (M1.C magic generation, M1.F move-list emission) can skip the `Option` cost when they've already validated the input. In debug builds, `debug_assert!(index < 64)` panics on misuse; in release builds the call is identical to a plain `Square(index)` construction. The release-build invariant is *not* guarded — that's accepted (zero-overhead boundary for code paths that have already proven the precondition).

8. **`Bitboard`-returning inherent methods are `#[must_use]`.** Every inherent method on `Bitboard` that returns a `Bitboard` and doesn't take `&mut self` gets `#[must_use]`, so a caller who writes `bb.with(sq);` (forgot the assignment) gets a compile-time warning. **Operator forms are also covered** because the stdlib `BitAnd::bitand` / `BitOr::bitor` / `BitXor::bitxor` / `Not::not` trait method declarations themselves carry `#[must_use]`, which propagates automatically to our impls — `bb1 & bb2;` (bare expression, forgot the assignment) warns. We do **not** add `#[must_use]` to our trait-impl method overrides because Rust rejects that placement (warning that will become a hard error). The explicit-discard form `let _ = bb1 & bb2;` is intentionally silent in either case; that's standard Rust semantics.

9. **Derive lists pinned in §"Type definitions and signatures."** `Square` derives `Copy, Clone, PartialEq, Eq, Hash, PartialOrd, Ord`; `Debug` is provided as a custom impl that prints the UCI string ("e4"), matching `Display`. `Bitboard` derives `Copy, Clone, PartialEq, Eq, Hash, Default`; `Debug` is a custom impl for the grid printer (do not derive). `Default` for `Bitboard` is `EMPTY`, which matches `u64::default() == 0`. `Hash` is derived prophylactically on both — no M1.A caller needs `HashMap<Square, _>` or `HashMap<Bitboard, _>`, but the derive cost is one trait impl per type, and removing it later for a real caller is friction we can avoid.

10. **Release-profile `debug-assertions` and `overflow-checks` left at Cargo defaults (both `false`).** This means `new_unchecked`'s invariant guard, and any future `debug_assert!`-style sanity checks (e.g., the M1.D Zobrist round-trip), are silent in `cargo build --release`. Accepted: production performance is more important than release-mode invariant checking. If we ever want a high-confidence release build (fuzzing, SPRT pre-flight), we'll add a `[profile.release-debug]` block at that point.

11. **Clippy lint level: `clippy::all` (default).** No `clippy::pedantic` opt-in for M1.A. Pedantic flags `Bitboard(pub u64)` for several "code smell" lints that we deliberately accept; the cost of `#[allow]` annotations everywhere isn't worth it.

### `src/square.rs` — public surface

```rust
#[derive(Copy, Clone, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct Square(u8);   // private inner; invariant: < 64

impl Square {
    pub const COUNT: usize = 64;

    // Named constants A1 through H8 (LERF: A1=0, H1=7, A8=56, H8=63)
    pub const A1: Square; pub const B1: Square; /* … through */ pub const H8: Square;

    pub const fn new(index: u8) -> Option<Self>;            // bounds-checked
    pub const fn new_unchecked(index: u8) -> Self;          // debug_assert!; no unsafe
    pub const fn from_file_rank(file: u8, rank: u8) -> Option<Self>;

    pub const fn index(self) -> u8;     // 0..=63
    pub const fn file(self) -> u8;      // 0..=7  (a=0, h=7)
    pub const fn rank(self) -> u8;      // 0..=7  (1=0, 8=7)

    pub fn parse_uci(s: &str) -> Option<Self>;   // "e4" -> Some(...)

    pub fn all() -> crate::bitboard::Squares;   // delegates to Bitboard::FULL.iter()
}

impl fmt::Display for Square { /* "e4" */ }
impl fmt::Debug for Square   { /* same as Display */ }
```

`File`/`Rank` are returned as `u8` with a documented `0..=7` invariant. Wrapping them in newtypes is deferred — they have zero callers in M1.A. **Note:** when M1.B's FEN parser becomes the first real consumer of `from_file_rank`, expect us to revisit this and possibly introduce `File(u8)`/`Rank(u8)` newtypes. The two `u8` parameters of `from_file_rank` *can* be transposed silently by callers; that risk lives until M1.B closes it.

**Module dependency direction:** `square` imports `Squares` from `bitboard`; `bitboard` imports `Square` from `square`. Mutual module-level imports are fine in Rust as long as type definitions don't form a cycle (they don't — `Square` is `u8`, `Bitboard` is `u64`, `Squares` wraps `Bitboard`). One canonical iterator type is preferable to a duplicate `AllSquares(u8)` counter that does the same thing.

### `src/bitboard.rs` — public surface

```rust
#[derive(Copy, Clone, PartialEq, Eq, Hash, Default)]   // NOT Debug — custom impl below
pub struct Bitboard(pub u64);

impl Bitboard {
    pub const EMPTY: Bitboard = Bitboard(0);
    pub const FULL:  Bitboard = Bitboard(!0);

    // File and rank masks
    pub const FILE_A: Bitboard; /* … through */ pub const FILE_H: Bitboard;
    pub const RANK_1: Bitboard; /* … through */ pub const RANK_8: Bitboard;

    // Single-bit operations  (#[must_use] on every Bitboard-returning method)
    pub const fn from_square(sq: Square) -> Bitboard;
    pub const fn contains(self, sq: Square) -> bool;
    pub const fn with(self, sq: Square) -> Bitboard;
    pub const fn without(self, sq: Square) -> Bitboard;

    // Population
    pub const fn count(self) -> u32;
    pub const fn is_empty(self) -> bool;
    pub const fn any(self) -> bool;

    // LSB / iteration
    pub const fn lsb(self) -> Option<Square>;     // returns None on EMPTY
    pub fn pop_lsb(&mut self) -> Option<Square>;  // mutating extract; None on EMPTY
    pub fn iter(self) -> Squares;                 // wraps a Bitboard; next() = pop_lsb

    // Directional shifts (LERF: north = << 8)
    pub const fn shift_north(self) -> Bitboard;
    pub const fn shift_south(self) -> Bitboard;
    pub const fn shift_east(self) -> Bitboard;        // masks !FILE_H to prevent wrap
    pub const fn shift_west(self) -> Bitboard;        // masks !FILE_A
    pub const fn shift_north_east(self) -> Bitboard;
    pub const fn shift_north_west(self) -> Bitboard;
    pub const fn shift_south_east(self) -> Bitboard;
    pub const fn shift_south_west(self) -> Bitboard;
}

// std::ops impls: BitAnd, BitOr, BitXor, Not + Assign variants. Not const-fn.
impl ops::BitAnd for Bitboard { /* ... */ }
// ...

impl fmt::Debug for Bitboard { /* multiline grid — see Pretty-print formats below */ }
impl fmt::Display for Bitboard { /* "Bitboard(0x...)" hex — see Pretty-print formats below */ }

// Iterator type. Used by both Square::all() and Bitboard::iter().
// Implementation note: Squares is just a wrapped Bitboard; next() = self.0.pop_lsb().
pub struct Squares(Bitboard);
impl Iterator for Squares { type Item = Square; /* delegates to pop_lsb */ }
```

`Bitboard::iter()` returns the named `Squares` struct rather than `impl Iterator<Item = Square>` so callers can store the iterator type in structs or generics if they need to (free flexibility, one extra type to name).

### Pretty-print formats

**`Debug` for `Bitboard`** — exact format, pinned for the `pretty_print_grid` snapshot test. Eight rank rows (rank 8 at top, rank 1 at bottom), each prefixed by its rank number and a space; cells are space-separated, `X` for set, `.` for clear; a trailing file-label row prefixed by two spaces. Each row terminated by `\n`. Example for `Bitboard::FILE_A | Bitboard::RANK_1`:

```
8 X . . . . . . .
7 X . . . . . . .
6 X . . . . . . .
5 X . . . . . . .
4 X . . . . . . .
3 X . . . . . . .
2 X . . . . . . .
1 X X X X X X X X
  a b c d e f g h
```

That is the literal byte sequence the snapshot test asserts on. Concrete encoding rules:

- Every line — including the file-label row — ends with `\n`. The full string therefore ends with `\n`.
- No leading newline; no blank line anywhere.
- Cells inside a row are separated by exactly one space; one space follows the rank-number prefix and precedes the first cell.
- No trailing whitespace on any line (the last cell of each row is followed directly by `\n`).
- The file-label row begins with two spaces (aligning labels under their cell columns).

**`Display` for `Bitboard`** — `Bitboard(0x{:016x})` format. Always 16 hex digits, lowercase, with the `Bitboard(...)` wrapper. Example: `Bitboard::from_square(Square::A1)` displays as `Bitboard(0x0000000000000001)`. Pinned by the `display_hex_format` test.

## Order of operations

Following `docs/workflow.md`'s 10-step per-feature loop. M1.A is now at step 4 (plan-review loop). Steps 5–10 happen *after* this plan is reviewer-approved and user-approved.

### Step 5 — Write tests (entire scope, before implementation)

Two-pass setup:

**Pass 5.0: Scaffolding** — single short task. Update `Cargo.toml` (description + `[profile.release]`). Create `src/lib.rs` with `pub mod square; pub mod bitboard;`. Create `src/main.rs` banner. Create `src/square.rs` and `src/bitboard.rs` populated with:

- struct definitions with the agreed derives,
- *function* stubs returning `todo!()` (function bodies),
- `pub const` declarations with their **real, computed values** (not `todo!()` — `const` initializers cannot be `todo!()` in stable Rust). The 64 named `Square` constants get `Square(0)`…`Square(63)` per LERF; the file/rank masks get their actual `u64` literals; `EMPTY = Bitboard(0)` and `FULL = Bitboard(!0)`.

`cargo build` succeeds; tests compile but every test that exercises a stubbed function fails with `todo!()`. Tests that read the named constants pass trivially against the const values — that's expected.

**Pass 5.A: Tests for `square.rs`** — write the tests from the §Test coverage table inline against the agreed signatures.

**Pass 5.B: Tests for `bitboard.rs`** — write the tests from the table inline against the agreed signatures.

5.A and 5.B can be written **in parallel** by two coding agents because they share no inputs beyond the plan's public surface. See parallelization map below.

End state after step 5: every test compiles and fails (against `todo!()` stubs). No real implementation exists yet.

### Step 6 — Test-suite review loop

Blind reviewer reads `src/square.rs`, `src/bitboard.rs`, the plan, and `docs/research/m1-engine-architecture.md` (for LERF convention) and `docs/research/m1-perft-and-rust.md` (for Rust idiom). Review dimensions: correctness to spec (LERF, file-mask wrap, snapshot grid format), confirmation bias (would tests pass against a stub returning canned values?), adequate checks, corner case coverage. Iterate via `SendMessage` until reviewer returns "no further substantive issues."

### Step 7 — Implement

Implementation order is sequential because `Bitboard` consumes `Square`. The wiring of `Square::all()` to `Bitboard::FULL.iter()` is straight-through from day one (no deferred re-wire) — the dependency arrow from `square` to `bitboard::Squares` is acceptable, see §"Type definitions and signatures" note.

1. **`src/square.rs` body**: replace `todo!()` stubs with real implementations — `new`/`new_unchecked`/`from_file_rank`, `index`/`file`/`rank`, `parse_uci`, `Display`, `Debug`. `Square::all()` returns `Bitboard::FULL.iter()`. The 64 named `A1..H8` constants are already in place from pass 5.0.
2. **`src/bitboard.rs` body**: single-bit ops (`from_square`, `contains`, `with`, `without`), population (`count`, `is_empty`, `any`), LSB ops (`lsb`, `pop_lsb`), `iter` returning `Squares`, std::ops trait impls + assigns, the eight directional shifts with file-mask wrap protection, `Debug` grid printer, `Display` hex. `EMPTY`/`FULL` and the file/rank mask constants are already in place from pass 5.0.

The bitboard implementation is one cohesive file (~250 LOC) — a single coding agent. Splitting it would create artificial coordination overhead, see §"Parallelization map."

### Step 8 — All tests pass

`cargo test` green. `cargo build --release` succeeds with new profile. `cargo run` prints the banner. No final review until this gate is met.

### Step 9 — Final review loop

Blind reviewer reads the new code + tests + plan + research. Review dimensions: correctness, corner cases not in tests, code quality (idiomatic Rust 2024, no premature abstractions), readability, simplicity, performance flags (e.g., is the shift implementation branch-free?). Iterate via `SendMessage` until "no further substantive issues."

### Step 10 — Benchmark

No benchmarks for M1.A. Criterion arrives in M1.G; the bitboard primitives don't have a measurable hot path yet (no callers). Skip cleanly; record nothing.
