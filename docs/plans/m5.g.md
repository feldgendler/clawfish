# M5.G — Singular extensions

**Plan unit.** `M5.G — Singular extensions`. Adds a per-node "is the TT move singular?" verification search that, when it confirms singularity, extends the TT move by 1 ply.

**Predecessor.** `baseline/m5f-qsearch-in-tt` (commit `b92c815`, tagged 2026-05-09 post-SPRT).

**Research.** [`docs/research/m5-singular-extensions.md`](../research/m5-singular-extensions.md). Headlines: depth ≥ 8, TT bound = Lower (Exact deferred to a follow-up campaign), `tt.depth >= depth - 3`, `singular_β = tt_score − depth · 1`, verification depth `(depth − 1) / 2`, exclude TT move via new `excluded_move: Option<Move>` parameter on `negamax`, single-ply extension only, no double-extension, no multi-cut for v1, NMP allowed inside verification, normal TT writes from recursive children inside verification subtree, **post-loop TT store suppressed at the verification frame itself**.

**Expected size.** ~400 LOC including tests + ADR + retrospective.

**Expected Elo.** Literature prior +10–30 Elo. Plan §11 SPRT is the gate; correctness is non-negotiable.

---

## §1. Scope and non-goals

**In scope.**
- One new pruning/extension block in `negamax`, keyed on the TT move's singularity.
- Three pure helpers (`singular_beta`, `verification_depth`, `singular_extension_eligible`) per the M3.D `negate_window` / M5.C `late_move_reduction` / M5.D `ffp_pruned_bound` precedent.
- One new constant block: `SE_MIN_DEPTH`, `SE_MARGIN_PER_DEPTH`, `SE_TT_DEPTH_DELTA`.
- New `excluded_move: Option<Move>` parameter on `negamax` (and `negamax_for_test`); ~50 mechanical migration sites in `src/search.rs`.
- Move-loop skip clause: when `excluded_move == Some(mv)`, `continue` before any quiet/LMR/FFP work.
- **Step-7 TT-cutoff suppression** when `excluded_move.is_some()` (load-bearing — without this guard, the verification frame's step-7 cutoff fires on the same TT entry the parent read, defeating SE entirely; see §6).
- **Step-9 NMP TT-store suppression** when `excluded_move.is_some()` (the verification frame must not pollute the current node's entry from an NMP cutoff inside verification).
- **Step-14 main TT-store suppression** when `excluded_move.is_some()` (same rationale as step-9 NMP store).
- Re-entrancy guard: SE block early-exits via predicate clause 1 when `excluded_move.is_some()`.
- `#[cfg(test)] se_extensions` counter + `_for_test` accessor (project convention).
- ADR-0029.
- Bench refresh; WAC + STS diagnostic suites; mixed-TC SPRT vs `baseline/m5f-qsearch-in-tt`.

**Out of scope (deferred to tuning backlog or follow-up campaign).**
- Lower-bound + Exact gate (start with Lower-only).
- Multi-cut on verification fail-high.
- Double extensions.
- SE on PV nodes.
- Check extensions (the project doesn't currently have any; SE doesn't introduce them).
- Mate-distance interaction tightening beyond the simple `tt_score.abs() < MATE_IN_MAX_PLY` guard.
- Excluded-move TT-key separation (Hyatt-style hashing the excluded-move into the TT key — research §5.4). The plan's three `excluded_move.is_none()` guards (step-7 cutoff, step-9 NMP store, step-14 main store) are the cheaper alternative; key separation would obviate all three but doubles the TT memory footprint or halves the unique-zobrist coverage. Defer per research §5.4 consensus.

## §3. Constants

```rust
/// M5.G singular-extension minimum remaining depth. Below this, SE is too
/// shallow to justify the verification-search cost. **Landed at v2 = 6**
/// (Xiphos default) after v1 (= 8, CPW majority) SPRT-failed at outcome 3
/// with bimodal per-TC pattern. ADR-0029 §1.
pub(crate) const SE_MIN_DEPTH: u32 = 6;

/// M5.G singular-extension margin per ply. `singular_beta = tt_score - depth *
/// SE_MARGIN_PER_DEPTH`. Xiphos / Ethereal defaults; conservative starting
/// value. Post-landing SPRT-tune candidate (tuning backlog: try 2). ADR-0029 §2.
pub(crate) const SE_MARGIN_PER_DEPTH: i32 = 1;

/// M5.G singular-extension TT-entry depth tolerance. SE fires only when the
/// TT entry's stored depth is at least `depth - SE_TT_DEPTH_DELTA`, i.e. the
/// TT score is "fresh enough" to be evidence at the current depth. Xiphos
/// default. ADR-0029 §3.
pub(crate) const SE_TT_DEPTH_DELTA: u32 = 3;

/// Compile-time invariant: at v1, FFP fires at `depth ≤ 1` and SE fires at
/// `depth ≥ 8`, so the two cannot co-fire at any node. Mirrors the existing
/// `FFP_MAX_DEPTH < LMR_MIN_DEPTH` invariant — load-bearing as a tripwire
/// against a future tuning that raises `FFP_MAX_DEPTH` or lowers `SE_MIN_DEPTH`
/// into overlap. A future patch that violates this MUST update ADR-0029 §4
/// (the move-loop integration guarantee that `tt_move_extension` does not
/// compose with FFP) and remove this assertion.
const _: () = assert!(FFP_MAX_DEPTH < SE_MIN_DEPTH);
```

**Placement.** Put the SE constants block alongside the existing M5.A–M5.D constants in `src/search.rs` (~line 425+). The new `const _: () = assert!(FFP_MAX_DEPTH < SE_MIN_DEPTH);` line goes **after** both `FFP_MAX_DEPTH` and `SE_MIN_DEPTH` are defined — alongside the existing `const _: () = assert!(FFP_MAX_DEPTH < LMR_MIN_DEPTH);` invariant currently at `src/search.rs:515`. Cluster the two assertions in a small "depth-disjointness invariants" sub-block so a future tuning patch sees both invariants together.

## §4. Pure helpers

Three pure functions, extracted for mutation-coverage discrimination per the project's helper precedent (M3.D `negate_window`, M5.C `late_move_reduction`, M5.D `ffp_pruned_bound`).

```rust
/// Singular-extension β (M5.G — ADR-0029 §2). `tt_score - depth * SE_MARGIN_PER_DEPTH`,
/// floored at `-(MATE - 1)` to avoid mate-score wrap when `tt_score` is near `-MATE`.
/// Pure function. The caller-side `tt_score.abs() < MATE_IN_MAX_PLY` gate
/// (§5 below) makes the floor a defense-in-depth invariant rather than a
/// hot-path concern, but the floor is unit-tested independently.
pub(crate) fn singular_beta(tt_score: i32, depth: u32) -> i32 {
    let raw = tt_score.saturating_sub(SE_MARGIN_PER_DEPTH * depth as i32);
    raw.max(-(MATE - 1))
}

/// Singular-extension verification-search remaining depth (M5.G — ADR-0029 §3).
/// `(depth - 1) / 2` (integer division), with a debug-assert that
/// `depth >= SE_MIN_DEPTH` — at SE_MIN_DEPTH = 8 this yields verif_depth = 3.
/// Pure function. ADR-0029 §3.
///
/// **Caller obligation.** `depth >= SE_MIN_DEPTH` is the contract.
/// `(0 - 1)` underflows in `u32` (panicking in debug, wrapping in release —
/// `(0_u32.wrapping_sub(1)) / 2 = u32::MAX / 2 = 2_147_483_647`, which would
/// then propagate into a deep verification recursion). The eligibility
/// predicate's clause 5 (`depth >= SE_MIN_DEPTH`) is the only call-site
/// protection; the helper's `debug_assert!` pins this in debug builds.
pub(crate) fn verification_depth(depth: u32) -> u32 {
    debug_assert!(
        depth >= SE_MIN_DEPTH,
        "verification_depth: caller must have passed the SE_MIN_DEPTH gate; depth={depth}"
    );
    (depth - 1) / 2
}

/// Singular-extension full eligibility predicate (M5.G — ADR-0029 §1).
/// All nine conditions must hold. Pure function. The caller passes the
/// **probed-but-not-yet-shadowed** TT data captured immediately after step-7's
/// `tt.probe`, and the `tt_move` bits **after** confirming the TT move is
/// at `moves_vec[0]` (i.e. step-12 promoted a non-zero, legal TT move to
/// the front of the move list — without that confirmation the call site
/// passes `tt_move = 0` and the predicate rejects via clause 9).
/// ADR-0029 §1.
///
/// Conjunction (in evaluation order; cheapest predicates first):
/// 1. `excluded_move.is_none()` — re-entrancy guard at the **immediate
///    verification frame**. The verification call passes
///    `excluded_move = Some(parent_tt_move)`; this clause prevents the
///    verification frame's own SE block from firing again (which would
///    yield nested verifications, worst-case exponential in parent
///    depth; see ADR-0029 §4 and the depth-budget invariant in §6 below).
///    The clause does **not** propagate through `search_child`; descendants
///    of the verification frame have `excluded_move = None` again. Recursion
///    of SE in the descendant subtree is bounded by the depth halving
///    `verification_depth(d) ≈ d/2` — at parent_depth = SE_MIN_DEPTH = 8,
///    the verification subtree's depth is 3 (= (8−1)/2), well below
///    SE_MIN_DEPTH, so clause 5 blocks descendant SE. At parent_depth ≥ 19,
///    descendant SE is mathematically possible (verification subtree's
///    grandchildren reach depth 8); the literature consensus (research §3.3)
///    is that the depth halving keeps the chain depth `O(log d)` and the
///    cumulative cost `O(b^{d/2})` (geometric sum dominated by the first
///    term), and we follow that consensus.
/// 2. `ply > 0` — root must search every move at full depth (no extension at root).
///    This also makes the searchmoves-filter / TT-move interaction a non-issue:
///    the searchmoves filter at `src/search.rs:1525-1530` runs only at `ply == 0`,
///    so the SE block (which fires at `ply > 0`) cannot interact with it.
/// 3. `!is_pv` — start conservative (literature majority); PV-SE deferred.
///    Justification at non-PV: TT entries at non-PV nodes are predominantly
///    Lower-bound (fail-high cutoffs) and Upper-bound (fail-lows); Exact
///    bounds are rare (only when the move loop produces a score strictly
///    inside `(original_alpha, beta)`). The Lower-only gate (clause 6)
///    captures the dominant case at non-PV; Exact is incremental, not
///    load-bearing for v1 — see §1 out-of-scope.
/// 4. `!in_check` — check evasions are already a search-quality hot spot;
///    re-running half-depth verification on top is poorly motivated and
///    hard to reason about. Project alignment with ADR-0024 §4 / ADR-0026 §4.
/// 5. `depth >= SE_MIN_DEPTH` — minimum-depth guard. Via the
///    compile-time invariant `FFP_MAX_DEPTH < SE_MIN_DEPTH` (§3 below),
///    SE and FFP are depth-disjoint and never co-fire. Via M5.F's qsearch
///    entries having `depth = 0`, clause 7's `tt_depth >= depth - 3 = 5`
///    naturally excludes them at `depth == SE_MIN_DEPTH`.
/// 6. `tt_data.bound == Lower` — Lower bound is the only sound starting case
///    (Exact deferred to a follow-up campaign per §1).
/// 7. `tt_depth as u32 >= depth - SE_TT_DEPTH_DELTA` — TT entry must be
///    "fresh enough"; saturating subtraction avoids underflow at depth = SE_MIN_DEPTH.
/// 8. `tt_score.abs() < MATE_IN_MAX_PLY` — mate-score guard; outside this
///    band, `singular_beta` arithmetic is meaningless. Combined with clause 5
///    (`depth >= 8`) and `SE_MARGIN_PER_DEPTH = 1`, this also guarantees that
///    the resulting `singular_beta` stays strictly below `MATE_IN_MAX_PLY`
///    (see `singular_beta_at_max_allowed_tt_score_is_below_mate_in_max_ply`
///    test in §8).
/// 9. `tt_move != 0` — non-sentinel TT move. `Move::default().bits() == 0` is
///    the no-move sentinel and is never produced by movegen (ADR-0018 §12),
///    so the call site's `moves_vec[0].bits() == tt_move` confirmation also
///    holds only for `tt_move != 0`. Folding the non-zero check into the
///    predicate (instead of leaving it implicit at the call site) makes the
///    eligibility surface fully pure-function-testable.
///
/// Pure predicate — no `pos` access, no side effects. The full set of
/// per-clause flip-mutants is independently testable.
///
/// **Argument-count ergonomics.** Nine positional arguments is at the edge of
/// readability; the alternative (`fn singular_extension_eligible(snapshot:
/// &TtProbeSnapshot, ctx: &SeGateCtx) -> bool`) was rejected because it would
/// couple the helper to the snapshot's struct layout, breaking the project's
/// pure-helper precedent (M3.D `negate_window`, M5.C `late_move_reduction`,
/// M5.D `ffp_pruned_bound` — all primitive args). The `#[allow(clippy::
/// too_many_arguments)]` attribute below is a deliberate exception. Argument
/// transposition mutants are largely caught by the type system (TtBound vs
/// u8 vs i32 vs u32 vs Option<Move> are mutually distinct), with the
/// remaining transposition risk covered by per-clause flip-mutant tests.
#[allow(clippy::too_many_arguments)]
pub(crate) fn singular_extension_eligible(
    excluded_move: Option<Move>,
    ply: u32,
    is_pv: bool,
    in_check_flag: bool,
    depth: u32,
    tt_bound: TtBound,
    tt_depth: u8,
    tt_score: i32,
    tt_move: u16,
) -> bool {
    excluded_move.is_none()
        && ply > 0
        && !is_pv
        && !in_check_flag
        && depth >= SE_MIN_DEPTH
        && tt_bound == TtBound::Lower
        && (tt_depth as u32) >= depth.saturating_sub(SE_TT_DEPTH_DELTA)
        && tt_score.abs() < MATE_IN_MAX_PLY
        && tt_move != 0
}
```

(Place alongside `null_move_reduction`, `reverse_futility_margin`, etc. in the helper block ~`src/search.rs:630+`.)

## §6. SE block placement and flow in `negamax`

**Placement.** New step **12.5**, between step 12 (move ordering) and step 13 (move loop). Rationale:

- After step 7 (TT probe): the SE block needs the probed TT data (`tt_score`, `tt.depth`, `tt.bound`, `tt_move`).
- After step 11 (terminal check): SE on a no-legal-moves position is meaningless.
- After step 12 (ordering): `moves_vec[0]` is the TT move (by step-12's promote-to-front). The SE block confirms this and uses `moves_vec[0]` as the TT-move handle for verification's exclusion.

**Pre-conditions captured at step 7.** During the existing TT probe, capture not just `tt_move: u16` but also the probed `bound` and `depth` and `score` into local variables. (At present step 7 reads them inline within the if-let and discards; the SE block needs them post-probe.)

**Verification-frame TT cutoff is suppressed (load-bearing).** The naive design — let the verification frame's step-7 TT probe cut off normally — is broken: the same TT entry that triggered SE at the parent (Lower bound, `tt_score`) re-cuts at the verification frame because `tt_score >= beta_verif = singular_beta = tt_score − depth_parent` reduces to `depth_parent >= 0` (always true). The verification call short-circuits via TT cutoff and returns `tt_score`, which trivially `>= singular_beta` → SE never fires. **0-Elo no-op.** The fix: gate the step-7 cutoff branch on `excluded_move.is_none()` so the verification frame's negamax body falls through past step 7 and runs the full move loop.

**Patch.** At `src/search.rs:1388` (the existing cutoff line `if !is_pv && entry.depth as u32 >= depth { ... }`), insert `excluded_move.is_none()` as a leading conjunct:

```rust
if excluded_move.is_none() && !is_pv && entry.depth as u32 >= depth {
    let tt_score = score_from_tt(entry.score as i32, ply as i32);
    match entry.bound() {
        TtBound::Exact => return tt_score,
        TtBound::Lower if tt_score >= beta => return tt_score,
        TtBound::Upper if tt_score <= alpha => return tt_score,
        _ => {}
    }
}
```

The probe itself (lines 1384-1387, capturing `tt_move` and the `tt_probe_snapshot`) runs unconditionally — extracting `tt_move` for step-12 ordering at the verification frame is harmless (the move-loop's excluded-move skip removes it anyway). Only the cutoff branch is suppressed.

**Outside the verification frame** (`excluded_move.is_none()`), the existing cutoff behavior is preserved byte-identically. This is the third in the project's growing set of `excluded_move.is_none()` guards, alongside the step-9 NMP store and step-14 main store. Pattern: TT side effects (probe-cutoff and store) are gated; TT reads-for-ordering are not.

**Why this is sound.** The verification call asks "are all moves except the TT move strictly below `singular_beta`?" The cached TT entry says "this position is `>= tt_score`", which includes the TT-move's contribution. Returning that as the verification result is wrong — it doesn't isolate the question from the TT-move's score. Suppressing the cutoff and running the full move loop with `excluded_move = Some(tt_move)` is the correct semantic.

**Caveat (research §5.2 reconciled).** The research note's "no documented engine suppresses TT probes inside the verification subtree" refers to the *subtree* below the verification frame — children, grandchildren, at *different* zobrist keys. There the cached entries describe different positions and their cutoffs are sound. Only the verification frame's *own* step-7 (same zobrist as the parent) needs the suppression. The earlier draft of this plan misread the research as covering the same-zobrist case; this section corrects.

**Flow at step 12.5 (pseudocode).**

```rust
// 12.5  Singular-extension verification (M5.G — ADR-0029).
//
// Fire only when:
//   - step 7 captured a probe snapshot (tt_probe_snapshot.is_some());
//   - moves_vec[0].bits() == snapshot.tt_move (step-12 promoted a non-zero,
//     legal TT move to the front; without this match, snapshot.tt_move is
//     either 0 or a stale-but-illegal value and we don't fire);
//   - singular_extension_eligible passes all 9 clauses (clause 9 is
//     `tt_move != 0` for defense-in-depth against a future order_moves
//     refactor).
//
// On verification fail-low (verif_score < singular_beta), set tt_move_extension = 1.
// On verification fail-high or non-fire, tt_move_extension stays 0.

// `in_check(pos)` is read here independently — lazy-dup per ADR-0024 §6 /
// ADR-0026 §3 (preserves SPRT-signal isolation; SE fires only at depth ≥ 8
// where wallclock impact of an extra in_check is well under 1%).
let in_check_se = in_check(pos);

let mut tt_move_extension: u32 = 0;
if let Some(snapshot) = tt_probe_snapshot
    && moves_vec[0].bits() == snapshot.tt_move
    && singular_extension_eligible(
        excluded_move,
        ply,
        is_pv,
        in_check_se,
        depth,
        snapshot.bound,
        snapshot.depth,
        snapshot.score,
        snapshot.tt_move,
    )
{
    let s_beta = singular_beta(snapshot.score, depth);
    let v_depth = verification_depth(depth);

    let verif_score = self.negamax(
        pos,
        v_depth,
        ply,
        s_beta - 1,
        s_beta,
        false,                          // is_pv
        true,                           // allow_null (research §6.1)
        Some(moves_vec[0]),             // exclude the TT move
        ctx,
        clock,
    );
    if self.aborted {
        return 0;
    }

    if verif_score < s_beta {
        tt_move_extension = 1;
        #[cfg(test)]
        {
            self.se_extensions += 1;
        }
    }
}
```

**TT probe snapshot.** Step 7 currently uses `if let Some(entry) = tt.probe(...) { tt_move = entry.best_move; ... }` and lets `entry` go out of scope. The new code introduces:

```rust
struct TtProbeSnapshot {
    tt_move: u16,
    bound: TtBound,
    depth: u8,
    /// **ply-adjusted to the current frame** via `score_from_tt(entry.score,
    /// ply)`; the TT stores ply-relative mate scores (ADR-0018 §1), and SE
    /// arithmetic operates in current-frame space. The score field here is
    /// already in current-frame space — `singular_beta(snapshot.score, depth)`
    /// is correct without further adjustment.
    score: i32,
}
let mut tt_probe_snapshot: Option<TtProbeSnapshot> = None;
if let Some(tt) = &self.tt
    && let Some(entry) = tt.probe(pos.zobrist())
{
    let tt_score = score_from_tt(entry.score as i32, ply as i32);
    tt_move = entry.best_move;
    tt_probe_snapshot = Some(TtProbeSnapshot {
        tt_move: entry.best_move,
        bound: entry.bound(),
        depth: entry.depth,
        score: tt_score,
    });
    // Cutoff branch gated on `excluded_move.is_none()` (load-bearing — see
    // "Verification-frame TT cutoff is suppressed" paragraph above). The
    // `tt_move` capture above runs unconditionally so step-12 ordering
    // works at the verification frame too (irrelevant in practice — the
    // move-loop excluded-move skip removes it anyway).
    if excluded_move.is_none() && !is_pv && entry.depth as u32 >= depth {
        match entry.bound() {
            TtBound::Exact => return tt_score,
            TtBound::Lower if tt_score >= beta => return tt_score,
            TtBound::Upper if tt_score <= alpha => return tt_score,
            _ => {}
        }
    }
}
```

This is a strict superset of the current step-7 work for normal calls (`excluded_move.is_none()` → cutoff behavior preserved byte-identically) plus the load-bearing v3 verification-frame cutoff suppression for verification calls.

**Move-loop integration: precise patch.** The current `negamax` move loop is in `src/search.rs:1605-1809`. The patch:

1. **First statement of the loop body** (currently `let child_is_pv = is_pv && i == 0;` at line 1606) — *insert before* `child_is_pv`:

   ```rust
   if Some(mv) == excluded_move {
       continue;
   }
   ```

   This skip fires before `quiet_move`, before `quiet_index` increment, before FFP/LMR work, before `child_is_pv` computation. The `continue` preserves the M5.D `quiet_index` semantic exactly: skipped moves are not "considered for reduction." The skip also preserves PV indexing: in the verification frame, `is_pv = false`, so `child_is_pv = false` regardless of `i`, but for forward compatibility with a future PV-SE variant, the skip-first placement is correct.

2. **Per-iteration extension computation** (insert after the excluded-move skip, before `quiet_move`):

   ```rust
   let move_extension: u32 = if i == 0 { tt_move_extension } else { 0 };
   ```

3. **Non-LMR branch** (currently at `src/search.rs:1736-1747`, the `else` block calling `self.search_child(pos, mv, depth - 1, ...)`): replace the `child_depth = depth - 1` argument with `depth - 1 + move_extension`.

4. **LMR branch untouched.** SE-extension fires only on `i == 0` (per step 2's `if i == 0 { tt_move_extension } else { 0 }`). LMR-reduction can fire on `i >= 1` (any move that passes the per-quiet LMR gate). The two cannot co-fire because the `i == 0` and `i >= 1` predicates are disjoint by construction — a stronger structural guarantee than appealing to `quiet_index >= 2` (which only holds when the TT move is quiet; for a TT-move capture the `quiet_index` argument doesn't apply, but the `i == 0` filter still does). The compile-time invariant `FFP_MAX_DEPTH < SE_MIN_DEPTH` (§3) similarly guarantees FFP and SE never co-fire on the same node, so the FFP per-quiet skip path doesn't need to know about `move_extension`.

5. **Post-loop TT-store suppression** (currently `src/search.rs:1816-1842`):

   ```rust
   if let Some(tt) = &self.tt
       && !self.aborted
       && excluded_move.is_none()                            // NEW
       && let Some(bound) = tt_bound_for_completed_node(...) { ... }
   ```

   Rationale (research §5.1): the verification frame ran with a candidate move excluded; the score it computes is for a sub-game that's *not* the position keyed by `pos.zobrist()`. Storing it at that key would pollute future probes that don't exclude anything.

6. **Step-9 NMP TT-store suppression** (currently `src/search.rs:1498-1513`, inside the NMP cutoff block):

   ```rust
   if excluded_move.is_none()
       && let Some(tt) = &self.tt
   {
       tt.store(...);
   }
   ```

   Same rationale as step 5: when an NMP cutoff fires inside the verification frame (which has `excluded_move = Some(...)`), the proved Lower bound is for the verification's modified game, not for `pos.zobrist()`. Suppress the store. (The NMP cutoff's `return cutoff_score` itself is fine — the verification's caller consumes that score; only the TT side effect is wrong.)

7. **Step-9 NMP block CAN STILL FIRE** at the verification frame (and at descendants thereof). The `allow_null` parameter is `true` at the verification call site (research §6.1: "NMP inside verification: allowed"). The only change is the TT-store suppression at step 6.

The patch in concise form: **two new lines at the loop top (excluded-move skip + per-iteration `move_extension`), three `excluded_move.is_none()` guards (step-7 cutoff branch, step-9 NMP store, step-14 main store), one one-line argument change at the non-LMR `search_child` call.**

---

**Why clause 1 (the immediate-frame re-entrancy guard) is cheap defense-in-depth.** Restating clause 1 of `singular_extension_eligible` plainly:

- The verification frame has `excluded_move = Some(M)` set by the SE block's verification call.
- At that frame, clause 1 fails → SE block doesn't fire → no nested verification.
- **Without clause 1**, the verification frame's own step 12.5 would re-attempt SE. The TT snapshot is the same Lower-bound entry the parent saw (clause 6 passes); other clauses are also satisfied at the verification frame except clause 5 at low parent depths (verification_depth(8) = 3 < SE_MIN_DEPTH). At parent_depth ≥ 17 the verification frame is at depth ≥ 8, clause 5 passes, and the verification frame would call **one** nested verification of its own — which itself has `excluded_move = Some(...)` set, so its nested step-12.5 re-attempts again face clause-1-equivalent (now `Some` → no fire). So **clause 1 saves exactly one wasted verification call per SE-firing parent at parent_depth ≥ 17**, not a chain. Cost: one geometric-sum `O(b^{verif_depth})` ≈ `O(b^{d/2})` extra subtree per SE firing. Cheap defense-in-depth, not load-bearing for NPS.
- **Note on terminology**: descendant recursion via `search_child` (where `excluded_move = None` is restored) is a *separate* mechanism — bounded by clause 5 + depth halving, not by clause 1. The two guards have disjoint scope: clause 1 catches the immediate-frame re-entry; clause 5 + depth halving catches descendant chains.

- **At descendants of the verification frame** (children at `verification_depth(d) - 1`, grandchildren at `verification_depth(d) - 2`, ...): `excluded_move = None` (search_child passes None — see §5). At parent_depth = SE_MIN_DEPTH = 8, the verification subtree's max depth is 2, well below SE_MIN_DEPTH = 8 → clause 5 blocks SE re-firing. **At parent_depth ≥ 19**, the verification subtree's children can reach depth 8 and re-fire SE. Walking the recurrence `f(d) = 1 + f((d−1)/2)` truncated at `d < SE_MIN_DEPTH = 8`: chain depth is `f(17) = 2`, `f(35) = 3`, `f(71) = 4`. At realistic engine depths (`d ≤ MAX_PLY = 64`), the chain is at most 3 deep. Per-layer cost is `O(b^{verif_depth_at_layer})`; geometric sum is dominated by the first term, total `O(b^{d/2})`. Per research §3.3, the literature consensus is that this cost is acceptable, and engines that rely on the immediate-frame guard alone (the `excluded_move.is_some()` check) report acceptable NPS. We follow the consensus. SPRT will quantify.

**Depth-budget invariant** (load-bearing for descendant-recursion bounds): clause 5 (`depth >= SE_MIN_DEPTH = 8`) + the depth halving in `verification_depth` together bound descendant recursion to a chain of depth at most 3 at realistic engine depths. Clause 1 cuts the immediate-frame nested-verification (saves exactly one wasted verification call at parent_depth ≥ 17); the depth budget bounds the descendant chain. Tests pin both layers (§8: `negamax_skips_se_when_excluded_move_some`, `negamax_se_block_does_not_fire_below_min_depth`).

## §11. SPRT decision criteria

Mirrors M5.F's criteria block (plan §11 in `docs/plans/m5.f.md`). Four landing outcomes:

1. **H1 accept (decisive positive).** Pentanomial GSPRT crosses elo1 = 10. Δ Elo CI lower bound > 0. Land normally, full retrospective tone.
2. **Small-but-not-regression (continue verdict, mean clearly ≥ 0).** Pentanomial verdict = continue at 400 games. **BOTH** mean Δ Elo ≥ 5 **AND** CI lower bound > −10 must hold (conjunction, not disjunction). The conjunction excludes M5.F-style `+13 [−11, +37]` patterns from this bucket — those land as outcome 3 (flat). The plan's intent: M5.F's "small-but-not-regression per plan §11 spirit" framing was anomalous and should not be reused; this plan's outcomes are tightened to prevent a second consecutive marginal landing. Land with retrospective noting the marginal-but-clean signal and tuning-backlog candidates.
3. **Flat (continue verdict, NOT (mean ≥ 5 AND CI lower > −10)).** Pentanomial verdict = continue at 400 games AND the negation of outcome 2's conjunction holds. This covers: |mean Δ Elo| < 5; mean ≥ 5 but CI lower < −10; mean < −5 with CI upper > 0 (the symmetric flat band on the negative side, where verdict hasn't crossed elo0 = 0 yet). **Do NOT land as "small-but-not-regression"** — M5.F's precedent already used that bucket once, and a second consecutive flat-but-positive landing would set a worrying pattern (the engine accumulates "small Elo fictions"). Instead: return to research, try the retunes from outcome 4. One retune attempt; if it also lands flat, abandon SE per outcome 4.
4. **H0 accept or hard regression.** Pentanomial GSPRT crosses elo0 = 0 (H0 accept) OR Δ Elo CI upper bound < 0. Do not land; return to research with a counter-example campaign (try `SE_MIN_DEPTH = 6`, try `SE_MARGIN_PER_DEPTH = 2`, try Lower+Exact gate). Each retune is a separate SPRT attempt; if three retunes fail, abandon SE and document the negative result in `docs/research/m5-singular-extensions.md`.

**Precedence.** GSPRT verdict precedence is: H0-accept (outcome 4) > H1-accept (outcome 1) > continue with mean/CI classification (outcomes 2 vs 3). If the verdict crosses elo0 = 0, that is outcome 4 *regardless* of the observed mean Δ Elo (a flat-band mean during an H0 acceptance still classifies as outcome 4, not outcome 3).

**SPRT-power tradeoff acknowledgment.** The conjunction outcome-2 criterion (`mean ≥ 5 AND CI lower > −10`) is power-conservative at the +15 Elo "should land" boundary — at 400 games / 4-bucket mixed-TC sampling the CI half-width is ~25, and the probability of a true +15 signal producing both `mean ≥ 5` and `CI lower > −10` is roughly 60%. So a real +15 Elo M5.G has ~40% chance of landing as outcome 3 ("flat → retune") on the first SPRT attempt. This is deliberate: the cost of a wrongly-rejected real signal is one retune campaign (~hours wallclock); the cost of a wrongly-accepted false signal is a "small Elo fiction" landing that erodes downstream SPRT signal-to-noise. The asymmetry favors the conservative criterion.

**WAC/STS gate.** Diagnostic-only, not landing-blocking. Expected: WAC ~268–272/300 (small positive), STS ~8830–8870/15000 (small positive or flat). Hard regression on either (e.g., WAC drops below 260 OR STS drops below 8780) is a flag to pause and investigate before landing — even if SPRT is positive, a tactical-suite regression suggests SE is missing tactical motifs that the SPRT corpus doesn't surface.

**Predicted survivors (acceptable equivalents).**
- `tt_move_extension = 1` → `2` mutant: the project's M5.G v1 doesn't enable double extension, but a `= 2` mutant produces a search with 2-ply extension. Tests assert the child is searched at `depth` (i.e., `depth - 1 + 1`); a `= 2` mutant would search at `depth + 1`. The `..._extension_increments_child_depth_by_one` test pins this iff its assertion is `child_searched_at_depth` (not `>= depth`). Write the assertion as exact equality to kill the mutant.
- Boundary inversion mutants on the eligibility predicate (`>=` ↔ `>`): tests at the boundary depth (`depth == SE_MIN_DEPTH` and `depth == SE_MIN_DEPTH - 1`) and at the TT-depth-delta boundary (`tt_depth == depth - SE_TT_DEPTH_DELTA` and `tt_depth == depth - SE_TT_DEPTH_DELTA - 1`) pin these. The two pairs of boundary tests in §8 (`..._passes_at_exact_threshold_depth` / `..._rejects_one_below_threshold_depth` and `..._passes_at_tt_depth_delta_boundary` / `..._rejects_at_tt_depth_one_below_boundary`) are the catch paths.
- `verification_depth` underflow at `depth == 0`: the `>= SE_MIN_DEPTH` gate's mutation `>=` → `>` lets `depth == SE_MIN_DEPTH - 1 == 7` pass through; `verification_depth(7) = 3` is well-defined, so the helper alone doesn't catch this mutant. The boundary test `..._rejects_one_below_threshold_depth` is the catch path.

Aim for **>95% mutation catch** on the SE surface. M5.F's 100%-on-viable is the recent precedent.

## §15. Dependencies

- M5.F TT semantics — qsearch entries are depth-0 and excluded by step-7 probe's `entry.depth >= depth` rule, so the SE gate's `tt_depth as u32 >= depth - 3` (with depth ≥ SE_MIN_DEPTH = 8 ⇒ minimum tt_depth = 5) trivially excludes them. No special handling needed at the SE site.
- M5.A NMP — the verification frame allows NMP at child positions; the verification frame's *own* NMP block can fire too, and its TT store is gated by the same `excluded_move.is_none()` guard as step 14.
- M5.C LMR — LMR fires on quiets at `quiet_index >= 2`, never on the TT move (i=0, quiet_index=1). No interaction; SE-extension and LMR-reduction never compose on the same move.
- ADR-0018 §7 (TT best-move preservation across overwrites) — load-bearing for the SE eligibility check (the TT move bits we read at step 7 must still match `moves_vec[0]` after step-12 reorder; the legality scan at step 12 enforces this).
