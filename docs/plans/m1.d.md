# M1.D — Polyglot Zobrist hashing

## Context

M1.A–C delivered `Bitboard`, `Square`, `Color`/`PieceKind`/`Piece`, `Position`, FEN parser, sliding-piece attacks, and the `magicgen` codegen binary. M1.D adds the **Polyglot Zobrist hash** that M1.E (make/unmake) needs for its debug round-trip assert and that M3+ (transposition table) and the future Polyglot opening-book reader will rely on.

> **A note on terminology.** "Polyglot" here refers to the *binary opening-book format and its 781-key Zobrist hash table* — a frozen, public spec implemented by every modern chess tool. The separate **PolyGlot adapter tool** (the C utility from Hartmut Kapsch / HGM that translated XBoard ↔ UCI for legacy engines) is essentially abandoned upstream and Homebrew is deprecating its formula. ADR-0009 §"A note on 'PolyGlot is being retired'" expands; the plan's commitment is to the format, not the tool.

This phase **binds ADR-0009** (`docs/decisions/0009-polyglot-zobrist.md`), pre-decided in the roadmap and grounded in `docs/research/m1-engine-architecture.md` §5. Headline calls (from the ADR): vendor the published Polyglot 781-key table verbatim; piece offset `64*kind_color + 8*row + file` with Polyglot's `BP=0,WP=1,BN=2,WN=3,BB=4,WB=5,BR=6,WR=7,BQ=8,WQ=9,BK=10,WK=11`; 4 castling keys (WK,WQ,BK,BQ); 8 EP-file keys; 1 turn key XORed iff White-to-move; **EP file hashed iff capture is pseudo-legally possible** (side-to-move pawn adjacent to opponent's just-pushed pawn — adjacency only, no pin/check tests).

### Research skip — justified

Workflow step 1 ("deep prior-art research") is a clean skip for this phase. `docs/research/m1-engine-architecture.md` §5 covers Zobrist exhaustively (key composition, why XOR works, the EP-spurious-cache-miss problem, the Polyglot-vs-legal-only EP refinement, random-source choice). The supplemental research pass on the Polyglot spec specifics (piece enumeration order verbatim, the "irrelevant if legal" EP wording, castle key order, side-to-move asymmetry) confirmed the engine-architecture doc's headlines and produced the 9 spec-published `(FEN, key)` test vectors used as gold-standard tests below.

The keys themselves are vendored *data*, not engine code — analogous to the perft fixtures in `docs/decisions/0006`. Source: the `book_format.html` document shipped with the Homebrew `polyglot` package (version 2.0.4, extracted 2026-04-27), which is byte-identical to the canonical `http://hgm.nubati.net/book_format.html`.

### What this phase delivers

1. **`src/zobrist.rs`** — public Zobrist API: per-piece, per-castling-right, per-EP-file, and per-turn key accessors; the `from_scratch` function that hashes a `Position`; the `ep_file_to_hash` helper that implements the Polyglot pseudo-legal EP rule.
2. **`src/zobrist/keys.rs`** — vendored `[u64; 781]` constant array, with header comment naming source/date/extraction recipe.
3. **`Position` integration** — adds `zobrist: u64` field; `starting_position()` and `from_fen()` populate it via `from_scratch`; public getter `Position::zobrist()`.
4. **ADR-0009** — already written; landed in the same commit.

**Not** in M1.D: `make_move`/`unmake_move` (M1.E's job — they will incrementally XOR using the helpers M1.D provides); transposition-table layer (M4); opening-book reader (post-roadmap).

## Decisions baked into this plan

1. **Module layout: `src/zobrist.rs` declaring `mod keys;` plus `src/zobrist/keys.rs`.** Mirrors `src/magic.rs` + `src/magic/constants.rs` from M1.C. The `keys.rs` file is vendored data, not generated by a tool we ship — see Decision §10.

2. **Public API surface (the lot, exported as `clawfish::zobrist::*`):**

   ```rust
   /// Polyglot piece-square key for `(piece, sq)`.
   /// Uses the Polyglot piece-color enumeration internally.
   pub fn piece_key(piece: Piece, sq: Square) -> u64;

   /// Polyglot castling-right key. `right` must have exactly one of the four
   /// named flags set; debug-asserts on `NONE` or multi-flag input.
   pub fn castling_key(right: CastlingRights) -> u64;

   /// Polyglot EP-file key for the given file index (0..8).
   /// Debug-asserts if `file >= 8`.
   pub fn ep_file_key(file: u8) -> u64;

   /// The single Polyglot turn key. XOR it in iff WHITE is to move
   /// (asymmetric — Black-to-move does NOT toggle this).
   pub const fn turn_key() -> u64;

   /// Returns `Some(file)` if `pos.ep_target()` is set AND a pawn of
   /// `pos.side_to_move()` sits adjacent (same rank as the just-pushed
   /// opponent pawn, file ±1) — i.e. EP capture is pseudo-legally
   /// possible per the Polyglot spec. Returns `None` otherwise.
   ///
   /// "Pseudo-legal" here is adjacency only — no pin or own-king-check
   /// test, per the spec ("irrelevant if the potential en passant
   /// capturing move is legal or not").
   pub fn ep_file_to_hash(pos: &Position) -> Option<u8>;

   /// From-scratch Polyglot Zobrist hash of `pos`. Used by FEN parsing,
   /// `Position::starting_position`, and (M1.E onward) the debug-build
   /// round-trip assert after every make/unmake.
   pub fn from_scratch(pos: &Position) -> u64;
   ```

   No `pub` on the `keys` submodule (it's `mod keys;`, not `pub mod keys;`); the constants reach the public surface only via the accessor functions. The accessors are individually `#[inline]` so the optimizer can fold a constant-piece/constant-square call into a single load.

3. **Polyglot piece-color encoding.** Internal helper:
   ```rust
   #[inline]
   const fn polyglot_piece_index(piece: Piece) -> usize {
       // Polyglot order: BP=0, WP=1, BN=2, WN=3, BB=4, WB=5, BR=6, WR=7, BQ=8, WQ=9, BK=10, WK=11.
       // Our PieceKind is Pawn=0..King=5 (matches Polyglot's kind sub-axis).
       // Our Color::White=0, Color::Black=1; Polyglot wants White=odd-position-in-pair (i.e. +1 over Black).
       // Therefore: `2 * kind + (1 - color)` maps White→1 component, Black→0 component within each kind pair.
       2 * piece.kind.index() + (1 - piece.color.index())
   }
   ```
   `piece_key` then returns `keys::POLYGLOT_KEYS[64 * polyglot_piece_index(piece) + sq.index() as usize]`. The mapping is unit-tested with explicit literal expectations (e.g. `polyglot_piece_index(BP) == 0`, `polyglot_piece_index(WP) == 1`, `polyglot_piece_index(WK) == 11`) — so a `1 - color` ↔ `color` flip is caught immediately instead of round-tripping silently through the spec test vectors.

4. **CastlingRights bit layout already matches Polyglot.** Per `src/position.rs` doc comment on `CastlingRights`: bit 0 = WK, 1 = WQ, 2 = BK, 3 = BQ. Polyglot order at offsets 768..772 is the same. So:
   ```rust
   pub fn castling_key(right: CastlingRights) -> u64 {
       debug_assert_eq!(right.bits().count_ones(), 1, "castling_key requires a single-flag right");
       keys::POLYGLOT_KEYS[768 + right.bits().trailing_zeros() as usize]
   }
   ```
   A const-time check pins the bit-layout assumption:
   ```rust
   const _: () = {
       assert!(CastlingRights::WHITE_KING.bits()  == 1 << 0);
       assert!(CastlingRights::WHITE_QUEEN.bits() == 1 << 1);
       assert!(CastlingRights::BLACK_KING.bits()  == 1 << 2);
       assert!(CastlingRights::BLACK_QUEEN.bits() == 1 << 3);
   };
   ```
   If `CastlingRights` is ever refactored to use a different bit order, this `const _: ()` fails to compile — caught at build time.

5. **`ep_file_to_hash` derivation.** The spec rule: hash iff a side-to-move pawn is adjacent to the opponent's just-pushed pawn. The opponent's just-pushed pawn is on the same file as `ep_target` and one rank toward the side-to-move:

   - White-to-move (so Black just double-pushed): `ep_target` is on rank index 5 (rank 6); just-pushed black pawn on rank index 4 (rank 5); a white pawn on rank index 4, file ±1 of `ep_target.file()` would capture.
   - Black-to-move (so White just double-pushed): `ep_target` on rank index 2 (rank 3); just-pushed white pawn on rank index 3 (rank 4); a black pawn on rank index 3, file ±1 captures.

   So the capturing-pawn rank is the *same* rank as the just-pushed pawn; in both cases that's `4` for White-to-move and `3` for Black-to-move.

   ```rust
   pub fn ep_file_to_hash(pos: &Position) -> Option<u8> {
       let ep = pos.ep_target()?;
       // The relevant pawn is the side-to-move's would-be CAPTURER, not the
       // opponent's just-pushed pawn (which sits on the same file as `ep`,
       // one rank toward us, and is irrelevant to this check beyond setting
       // the rank of where our capturer must be).
       let stm = pos.side_to_move();
       let capturer_rank: u8 = match stm {
           Color::White => 4,  // ep on rank index 5 → capturer on rank 5 (index 4)
           Color::Black => 3,  // ep on rank index 2 → capturer on rank 4 (index 3)
       };
       let our_pawns = pos.pieces_colored(stm, PieceKind::Pawn);
       let file = ep.file();
       let mut adjacent = Bitboard::EMPTY;
       if file > 0 {
           adjacent |= Bitboard::from_square(
               Square::from_file_rank(file - 1, capturer_rank).expect("file-1, rank in 0..8"),
           );
       }
       if file < 7 {
           adjacent |= Bitboard::from_square(
               Square::from_file_rank(file + 1, capturer_rank).expect("file+1, rank in 0..8"),
           );
       }
       if (our_pawns & adjacent) != Bitboard::EMPTY {
           Some(file)
       } else {
           None
       }
   }
   ```

   Note we do **not** revalidate the EP-target's own rank — the FEN parser already enforces it's on rank 3 or 6 (per `architecture.md` "FEN parsing" row), and `Position` only ever sets `ep_target` post-parse from a successful FEN parse.

6. **`from_scratch` composition:**
   ```rust
   pub fn from_scratch(pos: &Position) -> u64 {
       let mut h: u64 = 0;
       for sq in Square::all() {
           if let Some(piece) = pos.piece_at(sq) {
               h ^= piece_key(piece, sq);
           }
       }
       let cr = pos.castling_rights();
       if cr.has(CastlingRights::WHITE_KING)  { h ^= castling_key(CastlingRights::WHITE_KING); }
       if cr.has(CastlingRights::WHITE_QUEEN) { h ^= castling_key(CastlingRights::WHITE_QUEEN); }
       if cr.has(CastlingRights::BLACK_KING)  { h ^= castling_key(CastlingRights::BLACK_KING); }
       if cr.has(CastlingRights::BLACK_QUEEN) { h ^= castling_key(CastlingRights::BLACK_QUEEN); }
       if let Some(file) = ep_file_to_hash(pos) { h ^= ep_file_key(file); }
       if pos.side_to_move() == Color::White   { h ^= turn_key(); }
       h
   }
   ```

   Order of XORs is irrelevant (XOR is associative+commutative), but we list piece keys, castling keys, EP, then turn — same order as the Polyglot spec section ordering — so a future reader can audit one section at a time.

7. **`Position` integration.**
   - Add `zobrist: u64` field to the `Position` struct. **Visibility: private** (no modifier). Cross-module writes go through a `pub(crate)` setter (next bullet) — same pattern as `set_piece`/`set_aux_state`.
   - Add `pub(crate) fn refresh_zobrist(&mut self)` that internally sets `self.zobrist = crate::zobrist::from_scratch(self)`. Single-purpose mutator: callable from `fen.rs` after parse and from `starting_position()` after the literal-data initialization. Tests that mutate via `set_piece`/`set_aux_state` and want a fresh hash call this too. Living in `position.rs` keeps the field private.
   - `Position::empty()` — **stays `const fn`**. Initializes `zobrist: 0`; the parser calls `refresh_zobrist()` after filling the position. (Only `starting_position` needs to lose `const`-ness because it must invoke the non-const `from_scratch`.)
   - `Position::starting_position()` — drop `const fn` (since `from_scratch` is not const). After the literal-data constructor runs, call `self.refresh_zobrist()`. The starting-position hash equals Polyglot test vector #1: `0x463b96181691fc9c`.
   - Add `pub const fn zobrist(&self) -> u64` getter.
   - `crate::fen::parse()` — after `validate_post_parse(&pos)?`, call `pos.refresh_zobrist()`.
   - `Position::PartialEq` semantics: `zobrist` is derived from the other fields, so it doesn't influence equality (but it's compared as part of the auto-derived `PartialEq` trivially since two equal positions have equal hashes). This is fine — it's a convenience.

   **Note on `set_aux_state` and `set_piece`:** these mutators do *not* update zobrist incrementally. They are used only by tests and the FEN parser, and the FEN parser calls `refresh_zobrist()` after all set_* calls complete. M1.B's `equality_is_structural` test that calls `set_aux_state` post-`starting_position` will leave the zobrist field stale relative to the new aux state — but the test only checks `assert_ne!(p1, p_flipped)`, where the bitboards/aux differ, so the zobrist field's staleness doesn't affect the assertion outcome (and a stale-zobrist position deliberately stays unequal to its consistent counterpart, which is the correct behavior for "structural equality" anyway). Document this in the `set_piece`/`set_aux_state` doc comments: "These mutators do not refresh `zobrist`; callers that need a consistent hash must call `refresh_zobrist()` afterward." M1.E's make/unmake will be the only path that updates zobrist incrementally.

8. **Vendoring methodology.** The `src/zobrist/keys.rs` file is hand-vendored from `book_format.html`. The leading comment names the source, extraction date, and the awk-style one-liner used:

   ```
   // POLYGLOT_KEYS — 781-entry constant array vendored from
   //   /opt/homebrew/Cellar/polyglot/2.0.4/share/doc/polyglot/book_format.html
   //   (functionally identical to http://hgm.nubati.net/book_format.html)
   //   extracted 2026-04-27 with:
   //     grep -oE 'U64\(0x[0-9A-Fa-f]+\)' book_format.html \
   //       | sed -E 's/U64\((0x[0-9A-Fa-f]+)\)/\1/'
   //
   // Layout (per ADR-0009, matching the Polyglot spec):
   //   indices 000..767 — RandomPiece    (12 piece-colors × 64 squares,
   //                                       ordered: BP=0, WP=1, BN=2, ..., WK=11)
   //   indices 768..771 — RandomCastle   (WK, WQ, BK, BQ)
   //   indices 772..779 — RandomEnPassant (file a..h)
   //   index   780      — RandomTurn     (XORed iff WHITE to move)
   //
   // First key (sanity): 0x9D39247E33776D41
   // Last  key (sanity): 0xF8D626AAAF278509
   //
   // DO NOT edit by hand. To re-vendor, install Homebrew `polyglot` and run the
   // grep|sed pipeline above against book_format.html.
   ```

   The vendor file is a single `pub(super) const POLYGLOT_KEYS: [u64; 781] = [...]` array. Format: 8 keys per line for compactness (~98 lines + header). Trailing newline at EOF. The first/last entries are pinned by unit test as sentinel against accidental row-shift.

9. **Castling-rights bit layout pinning.** A const-time `assert!` block (Decision §4) pins the bit positions of WK/WQ/BK/BQ. A runtime test in `zobrist.rs::tests` also asserts `castling_key(WHITE_KING) == POLYGLOT_KEYS[768]` etc. — so a vendoring shift of the four castling slots is caught.

10. **No `unsafe`.** Same line as M1.A/B/C. Bounds-checked indexing into `POLYGLOT_KEYS` is fine; the table is a fixed `[u64; 781]` and indices are always known-in-bounds at call sites (the `debug_assert!`s on file, castling-flag, etc., catch the few places where caller-provided indices could be wrong).

11. **`#[inline]` on the accessors.** Each of `piece_key`, `castling_key`, `ep_file_key`, `turn_key`, `polyglot_piece_index`. Most call sites are inside `from_scratch` (already a non-hot path) but M1.E's incremental update path will hammer these.

12. **No `Cargo.toml` changes.** No new dependencies. The vendored constants are plain Rust source; the runtime is `std` only.

| `polyglot_keys_first_and_last_pinned` | `keys::POLYGLOT_KEYS[0] == 0x9D39247E33776D41` and `keys::POLYGLOT_KEYS[780] == 0xF8D626AAAF278509`. Sentinel against row-shift / typo in the vendored file. |

| `from_scratch_xor_decomposes` | A position with two known pieces placed: `from_scratch(p) == piece_key(p1, sq1) ^ piece_key(p2, sq2) ^ castling_xors ^ turn_xor`. Decomposable XOR. |
| `from_scratch_side_to_move_asymmetry` | **Constructed with NO EP target** (so flipping side-to-move doesn't also retoggle `ep_file_to_hash`): two positions otherwise identical, one with `side_to_move = White`, the other Black. Assert `from_scratch(white) ^ from_scratch(black) == turn_key()`. **Pins the asymmetric XOR.** A second pair of assertions on the same construction pins the direction: `from_scratch(white) ^ turn_key() == from_scratch(black)` (i.e., the white version IS the one that includes turn_key). The "no EP target" precondition must be explicit in the test body so a future reader doesn't add EP and silently reintroduce the EP-key delta. |
| `from_scratch_starting_position_pinned` | `from_scratch(Position::starting_position()) == 0x463b96181691fc9c` (Polyglot test vector #1). **The single most important sanity test** — if this fails, the vendoring is wrong. |

## Construction protocol — pinned for parallel implementation

Because step 7.C and 7.D run in parallel, their interfaces are pinned:

1. **`crate::zobrist::from_scratch(&Position) -> u64`** is the sole entry point both call sites use (transitively, via `refresh_zobrist`).
2. **`from_scratch` ignores `pos.zobrist`** — the hash is computed from the bitboards, mailbox, castling rights, side-to-move, and EP target only. So calling `refresh_zobrist()` before *or* after the literal-data initialization in `starting_position` is safe regardless of the field's current value; there's no read-before-write hazard on the field itself.
3. **The `Position` field name, type, visibility, and mutator** are fixed in pass 5.0: `zobrist: u64` is private; mutation goes through `pub(crate) fn refresh_zobrist(&mut self)`. Both 7.C and 7.D call `pos.refresh_zobrist();` (or `self.refresh_zobrist();` from inside `position.rs`).

## Risks and mitigations

- **Vendoring error in `keys.rs`** (silent typo; row-shift; missed entry). The 781 keys are pasted by hand from a `grep | sed` extraction — one stray digit silently breaks the hash. **Mitigation:** the four sentinel unit tests (`polyglot_keys_first_and_last_pinned`, `polyglot_keys_length_781`, `polyglot_keys_no_duplicates`, `polyglot_keys_no_zero`) catch the most likely categories. The 9 spec test vectors catch any subtler shift — every sub-axis (piece order, castle order, EP file mapping, turn key) is exercised by at least one vector. **In addition,** the `castling_key_table_offsets` and `ep_file_key_table_offsets` and `turn_key_matches_table` unit tests act as direct probes — if a vector fails, these immediately localize the section that was mis-shifted.

- **Piece-color encoding flip** (`2*kind + color` vs. `2*kind + (1-color)`). The 9 vectors catch it (any vector with both colors will diverge), but the unit test `polyglot_piece_index_pinned` localizes it instantly.

- **Side-to-move asymmetry mistake** (XOR turn key on every flip instead of iff white). The two-position assertion `from_scratch_side_to_move_asymmetry` catches this directly. The 9 vectors also catch it — vectors 1, 3, 5, 7 are white-to-move; vectors 2, 4, 6, 8, 9 are black-to-move.

- **EP rule drift** (legal-only refinement instead of pseudo-legal-only). Caught by `ep_file_to_hash_pinned_capturer_still_hashes`. Without a deliberate test for the pinned case, a "well, surely we should also check pin status" reasonable-sounding refinement could slip in and break Polyglot interop. The test name + comment make the spec stance explicit.

- **`Position::starting_position` no longer `const fn`** — a downstream caller using it in a const context would break. **Mitigation:** check (via `grep`) that nothing currently uses `starting_position()` in a `const` context. (Pre-M1.D: not used in any const context.)

- **Vendoring re-extractibility.** Constants are frozen; we don't re-vendor unless deliberately re-verifying against the spec. Fallback if brew is gone post-2027 deprecation: fetch `http://hgm.nubati.net/book_format.html` directly (user-pre-approved) or pull from the in-tree `docs/reference/polyglot-book-format.md` snapshot.

- **Stale zobrist field via `set_piece` / `set_aux_state`.** These mutators are pub(crate) and used only by tests + the FEN parser. Tests that mutate post-construction will see a stale `zobrist` field. **Mitigation:** documented in those mutators' doc comments (per Decision §7) — and M1.E's make/unmake will be the only "supported" mutation path. M1.E's debug round-trip assert will catch any drift in that path.
