# M3.A — Material + PST eval + GreedyMover (depth-1 production search)

## Context

M2.E closed M2 with `RandomMover` as production `Search`. M3.A is the first `Search` impl that *evaluates*. Two new pieces ship together because the smaller of them (`GreedyMover`) is meaningless without the larger (`evaluate`):

- **`eval` module** — pure-function `evaluate(&Position) -> i32` returning a side-to-move-relative score in centipawns. Material + PeSTO middlegame PST, single-phase.
- **Incremental eval in `Position` + `Undo`** — same NNUE-hook pattern as the M1.E Zobrist field. `static_eval_white: i32` maintained by `make_move`/`unmake_move` deltas; debug-build round-trip assert vs. from-scratch; release perf sentinel.
- **`GreedyMover` Search impl** — depth-1 best-eval with reservoir-sampled tie-break PRNG (one SplitMix64 step per tied move). Replaces `RandomMover` as the production `Search` in `run_stdio`.

### Bound ADRs

- **ADR-0014 — eval composition.** Drafted as part of this unit. Codifies: PeSTO MG values vendored; single-phase MG-only; combined material+PST in `Position::static_eval_white`; incremental delta in `Undo`; insufficient-material in eval; deferred (bishop pair, mobility, king safety, tapered eval) → M6.
- **ADR-0004 — NNUE hooks.** Consumed: incremental eval slots into `make_move` / `unmake_move` exactly where the future NNUE accumulator update will live.
- **ADR-0011 — UCI threading.** Unchanged. `Search::go` body is what changes; orchestrator-side wiring is the one-line `run_stdio` swap.
- **No new ADR for tie-break PRNG semantics** — the M2.D semantics carry over verbatim (state lives in `GreedyMover`; `setoption Random_Seed` resets state immediately; `ucinewgame` resets state to current seed; D1 SplitMix64 reference test stays).

### Not in M3.A

- Negamax / alpha-beta — M3.C.
- Quiescence — M3.D.
- Iterative deepening, time management — M3.E.
- Repetition / 50-move detection — M3.B (game-history plumbing) + consumption in M3.C.
- Tapered eval, bishop pair, mobility, king safety, pawn structure — M6.
- Underpromotions in greedy: not special-cased (movegen emits all four; eval scores each and the highest wins, which will always be queen for a winning capture but not always for blocking — accepted side effect).
- SPRT vs. RandomMover — M3.F (the bench command + first SPRT both ship together).

### Research skip — justified

`docs/research/m3-eval-material-pst.md` is the load-bearing source; `docs/research/m3-search-basics.md` is informational at this depth-1 stage. No new research pass needed.

## Decisions baked into this plan

### 1. PSQT layout — compile-time `[color][kind][square]` table

```rust
// src/eval.rs
pub(crate) const PSQT: [[[i32; 64]; 6]; 2] = build_psqt();
```

`PSQT[color][kind][sq]` is the signed contribution to `static_eval_white` of a piece of (color, kind) on `sq`. White pieces add; black pieces subtract.

- White lookup: `PSQT[White][kind][sq]      = +(MATERIAL[kind] + MG_PST[kind][sq ^ 56])`
- Black lookup: `PSQT[Black][kind][sq]      = -(MATERIAL[kind] + MG_PST[kind][sq])`

Square convention: our LERF (`a1 = 0`, `h8 = 63`); PeSTO array convention is `a8 = 0`, `h1 = 63`. The XOR-56 flip converts our index → PeSTO array index. This was the open-question §1 from `m3-eval-material-pst.md` — resolved by inspection of `src/square.rs::A1 = Square(0)`.

Rationale: pre-flattened lookup eliminates per-eval branches on color and on rank-flip. ~3 KB read-only data; trivial cache footprint.

### 2. Material constants (PeSTO MG)

```rust
const MATERIAL: [i32; 6] = [
    82,    // Pawn
    337,   // Knight
    365,   // Bishop
    477,   // Rook
    1025,  // Queen
    0,     // King — terminal detection in movegen owns checkmate; king is never captured
];
```

Indexed by `PieceKind::index()` (P=0, N=1, B=2, R=3, Q=4, K=5).

### 3. PST tables (PeSTO MG, vendored verbatim)

Six `[i32; 64]` arrays — `MG_PAWN`, `MG_KNIGHT`, `MG_BISHOP`, `MG_ROOK`, `MG_QUEEN`, `MG_KING`. Values copied verbatim from `docs/research/m3-eval-material-pst.md` "Recommended PST data" section.

The pawn table includes non-zero rank 1 / rank 8 entries that are unreachable (pawns never sit there). We vendor verbatim regardless; the values are dead weight, not dead bugs.

**King PST is included in the static eval despite king material being 0.** The PeSTO MG king PST is *positional*: it expresses the middlegame preference for a tucked-away king (corner) over a centralized king (open). Excluding it would silently drop a tuned middlegame term. King material = 0 is independent: kings cannot be captured, so material counting them would inflate evaluations symmetrically — a no-op that's clearer to omit.

### 4. `evaluate(&Position) -> i32`

Side-to-move-relative score. Two responsibilities:

1. **Insufficient-material override** — KvK, KvN, KvB (either color holding the lone minor) → return 0. Detected via popcount on each piece bitboard:
   - `total_count = occupied_all().count()`
   - if `total_count == 2`: KvK draw → 0
   - if `total_count == 3` AND (knight bitboard == 1 OR bishop bitboard == 1): KvN/KvB draw → 0
   - same-color bishops (KBvKB) deferred per research §6.
2. **Else** — return `static_eval_white` flipped by side-to-move: `if side == White { e } else { -e }`.

Pure function over `&Position`. ~5–10 ns including the popcount path.

### 5. `Position::static_eval_white: i32` field

- New `i32` field on `Position`. From-scratch computation in `eval::eval_white_from_scratch(&Position)`; setter `Position::refresh_static_eval()` (mirroring `refresh_zobrist`).
- Populated by `Position::starting_position()` + `fen::parse` (after `validate_post_parse`, before returning).
- Maintained incrementally by `make_move` / `unmake_move`.

#### 5.1 Why combined (material + PST), not separate

Single field = single delta-update site = one source of truth for `evaluate` to consult. Adding material on the fly via popcount would work too but doubles the field-update plumbing. The plan-reviewer/final-reviewer is invited to push back if the combined form costs clarity; the M1.E Zobrist field is precedent.

#### 5.2 Privacy

`pub(crate) fn static_eval_white(&self) -> i32` accessor for the eval module + tests; the field itself is private. Cross-module mutation goes through `refresh_static_eval` / `refresh_static_eval_from` (the latter is the M1.E `refresh_zobrist_from` pattern).

#### 5.3 `Position`'s `Copy + PartialEq + Eq` derives stay valid

`i32: Copy + PartialEq + Eq + 'static`, so the existing `#[derive(Copy, Clone, PartialEq, Eq)]` (line 96 of `src/position.rs`) carries over with no change. `static_eval_white` is invariant-derived from the rest of the position state; two `Position`s that compare equal on bitboards/mailbox/aux-state will also have equal eval — a stale field would itself be the bug we want to surface in `eq`.

### 6. `Undo::prior_static_eval: i32` field

One new `i32` field on `Undo`. Current layout is 16 B (4 small fields packed into 8 B + a u64 zobrist); adding `i32` brings the layout to 24 B after alignment. `Undo` is `Copy` and never on a hot allocation path; 24 vs. 16 B is meaningless.

### 7. Incremental delta in `make_move`

Same shape as the existing zobrist update. Six flag categories, one delta expression each:

| Flag | Δ on `static_eval_white` |
|---|---|
| Quiet / DoublePush | `PSQT[us][kind(mover)][to] - PSQT[us][kind(mover)][from]` |
| Capture | `PSQT[us][kind(mover)][to] - PSQT[us][kind(mover)][from] - PSQT[them][kind(captured)][to]` |
| EnPassant | `PSQT[us][Pawn][to] - PSQT[us][Pawn][from] - PSQT[them][Pawn][capture_sq]` (note: capture_sq ≠ to) |
| KingCastle / QueenCastle | `PSQT[us][King][k_to] - PSQT[us][King][k_from] + PSQT[us][Rook][r_to] - PSQT[us][Rook][r_from]` |
| `*Promo` (no capture) | `PSQT[us][promo_kind][to] - PSQT[us][Pawn][from]` |
| `*PromoCapture` | `PSQT[us][promo_kind][to] - PSQT[us][Pawn][from] - PSQT[them][kind(captured)][to]` |

Applied via a **separate private helper** `update_static_eval_after_make` (not merged into `update_zobrist_after_make`). The two helpers are independent: the eval delta needs only `mv`, `mover`, `captured`, `capture_sq` — a strict subset of the zobrist helper's 9 inputs. Keeping them separate matches the single-responsibility shape; the inliner will fuse the duplicate `match flag` cascades. New `static_eval_white` is written via `Position::refresh_static_eval_from(value)`.

### 8. `unmake_move` restores from `Undo` directly

Symmetric to zobrist: `pos.refresh_static_eval_from(undo.prior_static_eval)`. No incremental inversion.

### 9. Debug-only round-trip assert + release perf sentinel

In `make_move` (debug builds only): `debug_assert_eq!(pos.static_eval_white(), eval::eval_white_from_scratch(pos))` after the delta is applied.

`unmake_move` (debug builds only): same assert against the restored value.

Release: trust the delta exclusively. **Add `make_move_no_eval_recompute_in_release` perf sentinel** mirroring `make_move_no_from_scratch_in_release` from M1.E — anchors the contract that `eval::eval_white_from_scratch` is never called from the make/unmake hot path in release builds.

### 10. `GreedyMover` Search impl

```rust
pub(crate) struct GreedyMover {
    seed: u64,
    state: u64,
}
impl GreedyMover { pub(crate) fn new(seed: u64) -> Self { Self { seed, state: seed } } }
impl Search for GreedyMover {
    fn go(&mut self, position, ctx, info_sink) -> SearchResult { … }
    fn set_seed(&mut self, seed) { self.seed = seed; self.state = seed; }
    fn reset(&mut self) { self.state = self.seed; }
}
```

Identical seed/state semantics to M2.D's `RandomMover` (which is being removed).

#### 10.1 `go` algorithm

1. Generate legal moves into `MoveList`. Filter by `ctx.limits.searchmoves` if `Some`.
2. If empty: emit `info depth 0 score cp 0 nodes 0 time <ms> pv 0000`, return `SearchResult { bestmove: None, depth: 0, score_cp: Some(0), nodes: 0, … }`. (No PRNG advance, no eval calls.)
3. Else, **reservoir-sampled best-eval scan** (one PRNG step per tie):
   ```rust
   // Take ONE clone outside the loop; mutate in place via make/unmake.
   // Position is Copy, but cloning per iteration is wasteful — debug-build
   // round-trip asserts run inside make_move and would multiply 30×.
   let mut pos_clone = *position;

   // Seed best_* from move[0] in the same expression that scores it — no dead init.
   let undo0 = pos_clone.make_move(moves[0]);
   let mut best_score = -evaluate(&pos_clone);   // negate: post-make perspective is opponent
   pos_clone.unmake_move(moves[0], undo0);
   let mut best_mv: Move = moves[0];
   let mut tie_count: u32 = 1;

   for mv in &moves[1..] {
       let undo = pos_clone.make_move(*mv);
       let score = -evaluate(&pos_clone);
       pos_clone.unmake_move(*mv, undo);

       if score > best_score {
           best_score = score; best_mv = *mv; tie_count = 1;
       } else if score == best_score {
           tie_count += 1;
           let r = splitmix64_next(&mut self.state);
           if (r as usize) % (tie_count as usize) == 0 {
               best_mv = *mv;
           }
       }
   }
   ```
   - **One `pos_clone`, mutated in place** via make/unmake — not 30 separate clones. Required to keep the debug-build round-trip assert hot loop sane.
   - **Score sign:** `evaluate(post_make_pos)` returns from *post-make* side-to-move's perspective, which is the *opponent*. Negate to get our perspective.
   - Tie-break sampling uses `% tie_count`. Modulo bias for `tie_count ≤ 218` is < 4×10⁻¹⁸ — same justification as M2.D.
4. **Emit info line BEFORE the wait loop** — `info depth 1 score cp <best_score> nodes <N> time <ms> pv <bestmv-uci>` where `N = moves.len()` (root nodes; depth-1 doesn't recurse). Why before: GreedyMover's score is real (unlike M2.D's placeholder `cp 0`); a GUI watching `info score cp` to track the engine's eval should see it the moment the search decides, not after `go infinite` is cancelled.
5. Wait loop: if `infinite || movetime.is_some() || ponder`, sleep 1 ms while `!should_abort(0)`.
6. Return `SearchResult { bestmove: Some(best_mv), depth: 1, score_cp: Some(best_score), nodes: N, ponder: None }`.

The `score_cp` field on `SearchResult` is populated for forward compatibility; the M2.C orchestrator does not yet consume it (the `bestmove` line is what gets emitted from `result.bestmove`). M3.E's iterative deepening will use it.

#### 10.2 `score_cp` is reported to UCI

Unlike M2.D's `RandomMover` (which always emitted `score cp 0` as a fastchess-compliance-Step-12 placeholder), `GreedyMover` reports the *real* depth-1 score in centipawns. fastchess and any other GUI now sees a score that varies position-to-position.

#### 10.3 Mate-score handling — out of scope

Plain centipawns at this depth. M3.C will introduce mate scoring (`MATE - ply` etc.) and `score mate N` UCI emission.

#### 10.4 `score cp` from White's perspective vs side-to-move

UCI spec §"info" mandates `score cp <X>` is **from the engine's point of view** — the side to move. Our `evaluate` already returns side-to-move-relative; `best_score = -evaluate(post)` is also side-to-move-relative (the side that just played the move). Emit as-is.

#### 10.5 `searchmoves` empty filter

`Some(empty)` — same as `RandomMover`: yields `None`, no PRNG advance, no eval calls. `info depth 0 score cp 0 nodes 0 time <ms> pv 0000`. The `depth 0` is honest (nothing was searched); reserves `depth 1` for the case where moves were actually evaluated.

### B. Eval property tests (`src/eval.rs::tests::props`)

| ID | Name | Strategy |
|---|---|---|
| **B1** | `prop_psqt_symmetry_at_indices` | For all (kind, sq), `PSQT[White][kind][sq] == -PSQT[Black][kind][sq ^ 56]`. Pure constant invariant. Implemented as a `for kind in PieceKind::ALL { for sq in Square::all() { ... } }` exhaustive iteration (384 cases) — proptest scaffolding adds nothing here over a plain `#[test]`, but the assertion fails *loudly* per-(kind, sq) pair which is what we want for a regression. |

**Color-swap invariance (`evaluate(P) == evaluate(mirror(P))`) is intentionally not tested directly.** Writing a `mirror_position` helper (vertical board flip + per-piece color flip + EP recompute + side-to-move flip + castling-rights swap) costs ~50 LOC and its own test surface; the M3.A budget doesn't justify it. The property is triangulated by:

- **A1** (startpos, where mirror is identity, evaluates to 0).
- **A3** (constructed position with side-to-move flipped → eval is negated).
- **B1** (PSQT lookup symmetry — the data invariant that drives color-swap correctness).

Together these pin the property at the unit level. A future M6 or M7 phase that touches eval composition (tapering, mobility) is a better time to introduce the mirror helper, since multiple eval terms will benefit from it.

## Parallelization map

The unit is **sequential**, not parallel. Honest dependency graph:

| Slice | Files | Why it depends on the prior slice |
|---|---|---|
| **Slice 1: eval module + Position field/accessor** | `src/eval.rs` (full module: `evaluate`, `eval_white_from_scratch`, `MATERIAL`, `MG_*_PST`, `PSQT` const builder), `src/position.rs` (`static_eval_white` field + `static_eval_white(&self) -> i32` accessor + `refresh_static_eval` calling `eval::eval_white_from_scratch`), `src/lib.rs` | None — both eval functions and the field are introduced together. |
| **Slice 2: incremental hooks in `mov` + Undo extension** | `src/mov.rs`, `src/fen.rs` (single-line refresh call) | Depends on Slice 1's `eval::eval_white_from_scratch` (called by debug-build round-trip assert) AND on Slice 1's field accessor. |
| **Slice 3: GreedyMover + run_stdio swap + RandomMover deletion + ADR + integration test + match.sh + doc updates** | `src/search.rs`, `src/engine.rs`, `tests/uci_integration.rs`, `scripts/match.sh`, `docs/decisions/0014-eval-material-pst.md` | Depends on Slices 1 and 2 — `make_move` inside the scan loop traverses Slice 2's delta path; `evaluate` is from Slice 1. |

The unit is small enough (~700 LOC) that a single coding agent runs all three slices sequentially. **Test-writing within each slice is parallelizable** (e.g. inside Slice 1 the eval anchor tests A1–A10 are independent of the property test B1; inside Slice 3 the GreedyMover unit tests D13–D22 are independent of E38), but the *implementation order* is fixed by the dependency chain above.

Earlier-version drafts of this plan claimed parallelism between Slice 1 and Slices 2/3 — that was wrong. `evaluate` reads `position.static_eval_white()`, so Slice 1 cannot ship without Slice 2's accessor; the cleanest factoring is to land both together in one Slice-1-extended commit (the table above).
