# M1.F — Legal move generation

## Context

M1.A–E delivered the passive board model (`Position` + FEN), the sliding-piece attack lookup (`magic`, `slow_attacks`), Zobrist hashing (`zobrist`), and the mutating layer (`mov::make_move` / `mov::unmake_move`). M1.F is the final piece before perft (M1.G): the **legal move generator**.

This phase **binds ADR-0007** (`docs/decisions/0007-legal-direct-movegen.md`), already drafted. The ADR codifies:
- Legal-direct, mask-based generation.
- Per-call (not cached) computation of `checkers` / `pinned` / `capture_mask` / `push_mask`.
- Check-evasion specialization (no check / single check / double check).
- King-flee on `occupancy ^ king_bb` (fixes the slider-checks-through-king-square bug).
- EP horizontal-pin handled at emission time with a per-move legality test.
- Public surface: `generate_moves(&Position, &mut MoveList)` and `in_check(&Position) -> bool`.

### Research skip — justified

Workflow step 1 ("deep prior-art research") is a clean skip. `docs/research/m1-engine-architecture.md` covers M1.F's design space:
- §3 Move generation strategy — legal-direct vs. pseudo-legal-and-filter, evasion specialization, king-flee gotcha.
- §4 Make/unmake mechanics — already implemented; M1.F is a consumer.
- §5 Zobrist hashing — already implemented; M1.F is a consumer (only via make/unmake).
- §6 Edge case taxonomy — the 11 well-known bug classes and the test positions that expose them.

ADR-0007 distills the prose into the project's commitments. No fresh research is needed; concrete implementation choices that the prose left open (e.g. exact `MoveList` API shape) are settled in this plan.

## Decisions baked into this plan

### 1. Module layout: nested under `src/movegen/`

The total surface is too large for one file (combined estimate ~1200–1500 lines impl + ~700–1000 tests; bigger than `mov.rs`). Split mirrors `src/zobrist.rs` + `src/zobrist/keys.rs`'s convention: the parent file (`src/movegen.rs`) holds the public API and re-exports; submodule files (`src/movegen/*.rs`) hold per-piece-type implementations.

Per-file budget:
- `src/movegen.rs` — ~150 lines (public API, `generate_moves` orchestration, `in_check`, doc comments).
- `src/movegen/move_list.rs` — ~120 lines (`MoveList` type + iter + tests). Kept as a separate file (vs. inlined into `movegen.rs`) so the prereq shard can split it from the masks work if scheduling needs to.
- `src/movegen/masks.rs` — ~250 lines (`pinned`, `checkers`, mask-derivation helpers, `attacked_by_opponent`).
- `src/movegen/pawn.rs` — ~250 lines (most complex emission; EP horizontal-pin filter lives here).
- `src/movegen/knight.rs` — ~80 lines.
- `src/movegen/sliders.rs` — ~150 lines (rook + bishop + queen; queen = rook | bishop).
- `src/movegen/king.rs` — ~200 lines (king moves + both castling sides + flee-map filter + castling-through-attack tests).

Tests live alongside in `#[cfg(test)] mod tests`. Cross-cutting integration tests (end-to-end position counts, checkmate/stalemate detection on full positions) live in `tests/movegen.rs` (integration test crate root).

### 2. `MoveList` type

```rust
/// Stack-allocated fixed-capacity move buffer. Capacity 256 covers the
/// proven max legal-move count of 218 (Petrović 1964; integer-programming
/// proof 2025) plus comfortable headroom — though we only emit legal
/// moves so 218 is the true ceiling.
pub struct MoveList {
    moves: [MaybeUninit<Move>; 256],
    len: u16,
}

impl MoveList {
    pub const fn new() -> MoveList;
    pub(crate) fn push(&mut self, mv: Move);    // debug_assert!(len < 256)
    pub fn len(&self) -> usize;
    pub fn is_empty(&self) -> bool;
    pub fn as_slice(&self) -> &[Move];
    pub fn iter(&self) -> impl Iterator<Item = Move> + '_;
    pub(crate) fn clear(&mut self);
}

impl Default for MoveList { /* delegates to new() */ }
impl fmt::Debug for MoveList { /* prints as_slice() */ }
```

**`len: u16`, not `u8`.** A `u8` can represent only 0..=255, so a 256-capacity buffer with `u8 len` is off-by-one (push-256 would overflow). `u16` is two bytes, costs nothing relative to the 512-byte `moves` array, and admits 0..=256 cleanly.

**`push` and `clear` are `pub(crate)`** so the soundness contract stays inside the crate. External consumers (search, UCI, integration tests) interact via `as_slice` / `iter` after `generate_moves` populates the buffer. Movegen is the only producer; making the producer surface crate-private keeps "release-build over-push is UB" an internal contract instead of leaking it across the crate boundary.

**`iter` yields `Move` by value** (not `&Move`) since `Move` is `Copy + 2 bytes` — the by-value form is the idiomatic shape for tiny `Copy` types and matches the bitboard-iterator convention (`Bitboard::iter` yields `Square` by value).

`MaybeUninit<Move>` avoids the 256× `Move::default()` initialization cost on every `MoveList::new()` call. The `as_slice` impl is the codebase's first `unsafe` block:

```rust
pub fn as_slice(&self) -> &[Move] {
    // SAFETY: indices 0..len are always initialized by `push`, and
    // `len <= 256` by the debug_assert in `push`. `MaybeUninit::slice_assume_init_ref`
    // is stable since Rust 1.83; edition = "2024" requires >= 1.85.
    unsafe { MaybeUninit::slice_assume_init_ref(&self.moves[..self.len as usize]) }
}
```

`push` writes through `MaybeUninit::write`. The `len` invariant is the soundness contract: indices `0..len` are always initialized.

**Release-build over-push is UB by contract.** `push` debug-asserts `len < 256`; in release this assertion compiles out, and an over-push would silently bump `len` to 257 — at which point `as_slice` exposes one byte of uninit memory as a `Move`, which is undefined behavior. The 218-move proven legal-move ceiling, plus the legal-direct-only generation discipline AND the `pub(crate) push`, guarantees this never fires in practice. The contract is documented; release trusts.

The single `&[Move]` slice is the consumer-facing view; consumers don't care about `MaybeUninit`.

**No `Vec` allocation.** Both because of perft hot-path implications and because the heap-allocation noise would dominate the benchmark in M1.G.

### 3. `generate_moves` orchestration

```rust
pub fn generate_moves(pos: &Position, out: &mut MoveList) {
    out.clear();
    let us = pos.side_to_move();
    let king_sq = pos.king_square(us);
    let info = MaskInfo::compute(pos, us, king_sq);

    // King moves work the same regardless of single/double check; the only
    // thing that changes is whether non-king moves are legal at all.
    king::emit_king_moves(pos, us, king_sq, &info, out);
    if info.checkers.count() <= 1 {
        // Castling and most piece moves are legal only when not in double
        // check. (Castling is also illegal in single check, gated inside
        // king::emit_king_moves.)
        pawn::emit_pawn_moves(pos, us, &info, out);
        knight::emit_knight_moves(pos, us, &info, out);
        sliders::emit_slider_moves(pos, us, &info, out);
    }
}

pub fn in_check(pos: &Position) -> bool {
    let us = pos.side_to_move();
    let king_sq = pos.king_square(us);
    masks::any_attacker(pos, us.flip(), king_sq, pos.occupied_all()).any()
}
```

`MaskInfo` bundles the per-call masks + checker bitboard + king attack map (computed on `occupancy ^ king_bb`). The struct lives in `masks.rs`; the per-piece-type emit functions take it by reference.

**The orchestration is dumb on purpose.** All edge-case logic is inside the per-piece-type emitters. `generate_moves` itself is ~10 lines once the prelude lands.

### 4. `MaskInfo` — per-call mask bundle

```rust
pub(crate) struct MaskInfo {
    pub checkers: Bitboard,
    pub pinned: Bitboard,
    pub capture_mask: Bitboard,
    pub push_mask: Bitboard,
    /// Squares attacked by the opponent on `occupancy ^ king_bb`. Used by
    /// king move filtering — the king cannot move to any square in this set.
    pub king_danger: Bitboard,
    /// For each pinned own piece, the king-pinner ray (line through king
    /// and pinner, clamped to mask covering the pinner direction). Indexed
    /// by `Square::index()`. Entries for non-pinned squares are unspecified
    /// (callers must check `pinned.contains(sq)` first).
    pub pin_rays: [Bitboard; 64],
}

impl MaskInfo {
    pub(crate) fn compute(pos: &Position, us: Color, king_sq: Square) -> MaskInfo;
}
```

**`pin_rays`** stores per-pinned-piece the bitboard of squares the piece may legally move to **direction-wise** (i.e., the king-through-pinned-piece-and-on-to-the-pinner line). At emission time:
- Pawn / slider pinned moves: AND the destination set with `pin_rays[from.index()]`.
- Knight pinned moves: skip (knights cannot move along any line).

The 64-entry array is 512 bytes on the stack — cheap. We populate it sparsely (only the pinned squares' entries are touched); other entries are left at `Bitboard::EMPTY` initialization.

**Why store rays, not just the pinned set:** the per-pinned-piece ray must be intersected with the move's destination set. Without the ray, every emitted move would need a re-computed "is this destination on the king-pinner line" predicate, which is more code at every emission site. The 64-entry array is paid once per `generate_moves` call; the savings are amortized across every move emitted in that call.

**Cost note (profile-driven; revisit at M1.G).** The 64-entry `pin_rays` array zero-fills 512 B per `MaskInfo::compute` call. That's eight 64-byte cache-lines worth — well within L1 capacity (192 KiB on Apple Silicon M-series P-cores) and not measurably worse than the rest of the prelude (mask setup itself takes more cycles than a stack zero-fill). Two alternatives exist if profiling later flags it:

- Switch to `pin_rays: [MaybeUninit<Bitboard>; 64]` with a `pinned`-mask-gated read (callers always check `pinned.contains(sq)` first per the field's contract, so reads on uninit slots are excluded by construction).
- Drop the array entirely and recompute the king-pinner ray on the fly via a `between_bb(king, pinner)` helper at each emission site.

Both are local optimizations behind the existing `MaskInfo` API; we accept the zero-fill in M1.F and revisit at M1.G if `samply`/`criterion` shows it on the hot path.

### 5. Pin computation

For each opponent slider (rook/queen on rank/file ray to king; bishop/queen on diagonal ray to king):

1. Compute `between` = squares strictly between king and slider, exclusive of both.
2. Count `between & all_occupancy`. If exactly 1, the single intervening piece is pinned (regardless of color — but we only care about own-side pieces for legality filtering; opponent pieces "pinned to our king" are not constrained by us).
3. If the single piece is one of ours, mark the square in `pinned` and record the king-pinner ray (king ∪ between ∪ slider) in `pin_rays[sq]`.

**Implementation strategy:** for each of {rook-rays, bishop-rays} run `magic::*_attacks(king_sq, opponent_slider_bb_of_matching_kind)`. The hits are pinner candidates. For each, do the `between` count.

**Optimization (deferred):** the standard "X-ray attacks" trick computes `xray = magic_attack(king, occ ^ blockers)` and intersects with opponent sliders to find pinners directly. We do the simpler per-pinner loop in M1.F; revisit in M1.G profiling if it shows on the hot path.

### 6. Checker computation

```rust
pub(crate) fn checkers_of(pos: &Position, us: Color, king_sq: Square,
                          occupancy: Bitboard) -> Bitboard {
    let them = us.flip();
    let mut chk = Bitboard::EMPTY;
    // Pawns: opponent pawns whose attack pattern reaches king_sq.
    chk |= masks::pawn_attacks_from(king_sq, us) & pos.pieces_colored(them, PieceKind::Pawn);
    // Knights.
    chk |= masks::knight_attacks(king_sq) & pos.pieces_colored(them, PieceKind::Knight);
    // Bishops + queens (diagonal).
    let diag = pos.pieces_colored(them, PieceKind::Bishop)
             | pos.pieces_colored(them, PieceKind::Queen);
    chk |= magic::bishop_attacks(king_sq, occupancy) & diag;
    // Rooks + queens (orthogonal).
    let orth = pos.pieces_colored(them, PieceKind::Rook)
             | pos.pieces_colored(them, PieceKind::Queen);
    chk |= magic::rook_attacks(king_sq, occupancy) & orth;
    chk
}
```

Note `pawn_attacks_from(king_sq, us)` — this is the attack pattern of an own-color pawn standing on `king_sq`, mirrored against opponent pawns. It works because pawn captures are color-asymmetric: if our pawn on `king_sq` could capture an opponent pawn at `S`, then conversely the opponent pawn at `S` could capture *us* on `king_sq`.

**Index orientation pinned.** The `PAWN_ATTACKS` table is indexed by the **attacker's color**: `PAWN_ATTACKS[Color::White as usize][sq]` is the set of squares a white pawn on `sq` would attack. The helper:

```rust
#[inline]
pub(crate) fn pawn_attacks_from(sq: Square, us: Color) -> Bitboard {
    PAWN_ATTACKS[us.index()][sq.index() as usize]
}
```

`pawn_attacks_from(king_sq, us)` reads the **own-color** attacker row at index `us`, returning the squares an own-color pawn on `king_sq` would attack. ANDing this with the opponent's pawn bitboard yields the opponent pawns whose attack ray hits `king_sq`. Reading `PAWN_ATTACKS[them]` here would be the off-by-one inversion bug the index documentation pins against.

`occupancy` is parameterized so that king-flee filtering can pass `occupancy ^ king_bb` (the king's own square removed) without disturbing the rest of the position state.

`checkers_of` returns only pieces whose attacks land **on** `king_sq` — it does not need to consider the opponent king (kings cannot put each other in check; adjacency is illegal but not "check"). The opponent-king-adjacency rule lives in §7's `compute_attacked_squares`, not here.

### 7. King danger (the "flee through check ray" fix)

When deciding which squares the king may move to, opponent attacks are computed against `occupancy ^ king_bb`. The standard taxonomy bug: opponent rook on a-file, king on a-rook ray, king tries to flee further along the ray; without removing the king from occupancy, the rook's attack ray stops at the king's *current* square, so the further-along square is not flagged as attacked.

```rust
pub(crate) fn compute_attacked_squares(pos: &Position, attacker: Color,
                                       occupancy: Bitboard) -> Bitboard;
```

This is **distinct from `checkers_of`**: `checkers_of` returns the set of opponent pieces whose attack-set contains `king_sq`; `compute_attacked_squares` returns the union of *every* square at least one opponent piece attacks. The two functions walk different result domains; both are needed.

`compute_attacked_squares` enumerates **all** opponent piece kinds, including the king:
- Pawns — opponent pawn attack pattern (color-asymmetric).
- Knights — knight-attack lookup table.
- Bishops + queens — bishop magic against `occupancy`.
- Rooks + queens — rook magic against `occupancy`.
- **King** — opponent king's 8 adjacent squares, via the `king_attacks` lookup table. Required because the rule is "you cannot move your king to a square the opponent attacks," and the opponent king attacks its 8 neighbors. (Kings cannot put each other in check in the strict sense — the rule is symmetric mutual-non-adjacency, enforced by computing both kings' attacks against each other.)

```rust
let king_danger = compute_attacked_squares(pos, them, occupancy ^ king_bb);
```

The king's emit step then:
```rust
let candidates = masks::king_attacks(king_sq) & !pos.occupied(us) & !king_danger;
```

emits a quiet/capture for each set bit (capture iff the destination is in `pos.occupied(them)`).

### 8. Pawn emission — 8 sub-cases

Pawn is the most complex piece. Emission is split into:

- **Single push** (one square forward, target empty). On promotion rank → emit four `*Promo` flags; else emit `Quiet`.
- **Double push** (two squares forward, both squares empty, pawn on starting rank). Emit `DoublePush`. Never a promotion.
- **Capture left / right** (diagonal capture targeting opponent piece). On promotion rank → emit four `*PromoCapture` flags; else emit `Capture`.
- **En passant** — if `pos.ep_target()` is Some, for each of our pawns adjacent to the EP target on the appropriate rank, emit an EP move **after** validating:
  1. The pawn isn't pinned along a non-EP direction (standard pin filter).
  2. The post-EP occupancy doesn't expose the king to a horizontal slider attack on the king's rank. This is the Position-3 horizontal-pin trap. Computed by simulating the post-EP occupancy (remove our pawn from `from`, remove opponent pawn from EP-capture-square, add our pawn at `ep_target`) and running `magic::rook_attacks(king_sq, post_ep_occ)` against opponent rook+queen bitboard.

**Mask intersection** at every emission: destination must be in `capture_mask | push_mask` (with `push_mask` covering the empty-square cases for pushes; `capture_mask` covering the capture-target cases). For pinned pawns: AND with `pin_rays[from]`.

**Color-symmetric implementation.** Writing color-generic pawn code via parameterizing on `Color` and using `Bitboard::shift_north` / `shift_south` is a documented pattern; we follow it. Compile time will dead-code-eliminate the unused branch given a color-known caller.

**Promotion-rank detection:** white pawns reach rank 8 from rank 7 (any push from rank 7 promotes); black pawns reach rank 1 from rank 2. A pawn cannot reach the promotion rank by single push without being on rank 7 (white) / rank 2 (black). Plan-references to specific 1-indexed ranks: white promotion-from-rank = 7, white promotion-target-rank = 8.

**Starting-position pawn-move count (sanity).** From the standard initial position with white to move, pawn moves emit as 8 single-pushes (rank 2 → rank 3) plus 8 double-pushes (rank 2 → rank 4) = 16 pawn moves. No captures, no EP, no promotions. Used by the integration test below.

### 9. Knight emission

Simplest piece. For each non-pinned own knight (pinned knights emit nothing — there's no overlap between any pin ray and knight-jump destinations):

```rust
let from = ...;
let dests = masks::knight_attacks(from) & !pos.occupied(us)
          & (info.capture_mask | info.push_mask);
for to in dests.iter() {
    let flag = if pos.occupied(them).contains(to) { Capture } else { Quiet };
    out.push(Move::new(from, to, flag));
}
```

`masks::knight_attacks` is a 64-entry pre-computed `[Bitboard; 64]` table built at startup (or const-evaluated — small enough for `LazyLock` cost to be invisible).

### 10. Slider emission (bishop, rook, queen)

For each non-king sliding piece of the moving side:

```rust
let attack_set = match kind {
    Bishop => magic::bishop_attacks(from, all_occ),
    Rook   => magic::rook_attacks(from, all_occ),
    Queen  => magic::queen_attacks(from, all_occ),
};
let mut dests = attack_set & !pos.occupied(us)
              & (info.capture_mask | info.push_mask);
if info.pinned.contains(from) {
    dests &= info.pin_rays[from.index() as usize];
}
for to in dests.iter() {
    let flag = if pos.occupied(them).contains(to) { Capture } else { Quiet };
    out.push(Move::new(from, to, flag));
}
```

Bishop-rook-queen consolidate into one inner loop with a `kind` switch on the attack lookup. No reason to duplicate the surrounding code three times. (`magic::queen_attacks` is internally `rook | bishop`; using it directly in the queen branch is straightforward.)

### 11. King emission

King moves split into two paths:

**Regular king moves.** Use `masks::king_attacks(from)` (8-direction attack pattern, 64-entry pre-computed table). Filter by:
- `!pos.occupied(us)` — can't capture own piece.
- `!info.king_danger` — destination not attacked by opponent on `occ ^ king_bb`.

For each survivor, emit `Quiet` or `Capture` per opponent occupancy.

**Castling.** Only attempted if not currently in check. For each castling right held by the moving side that hasn't been lost:
- The squares between king and rook are empty.
- The squares the king passes over (including king-from and king-to) are not attacked.

Concretely, for white kingside (`O-O`):
- Castling right `WHITE_KING` set.
- `f1` and `g1` empty.
- `e1`, `f1`, `g1` not in `king_danger`.

The "king on e1, white rook on h1" invariant is enforced **at FEN parse time** by the strengthened `validate_post_parse` (§13). Movegen trusts this invariant. In debug builds, the castle-emission path includes a `debug_assert!` matching the mailbox against the expected pieces; release trusts the invariant per the project's defensive-checks-debug-only convention (`docs/workflow.md` "Final review loop" → Code quality).

If both clauses pass, emit `Move::new(e1, g1, MoveFlag::KingCastle)` (using the existing `Move::new` constructor in `src/mov.rs`; `Move::quiet` / `Move::capture` exist as ergonomic helpers but castling has its own flag and uses the general constructor). Mirror for `WHITE_QUEEN`, `BLACK_KING`, `BLACK_QUEEN`.

The squares-the-king-passes-over check is: for kingside, `f1 | g1` (king transit and final). The king's *initial* square (`e1`) is also implicitly required (castling out of check is illegal); the "not in check" gate at castling time covers it directly. (We do not rely on the orchestrator's check-counter to gate castling — the per-side castle-emission code carries the explicit "king's square not attacked" check itself, so it's correct in isolation.)

### 12. Pre-computed attack tables

`masks::KNIGHT_ATTACKS: [Bitboard; 64]` and `masks::KING_ATTACKS: [Bitboard; 64]`: const-fn-built at compile time. The patterns are simple bit-shifts (8-direction shift mask for king; 8 knight-jump deltas with file-mask guards), well within stable `const fn` reach in the project's `edition = "2024"` baseline.

`masks::PAWN_ATTACKS: [[Bitboard; 64]; 2]`: same — color-asymmetric attack pattern via `Bitboard::shift_north_east` etc., all `const fn`-callable.

**Why `const fn` here, but `LazyLock` for magic (ADR-0008):** the leaf-piece tables are tiny (3 × 64 entries × 8 bytes = 1.5 KiB), have trivial-to-evaluate construction, and avoid the per-call `LazyLock::deref` atomic check that movegen's hot inner loop pays for. The magic tables are ~840 KiB and require running the slow ray-walker — that *did* push back on `const fn` per ADR-0008. The leaf-piece tables don't.

Pinned by tests: each table's row at d4 (and one corner) is asserted against hand-computed expected values, ensuring const-fn evaluation doesn't silently miscompile.

### 13. Per-FEN structural sanity for castling

A FEN like `4k3/8/8/8/8/8/8/4K2R w K - 0 1` (castling right `K` set, but no rook on `h1`) is technically ill-formed — castling rights imply specific king and rook positions. M1.B's `validate_post_parse` does NOT enforce this (it only checks king count, pawn-rank prohibition, EP-target rank).

Per the project's defensive-checks-debug-only convention (`docs/workflow.md` "Final review loop" → Code quality, added in this same change), validation belongs **at the boundary that creates the invariant** (the FEN parser), not redundantly on every consumer call. M1.F therefore extends `validate_post_parse` rather than guarding at castle-emission time.

**Extension to `validate_post_parse`** (in `src/fen.rs`, scope-creep into the M1.F commit):

For each set bit in `pos.castling_rights()`, assert via the **mailbox** (not bitboards alone — a bitboard test would accept a black rook on h1):
- `WHITE_KING` ⇒ `pos.piece_at(E1) == Some(Piece { color: White, kind: King })` AND `pos.piece_at(H1) == Some(Piece { color: White, kind: Rook })`.
- `WHITE_QUEEN` ⇒ same king check + `pos.piece_at(A1) == Some(Piece { color: White, kind: Rook })`.
- `BLACK_KING` ⇒ `pos.piece_at(E8) == Some(Piece { color: Black, kind: King })` AND `pos.piece_at(H8) == Some(Piece { color: Black, kind: Rook })`.
- `BLACK_QUEEN` ⇒ same black king check + `pos.piece_at(A8) == Some(Piece { color: Black, kind: Rook })`.

Failures yield a new `FenError::InconsistentCastlingRights` variant, surfaced from `Position::from_fen`. New unit tests in `src/fen.rs` cover the four corruption cases (one per right).

**Movegen posture.** At castle-emission time, the king/rook-on-starting-square invariant is held by construction (the FEN parser is the only entry point that produces a `Position`; `set_piece` / `set_aux_state` are crate-private). The castle code:

```rust
debug_assert_eq!(pos.piece_at(Square::E1), Some(Piece::new(Color::White, PieceKind::King)));
debug_assert_eq!(pos.piece_at(Square::H1), Some(Piece::new(Color::White, PieceKind::Rook)));
```

These compile out in release. A future regression that violates the invariant — e.g. a buggy `make_move` rewrite that places a king elsewhere with kingside-castling-right intact — fails loudly in tests; release trusts.

This is the canonical example of the project's defensive-checks convention: invariant created at FEN parse; pinned by `debug_assert!` at consumers; release trusts.

**Pre-flight FEN audit.** Before FENVAL lands, every existing test-FEN with castling rights set must be checked against the new validation. Audit performed at plan-write time (2026-04-27): all FENs in `src/fen.rs`, `src/mov.rs`, `src/position.rs`, and `tests/*.rs` with `K`/`Q`/`k`/`q` castling rights have matching mailbox state — kings on e1/e8 and rooks on a1/h1/a8/h8 wherever the corresponding right is set. Specifically:
- Standard starting position, Kiwipete, Position 4, Position 5, all canonical six — all match.
- M1.E's curated castling test FENs (`4k3/.../4K2R w K`, `R3K3 w Q`, `r3k3/.../4K3 b q`, `4k2r/.../4K3 b k`, `r3k2r/.../R3K2R w KQkq`, etc.) — all match.
- M1.E's "captures clear castling on corner" cases (`...K w k - 0 1` style) — castling rights match the corner-rook-color contract.

If a future test wants to construct a corrupt-FEN position to exercise the new validation, it does so via `Position::from_fen` and asserts the new `FenError::InconsistentCastlingRights` — never via the parsed-position path.

### 14. Behavior on positions that violate "side-not-to-move is in check"

Standard chess says: after the side-to-move makes a legal move, the *opponent* may not be in check. Equivalently, before our move, the side-not-to-move may be in check (we'd capture the king on our move) — that position is unreachable from a legal game.

`generate_moves` does not validate this. Such a position is **caller error**, akin to `make_move`'s "trusts the caller" wording. A test fixture that constructs such a position via `Position::from_fen` will get whatever output the generator produces.

We do not panic. We do not refuse. We trust the input. The FEN parser's `validate_post_parse` (extended in §13) covers king-count, pawn-rank prohibition, EP-target rank, AND castling-rights/mailbox consistency. The "side-not-to-move is in check" check is a separate validation surface that may be added under a future ADR; M1.F does not implement it. (Diagnosing such corrupt FENs at the perft level would manifest as a count mismatch that points back at the FEN.)

### 15. `in_check`

Public helper: `pub fn in_check(pos: &Position) -> bool` returns whether the side-to-move's king is currently attacked. Implemented via `checkers_of(pos, us, king_sq, occupancy).any()`.

Used by:
- Tests that want to anchor a position is in check.
- Future search code that wants quick access without computing the full `MaskInfo`.
- M1.F's own internal castling checks (`castling_legal_when_not_in_check`).

`in_check` does *not* depend on `MaskInfo`. It's a thin wrapper around `checkers_of`.

### Property tests (`#[cfg(test)] mod proptests`)

Property tests live alongside ordinary tests in their submodule's `tests` module per `feedback_property_tests_workflow.md` and `docs/workflow.md`'s "Property tests vs. unit tests".

- **`prop_no_legal_move_leaves_us_in_check`** — capture `us = pos.side_to_move()` and `king_sq = pos.king_square(us)` *before* the move. (Note: after the move, our king square is unchanged unless this *is* a king move; for king moves, use `mv.to_square()` as the post-move king square.) - **`prop_legal_move_count_within_218`** — every position's `generate_moves` produces ≤218 moves (Petrović 1964 ceiling).
- **`prop_double_check_emits_only_king_moves`** — given a hand-built list of double-check **post-positions** (random walk almost never reaches double check, so this property is anchored on explicit seeds, not random sampling). The corpus is built deterministically at plan-execute time:
  - Seed FEN A: `4r3/8/8/8/8/5n2/8/4K3 w - - 0 1` (rook on e8 + knight on f3 both check king on e1; pure double check by independent attackers, no preceding move needed).

  - Seed FEN C: build by parsing `4r2k/8/8/8/3Pp3/8/4K3/8 b - d3 0 1`, calling `make_move(&mut pos, e4xd3 EP)` once at corpus-build time, and using the *post-move* `Position` as the seed. Skipping the random-walk for this seed because the EP move is the only move that produces double check from the parent FEN.
  - Seed FEN D: TBD — one additional bishop+rook discovered double check fixture at plan-execute time.
  
  Each seed is added directly to the proptest input as a deterministic position (not a random-walk root). For each seed, `generate_moves` is called and every emitted move's `from_square` must equal the side-to-move king's square.

### Test fixtures and generators

The `proptest` corpus comes from two sources, combined:

1. **Edge-class seeds** — explicit FEN strings from `docs/research/m1-engine-architecture.md` §6 (the 11 well-known bug-class fixtures, including the canonical 6, the Position-3-style horizontal-pin minis, the EP-double-check position, the king-flee-along-ray positions, the promotion-from-check position, etc.). These are anchors that hand-built fixture coverage already addresses; the property tests run *additionally* across them.
2. **Random walks rooted at each seed** — for each seed, walk 0..50 random legal moves (using the just-built `generate_moves` to pick from the legal set on each ply). Distribution: a random walk from the starting position is *very unlikely* to land in EP-horizontal-pin, double-check, or stalemate states — but a walk *rooted at* an §6 edge fixture stays near the corner for the first few plies, and the walk perturbs the corner-adjacent positions, exercising mask edge cases the unit fixtures don't cover.

The corpus is intentionally **seeded**, not random-from-scratch. A pure random-walk-from-starting-position strategy concentrates on common middle-game patterns and statistically misses the rare-but-bug-prone edge positions; the §6 seed list is the corrective.

The strategy's pseudocode:

```rust
fn proptest_strategy_legal_position() -> impl Strategy<Value = Position> {
    let seeds: Vec<Position> = SEED_FENS.iter().map(|f| Position::from_fen(f).unwrap()).collect();
    (any::<u32>(), 0..seeds.len(), 0..50usize).prop_map(move |(rng_seed, seed_idx, walk_len)| {
        let mut pos = seeds[seed_idx];
        let mut rng = rng_from(rng_seed);
        for _ in 0..walk_len {
            let mut ml = MoveList::new();
            generate_moves(&pos, &mut ml);
            if ml.is_empty() { break; }  // Mate or stalemate; can't continue.
            let pick = ml.as_slice()[rng.next_u32() as usize % ml.len()];
            pos.make_move(pick);
        }
        pos
    })
}
```

### Honesty about dependencies

- The four parallel shards (A, B, C, D) genuinely don't see each other.
- Shard A's EP horizontal-pin code is the most complex and does not refer to king/slider/knight modules; it directly calls into `magic::rook_attacks` (already-shipped, M1.C) and `pos.pieces_colored`.
- Shard C consumes `magic::*_attacks` directly; that's a non-movegen dependency that the prereq shard does not transitively own.
- Tests within each shard can import the shard's emit function in isolation — no transitive dependency on the other emit functions.
- The orchestrator (Shard E) is the strict join point. It cannot land before all four parallel shards are mergeable (compile-clean and test-clean).
- A single agent could run all of A–D sequentially without the parallelism. Spawning four agents is purely throughput.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| **EP horizontal-pin trap** missed | Dedicated `pawn_ep_horizontal_pin_filtered` test on Position-3-shape fixture. The construct-the-post-EP-occupancy logic has its own helper function that's directly unit-tested (`pawn_ep_legal_after_horizontal_check(...)`). |
| **King-flee-along-check-ray** missed | Dedicated `king_flee_along_check_ray_blocked` test; `king_danger_through_king_square` mask test pins the `^ king_bb` infrastructure independently. |
| **Castling-through-attack** missed | Six dedicated castling tests covering each slot in the 3-square transit × {no, transit-attacked, dest-attacked} matrix. |
| **Promotion under-promotion** dropped | Dedicated test `pawn_promotion_emits_four_flags_per_target` enumerates all four; mutation testing on the four-flag literal will surface drops. |
| **Pinned knight emits a move** | `knight_pinned_emits_nothing` test with a constructed pinner. |
| **Mutation testing time blow-up** | Per-unit `cargo mutants --in-diff` keeps surface bounded to M1.F-touched lines. |
| **Performance regression vs M1.E baseline** | M1.G's perft benchmark is the real test; M1.F's smoke benchmark (movegen on the canonical 6 starting positions) flags catastrophic slowness (>10 µs/call). |
| **`MoveList` `MaybeUninit` unsoundness** | `as_slice` and `iter` both go through `slice_assume_init_ref(slice[0..len])`; the `len` invariant is the contract. Pinned by `move_list_iter_yields_all_pushed`. Property test that `len <= 256` invariably. |
| **Subtle bug in pin computation when pinner direction is ambiguous (queen)** | Tested explicitly: `pinned_diagonal_bishop_pinner` (bishop), and a queen-pinner test for both rook-direction and bishop-direction pin via the queen. |

## Verification plan

- **Smoke throughput sanity (no `criterion`).** A `#[test] #[ignore]` throughput sanity test in `tests/movegen.rs` mirroring the M1.E pattern (`bench_make_unmake_throughput`): runs `generate_moves` on each of the canonical 6 in a tight loop (100k iterations is fine — a per-call generator does much more work than per-move make/unmake), prints ns/call, asserts ns/call < 5000 (5 µs/call upper bound). Methodology: a competent legal-direct generator does mask setup (~30 attack lookups + pin computation) plus per-move emission for 6–48 legal moves (~10–50 ns/move with stack-allocated `MoveList::push`). On Apple Silicon this should land in the 1–3 µs/call range; 5 µs is the regression-detection ceiling, not a target. Run via `cargo test --release -- --ignored`. The full `criterion` benchmark harness is M1.G — see "Out of scope" below; no `criterion` dependency lands in M1.F.
