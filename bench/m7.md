# M7 — SEE (Static Exchange Evaluation)

Milestone summary per ADR-0010. SEE is a permanent search primitive (survives
NNUE); M7 is decomposed into SPRT-gated sub-phases (M7.A evaluator + ordering
split, M7.B qsearch SEE-pruning, M7.C SEE capture-futility). ADR-0039.

### Capture-ordering split — EXPLORED, SHELVED (two flat SPRTs)

The split was the planned first consumer. Both variants SPRT'd vs `M5.K`
(mixed-TC `10+0.1:1,20+0.2:1,40+0.4:1,60+0.6:1` + virtual-clock, elo0=0/elo1=5,
400 games, 2026-06-15):

| Variant | rule | Δ Elo (pentanomial CI) | raw | verdict |
|---|---|---|---|---|
| **v1** | demote every `SEE < 0` below quiets | **−10.43 [−34.69, +13.74]** | 97-109-194 (48.5%) | no-ship |
| **v2** | demote only `SEE < −100` (≈1 pawn) | **+2.61 [−22.39, +27.62]** | 104-101-195 (50.4%) | no-ship |

Per-TC score% (v1 / v2): 10+0.1 46.0 / 46.4 · 20+0.2 55.2 / 53.1 · 40+0.4 44.6 /
42.2 · 60+0.6 50.0 / 57.9. The retune moved the estimate **+13 Elo** (confirming
the over-demotion hypothesis — v1 over-demoted marginally-losing /
pin-or-tactic-misclassified captures, since SEE is static) but landed **flat**:
neither clears an ADR-0037 ship rung (rung-1 CI-lower > 0; rung-2 mean ≥ 5 ∧
CI-lower > −10). No clean depth amplification.

**Conclusion: ordering-by-SEE is neutral for this engine.** The −7.6% node
reduction the split produced did **not** convert to Elo — the existing
MVV-LVA + TT + killer + history ordering is already strong enough that reordering
captures by SEE adds nothing measurable. **The split is reverted on `main`** and
the split *code* is not retained — this table is the record (the result is
conclusive enough that re-deriving it is cheaper than carrying the code). SEE's
strength payoff is deferred to **M7.B (qsearch SEE-pruning)** / M7.C, which prune
rather than reorder.

> Harness note: the legacy Robbins-Monro `progress: … elo=` line diverged (climbed
> to +700+ while the raw score stayed near 50%) — a display bug in `elo-iterate`'s
> progress output; the pentanomial GSPRT `ci:`/`ptnml` lines (independent) are
> authoritative and were used for both verdicts. Filed as a tooling follow-up.

## M7.B — qsearch SEE-pruning (first production consumer of the SEE evaluator)

**Implemented 2026-06-16.** The first production caller of `see()`: inside the

### Performance gate (ADR-0030 §10 scar — sustained-go NPS, hard gate)

`see()` is allocation-free (stack `[i32; 32]`); the fast-out keeps it off the hot
path for winning/equal captures. Sustained-go, with-prune vs stashed baseline
(production HEAD), `go depth 13`:

| Position | Baseline nodes | Prune nodes | node Δ | Baseline knps | Prune knps | NPS Δ | time-to-d13 |
|---|---|---|---|---|---|---|---|
| startpos | 6 529 171 | 3 961 351 | −39% | 2263 | 2090 | −7.6% | **−34%** (1895 vs 2885 ms) |
| Kiwipete¹ | 10 768 079 | 6 496 255 | −40% | 2748 | 2649 | −3.6% | **−37%** (2452 vs 3918 ms) |

¹ `r3k2r/p1ppqpb1/bn2pnp1/3PN3/1p2P3/2N2Q1p/PPPBBPPP/R3K2R w KQkq - 0 1` (capture-dense).

The per-node `see()` cost is a small NPS dip (4–8%, pure compute — no allocation
regression like the §10 scar), **overwhelmingly offset** by the ~40% node
reduction ⇒ net **34–37% faster to reach depth 13**. Gate PASSED.

### SPRT (strength confirmation) — SHIPPED (rung-1, user-approved)

Mixed-TC `10+0.1:1,20+0.2:1,40+0.4:1,60+0.6:1` + virtual-clock vs `M5.K`
(≡ production HEAD; the only behavioural delta is the prune), elo0=0/elo1=5,
400 games (2026-06-16). Full record:
[`bench/sprt/2026-06-16-m7b-qsearch-see-prune-vs-m5k.md`](sprt/2026-06-16-m7b-qsearch-see-prune-vs-m5k.md).

**Δ Elo = +40.13 [+12.97, +67.80]** (pentanomial, 200 pairs, ptnml
[12,42,64,52,30]; W-L-D 138-92-170). CI-lower +12.97 > 0 ⇒ **rung-1 ship-by-CI**
(ADR-0037 §9; verdict=continue/llr=0.99 at the 400-game cap — the M6.I/M6.J
continue-at-cap ship precedent). Largest single-change gain since M6.I; confirms
SEE's Elo is in *pruning*, not ordering (M7.A's split was flat).

**Caveat — INVERSE depth profile (slow-TC regression):** per-TC ≈Elo 10+0.1
**+109**, 20+0.2 **+73**, 40+0.4 **+109**, but **60+0.6 ≈ −104** (10W-42L-58D,
≈4.4σ — not noise). Pruning dominates at fast/mid TC (the −40% nodes buys depth
when the budget is tight) but regresses at the slowest TC — the inverse of M6.I,
and 60+0.6 is the strength-relevant TC. Hypothesised cause: `QS_SEE_PRUNE_THRESHOLD
= 0` is too aggressive at depth (the engine can refute "losing" tactical captures
given the time). **Shipped on the +40 aggregate (user "ship now, tune later");
the slow-TC fix is M7.B.1 (negative-threshold tune, HIGH priority — see
`docs/tuning-backlog.md`).**

## M7.C — SEE capture futility / delta pruning (negamax frontier nodes)

**Implemented 2026-06-17.** The negamax-side complement of FFP and the second
production consumer of `see()` (ADR-0042). At a frontier node (FFP's gate), a
non-promotion capture is skipped when an optimistic material-plus-margin ceiling
can't reach alpha. Two layers: **(a)** MVV delta-prune `static_eval + victim +
margin ≤ alpha` (sound optimistic ceiling, no `see()` call); **(b)** SEE refinement
on materially-losing captures (`victim < attacker`) `static_eval + see(mv) + margin
≤ alpha`. `CFP_MARGIN_D1 = 150`. No root-depth ramp — alpha-relative futility is
self-regulating in TC (research §4), the opposite of M7.B's alpha-independent
threshold. Baseline tag: production HEAD `M7.B.2`. Plan:
[`docs/plans/m7.c.md`](../docs/plans/m7.c.md). Research:
[`docs/research/m7-see-capture-futility.md`](../docs/research/m7-see-capture-futility.md).

### Bench node counts (determinism anchors, NOT a strength signal)

| Build | d4 nodes | default (d7) nodes |
|---|---|---|
| `M7.B` / `M7.B.2` (pre-CFP HEAD) | 45788 | 662085 |
| **M7.C (capture futility)** | **43128** (−5.8%) | **588673** (−11.1%) |

Far smaller than M7.B's qsearch prune (frontier nodes are rare vs qsearch leaves).
The depth-4 determinism pin (`tests/uci_integration.rs`) re-pinned to `43_128`.
NPS: warm d7 ≈ 4.3–4.4 Mnps vs `M7.B.2` ≈ 4.76 Mnps (the bounded branch-(b)
`see()` cost), but the −11% node saving outweighs it — time-to-depth-7 ≈ 0.137 ms
(CFP) vs 0.139 ms (baseline), i.e. slightly faster. `see()` is allocation-free and
bounded to branch (b)'s losing-capture class (the `qsearch_see_pruneable` fast-out
class).
